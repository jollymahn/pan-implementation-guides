# Validation Report Orchestrator — Design Spec

> **Date:** 2026-06-05
> **Status:** Draft
> **Author:** Claude + Sean

## Problem

Each VM-Series deployment guide needs a comprehensive validation report that proves: the guide is accurate, the configuration files match what was deployed, traffic flows work end-to-end, and the infrastructure is correctly configured. Currently, validation is spread across separate skills (health-check, traffic-validation) and manual processes with no unified report format.

## Solution

A new `/guides/validation-report` skill that orchestrates the full validation workflow — calling existing skills, running new automated checks, creating missing sanitize scripts, and producing a single self-contained markdown report per deployment variant.

## Invocation

```
/guides/validation-report <cloud> <variant> <prefix> --key <ssh-key-path> [--region <region>]
```

### Parameters

| Parameter | Required | Description | Examples |
|-----------|----------|-------------|---------|
| `<cloud>` | Yes | Cloud provider | `aws`, `azure`, `gcp` |
| `<variant>` | Yes | Deployment variant matching the guide path | `non-overlay-panorama`, `overlay-panorama`, `scm`, `common-model`, `tvnet-dedicated` |
| `<prefix>` | Yes | Deployment name prefix used in resource tags | `sj-cld`, `prod-east`, `sj-ded` |
| `--key` | Yes | SSH private key path (passed to sub-skills) | `~/.ssh/sj-cld-validation.pem` |
| `--region` | No | Cloud region. Defaults: `us-west-2` (AWS), `eastus` (Azure), `us-central1` (GCP) | `us-east-1` |

### Examples

```bash
/guides/validation-report aws non-overlay-panorama sj-cld --key ~/.ssh/sj-cld-validation.pem
/guides/validation-report azure common-model sj-az --key ~/.ssh/az-key.pem --region eastus
/guides/validation-report aws overlay-panorama sj-cld --key ~/.ssh/sj-cld-validation.pem --region us-west-2
```

### File Path Resolution

The skill resolves all file paths from the arguments:

| File | Path Pattern |
|------|-------------|
| Guide HTML | `docs/guides/<cloud>/vm-series-deployment.html` |
| Live Panorama .set | `workspace/<cloud>/panorama-config-*.set` (matched by variant keywords) |
| Reference Panorama .set | `docs/guides/<cloud>/reference/panorama-config-*.set` |
| Live terraform.tfvars | `workspace/<cloud>/terraform-swfw-modules/examples/*/terraform.tfvars` |
| Reference .tfvars | `docs/guides/<cloud>/reference/tfvars/*.tfvars` |
| Sanitize script | `scripts/sanitize-<variant>.sh` (creates if missing) |
| Output report | `workspace/<cloud>/VALIDATION-REPORT-<variant>.md` |

#### Variant-to-file mapping

The `<variant>` argument maps to specific files and Terraform examples:

| Variant | Panorama .set keyword | Terraform example dir | Routing model |
|---------|----------------------|----------------------|---------------|
| `non-overlay-panorama` | `non-overlay` | `combined_design` | Non-overlay |
| `overlay-panorama` | `overlay` | `combined_design` | Overlay |
| `overlay-dedicated-panorama` | `overlay-dedicated` | `combined_design` | Overlay + dedicated inbound |
| `scm` | N/A (no .set file) | `combined_design` | Varies |
| `common-model` | `common-model` | `vmseries_transit_vnet_common` | Azure common |
| `tvnet-dedicated` | `tvnet-dedicated` | `vmseries_transit_vnet_dedicated` | Azure dedicated |

### Section 3: Panorama Config Alignment (Automated)

Three comparisons that validate the Panorama configuration is consistent across guide, live deployment, and reference files.

#### Comparison A: Guide HTML → Live .set file

**Process:**
1. Parse the guide HTML for all Panorama `set` commands (found in `<code>` blocks within collapsible bodies, specifically in Phase 2A/2B sections)
2. Parse the live workspace `.set` file
3. Normalize both command sets (strip whitespace, sort, deduplicate)
4. Group by namespace: `device-group`, `template`, `template-stack`, `shared`
5. Produce a diff report:
   - Commands in guide but NOT in live config → "Guide instructs this but it wasn't configured"
   - Commands in live config but NOT in guide → "Undocumented configuration"
   - Structural matches → "Aligned"

**Edge cases:**
- Guide may use placeholder values (`YOUR-AUTH-KEY`, `example-`) while live config has real values — compare structure, not values
- Some commands in the guide are wrapped in tab panels (Panorama vs SCM) — only parse commands from the matching management plane panel
- Template variable values differ per deployment — compare variable names exist, not values

#### Comparison B: Live .set file → Reference .set file

**Process:**
1. Load the live `.set` from `workspace/<cloud>/`
2. Load the reference `.set` from `docs/guides/<cloud>/reference/`
3. Diff with deployment-specific values normalized out (IPs, prefixes, auth keys, account IDs replaced with `*`)
4. Report structural differences only: missing rules, extra objects, different zone assignments, different interface configs

#### Comparison C: Reference .set file audit

**Process:**
1. Run credential scan against the reference file using the patterns from `build-panorama-set.sh`:
   ```
   mgt-config users|phash|public-key|private-key|passphrase|secret|bind-password|password|api-key|auth-key [^ ]|ssh-rsa AAAA|ssh-ed25519 AAAA|BEGIN (CERTIFICATE|RSA|OPENSSH|EC)
   ```
2. Run deployment-specific value scan using the patterns from the matching sanitize script
3. Report: PASS/FAIL with line numbers for any leaks

**Output format:**
```markdown
## 3. Panorama Config Alignment

### Guide vs. Live Config

| Status | Namespace | Detail |
|--------|-----------|--------|
| MATCH | DG: CLD-AWS-COMBINED | 12 security rules — all present |
| DRIFT | Template: TPL-AWS-COMBINED | Guide: 3 zones, Live: 4 zones (extra: UNTRUST) |
| MISSING | Template: TPL-AWS-ADMINS | In guide but not in live config |

- Commands in guide: 424
- Commands in live config: 431
- Matched: 420
- Guide-only: 4 (listed above)
- Live-only: 7 (listed above)

### Live vs. Reference File

- Reference file: docs/guides/aws/reference/panorama-config-combined-non-overlay.set
- Structural differences: 2
  1. Line 45: Live has `set ... zone UNTRUST`, reference does not
  2. Line 112: Live has additional address object `H-APP3-SERVER`
- Deployment-value differences: 14 (expected — these are replaced by sanitize script)

### Reference File Audit

- Credential scan: PASS (0 leaks)
- Deployment-specific value scan: PASS (all replaced with placeholders)
```

### Section 4: Terraform Config Alignment (Automated)

Validates the Terraform configuration files are consistent between live deployment, reference files, and guide instructions.

#### Step 1: Sanitize script check/create

**Process:**
1. Check if `scripts/sanitize-<variant>.sh` exists
2. If it exists, use it as-is
3. If it does NOT exist, create one:
   a. Read the live `terraform.tfvars`
   b. Identify deployment-specific values by pattern:
      - `name_prefix` value → replace with `"example-"`
      - `ssh_key_name` value → replace with `"example-ssh-key"`
      - Any IP matching the admin's public IP (from `curl checkip.amazonaws.com`) → `YOUR-PUBLIC-IP`
      - Panorama IP (`10.251.2.51` or equivalent) → `YOUR-PANORAMA-IP`
      - VPC/VNet IDs → `YOUR-*-ID`
      - Account/subscription IDs → `YOUR-ACCOUNT-ID`
      - Auth keys → `YOUR-AUTH-KEY`
      - Auth codes → `YOUR-AUTHCODE`
   c. Generate sed commands following the pattern from `sanitize-dedicated-inbound.sh`
   d. Include credential and deployment-value audits
   e. Write to `scripts/sanitize-<variant>.sh`
   f. Report: "CREATED — new sanitize script for <variant>"

#### Step 2: Run sanitize script

Execute the sanitize script to generate the reference `.tfvars` file. Capture and report:
- Number of replacements applied
- Credential audit result (PASS/FAIL)
- Deployment-value audit result (PASS/FAIL)

#### Step 3: Generated vs. published reference diff

If a published reference `.tfvars` already exists in `docs/guides/<cloud>/reference/tfvars/`:
- Diff the newly generated file against the published one
- Report structural differences (new variables, removed variables, changed defaults)
- If no published reference exists, note it and offer to publish the generated one

#### Step 4: Guide vs. live tfvars

Parse the guide HTML for tfvars configuration instructions (typically in Phase 5 collapsible steps) and compare key settings against the live `terraform.tfvars`:

| Setting | Guide Says | Live Value | Match? |
|---------|-----------|------------|--------|
| `vmseries_version` | `"11.2.3"` | `"11.2.3"` | MATCH |
| `name_prefix` | `"example-"` | `"sj-cld-"` | OK (deployment-specific) |
| `bootstrap_options.auth-key` | `"YOUR-AUTH-KEY"` | `"_AQ__..."` | OK (deployment-specific) |
| `bootstrap_options.plugin-op-commands` | `"advance-routing:enable"` | `"advance-routing:enable"` | MATCH |
| `vmseries_common.bootstrap_options.panorama-server` | guide value | live value | MATCH/DRIFT |

**Output format:**
```markdown
## 4. Terraform Config Alignment

### Sanitize Script
- Script: scripts/sanitize-non-overlay-panorama.sh (EXISTS)
- Input: workspace/aws/terraform-swfw-modules/examples/combined_design/terraform.tfvars
- Output: docs/guides/aws/reference/tfvars/combined_design.tfvars
- Credential audit: PASS
- Deployment-value audit: PASS (14 replacements applied)

### Generated vs. Published Reference

### Guide vs. Live tfvars

|---------|-----------|------------|--------|
| vmseries_version | "11.2.3" | "11.2.3" | MATCH |
| name_prefix | "example-" | "sj-cld-" | OK (deployment-specific) |
| bootstrap auth-key | (placeholder) | "_AQ__..." | OK (deployment-specific) |
| plugin-op-commands | "advance-routing:enable" | "advance-routing:enable" | MATCH |
```

```bash
# VPCs

# Transit Gateway
aws ec2 describe-transit-gateways --filters "Name=tag:Name,Values=*<prefix>*" ...

# GWLB + endpoints
aws elbv2 describe-load-balancers ...
aws ec2 describe-vpc-endpoints --filters "Name=tag:Name,Values=*<prefix>*" ...

aws ec2 describe-nat-gateways --filter "Name=tag:Name,Values=*<prefix>*" ...
```

### Section 9: Config Sync Verification (Automated)

Goes beyond health-check's Connected/Synchronized status to verify specific config elements.

**Process:**
1. SSH to Panorama, run `show devices all` — capture sync status per firewall
2. For each firewall, SSH and run:
   - `show system info` — check `config-status`, `dg-config-status`, `shared-policy-status`
   - `show zone-protection zone all` — verify zones match template definition
   - `show running security-policy` — verify rules match DG definition
   - `show running nat-policy` — verify NAT rules match DG definition
3. Compare each element against the expected config from the `.set` file
4. Flag any local overrides (changes made directly on the firewall)

### Section 10: Security Group / NSG Audit (Automated)

Verifies all required network access rules are present and no overly permissive rules exist.

**Required ports matrix:**

| Interface Role | Required Ports | Allowed Sources |
|---------------|---------------|-----------------|
| Management | TCP 22 (SSH), TCP 443 (HTTPS) | Admin CIDR + Panorama IP only |
| Data/GWLB (eth1/1) | UDP 6081 (GENEVE), TCP 80 (health probes) | GWLB subnets, security VPC CIDR |
| Public (eth1/2) | Outbound all | N/A |
| Spoke VMs | TCP 22 (SSH), TCP 80 (HTTP) | Varies by app |

**Process:**
1. For each firewall instance, query all attached security groups/NSGs per network interface
2. Check each interface against the required ports matrix
3. Flag missing rules (required port not open)
4. Flag overly permissive rules:
   - `0.0.0.0/0` on management interface → HIGH risk
   - `0.0.0.0/0` on data interface for non-health-check ports → MEDIUM risk
   - Unrestricted outbound on management → LOW risk (but note it)

**Output format:**

## Execution Flow

The skill runs sections in this order:

```
Phase 0: Parse arguments, resolve file paths, verify cloud auth
    ↓
Phase 1: Generate Section 1 (metadata)
    ↓
Phase 2: Scaffold Section 2 (guide accuracy template)
    → User fills in findings during walkthrough (can be done before or after automated sections)
    ↓
Phase 3: Run Section 3 (Panorama config alignment)
    → Parse guide HTML for set commands
    → Parse live .set file
    → Parse reference .set file
    → Produce diff tables
    ↓
Phase 4: Run Section 4 (Terraform config alignment)
    → Check/create sanitize script
    → Run sanitize script
    → Diff generated vs. published reference
    → Parse guide for tfvars instructions
    ↓
Phase 5: Run Section 5 (infrastructure snapshot)
    → Query cloud CLI for all deployment resources
    ↓
Phase 6: Run Section 6 (Terraform audit)
    → Read TF output or prompt user for apply details
    → Run drift check (terraform plan)
    ↓
Phase 7: Run Section 7 (health check)
    → Invoke /guides/health-check <prefix> --region <region>
    → Capture and format output
    ↓
Phase 8: Run Section 8 (traffic validation)
    → Invoke /guides/traffic-validation <prefix> --key <key> --region <region>
    → Capture and format output
    ↓
Phase 9: Run Section 9 (config sync verification)
    → SSH to Panorama
    → SSH to each firewall
    → Compare running config against .set file
    ↓
Phase 10: Run Section 10 (security group audit)
    → Query cloud CLI for SGs/NSGs
    → Check against required ports matrix
    → Flag permissiveness issues
    ↓
Phase 11: Generate Section 11 (verdict)
    → Aggregate pass/fail across all sections
    → Generate recommendations
    → Write complete report to workspace/<cloud>/VALIDATION-REPORT-<variant>.md
```

### Checkpoint behavior

After each phase, the skill writes the current report state to the output file. If the session is interrupted, the partial report is preserved and the skill can be re-run to complete remaining sections.

### Sub-skill orchestration

The validation-report skill incorporates the logic from existing skills directly rather than invoking them as separate commands. For Phase 7 (health check) and Phase 8 (traffic validation), the skill follows the same protocols defined in `/guides/health-check` and `/guides/traffic-validation` respectively — running the same AWS CLI queries, SSH commands, and verification steps — but captures the results directly into report sections instead of producing standalone output.

This avoids the limitation that skills can't invoke other skills programmatically, while ensuring the validation logic stays consistent. If the health-check or traffic-validation skills are updated, the validation-report skill's corresponding phases should be updated to match.

## Missing Sanitize Script Creation

When `scripts/sanitize-<variant>.sh` does not exist, the skill creates one by:

1. Reading the live `terraform.tfvars`
2. Running `curl -s https://checkip.amazonaws.com` to get the user's public IP
3. Reading `workspace/<cloud>/pano-creds.txt` or asking for Panorama IP
4. Identifying all deployment-specific values by pattern matching
5. Generating a shell script following the exact structure of `scripts/sanitize-dedicated-inbound.sh`:
   - Shebang + header comment with usage, inputs, outputs
   - `set -euo pipefail`
   - Input/output path variables
   - Input validation
   - Replacement map comment block documenting all substitutions
   - Common sed array for shared replacements
   - .set file sanitization
   - .tfvars file sanitization with `# TODO: update here` markers
   - Credential audit (same patterns as `build-panorama-set.sh`)
   - Deployment-specific value audit
6. Writing to `scripts/sanitize-<variant>.sh`
7. Making it executable (`chmod +x`)

The generated script follows the proven pattern and includes both credential and deployment-value audits.
