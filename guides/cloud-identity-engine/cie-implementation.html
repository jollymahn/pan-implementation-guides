Guide Approach

The Cloud Identity Engine (CIE) is Palo Alto Networks' cloud-native identity service. It replaces per-firewall IdP connections with a single, centralized identity hub — firewalls connect to CIE once, and CIE handles all directory and authentication communication.

CIE is free. No auth code or standalone subscription needed. Enforcement points (NGFWs, Panorama, Prisma Access) require their own licenses, but CIE itself has no licensing cost.

This guide covers four directory types (Entra ID, Okta, Google, on-prem AD) and both management planes (Panorama and SCM). Pick your path at each branching point — you only need to follow the sections that match your environment.

Architecture Overview

CIE sits between your identity providers and your enforcement points. Instead of configuring each firewall to connect directly to each IdP, every firewall connects to CIE once. CIE aggregates and normalizes identity data from all sources and presents a unified view.

▶ How CIE Fits Into the Stack

Identity Sources (left side) feed into CIE:

  • Cloud directories — Microsoft Entra ID, Okta, Google Workspace (API-based sync)
  • On-premises AD / OpenLDAP — via the Cloud Identity Agent installed on a Windows server near your domain controllers
  • CIE Directory — built-in cloud directory for testing or small user sets (max 200 users)

CIE (center) provides:

  • User and group synchronization from all directories
  • SAML 2.0 and OIDC authentication brokering
  • Cloud Dynamic User Groups (attribute-based membership)
  • Identity redistribution (IP-to-user, user tags, quarantine lists)

Enforcement Points (right side) consume CIE data:

  • PA-Series and VM-Series NGFWs (PAN-OS 10.1+)
  • Panorama (PAN-OS 10.1+)
  • Prisma Access (any version with Panorama plugin)
  • Strata Cloud Manager

Region Cannot Be Changed

Once activated, the CIE tenant region cannot be migrated. Choose carefully based on your compliance requirements and where your enforcement points are deployed.

▶ 1.5 — Prepare Directory Domains

Prepare your identity source before connecting to CIE:

On-Premises Active Directory

  • Create a service account with LDAP read/query permissions against all target domains
  • Plan Cloud Identity Agent placement — install on a Windows server physically near the domain controllers
  • For redundancy: configure multiple agents per domain, multiple DCs per agent
  • For cross-domain group membership: configure all relevant domains on the agent(s)

Microsoft Entra ID

  • Identify a Global Administrator (or someone with that role) for the CIE Enterprise App consent flow
  • Verify there are no circular group references (Group A member of Group B and vice versa) — CIE cannot accurately compute membership with circular references

Okta

  • Identify an Okta admin who can install Okta Integration Network apps and grant API scopes
  • You must create a separate OIDC app for CIE directory sync, even if Okta is already configured as a SAML IdP — reusing the SAML gallery app causes sync failures

Google Workspace

  • Identify a Google Admin with privileges for: Organizational Units, Users, Groups, Device Management, and Domain Settings
  • Get your Customer ID from Google Admin → Account → Account Settings
▶ 1.6 — Set Up Your Directory Service

If your directory service is already populated with users and groups, skip to Phase 2. Otherwise, follow the section below for each directory type you plan to connect to CIE.

▶ Microsoft Entra ID (Azure AD)
  1. Access the Entra admin center
    • Open entra.microsoft.com and sign in.
    • If you don't have an Azure subscription, you can create a free Azure AD tenant — the Free tier includes up to 50,000 users and groups.
  2. Verify your admin role
    • Go to Identity → Roles & admins → search for your account.
    • You need Global Administrator to consent to the CIE Enterprise App in Phase 3A. If you only have Application Administrator, you will need a Global Admin to complete the consent step.
  3. Create test users
    • Identity → Users → All users → New user → Create new user.
    • Create at least 2–3 users with display names, UPNs, and passwords.
    • Note the UPN format (e.g., testuser@yourdomain.onmicrosoft.com) — this is what CIE will sync.
  4. Create a security group
    • Identity → Groups → All groups → New group.
    • Group type: Security.
    • Add your test users as members.
  5. Copy your Directory (Tenant) ID
    • Go to Overview in the Entra admin center.
    • Copy the Tenant ID (a GUID) — you will need this in Phase 3A.
Circular Group References

Before connecting to CIE, verify your Entra ID has no circular group memberships (Group A is a member of Group B, which is a member of Group A). CIE cannot accurately resolve membership with circular references. Check under Groups → select each group → Members.

Phase 3: Directory Setup

Connect CIE to your identity source. Pick the tab that matches your directory type — your selection persists across the page. Most deployments use one or two directories; you can configure multiple directory types on the same CIE tenant.

Which directory type should I pick?
  • Entra ID — choose for Microsoft 365 / Azure AD environments. Two methods available: Enterprise App (simpler) or Client Credential Flow (service-account based).
  • Okta — choose for Okta-managed identity. Client Credential Flow recommended; Auth Code Flow available but requires 90-day reconnects.

Microsoft Entra ID (Azure AD)

Two connection methods are available. The CIE Enterprise App is simpler; the Client Credential Flow uses a service account and avoids tying the connection to a specific admin user.

▶ Method 1: CIE Enterprise App (Recommended)
  1. Get your Directory (Tenant) ID
    • Log in to the Microsoft Entra admin center or Azure Portal.
    • Select Overview and copy the Directory (tenant) ID.
  2. Start directory setup in CIE
    • CIE app → Directories → Add New Directory → Set Up an Entra ID Cloud Directory.
  3. (Optional) Select additional data to collect:
    • User risk information (requires IdentityRiskyUser.Read.All, IdentityRiskEvent.Read.All)
    • Roles and Administrators (requires Directory.Read.All or RoleManagement.Read.Directory)
    • Enterprise applications (requires Application.Read.All)
    • Device information (requires Device.Read.All)
  4. Enter your Directory ID and click Generate URL.
    • If you are a Global Admin: open the URL in a new tab to register instantly.
    • If not: share the URL with a Global Admin to complete offline.
  5. Authenticate and consent — sign in with Global Admin credentials and accept the permission prompt.
  6. Test Connection — confirm CIE can reach your Entra ID tenant.
  7. (Optional) Customize the directory name (max 15 chars, lowercase alphanumeric + . - _).
  8. (Optional) Filter groups — CSV upload or manual filter rules (by group name or UUID).
  9. Click Submit.

Permissions automatically granted after consent:

  • Device.Read.All — Read all devices
  • Group.Read.All — Read all groups
  • User.Read.All — Read all users' full profiles

▶ Supplementary: Understanding the Entra ID Consent Flow

When you open the generated URL, Azure presents an admin consent prompt. Here's what happens:

  1. Authentication — You sign in with a Global Admin account. This account is only used for the consent step; CIE does not store the admin's credentials.
  2. Permission review — Azure lists the Graph API permissions CIE is requesting. All permissions are application-level (not delegated), meaning CIE accesses data as a service, not on behalf of a user.
  3. Consent grant — Clicking "Accept" registers the CIE Enterprise App in your Entra ID tenant. You can find it under Enterprise Applications in the Azure Portal.

Verifying Permissions After Consent

  1. Azure Portal → Entra ID → Enterprise Applications.
  2. Search for "Palo Alto Networks Cloud Identity Engine" or "Cloud Identity Engine".
  3. Click the app → Permissions tab.
  4. Confirm all required permissions show "Granted for [your directory]".

Revoking or Re-Granting Access

If you need to revoke CIE access: Enterprise Applications → select the CIE app → Properties → Delete. To reconnect, generate a new URL in CIE and repeat the consent flow. CIE also provides a dedicated revocation guide under Directories → Actions → Revoke Permissions.

▶ Method 2: Client Credential Flow

    • Azure Portal → Azure Active Directory → App Registrations → New registration.
    • Enter a name (e.g., "CIE Directory Sync"), click Register.

  5. Configure in CIE

    • Enter Directory ID, Client ID, and Client Secret.
    • (Optional) Select additional data collection checkboxes.
  6. Test Connection → (Optional) Customize Directory Name.
  7. Click Submit.
▶ Supplementary: Azure App Registration Walkthrough

This walkthrough covers the Azure Portal steps in detail for administrators who haven't created an app registration before.

Navigate to App Registrations

  1. Open portal.azure.com.
  2. In the search bar at the top, type "App registrations" and select it from the results.
  3. Click + New registration at the top.
  4. Under Name, enter something descriptive (e.g., "CIE Directory Sync").
  5. Under Supported account types, select "Accounts in this organizational directory only" (the default).
  6. Leave Redirect URI blank — CIE does not need a redirect for client credentials.
  7. Click Register.

Add API Permissions

  1. On the app's overview page, click API permissions in the left nav.
  2. Click + Add a permission → Microsoft Graph.
  3. Select Application permissions (not Delegated).
  4. Search and add each permission:
    • Device.Read.All — under Device
    • GroupMember.Read.All — under GroupMember
    • User.Read.All — under User
  5. Click Add permissions.
  6. Then click + Add a permission again → Microsoft Graph → Delegated permissions → add User.Read.
  7. Click the Grant admin consent for [Directory Name] button (requires Global Admin). Confirm with Yes.
  8. Verify each permission shows a green checkmark under Status.

Create and Copy the Client Secret

  1. Click Certificates & secrets in the left nav.
  2. Click + New client secret.
  3. Enter a description (e.g., "CIE sync") and select an expiration (6 months, 12 months, or 24 months max).
  4. Click Add.
  5. Immediately copy the Value column (not the Secret ID). This is your client secret.
Secret Visibility

The secret value disappears permanently once you navigate away from this page. If you lose it, you must delete the secret and create a new one.

Copy Application and Directory IDs

  1. Click Overview in the left nav.
  2. Copy the Application (client) ID — this is the Client ID for CIE.
  3. Copy the Directory (tenant) ID — this is the Directory ID for CIE.

Managing Secret Expiration

Client secrets expire after the period you selected. When a secret expires, CIE sync stops silently. Set a calendar reminder to rotate the secret before expiration:

  1. Azure Portal → App Registrations → your CIE app → Certificates & secrets.
  2. Create a new secret before the old one expires.
  3. Update the secret in CIE: Directories → select the directory → Actions → Update Credentials.
  4. After confirming the new secret works, delete the old one from Azure.

▶ Method 2: Auth Code Flow
90-Day Reconnect Required

Auth Code Flow requires reconnection every 90 days to refresh tokens, or sync will stop. Client Credential Flow (above) avoids this.

  1. Get the CIE redirect URI: https://directory-sync.<region>.paloaltonetworks.com/authorize
  2. Create an Okta admin account with assigned admin roles (Security → Administrators).
  3. Create an OIDC app integration in Okta:
    • Sign-in method: OIDC - OpenID Connect
    • Application type: Web Application
    • Sign-in redirect URI: paste the CIE redirect URI
  4. Configure grant type: Edit General Settings → select Refresh token → Use persistent token → Save.
  5. Copy Client ID, Client Secret, and Okta domain.
  6. Assign the app to the admin user (Assignments tab).
  7. Grant API scopes (Okta API Scopes tab):
    • okta.groups.read
    • okta.users.read
    • okta.users.read.self
    • okta.logs.read
    • okta.authorizationServers.read (if multiple auth servers)
    • okta.apps.read (if collecting app data)
  8. Configure in CIE: Add Directory → Okta → Auth Code Flow → enter credentials.
  9. Sign in with Okta admin credentials → Test Connection → Submit.

On-Premises Active Directory

▶ Install and Configure Cloud Identity Agent
  1. Download the Cloud Identity Agent installer from the CIE app.
  2. Install on a Windows server physically near your domain controllers.
    Placement Matters

    The agent communicates directly with your DCs via LDAP/LDAPS. Place it on a server with low-latency access to the domain controllers. If DCs span multiple sites, deploy multiple agents — each near its local DCs.

  3. Configure the service account
    • Use the service account created in Phase 1.5 with LDAP query permissions.
    • The account must be able to query all configured domains.
  4. Enter domain controller addresses
    • LDAP: port 389 (default)
    • LDAPS: port 636
    • Do NOT use Global Catalog ports (3268/3269).
  5. Mutual certificate authentication is established automatically between the agent and CIE.
  6. (Optional) Configure object filters to limit sync scope to specific OUs, containers, or computer objects.
  7. Verify the agent connects to the CIE cloud service (agent status should show "Connected").
▶ Configure Redundancy
  • Configure multiple domain controllers per domain for DC-level failover.
  • Deploy multiple agents per domain for agent-level redundancy.
  • For cross-domain group membership, configure all relevant forest domains on the agent(s).

Phase 6: Identity-Based Security Policy

With directories synced and authentication configured, build security policies that use identity instead of (or alongside) IP addresses.

▶ 6.1 — Create Authentication Profile in CIE
  1. CIE app → Authentication → Authentication Profiles → Add Authentication Profile.
  2. Enter a unique Profile Name.
  3. Select Authentication Mode:
    • Single — one authentication type for all users
    • Multiple — different authentication types per group (requires a configured directory)
  4. (Multiple mode) Define the authentication mapping order — drag to reorder. First matching group wins.
  5. Select Default authentication type (used when a user doesn't match any assigned group).
  6. Choose directories and select groups.
  7. Assign authentication types to groups.
  8. Review assignments, then click Submit.
Best Practice

Use UPN format (user@domain.com) for the Directory Sync Username Attribute. This ensures consistent matching between directory sync and authentication.

▶ 6.2 — Create Cloud Dynamic User Groups (Optional)

Cloud Dynamic User Groups (CDUGs) automatically update membership based on user attributes like department, location, job title, or risk level.

  1. CIE → Directories → click the Groups column number → Create New Dynamic User Group.
  2. Select Category:
    • Attribute Based — membership determined by rules
    • On Demand Assignment — manually assign users
  3. Enter a Common Name (CIE auto-appends _cdug to generate the Distinguished Name).
  4. For Attribute Based, define rules:
    • Match logic: Any (OR) or All (AND)
    • Select attribute (department, location, title, risk level, etc.)
    • Select operator: is equal to, contains, starts with, is not equal to
    • Enter value(s)
  5. Click Submit.
Azure AD Risk Integration

To create CDUGs based on user risk level (from Azure AD Identity Protection), you need the Client Credential Flow for Azure AD with IdentityRiskyUser.Read.All and IdentityRiskEvent.Read.All permissions. Enable "Collect user risk information" in the directory config.

▶ 6.3 — Build User/Group-Based Security Policy
  1. On Panorama or SCM, navigate to Security Policy.
  2. Create or edit a security policy rule.
  3. In the Source tab, use the Source User or Source User Group fields.
  4. Select CIE-synced groups or Cloud Dynamic User Groups.
  5. Configure the rule action, application, and destination as needed.
  6. Commit and push to managed firewalls.

Example rules:

  • Allow the Engineering_cdug group access to developer tools
  • Restrict the Contractors group to only web browsing
  • Block high-risk users (via risk-based CDUG) from accessing sensitive applications

Phase 7: MFA Integration

Multi-factor authentication adds a verification layer beyond passwords. CIE passes the MFA status from your IdP to the firewall so you can build policies that differentiate between MFA-authenticated and password-only sessions.

▶ 7.1 — Enable MFA at the IdP

Configure MFA in your identity provider. This is done entirely on the IdP side — CIE does not manage MFA configuration directly.

  • Entra ID: Azure Portal → Security → Conditional Access → create a policy requiring MFA
  • Okta: Security → Multifactor → configure MFA factors and enrollment policies
  • Google: Security → 2-Step Verification → enable and enforce
▶ 7.2 — Enable MFA Flag in CIE SAML Profile
  1. CIE → Authentication → Authentication Types → edit your SAML profile.
  2. Check the MFA checkbox.
  3. This tells the firewall that users authenticated through this profile have completed MFA.
  4. Click Submit.
▶ 7.3 — Enable Force Authentication (Optional)

Force Authentication forces re-login on GlobalProtect reconnects instead of using cached sessions.

  1. Edit your SAML authentication type in CIE.
  2. Enable the Force Authentication checkbox.
  3. Submit.
Okta Compatibility

If Force Authentication is enabled in CIE, you must uncheck "Disable Force Authentication" in the Okta SAML app settings. Otherwise the settings conflict and force-auth will not work.

▶ 7.4 — Use MFA Status in Security Policy

With MFA enabled, you can create tiered access policies:

  • MFA-authenticated users → full access to sensitive applications
  • Password-only users → restricted access, prompted for MFA on sensitive resources

Configure this in your Authentication Policy (on Panorama or SCM) by referencing the MFA-enabled authentication profile.

▶ D.4 — Create the CIE Service Account

The Cloud Identity Agent uses this account to bind to AD and perform LDAP queries.

  1. Create a dedicated Service Accounts OU if one does not exist.
  2. Create a user named svc-cie-sync (or similar svc- prefix).
  3. Set a strong password (20+ characters recommended).
  4. Check "Password never expires" — the agent stores the password in the Windows credential store.
  5. Uncheck "User must change password at next logon".
New-ADUser -Name "svc-cie-sync" `
  -SamAccountName "svc-cie-sync" `
  -UserPrincipalName "svc-cie-sync@corp.example.com" `
  -Path "OU=Service Accounts,DC=corp,DC=example,DC=com" `
  -AccountPassword (ConvertTo-SecureString "YourStr0ngP@ssword!" -AsPlainText -Force) `
  -Enabled $true -PasswordNeverExpires $true `
  -Description "CIE Cloud Identity Agent - LDAP read access"

# Get the Distinguished Name (needed for agent Bind DN)
Get-ADUser -Identity "svc-cie-sync" | Select-Object DistinguishedName

Required permissions: Membership in Domain Users is typically sufficient — AD grants read access to directory objects by default. The account does not need Domain Admins, Enterprise Admins, or replication permissions.

Hardened Environments

If default read access has been restricted, delegate explicit read permissions: right-click domain root in ADUC → Delegate Control → add svc-cie-sync → grant Read All Properties on User, Group, and Computer objects.

▶ D.7 — Multi-Domain and Multi-Forest
  • Single forest, multiple domains: A single agent can communicate with up to 20 domains. Configure all relevant domains on the agent for cross-domain group membership resolution.
  • Multiple forests: Deploy a separate agent per forest. Each uses its own service account. All agents can report to the same CIE tenant.
  • Agent redundancy: Deploy multiple agents per domain. CIE automatically handles failover and deduplicates data.
  • Agent placement: Place the agent server near its domain controllers for low-latency LDAP queries. If DCs span multiple sites, deploy separate agents per site.
