This questionnaire collects the information needed to configure a VM-Series transit VNet deployment on Azure using the official Palo Alto Networks Terraform modules. Complete each section and return this document so we can prepare your customized terraform.tfvars and deployment package.

About Existing Infrastructure

The Terraform modules are designed to deploy the complete transit VNet — VNet, subnets, NSGs, route tables, load balancers, and VM-Series firewalls — as a single managed unit. This is the preferred approach because the firewall deployment has many tightly coupled moving parts: subnet-to-NSG bindings, blackhole UDRs between zones, load balancer backend pool associations, and availability zone placement all need to be coordinated precisely.

That said, we can modify the Terraform to work with existing infrastructure — for example, peering into a VNet you've already provisioned, reusing existing NSGs or route tables, or attaching to load balancers managed outside of Terraform. This is common in enterprises where networking teams provision VNets independently, or where the transit VNet was created through a landing zone accelerator.

Section 2 below asks you to describe what infrastructure is already in place (or will be built by another team) so we know what Terraform needs to create vs. reference. If you answer "greenfield" (Terraform builds everything), no extra integration work is needed.

2 Existing Infrastructure Assessment

Why this matters

The VM-Series transit VNet deployment creates a VNet with specialized subnets (management, public/untrust, private/trust), NSGs with inter-zone blackhole rules, route tables with specific UDR chains, and load balancers with health probes — all tightly interdependent. Letting Terraform create and manage these as a unit is the cleanest path. However, if your organization has already provisioned some of these components (or a different team will), we need to know so we can wire Terraform to reference them via data sources instead of creating them.

3 Architecture Model

Common Model vs. Dedicated Model
  • Common Model — All firewall instances handle all traffic directions (inbound, outbound, east-west). Simpler to manage, fewer VMs, good for most deployments. Typically 2 firewalls across availability zones.
  • Dedicated Model — Separate firewall pairs for inbound vs. outbound/east-west traffic. Higher throughput ceiling, independent scaling per direction, but more VMs (typically 4+). Choose this for high-throughput environments or when inbound and outbound security policies diverge significantly.

4 Network & IP Planning

Subnet sizing

The transit VNet needs at least 3 subnets (management, public/untrust, private/trust), each with enough IPs for the firewall count. A /28 (14 usable IPs) per subnet is typical. If using Application Gateway (Common Model), a 4th /28 subnet is needed. The default example uses a /25 VNet CIDR to accommodate all subnets.
