VM-Series Active/Passive HA on Azure

Configure an active/passive HA pair for VM-Series firewalls managed by Strata Cloud Manager, covering Azure network prerequisites, Service Principal setup, VM-Series plugin configuration, and SCM HA provisioning.

What this guide covers

This guide walks through configuring active/passive HA for VM-Series firewalls already deployed on Azure and managed by Strata Cloud Manager (SCM). It assumes both firewalls are deployed, licensed, and connected to SCM. If you need to deploy the firewalls first, complete the VM-Series Deployment Guide before returning here.

SCM Pro license required. HA configuration for SCM-managed NGFWs requires a Strata Cloud Manager Pro license on both peers.

Active/passive only on Azure

VM-Series firewalls on Azure support active/passive HA only. Active/active HA is not supported on Azure. Both peers must be in the same Azure Resource Group and must run the same version of the VM-Series plugin.

HA Modes & Design

Azure active/passive HA uses the VM-Series plugin to interact with Azure APIs and move IP resources from the failing peer to the peer that takes over. There are two distinct HA types, and the choice determines the NIC and IP configuration required:

▶ Secondary IP Move — North-South and East-West Traffic

On failover, the VM-Series plugin calls the Azure API to detach secondary IP configurations from the previously active peer and attach them to the now-active peer. This enables the floating IPs on both untrust and trust interfaces to follow the active firewall, preserving inbound and outbound traffic flows.

  • Untrust interface: secondary IP configuration with a private IP (any netmask) and a public IP. The public IP is the internet-facing floating address for inbound traffic.
  • Trust interface: secondary private IP address only. Moves on failover so servers can route return traffic through the active firewall.
  • Failover time: several minutes (Azure API calls to detach and reattach IPs).

Use when you need to inspect north-south (internet-facing) traffic in addition to east-west.

▶ UDR — East-West Traffic Only

No floating IPs are required. On failover, the VM-Series plugin updates the Azure route tables (UDRs) so the next-hop points to the primary IP of the peer that has taken over. Because route table updates are faster than secondary IP moves, failover time is significantly lower.

  • Untrust and trust interfaces: primary private IPs only. No secondary IP configurations needed.
  • Route tables: UDRs point to the active firewall's trust interface primary IP as next-hop. The plugin updates these routes on failover.
  • Failover time: faster than Secondary IP Move.

Use when all resources are within the Azure VNet and there is no requirement for north-south internet traffic inspection through the firewall pair.

▶ Cross-Availability-Zone Deployment

You can deploy the active and passive firewall peers in separate Azure Availability Zones (AZs). This is the recommended architecture for production because it protects against zone-level failures. Both peers still must be in the same Azure Resource Group and VNet.

HA pair AZs and Azure Health Monitoring

Palo Alto Networks recommends placing HA peers in different AZs to avoid both being affected by the same Azure scheduled maintenance event. Azure Health Monitoring (configured in Phase 2) proactively fails over the active firewall when an Azure scheduled maintenance freeze event is detected, before the instance becomes unresponsive.

Phase 1: Prerequisites: Azure Requirements

▶ 1.1 VM Placement Requirements
  • Same Azure Resource Group: both HA peers must be in the same resource group. This is required for the VM-Series plugin to manage IP configurations and route tables via Azure API.
  • Same VNet: both peers must be deployed in the same Virtual Network.
  • Same VM-Series plugin version: install identical versions of the VM-Series plugin on both peers.
  • Matching hostname and VM Name: the VM Name in Azure must match the firewall hostname set under Device > Setup > Management. The hostname is used to trigger failover detection.
  • IPv4 only: all firewall interfaces must use IPv4. IPv6 is not supported on Azure VM-Series.
  • Layer 3 interfaces only: the Azure VNet is a Layer 3 network. All dataplane interfaces on the VM-Series must be configured as Layer 3.
▶ 1.2 NIC Requirements (Minimum 4 per Firewall)

Each HA peer requires a minimum of four network interfaces:

Untrust (eth1/1)ethernet1/1Internet-facing dataplane interface. Requires secondary IP configuration for north-south HA; primary IP only for UDR (east-west) HA.
Trust (eth1/2)ethernet1/2Internal dataplane interface. Requires secondary IP configuration for north-south HA; primary IP only for UDR HA.

Optional: dedicated HA1 interface

By default, the management interface serves as the HA1 control link. If you want a dedicated HA1 interface, add a fifth NIC to each firewall. Configure it as the HA1 port under the HA settings (Step 4.4 below).

Phase 1 (cont.): SCM & Folder Setup

▶ 1.3 Place Both Firewalls in the Same SCM Folder
Both firewalls must be in the same folder before you configure HA

SCM requires both HA peers to be in the same folder to configure HA. You cannot move firewalls to a different folder once they are in an HA configuration without first breaking the HA pair, moving both firewalls to the new folder, and then reconfiguring HA.

  1. In SCM, go to System Settings > Folder Management.
  2. If a target folder does not exist, click Add Folder, give it a name, and set its parent (typically All Firewalls or a regional parent folder).
  3. For each firewall, expand the Actions menu and select Move.
  4. Select the same destination folder for both peers and confirm the move.
Verification

Both firewalls appear listed under the same folder in System Settings > Folder Management.

Phase 1 (cont.): Azure Service Principal

The VM-Series plugin authenticates to Azure APIs to move secondary IPs and update route tables on failover. This requires an Azure Active Directory application and Service Principal with specific permissions.

▶ 1.4 Create the Azure AD App Registration and Service Principal
  1. In the Azure Portal, go to Azure Active Directory > App registrations > New registration.
  2. Give the application a descriptive name (for example, vmseries-ha-sp) and register it.
  3. Copy and save the following values; you will enter them into the VM-Series plugin in Phase 3:
    • Client ID (Application ID): displayed on the Overview page of the app registration.
    • Tenant ID (Directory ID): go to Azure Active Directory > Properties > Directory ID.
    • Azure Subscription ID: found in the Azure Portal under Subscriptions.
    • Resource Group Name: the resource group containing both VM-Series firewalls.
  4. Create a client secret: navigate to Certificates & secrets > New client secret, set an expiry, and copy the Value immediately (it is only shown once).

Creating a custom role via Azure CLI

You can define the permissions above in a JSON role definition and create it with:

az role assignment create \

  --role "VM-Series HA" \
  --scope /subscriptions/<sub-id>/resourceGroups/<rg-name>

Phase 2: Azure Network Setup

Choose your HA type first

The steps below differ depending on whether you are doing Secondary IP Move (north-south + east-west) or UDR (east-west only). Complete the section that matches your choice; skip the other.

▶ 2A.1 Add Secondary IP to the Untrust Interface (Active Peer)

The active peer's untrust NIC requires a secondary IP configuration with both a private IP and a public IP. This secondary configuration is what floats to the passive peer on failover.

  1. In the Azure Portal, go to the active firewall VM > Networking > Network settings.
  2. Click the untrust NIC (typically named *-untrust-nic).
  3. Under IP configurations, click Add.
  4. Set Allocation to Static and assign a private IP address in the untrust subnet (any netmask).
  5. Associate a public IP address with this secondary IP configuration (create a new Standard SKU public IP if needed). Standard SKU is recommended.
  6. Save the IP configuration.
Do not add a secondary IP to the passive peer's untrust interface

The secondary IP configuration (including the public IP) lives on the active peer only. On failover, the VM-Series plugin moves it to the passive peer. Do not pre-create a secondary IP on the passive peer's untrust interface.

▶ 2A.2 Add Secondary IP to the Trust Interface (Active Peer)

The active peer's trust NIC also requires a secondary IP configuration, but with a private IP only (no public IP). This secondary IP moves to the passive peer on failover so traffic continues flowing through the trust interface.

  1. Click the trust NIC for the active firewall VM.
  2. Under IP configurations, click Add.
  3. Set Allocation to Static and assign a private IP in the trust subnet (matching the netmask of the servers it secures).
  4. Do not associate a public IP with this secondary IP configuration.
  5. Save.
▶ 2A.3 Configure Route Tables to Use the Floating IP

Route tables (UDRs) in spoke subnets should route traffic toward the secondary (floating) IP of the trust interface, not the primary IP. This ensures traffic follows the floating IP after failover.

# Example: set default route in spoke subnet UDR to floating trust IP
az network route-table route create \
  --resource-group <rg> \
  --route-table-name <spoke-rt-name> \
  --name default-to-firewall \
  --address-prefix 0.0.0.0/0 \
  --next-hop-type VirtualAppliance \
  --next-hop-ip-address <trust-secondary-floating-ip>
▶ 2B.1 Verify Primary IP Configurations (No Secondary IPs Required)

For UDR-based east-west HA, only the primary IP configuration is needed on the trust and untrust interfaces of each peer. No secondary IP configurations are added. Confirm the following on both firewall VMs:

  • Untrust NIC: one primary private IP address, no secondary.
  • Trust NIC: one primary private IP address, no secondary.
  • Management NIC: primary private IP and public IP (for management access).
  • HA2 NIC: primary private IP in the HA2 subnet.
▶ 2B.2 Configure Route Tables Pointing to the Active Peer

Create UDR routes pointing to the primary trust IP of the active firewall as the next-hop virtual appliance. On failover, the VM-Series plugin automatically updates these routes to point to the new active peer's primary trust IP.

# Route traffic from spoke subnet through the active firewall trust interface
az network route-table route create \
  --resource-group <rg> \
  --route-table-name <spoke-rt-name> \
  --name default-to-firewall \
  --address-prefix 0.0.0.0/0 \
  --next-hop-type VirtualAppliance \
  --next-hop-ip-address <active-peer-trust-primary-ip>
After failover

When failover occurs, the VM-Series plugin updates the next-hop in these route tables to the primary trust IP of the peer that has become active. No manual route changes are required.

▶ 2C: Add HA2 Network Interface to Both Firewalls (Both HA Types)

Both HA peers require a dedicated HA2 NIC for session synchronization. Complete these steps on both firewall VMs.

  1. In the Azure Portal, add a subnet in the Transit VNet for the HA2 link (for example, ha2-subnet / 10.51.0.96/27).
  2. Create a new NIC in the Azure Portal:
    • Subscription and Resource Group: same as the firewall VMs.
    • Network and subnet: the HA2 subnet created above.
    • Private IP: assign a static private IP for each peer.
  3. Attach the NIC to the firewall VM: VM > Networking > Attach network interface. The VM must be stopped to attach a NIC.
  4. Start the VM after attaching the NIC.
Verification

Each firewall VM shows four (or more) network interfaces in Azure Portal > VM > Networking. The HA2 NIC has a private IP in the HA2 subnet.

Azure Health Monitoring

▶ 2D: Enable Azure Health Monitoring Auto-Remediation

Azure health monitoring is a daemon built into the VM-Series firewall that detects Azure scheduled maintenance events (freeze events) and hotplug events. When auto-remediation is enabled, it proactively fails over the active firewall before the instance becomes unresponsive, rather than waiting for the HA heartbeat to time out.

Enable auto-remediation by adding the following key-value pair to the VM's custom data (bootstrap options) at deployment time, or update it in the Azure Portal under VM > Configuration > Custom data:

health-auto-remedy=true

With this set, a detected freeze event triggers an immediate active-to-passive failover on the firewall where the event is detected. The passive peer then takes over.

Best practice: deploy HA peers in different Availability Zones

To avoid both peers being affected by the same Azure maintenance event, place the active and passive firewalls in separate Azure Availability Zones (AZs). Both must still be in the same Resource Group and VNet.

Phase 3: VM-Series Plugin Configuration

The VM-Series plugin must be configured on the active peer only with the Azure credentials. The plugin configuration is synced to the passive peer automatically after HA is established.

▶ 3.1 Configure the VM-Series Plugin on the Active Peer
Plugin version requirement

Use VM-Series plugin version 1.0.4 or later to encrypt the client secret. Both peers and any managing Panorama instance must run the same plugin version.

  1. Log in to the active firewall web interface.
  2. Navigate to Device > VM-Series.
  3. Enter the following fields from the Service Principal created in Phase 1:
    • Client ID: the Application ID of your Azure AD app registration.
    • Client Secret: the secret value you copied when creating the client secret. Enter it twice to confirm.
    • Tenant ID: the Directory ID of your Azure AD tenant.
    • Subscription ID: the Azure subscription ID where the firewalls are deployed.
    • Resource Group: the resource group name containing both firewall VMs.
  4. (Azure Stack only) Enter the Resource Mgr Endpoint URL. Leave this field empty for standard Azure Cloud deployments. Do not enter a value here for non-Azure Stack deployments because HA failover will fail if this field is set incorrectly.
  5. Click Validate to confirm the plugin can authenticate to Azure and reach the required resources.
  6. Commit the changes.
Verification

Validate returns success with no errors. The plugin is now authenticated to the Azure resource group and has the permissions to move IP configurations and update route tables on failover.

Phase 4: Configure HA in SCM: Basic Settings

Where to find HA configuration in SCM

In SCM, navigate to Configuration > NGFW and Prisma Access and select the Folder that contains both HA peers (the folder you set up in Phase 1). The HA Setup section appears within the folder configuration scope.

▶ 4.1 Create HA Pair and Set Basic Options
  1. In the HA Setup section, click Create HA.
  2. Set HA Mode to Active-Passive.
  3. Enable Config Sync. This enables configuration synchronization between the two HA peers so they stay in sync at all times.
  4. Set a Group ID (1–63) that is unique across all HA pairs on the same broadcast domain. If only one HA pair exists on this segment, any value works.
  5. (Optional) Enter a Description for the HA pair.
  6. Select an SSH HA Profile to apply to SSH sessions between HA peers on your network.
  7. (Active-Passive) Configure the Passive Link State. The default is Shutdown (HA ports on the passive peer show as down). Setting it to Auto allows you to monitor the passive peer's link state and reduces failover time because the passive peer's interfaces are ready.
  8. (Optional) Set the Monitor Fail Hold Down Time (1–60 minutes, default 1): the number of minutes to wait before retesting a down link.
  9. Select the Primary Device (the firewall to act as the active peer).
  10. Select the Secondary Device (the firewall to act as the passive peer).
  11. Click Next.

Phase 4 (cont.): Election Settings

▶ 4.2 Configure Election Settings
  1. Set Device Priority for each peer. A lower numerical value means higher priority (the firewall with the lower value will be preferred as the active peer). If both firewalls share the same value, the one with the lowest MAC address on the HA1 control link becomes active.
  2. Enable Preemptive on both the primary and secondary devices. With preemptive enabled, the higher-priority firewall will reclaim the active role after it recovers from a failure.
  3. Enable Heartbeat Backup. This routes heartbeat messages over the management interface as a backup to the HA1 control link. Enabling heartbeat backup prevents a split-brain scenario: when the HA1 link fails but both firewalls are still running, each peer would otherwise believe the other is down and both would attempt to become active simultaneously.
  4. (Optional) Modify HA Timers. The default profile is Recommended, suited for most deployments. Select Aggressive for faster failover triggering, or Advanced to define custom timer values. To view the preset timer values for your hardware model, select Advanced then Load Recommended or Load Aggressive.
  5. Click Next.

Phase 4 (cont.): HA1 and HA2 Links

▶ 4.3 Configure the HA1 Control Link

The HA1 control link carries hello messages, heartbeats, HA state information, and management-plane routing synchronization. It also carries configuration changes pushed from SCM.

By default, the management interface is used as the HA1 link. If you have added a dedicated HA1 NIC to each firewall, select that interface here instead.

Primary Device (Active Peer)

  1. Select the Ethernet Port for the HA1 control link (management interface or dedicated HA1 NIC).
  2. Enter the IPv4 Address, Netmask, and Gateway for the HA1 interface on the primary peer.
  3. (Optional) Expand Advanced Settings and set the Monitor Hold Time (ms): how long the firewall waits before declaring a peer failure due to a control link failure. Range is 1,000 to 60,000 ms; default is 3,000 ms.

Secondary Device (Passive Peer)

  1. Select the same interface type for the HA1 link on the secondary peer.
  2. Enter the IPv4 Address, Netmask, and Gateway for the HA1 interface on the secondary peer.

(Optional) HA1 Backup Link

Configure an HA1 backup link to provide redundancy if the primary HA1 link fails. Observe these constraints:

  • The HA1 backup IP addresses must not overlap with the primary HA1 IP addresses.
  • The HA1 backup link must be on a different subnet from the primary HA1 link.
  • HA1 backup and HA2 backup ports must be on separate physical ports.
  • The HA1 backup link uses TCP ports 28770 and 28260.

Click Next when done.

▶ 4.4 Configure the HA2 Data Link

The HA2 data link synchronizes sessions, forwarding tables, IPSec security associations, and ARP tables from the active to the passive peer. Data flow on HA2 is unidirectional (active to passive) except for HA2 keep-alive messages.

Azure transport mode

In Azure environments, the HA2 link must use UDP transport (Layer 4, port 29281). Layer 2 (Ethernet) transport is not supported on Azure because Azure VNets are Layer 3 networks. Select Layer4 transport via UDP/29281 as the transport method.

Primary Device (Active Peer)

  1. Select the Ethernet Port for the HA2 data link. This should be the NIC you attached to the HA2 subnet in Phase 2C (typically ethernet1/3).
  2. Enter the IPv4 Address, Netmask, and Gateway of the HA2 interface on the primary peer.
  3. (Optional) Expand Advanced Settings:
    • Verify Enable Session Synchronization is checked. With session synchronization enabled, the passive peer maintains the session in its dataplane, allowing it to immediately forward packets using the synchronized session on failover rather than rebuilding sessions from scratch.
    • Set Transport to Layer4 transport via UDP/29281 for Azure deployments.
    • Enable and configure HA2 Keep-alive:
      • Set Keep-alive Action to Log Only for active/passive deployments. The passive peer is in backup state and is not forwarding traffic, so a split datapath is not a risk.
      • Set the Keep-alive Threshold (ms): range is 5,000 to 60,000 ms; default is 10,000 ms.

Secondary Device (Passive Peer)

  1. Select the same interface for HA2 on the secondary peer.
  2. Enter the IPv4 Address, Netmask, and Gateway for the HA2 interface on the secondary peer.

(Optional) HA2 Backup Link

Configure an HA2 backup link to maintain session synchronization if the primary HA2 link fails. With HA2 keep-alive enabled, failover to the backup link also occurs when keep-alive messages fail beyond the configured threshold.

Click Next when done.

Phase 4 (cont.): Failover Conditions and Push Config

▶ 4.5 Define HA Failover Conditions

Define which monitored link or path failures trigger a failover. SCM presents link monitoring and path monitoring options at this step. For Azure deployments, standard link monitoring on the management and dataplane interfaces is typical.

  • Link Monitoring: triggers failover when one or more specified interfaces go down.
  • Path Monitoring: triggers failover when specified destination IP addresses become unreachable from the firewall.

Configure the conditions appropriate for your environment, then proceed to push the configuration.

▶ 4.6 Push Configuration to Both Peers
  1. In SCM, click Push Config to push the HA configuration to both firewall peers.
  2. Monitor the push status. Both firewalls should show Success in the push results.
  3. After the push completes, the firewalls will negotiate HA roles and synchronize configuration automatically.
Expected behavior after push

The firewall you designated as primary will become the active peer. The secondary firewall will enter passive state. Configuration synchronization begins immediately.

Phase 5: Post-Configuration Verification

▶ 5.1 Verify HA State via CLI

SSH into each firewall and run the following commands:

# Check overall HA state (should show active or passive)
show high-availability state

# Check HA peer status and synchronization
show high-availability all

# Verify VM-Series plugin is authenticated to Azure
show plugins vm_series

# Check session synchronization state
show high-availability transitions
Expected output
  • Active peer: Local state: active, Running Config: synchronized
  • Passive peer: Local state: passive, Running Config: synchronized
  • Both peers show Peer state: established
▶ 5.2 Verify VM-Series Plugin Sync on the Passive Peer

The VM-Series plugin configuration (Azure credentials) should have synced from the active peer to the passive peer automatically. Verify this on the passive firewall:

  1. Log in to the passive firewall web interface.
  2. Navigate to Device > VM-Series.
  3. Confirm that the Client ID, Tenant ID, Subscription ID, and Resource Group are populated (synced from the active peer). The Client Secret will not display for security reasons but should be present.
  4. Click Validate to confirm the passive peer can also authenticate to Azure.
Verification

Validate succeeds on the passive peer without you manually entering credentials. If fields are empty, the sync has not completed: wait a few minutes and refresh, or manually trigger a sync from the active peer's HA dashboard.

▶ 5.3 Test Failover
Plan a maintenance window

Testing failover will briefly interrupt traffic while the IP configurations move (Secondary IP Move) or route tables update (UDR). Coordinate with stakeholders before triggering a test failover in production.

  1. On the active firewall, trigger a manual failover via CLI:
request high-availability state suspend
  1. Verify the passive peer transitions to active:
show high-availability state
  1. For Secondary IP Move: verify in the Azure Portal that the secondary IP configuration has moved from the previously active VM to the now-active VM.
  2. For UDR: verify in the Azure Portal that the route table next-hops now point to the primary trust IP of the new active peer.
  3. Restore the suspended peer to functional state:
request high-availability state functional
Verification

The originally active firewall returns to the passive state (or reclaims the active role if preemption is enabled). Both peers show Running Config: synchronized.
