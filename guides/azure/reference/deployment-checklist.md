# Azure VM-Series Transit VNet: Deployment Checklist

Companion to [`vm-series-deployment.html`](../vm-series-deployment.html). Fill this in **before** you edit `terraform.tfvars` so every operator-specific value comes from one place.

> **Why this exists:** the single most common bootstrap failure is a `panorama-server` IP lifted from an existing template or a lab environment instead of the customer's actual Panorama. The firewalls boot, register with the **wrong** Panorama (or nothing at all), and have to be destroyed and re-deployed. A pre-flight checklist catches this before `terraform apply`.

---

## Section A: Bootstrap parameters (`bootstrap_options` block)

These end up in `terraform.tfvars` and are joined by Terraform into a single semicolon-separated string that Azure passes to each firewall as **custom data** on first boot. **Get them right before the first `terraform apply`**: fixing them after means destroying the firewall VMs and re-applying, because custom data is read only once.

Where the block lives depends on the model you chose in Phase 2A.4:

| Model | Where `bootstrap_options` goes | Guide step |
|---|---|---|
| Common (2 firewalls) | `vmseries_universal.bootstrap_options` (one block shared by both firewalls) | 4A.1 |
| TVNet Dedicated (4 firewalls) | `vmseries.<fw-key>.virtual_machine.bootstrap_options` (one block per firewall, values differ per tier) | 4B.1 |

| Parameter | Source | Example | Your value |
|---|---|---|---|
| `type` | **Fixed** for Azure (management IP is DHCP-assigned by the subnet) | `dhcp-client` | `dhcp-client` |
| `plugin-op-commands` | License Manager > **Show Bootstrap Parameters** (Phase 3) | `advance-routing:enable,panorama-licensing-mode-on` | _____________ |
| `panorama-server` | **Customer / your network**: IP or FQDN reachable from the firewall management subnet via VNet peering, ExpressRoute, or VPN. Confirm with the customer; **do NOT copy from existing baseline templates** | `10.52.0.4` | _____________ |
| `panorama-server-2` | **Customer / your network**: secondary Panorama (HA peer). Same rules as above | `10.52.0.5` | _____________ |
| `auth-key` | License Manager > **Show Bootstrap Parameters** (Phase 3). Generated by the SW Firewall License plugin; **not** a manually created VM auth key | `_AQ__K9YajjW...` | _____________ |
| `dgname` | Device Group name created in Phase 2A.4 | `DG-AZ-COMMON-MODEL` | _____________ |
| `tplname` | Template Stack name created in Phase 2A.4 | `STK-AZ-COMMON-MODEL` | _____________ |
| `vm-series-auto-registration-pin-id` | CSP Portal > Products > Device Certificates > **VM Registration PIN** (Phase 1.5) | UUID | _____________ |
| `vm-series-auto-registration-pin-value` | Same step as above | hex string | _____________ |

### Validation before `terraform apply`

- [ ] `panorama-server` and `panorama-server-2` are **reachable from the planned firewall management subnet** via VNet peering, ExpressRoute, or VPN. If not, the firewall will boot but never register.
- [ ] `dgname` and `tplname` **exist** in Panorama (you created them in Phase 2A.4) and match character for character (case-sensitive).
- [ ] `dgname` and `tplname` are **not already in use** by another tenant on a shared Panorama.
- [ ] `auth-key` is the active key for its License Manager (it can be rotated; check it has not been replaced since you copied it).
- [ ] The registration PIN shows as valid (not expired) in the CSP Portal.
- [ ] The management NSG allows outbound TCP/443 to `updates.paloaltonetworks.com` and the licensing endpoints, and outbound TCP/3978 and TCP/28443 to the Panorama subnet. Without these the firewall boots and registers but licensing, config push, and log forwarding silently fail.
- [ ] No value contains a semicolon or leading/trailing whitespace (the Terraform join is literal).

## Section C: Prerequisites that must exist before `terraform apply`

These are not tfvars values but the bootstrap sequence depends on them.

| Item | Where | Verified? |
|---|---|---|
| Software NGFW credits activated and a Deployment Profile created | CSP Portal (Phase 1.1, 1.4) | ☐ |
| Auth code recorded from the Deployment Profile | CSP Portal (Phase 1.4) | ☐ |
| Auto-Registration PIN generated and copied | CSP Portal (Phase 1.5) | ☐ |
| Azure Marketplace EULA accepted for VM-Series | Azure (Phase 1.6) | ☐ |
| Service Principal has Contributor on the subscription | Azure (Phase 1.7) | ☐ |
| Remote state Storage Account and container exist | Azure (Phase 1.9) | ☐ |
| SW Firewall License plugin installed and licensing API key set | Panorama > Plugins (Phase 2A.1, 2A.2) | ☐ |
| Bootstrap Definitions created with the auth code | Panorama > SW Firewall License (Phase 2A.3) | ☐ |
| Device Groups and Template Stacks created | Panorama (Phase 2A.4) | ☐ |
| License Managers created, bound to DG / Stack / BD, and **Active** | Panorama > SW Firewall License > License Managers (Phase 2A.11) | ☐ |
| Commit to Panorama completed with no errors | Panorama (Phase 2A.13) | ☐ |
| Panorama VNet exists and the Terraform identity has Contributor on its resource group (needed for the peering in 4.6); or, for on-prem Panorama, the ExpressRoute / VPN path from the management subnet is confirmed | Azure / customer network team | ☐ |

## How to use this sheet

1. Make a copy per deployment (do not fill in the canonical file in the repo).
2. Walk Phase 1 to Phase 3 of the guide and fill values in as you go.
3. Hand the completed sheet to whoever runs `terraform apply`. They should be able to populate `terraform.tfvars` from this sheet alone, with no need to revisit Panorama.
4. Keep the completed sheet attached to the deployment ticket or runbook for audit and post-mortem.
