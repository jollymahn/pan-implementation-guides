Cloud NGFW on Azure — Native Rulestack Managed by SCM

End-to-end guide: Azure subscription setup through SCM-managed security policy with native rulestack deployment

Cloud NGFW (Panorama/SCM Managed) VM-Series on Azure
Phase 1 Prerequisites Phase 2 Deploy Phase 3 Network Phase 4 Connect SCM Phase 5 Security Policy Phase 6 Advanced Phase 7 NAT Phase 8 Logging Phase 9 Verify
Guide Approach

This guide follows a deploy-then-connect approach. Cloud NGFW is deployed with a native local rulestack through the Azure portal, then connected to Strata Cloud Manager (SCM) for centralized security policy management. The core principle: Azure portal for infrastructure, SCM for security policy.

Design model: Cloud NGFW for Azure with native local rulestack, supporting both VNet and vWAN deployment topologies (tabbed where they diverge). NAT, DNS proxy, and network plumbing remain in the Azure portal; security rules, profiles, and advanced features are managed in SCM.

Deployment method: Azure portal for Cloud NGFW resource creation and network configuration. No Terraform or IaC required — all infrastructure is provisioned through the Azure console. Security policy is configured and pushed through the Strata Cloud Manager UI.

Complete these one-time setup tasks before deploying any Cloud NGFW resources. If all prerequisites are already in place, skip to Phase 2.

▶ Step 1.5: Plan Network Topology

Cloud NGFW for Azure deploys into either a VNet (hub-and-spoke) or vWAN (virtual hub) topology. The subnet sizing requirements differ between the two models and must be planned before creating the Cloud NGFW resource in Phase 2. Undersized subnets will cause the deployment to fail.

VNet (Hub-and-Spoke) Requirements

Cloud NGFW manifests as two private IP addresses (public-facing and private-facing) inside delegated subnets in the hub VNet. User-defined routes (UDRs) steer traffic through these IPs.

ResourceMinimum SizeDelegationNotes
Hub VNet/25n/aMust contain two delegated subnets
Public subnet (untrust)/26PaloAltoNetworks.Cloudngfw/firewallsHosts the public-facing IP of the Cloud NGFW
Private subnet (trust)/26PaloAltoNetworks.Cloudngfw/firewallsHosts the private-facing IP of the Cloud NGFW
Note

For deployments targeting 100 Gbps throughput, each delegated subnet requires 40 free IP addresses (80 total across both subnets). Size the subnets accordingly — a /25 subnet provides 123 usable IPs, which accommodates high-throughput deployments with room to spare.

Reference: Deploy the Cloud NGFW in a VNet

vWAN (Virtual Hub) Requirements

Cloud NGFW deploys as a SaaS NVA into the vWAN virtual hub. The hub address space determines the NVA subnet size and maximum throughput.

Hub Address SpaceNVA SubnetHosts per NVA SubnetMax Throughput
/16/25123~100 Gbps
/21/2727~50 Gbps
/23/2811~30 Gbps
/24/2811~30 Gbps
Important: Hub address space cannot be resized after creation

The vWAN hub address space is immutable once the hub is provisioned. To maximize throughput and auto-scaling capacity, use a /16 address space. Undersizing the hub to /24 caps the deployment at ~30 Gbps and limits future scale-out. See the Microsoft Virtual WAN FAQ for additional guidance.

Reference: Deploy the Cloud NGFW in a vWAN

Planning Checklist

Record the following values before proceeding to Phase 2:

  1. Topology model: VNet or vWAN.
  2. Azure region: The region where Cloud NGFW will be deployed. Verify Cloud NGFW availability in the target region at the Azure Virtual WAN partners page or in the Azure portal.
  3. Resource group: Existing or new resource group for Cloud NGFW resources.
  4. Hub VNet/vWAN address space: CIDR block sized per the tables above.
  5. Delegated subnet CIDRs: Two subnets (VNet model) or the NVA subnet allocation (vWAN model).
  6. Spoke VNets/VNet connections: List of application VNets that will be peered or connected to the hub.
  7. Public IP addresses: Number of public IPs needed for SNAT and DNAT.
Verification

A completed network planning worksheet exists with topology model, region, resource group, hub address space, delegated subnet CIDRs, and spoke VNet list. For VNet deployments: the hub VNet is at least /25 with two /26 subnets delegated to PaloAltoNetworks.Cloudngfw/firewalls. For vWAN deployments: the hub address space matches the throughput target from the table above.

Phase 5: Security Policy (SCM)

Build and deploy a security policy through Strata Cloud Manager. Cloud NGFW for Azure processes security rules differently from traditional PAN-OS firewalls — understanding these differences before creating rules prevents misconfiguration and rework.

Important: Cloud NGFW Has No Zones

Cloud NGFW for Azure operates with a single implicit zone. Every security rule must set both Source Zone and Destination Zone to ANY. Attempting to specify individual zones will fail. Source and destination matching is done entirely through prefix lists (IP/CIDR), FQDN lists (domain names), and country codes — not through zone-based segmentation.

▶ Step 6.6: Configure TLS Decryption

TLS decryption enables the Cloud NGFW to inspect encrypted traffic that would otherwise bypass threat prevention, URL filtering, and data inspection. Without decryption, the firewall can identify applications via TLS handshake metadata (SNI, certificate fields) but cannot inspect the payload for threats or sensitive data.

Reference: Set Up Inbound Decryption | Set Up Outbound Decryption | Add a Certificate to Cloud NGFW

Cloud NGFW supports two decryption modes. Select the tab that matches the traffic direction to inspect.

Which decryption mode do I need?
  • Inbound Decryption (SSL Inbound Inspection) — inspects encrypted traffic from external clients to internal servers that the organization owns. Requires the server’s private key. Use this for HTTPS services hosted in Azure (e.g., web applications behind the Cloud NGFW).
  • Outbound Decryption (SSL Forward Proxy) — inspects encrypted traffic from internal workloads to external servers on the internet. The Cloud NGFW acts as a man-in-the-middle proxy, generating ephemeral certificates for each session. Use this for outbound web browsing, API calls, and SaaS access from Azure VMs.

Both modes can be enabled simultaneously. Each requires its own certificate configuration and decryption rules.

Inbound decryption uses the server’s own certificate and private key to decrypt TLS sessions between external clients and internal servers. The Cloud NGFW terminates the client’s TLS session, inspects the plaintext, then re-encrypts and forwards the traffic to the backend server.

Prepare the Certificate in Azure Key Vault

  1. Concatenate the server certificate and private key into a single .pem or .pfx file. Do not upload the certificate and key as separate secrets.
  2. In the Azure portal, navigate to the Azure Key Vault that the Cloud NGFW resource can access.
  3. Upload the concatenated certificate file as a Certificate (not a Secret). Navigate to Certificates > Generate/Import, select Import, and upload the file.
  4. After the upload completes, click the certificate and copy the Secret Identifier URI. This URI is used in the next section to reference the certificate from the Cloud NGFW.
Important: Certificate Format and Type

PKCS8 is the supported certificate format. Only self-signed and root CA-signed certificates are supported — chained certificates (intermediate CA certificates) are not supported for inbound decryption. If the server uses a certificate chain, upload only the end-entity certificate with its private key.

Create a Managed Identity and Key Vault Access Policy

  1. Create a user-assigned managed identity in the same resource group as the Key Vault. See Create a user-assigned managed identity.
  2. In the Azure Key Vault, navigate to Access Policies.
  3. Click Create and assign the following permissions to the managed identity:
    • Key Vault Certificates Officer
    • Key Vault Secrets User
  4. Save the access policy.

Add the Certificate to the Cloud NGFW Rulestack

  1. In the Azure portal, navigate to the Cloud NGFW Local Rulestack.
  2. Click Certificates in the left pane, then click Add.
  3. Enter a descriptive Name (e.g., InboundCert-WebApp).
  4. Under Certificate source, choose Select from Key vault or Paste URI and provide the Secret Identifier URI copied earlier.
  5. Click Add.
  6. Navigate to the Managed Identity page in the rulestack. From the Enable MI dropdown, select the managed identity associated with the Key Vault.
  7. Click Save.

Create an Inbound Decryption Rule

  1. In the rulestack, navigate to Rules and click Create.
  2. Under General, provide:
    • Name: Decrypt-Inbound-WebApp
    • Priority: assign a unique priority (lower number = higher priority)
    • Enabled: Yes
  3. Configure Source and Destination matching to target the inbound traffic to the specific server IPs or subnets.
  4. Under Granular Controls, set Application to SSL.
  5. Under TLS Decryption, select Inbound and choose the Inbound Inspection Certificate created in the previous section.
  6. Enable Logging.
  7. Click Validate, then Config Actions > Deploy Configuration > Commit.
Verification

From an external client, connect to the HTTPS service behind the Cloud NGFW. The TLS handshake completes with the server’s original certificate (clients see the same certificate as without decryption). Check the Traffic logs for the session — decrypted sessions display the application as the identified Layer 7 protocol (e.g., web-browsing) rather than just ssl. The Decryption logs show the session with action decrypted and the certificate name.

Outbound decryption (SSL Forward Proxy) enables the Cloud NGFW to intercept, decrypt, and inspect HTTPS traffic from internal workloads to external servers. The firewall presents dynamically generated certificates to internal clients — a trust certificate for destinations with valid CA-signed certificates, and an untrust certificate for destinations with certificates the firewall does not trust.

Generate CA Certificates

Outbound decryption requires two CA certificates stored in Azure Key Vault:

Certificate Purpose Requirements
Forward Trust CA Presented to clients connecting to trusted external servers Must be a CA certificate (CA:TRUE in Basic Constraints). Cannot be self-signed. Must be signed by a root or intermediate CA that internal workloads trust.
Forward Untrust CA Presented to clients connecting to untrusted external servers Must be a CA certificate (CA:TRUE in Basic Constraints). Can be self-signed or CA-signed.
  1. Generate or obtain two CA certificates that meet the requirements above. Both must be in PKCS8 format.
  2. Concatenate each certificate with its private key into a single .pem or .pfx file.
  3. Upload both certificate files to Azure Key Vault > Certificates (as described in the Inbound tab).
  4. Copy the Secret Identifier URI for each certificate.
Important: Trust Certificate Distribution

Internal workloads must trust the Forward Trust CA certificate. If the certificate is not already in the workloads’ trust store (e.g., signed by the organization’s internal root CA), distribute the CA certificate to all Azure VMs whose outbound traffic will be decrypted. Without this, clients will receive TLS certificate errors for every HTTPS connection.

Configure Egress Decryption in the Rulestack

  1. In the Azure portal, navigate to the Cloud NGFW Local Rulestack.
  2. Add both certificates to the rulestack via Certificates > Add (same process as the Inbound tab).
  3. Navigate to Encrypted Threat Protection > Egress Decryption.
  4. Select the Trust Certificate from the dropdown.
  5. Select the Untrust Certificate from the dropdown.
  6. Navigate to the Managed Identity page. From the Enable MI dropdown, select the managed identity associated with the Key Vault.
  7. Click Save.

Create an Outbound Decryption Rule

  1. In the rulestack, navigate to Rules and click Create.
  2. Under General, provide:
    • Name: Decrypt-Outbound-SSL
    • Priority: assign a unique priority
    • Enabled: Yes
  3. Configure Source to match internal workload subnets and Destination to ANY (or specific external destinations to decrypt selectively).
  4. Under Granular Controls, set Application to SSL.
  5. Under TLS Decryption, select Outbound.
  6. Enable Logging.
  7. Click Validate, then Config Actions > Deploy Configuration > Commit.
Selective Decryption

Decrypting all outbound traffic can cause issues with certificate-pinned applications (e.g., some Azure services, Windows Update, certain SaaS tools). Create a no-decrypt rule with higher priority that matches traffic to certificate-pinned destinations and leaves TLS decryption set to None. This allows pinned applications to bypass decryption while all other outbound HTTPS traffic is inspected.

Verification

From an internal Azure VM, browse to an external HTTPS site. Inspect the certificate presented by the browser — it should be issued by the Forward Trust CA (not the original site’s CA). If the certificate shows the original CA, the decryption rule is not matching the traffic. Check the Decryption logs for entries with action decrypted. The Traffic logs should display full application identification (e.g., web-browsing, google-base) rather than generic ssl.

Critical: Test Decryption in a Staging Environment First

TLS decryption changes the trust chain for all matching traffic. Misconfigured certificates or missing trust store updates cause application failures, TLS errors, and potential outages. Deploy and test decryption rules in a staging environment or on a limited subset of workloads before enabling for production traffic.

Verification

Both inbound and outbound decryption rules (if configured) appear in the rulestack rules list with TLS Decryption mode set to the appropriate direction. The Decryption logs show entries for intercepted sessions. Security profiles (threat prevention, URL filtering, WildFire) can now inspect the plaintext payload of encrypted traffic — previously opaque ssl sessions now resolve to specific App-IDs in the Traffic logs.

  • Security policy → managed in SCM (Phases 5–6)
  • NAT rules → managed in Azure portal on the Cloud NGFW resource (this phase)

▶ Step 7.1: Understand NAT Scope

Cloud NGFW for Azure supports three types of NAT, each addressing a different traffic flow pattern. Reviewing these before configuration prevents applying the wrong NAT type to a given use case.

NAT Type Direction Use Case Configured Where
Source NAT (Egress SNAT) Outbound → Internet Spoke workloads reach the internet using the Cloud NGFW’s public IP. Provides a consistent egress IP for allowlisting by external services. Networking & NAT > Source NAT toggle
Destination NAT (DNAT) Inbound ← Internet External clients reach internal services (web servers, APIs) by mapping a Cloud NGFW frontend public IP and port to a backend private IP and port. Networking & NAT > Destination NAT rules
Private Source NAT East-West (private ↔ private) Traffic to private endpoints or PaaS services where UDR cannot be configured on the remote side. Prevents asymmetric routing by translating the source to the firewall’s private interface IP. Networking & NAT > Private Source NAT toggle
Important: 299-Rule SLB Limit for DNAT

Each DNAT rule consumes one rule slot on the underlying Azure Standard Load Balancer (SLB). Port ranges expand — a range of 443-500 consumes 58 SLB rule slots (one per port). The SLB enforces a hard platform limit of 299 rules total. This is an Azure platform constraint, not a Cloud NGFW limit. Plan DNAT rules carefully and prefer single ports over broad ranges to conserve capacity.

Example: 50 existing single-port DNAT rules + a new range of 100-350 (251 ports) = 301 total rules. This exceeds the 299-rule limit and causes the configuration to fail.

Source NAT During Initial Deployment

Source NAT can be enabled during the initial Cloud NGFW deployment in Phase 2 via the Source NAT Settings toggle on the Networking screen. If it was already enabled during deployment, Step 7.2 reviews and validates the existing configuration rather than creating it from scratch.

Verification

Review the three NAT types in the table and identify which ones apply to the deployment. At minimum, most deployments require Source NAT (egress). DNAT is needed only if external clients must reach internal services. Private Source NAT is needed only when east-west traffic targets private endpoints where UDR cannot enforce symmetric routing.

▶ Step 7.4: Configure Private Source NAT (East-West)

Private Source NAT solves an asymmetric routing problem that occurs when traffic flows from a spoke workload to a PaaS service or partner network accessible through a private endpoint. UDR directs outbound traffic to the Cloud NGFW, but the remote side — where UDR cannot be configured — sends return traffic directly to the client’s source IP, bypassing the firewall. Private Source NAT translates the source IP to the Cloud NGFW’s private interface IP, forcing return traffic back through the firewall.

Reference: Deploy the Cloud NGFW in a VNet — Edit an Existing Firewall to Enable Private Source NAT

When Is Private Source NAT Needed?

Private Source NAT is required when all three of the following conditions are true:

  • Traffic flows east-west between a spoke VNet and a private endpoint (PaaS service, partner network, or on-premises via ExpressRoute/VPN).
  • The remote side of the connection does not have UDR configured to route return traffic through the Cloud NGFW.
  • Asymmetric routing causes TCP handshakes to fail because return packets bypass the firewall.

If both sides of the east-west traffic flow have UDR pointing to the Cloud NGFW, Private Source NAT is not needed. Skip this step for standard spoke-to-spoke traffic where UDR is fully configured on all subnets.

  1. Navigate to the Cloud NGFW resource in the Azure portal.

  3. Click Edit.
  4. Scroll to the Private Source NAT section.
  5. Select the Enable Private Source NAT checkbox.
  6. Enter the destination address in CIDR notation. This is the IP range of the private endpoint or remote network that requires source translation. Multiple destination addresses can be added as comma-separated values.
  7. Click Save.
Important: Private Source NAT Hides Original Source IPs

When Private Source NAT is enabled, all traffic matching the configured destination addresses appears to originate from the Cloud NGFW’s private interface IP. This means the backend service sees the firewall’s IP as the client — not the original spoke workload IP. Security rules, access logs, and backend application logic that rely on client source IP will see the translated address. Factor this into security policy design and application-level access controls.

On the remote side, the connection’s source IP should match the Cloud NGFW’s private interface IP rather than the spoke workload’s original IP.

Phase 9: Verify & Validate

Perform end-to-end verification that Cloud NGFW is actively inspecting and enforcing policy on all traffic flows. Each step generates test traffic for a specific flow pattern (egress, ingress, east-west), then confirms the traffic appears in logs with the correct rule match. By the end of this phase, every configured traffic path has been validated from source to destination with log evidence.

Prerequisites for This Phase
  • Logging configured and active — Phase 8 must be complete. Diagnostic logs take 5–10 minutes to start flowing after initial configuration.
  • At least one spoke VM deployed — a test VM in a spoke VNet with no direct internet access (no public IP, or NSG blocking direct outbound) so that egress traffic routes through Cloud NGFW.
  • SSH or serial console access — connect to spoke VMs via Azure Bastion, serial console, or a jump host to run test commands.
  • Security policy pushed — at least the egress allow rule created in Phase 5 must be deployed and in sync.
▶ Step 9.1: Test Egress Traffic

Confirm that outbound internet traffic from a spoke VM flows through Cloud NGFW, matches the egress security rule configured in Phase 5, and exits with the expected public source IP (if Source NAT was configured in Step 7.2).

  1. Connect to a spoke VM via Azure Bastion, serial console, or SSH through a jump host.
  2. Run a basic HTTP connectivity test. This confirms outbound internet access is working through Cloud NGFW: 
    # Linux
curl -s -o /dev/null -w "%{http_code}" https://www.paloaltonetworks.com

# PowerShell (Windows)
(Invoke-WebRequest -Uri https://www.paloaltonetworks.com -UseBasicParsing).StatusCode

    Expected result: 200.

  3. Test DNS resolution to verify that DNS traffic passes through Cloud NGFW: 
    # Linux
nslookup www.paloaltonetworks.com

# PowerShell (Windows)
Resolve-DnsName www.paloaltonetworks.com

    Expected result: one or more IP addresses returned with no timeout.

  4. If Source NAT was enabled in Step 7.2, verify that the egress public IP matches the Cloud NGFW SNAT address: 
    # Linux
curl -s https://ifconfig.me

# PowerShell (Windows)
(Invoke-WebRequest -Uri https://ifconfig.me -UseBasicParsing).Content

    Expected result: the public IP address returned should match the Source NAT IP configured on the Cloud NGFW resource under Settings > Networking & NAT.

  5. Test a connection that the security policy should deny (if a deny rule exists). For example, if a rule blocks a specific FQDN: 
    # Linux — attempt to reach a blocked FQDN
curl -s -o /dev/null -w "%{http_code}" https://blocked-site.example.com

# PowerShell (Windows)
try { (Invoke-WebRequest -Uri https://blocked-site.example.com -UseBasicParsing).StatusCode } catch { $_.Exception.Message }

    Expected result: the connection should time out or be reset. Replace blocked-site.example.com with an actual FQDN matched by a deny rule in the security policy.

Important: DNS Proxy and Egress Path

If DNS Proxy was configured in Phase 3, DNS queries from spoke VMs are intercepted by Cloud NGFW before forwarding to the configured DNS servers. The nslookup test above validates both DNS Proxy functionality and the egress path in a single step. If DNS resolution fails but HTTP to IP addresses succeeds, the issue is in DNS Proxy configuration, not in the egress routing path.

Verification

curl returns HTTP 200 for allowed sites. nslookup resolves hostnames without timeout. ifconfig.me returns the Cloud NGFW Source NAT public IP (if SNAT is enabled). Denied FQDNs time out or are reset. All results confirm that egress traffic is flowing through Cloud NGFW and the security policy is being enforced.

▶ Step 9.2: Test Ingress Traffic

Confirm that inbound traffic from external clients reaches internal services through the DNAT rules configured in Step 7.3. Skip this step if no DNAT rules were configured.

No DNAT Configured?

If no Destination NAT rules were created in Phase 7, skip this step. Ingress testing requires at least one DNAT rule mapping a frontend public IP and port to a backend private IP and port.

  1. Identify the DNAT frontend IP and port. Navigate to the Cloud NGFW resource in the Azure portal > Settings > Networking & NAT. Note the Frontend IP and Frontend Port from the DNAT rule.
  2. From an external machine (outside the Azure environment — a local workstation or a VM in a different network), test connectivity to the DNAT frontend: 
    # Linux — HTTP/HTTPS service
curl -s -o /dev/null -w "%{http_code}" http://<FRONTEND_IP>:<FRONTEND_PORT>

# Linux — any TCP service
nc -zv <FRONTEND_IP> <FRONTEND_PORT>

# PowerShell (Windows)
Test-NetConnection -ComputerName <FRONTEND_IP> -Port <FRONTEND_PORT>

    Replace <FRONTEND_IP> and <FRONTEND_PORT> with the values from the DNAT rule.

  3. Verify the backend server received the connection. On the backend VM, check the application logs or run a listener test: 
    # Linux — check if a connection was received (if running a web server)
sudo tail -5 /var/log/nginx/access.log

# Linux — check active connections on the backend port
ss -tn | grep <BACKEND_PORT>

# PowerShell (Windows)
Get-NetTCPConnection -LocalPort <BACKEND_PORT> -State Established
  4. Confirm the source IP seen by the backend server. The backend server should see the original external client IP as the source (Cloud NGFW does not SNAT inbound DNAT traffic by default).
Important: NSG Rules for Inbound Traffic

The Network Security Group (NSG) on the Cloud NGFW public subnet must allow inbound traffic on the DNAT frontend port. If the connection times out despite a valid DNAT rule, check the NSG inbound security rules configured in Phase 3. The NSG acts before Cloud NGFW — blocked traffic never reaches the firewall.

Verification

External curl or Test-NetConnection succeeds against the DNAT frontend IP and port. The backend server shows the inbound connection in its logs or active connections. The DNAT translation — frontend IP/port to backend IP/port — is functioning correctly.

▶ Step 9.3: Test East-West Traffic (VNet Model)

Confirm that traffic between spoke VNets is inspected by Cloud NGFW. East-west inspection validates that the UDR configuration from Phase 3 is correctly routing inter-spoke traffic through the firewall rather than allowing it to flow directly between peered VNets.

Important: VNet Model Only

This step applies to VNet (hub-and-spoke) deployments only. In vWAN deployments, east-west traffic between spoke VNets is handled automatically by the routing intent configured in Phase 3 — the vWAN hub routes all inter-spoke traffic through Cloud NGFW without explicit UDRs on spoke subnets. vWAN users should still verify east-west traffic flows by running the test commands below, but there are no additional UDR route tables to troubleshoot if traffic fails.

  1. Identify two VMs in different spoke VNets. Note the private IP address of each VM. For this test:
    • Spoke A VM: the source (initiate connection from here)
    • Spoke B VM: the destination (listen for connection here)
  2. On the Spoke B VM, start a listener or confirm a service is running on a known port: 
    # Linux — start a temporary TCP listener on port 8080
nc -l 8080

# PowerShell (Windows) — check if a service is listening
Get-NetTCPConnection -LocalPort 8080 -State Listen
  3. On the Spoke A VM, test connectivity to the Spoke B VM: 
    # Linux
nc -zv <SPOKE_B_PRIVATE_IP> 8080

# Linux — alternative: test with curl if a web service is running
curl -s -o /dev/null -w "%{http_code}" http://<SPOKE_B_PRIVATE_IP>:8080

# PowerShell (Windows)
Test-NetConnection -ComputerName <SPOKE_B_PRIVATE_IP> -Port 8080

    Replace <SPOKE_B_PRIVATE_IP> with the actual private IP of the Spoke B VM.

  4. Verify the connection succeeded. On the Spoke B VM, the nc listener should show the incoming connection. On the Spoke A VM, nc -zv should report succeeded or Test-NetConnection should show TcpTestSucceeded : True.
East-West Security Rule

East-west traffic must be explicitly allowed by a security rule in the SCM policy. Cloud NGFW denies all traffic by default. If this test fails, verify that a security rule exists in Phase 5 that matches the source and destination spoke CIDR ranges with the appropriate application and service definitions.

VNet Model: UDR Route Verification

If east-west traffic fails, verify that the UDR on each spoke subnet includes a route for the other spoke’s CIDR range with the next hop set to the Cloud NGFW private IP address. Without this route, Azure sends inter-spoke traffic directly through VNet peering, bypassing the firewall entirely. See Step 3.2 for UDR configuration details.

Verification

TCP connection from Spoke A to Spoke B succeeds. The Spoke B listener receives the inbound connection. Traffic logs in Step 9.4 confirm the east-west connection was inspected by Cloud NGFW and matched the correct security rule.

▶ Step 9.4: Verify Rule Hits in Logs

Query Azure Log Analytics to confirm that all test traffic generated in Steps 9.1–9.3 produced log entries with the correct rule matches. Log evidence is the definitive proof that Cloud NGFW is inspecting traffic — a successful connection alone does not confirm firewall inspection.

Important: Log Ingestion Delay

Diagnostic logs may take 5–10 minutes to appear in Log Analytics after the traffic is generated. If queries return no results immediately after testing, wait 10 minutes and re-run the query. Do not reconfigure logging or routing based on empty query results within the first 10 minutes.

  1. Navigate to the Log Analytics workspace in the Azure portal (created in Step 8.1).
  2. Click Logs in the left menu. Dismiss the query templates dialog if it appears.
  3. Run the following KQL query to verify egress traffic from Step 9.1. This query looks for outbound sessions to the test URLs: 
    NGFWTrafficLogs
| where TimeGenerated > ago(30m)
| where DestinationIP !startswith "10." and DestinationIP !startswith "172." and DestinationIP !startswith "192.168."
| project TimeGenerated, SourceIP, DestinationIP, DestinationPort, Protocol, Action, RuleName, SessionEndReason, BytesSent, BytesReceived
| order by TimeGenerated desc
| take 50

    Expected result: rows showing the spoke VM’s private IP as SourceIP, external IPs as DestinationIP, Action of Allow, and the egress rule name from Phase 5 in the RuleName column.

  4. Run the following KQL query to verify ingress traffic from Step 9.2 (skip if no DNAT was configured): 
    NGFWTrafficLogs
| where TimeGenerated > ago(30m)
| where DestinationPort == <BACKEND_PORT>
| where DestinationIP == "<BACKEND_PRIVATE_IP>"
| project TimeGenerated, SourceIP, DestinationIP, DestinationPort, Protocol, Action, RuleName, NATDestination, SessionEndReason
| order by TimeGenerated desc
| take 20

    Replace <BACKEND_PORT> and <BACKEND_PRIVATE_IP> with the actual DNAT backend values. Expected result: rows showing the external client IP as SourceIP, the backend private IP as DestinationIP, and an Allow action with the inbound rule name.

  5. Run the following KQL query to verify east-west traffic from Step 9.3: 
    NGFWTrafficLogs
| where TimeGenerated > ago(30m)
| where SourceIP startswith "10." and DestinationIP startswith "10."
| where SourceIP != DestinationIP
| project TimeGenerated, SourceIP, DestinationIP, DestinationPort, Protocol, Action, RuleName, SessionEndReason
| order by TimeGenerated desc
| take 20

    Adjust the IP prefix filter if spoke VNets use 172.16.x.x or 192.168.x.x ranges instead of 10.x.x.x. Expected result: rows showing Spoke A IP as SourceIP, Spoke B IP as DestinationIP, and the east-west rule name in RuleName.

  6. Check for unexpected deny entries that may indicate missing or misconfigured rules: 
    NGFWTrafficLogs
| where TimeGenerated > ago(30m)
| where Action == "Deny" or Action == "Drop" or Action == "Reset"
| summarize DenyCount=count() by RuleName, SourceIP, DestinationIP, DestinationPort, Action
| order by DenyCount desc
| take 20

    Expected result: deny entries should only appear for traffic that is intentionally blocked by the security policy. Unexpected denies — such as spoke-to-spoke traffic, DNS queries, or expected egress traffic — indicate a missing allow rule in the security policy configured in Phase 5.

Threat Logs

In addition to traffic logs, check the NGFWThreatLogs table for any threat detections triggered during testing. A healthy deployment with Advanced Security profiles (Phase 6) active should not produce threat alerts for legitimate test traffic. If threat entries appear, review the ThreatCategory and ThreatName columns to determine whether a false positive requires a security profile exception.

Strata Logging Service Alternative

If Strata Logging Service was configured in Step 8.3, the same traffic logs are available in the SCM console under Incidents and Alerts > Log Viewer. Select the Firewall/Traffic log type and filter by the Cloud NGFW resource name to view matching entries. Reference: View Strata Logging Service Logs.

Verification

All three KQL queries (egress, ingress, east-west) return log entries matching the test traffic generated in Steps 9.1–9.3. Each entry shows the correct RuleName, an Allow action, and expected source/destination IPs. The deny query returns only intentionally blocked traffic — no unexpected drops for legitimate flows.
