Understanding Security Zones

In traditional PAN-OS firewalls (PA-Series, VM-Series), every physical or logical interface is bound to a security zone: trust, untrust, dmz, and so on. Security policy rules then specify zone pairs (e.g., trust → untrust) to control which traffic is allowed. This 1:1 interface-to-zone binding is a foundational concept that PS engineers and customers carry into cloud deployments.

Cloud NGFW breaks this model. Because Cloud NGFW is a fully managed service with no customer-visible interfaces, there are no interfaces to bind zones to. How zones are handled (and whether they exist at all) depends entirely on the cloud platform and management mode.

Critical: Azure Panorama Intrazone Default = ALLOW

When managing Cloud NGFW for Azure through Panorama, east-west traffic (private → private) is intrazone traffic. The default intrazone rule is ALLOW, meaning all spoke-to-spoke traffic passes without inspection unless you explicitly override it.

Immediately after deploying Cloud NGFW with Panorama management, change the intrazone-default action to DENY in the Panorama security policy. Without this override, your east-west segmentation is not enforced.

This does not apply to AWS (no zones), Azure SCM (any/any rules), or Azure Native Rulestack (ANY/ANY rules); in those modes, all traffic is matched by explicit policy rules.

Why do zones differ across clouds?

The zone model depends on the underlying data plane architecture:

  • AWS uses GWLB (Gateway Load Balancer) — all traffic enters through a single GWLB endpoint, so there is no directional interface to bind a zone to. All rules use any/any zones.
  • Azure (Panorama/SCM) uses delegated subnets — traffic enters through a public subnet or a private subnet, giving the firewall two natural zone assignments. Panorama exposes these as zone names; SCM abstracts them to any.
  • Azure Native Rulestack uses the same delegated subnet model, but the native rulestack policy engine does not expose zone fields — all rules match ANY/ANY.

Architecture Overview

Cloud NGFW for AWS is a Palo Alto Networks next-generation firewall delivered as a fully managed, cloud-native service. Palo Alto Networks owns and operates the underlying firewall infrastructure (including scaling, patching, and high availability) while you retain full control over security policy. Traffic reaches the Cloud NGFW through NGFW endpoints (AWS Gateway Load Balancer endpoints) that you place in your VPC subnets and reference in VPC route tables.

Security Zones on AWS

Cloud NGFW for AWS has no security zone concept. Because traffic reaches the Cloud NGFW through GWLB endpoints (a single data plane tunnel), there is no interface-to-zone binding. All security rules must use any for both source and destination zones.

Tip: Organize rules by direction

Without zones, use separate rulestacks or device groups per traffic direction (inbound, outbound, east-west) as an organizational equivalent. Within each rulestack, use IP address ranges and address groups to distinguish traffic flows. This replaces the zone-pair logic from traditional PAN-OS.

Five deployment models exist. Each balances control, complexity, and blast radius differently. Expand the model that matches your environment to study the architecture and traffic flows.

Which model should I pick?
  • Combined — Best for most environments. Centralizes east-west and outbound inspection in a security VPC via TGW, while distributing inbound inspection via cross-account NGFW endpoints in each spoke VPC. Start here if unsure.
  • Centralized — All traffic flows (inbound, outbound, east-west) route through a central security VPC via TGW. Simplifies management but requires an internet-facing ELB in the security VPC for inbound traffic.
  • Distributed — Each VPC has its own Cloud NGFW. No TGW required. Simplest to deploy but does not inspect inter-VPC (east-west) traffic across VPCs.
  • Isolated — Cloud NGFW shared across multiple standalone VPCs via cross-account endpoints. No TGW. Good for independent VPCs that do not need east-west connectivity.
  • Cloud WAN — Replaces TGW with AWS Cloud WAN for global, multi-region connectivity. Use when Cloud WAN is already your backbone.

Key Concepts

Availability Zone mapping is account-specific. AWS maps AZ names (e.g., us-east-1a) to physical AZ IDs (e.g., use1-az1) independently per account. This means us-east-1a in Account A may correspond to a different physical data center than us-east-1a in Account B. When deploying cross-account NGFW endpoints, always use AZ IDs, not AZ names, to ensure endpoints and workloads share the same physical AZ and avoid cross-AZ data transfer charges.

▶ Combined Model (recommended)

The Combined model uses a hub-and-spoke topology with AWS Transit Gateway at the center. East-west and outbound traffic routes through a centralized security VPC, while inbound traffic enters each spoke VPC directly and is inspected by cross-account NGFW endpoints before reaching application workloads.

This model deploys two logical Cloud NGFW resources:

  • An East-West & Outbound NGFW in the centralized security VPC — inspects all inter-VPC and internet-bound traffic.
  • An Inbound NGFW with cross-account endpoints placed in each spoke VPC — inspects traffic arriving from the internet before it reaches the application load balancer.

  6. The ELB distributes the request to healthy EC2 targets.

▶ Centralized Model

The Centralized model routes all traffic flows (inbound, outbound, and east-west) through dedicated security VPCs connected via Transit Gateway. No NGFW endpoints are placed in spoke VPCs.

This model deploys two security VPCs:

  • An East-West & Outbound Security VPC with NGFW endpoints, NAT gateways, and IGW.
  • A Centralized Inbound Security VPC with NGFW endpoints and an internet-facing ELB that accepts all inbound traffic.

Centralized Design high-level architecture:

When to Use Centralized

  • Regulatory requirements mandate that inbound traffic is inspected outside the application VPC.
  • A single ingress point is preferred for all applications.
  • Fewer Cloud NGFW resources to manage (one per traffic direction, not one per spoke).

▶ Distributed Model

In the Distributed model, each VPC that requires protection deploys its own NGFW endpoints. No Transit Gateway is required. This is the simplest model to deploy but does not provide cross-VPC (east-west) inspection between separate VPCs.

Three traffic patterns are supported within a single VPC:

Distributed East-West (Intra-VPC)

Traffic between subnets within the same VPC routes through NGFW endpoints placed in a firewall subnet. Subnet route tables direct inter-subnet traffic to the endpoint.

  1. Traffic from the source subnet routes to the NGFW endpoint.
  2. The NGFW endpoint tunnels traffic to the Cloud NGFW for inspection.
  3. If allowed, the NGFW returns the packet to the NGFW endpoint, which delivers it to the destination subnet.

Distributed Outbound

Outbound internet traffic from a private subnet routes through the NGFW endpoint before reaching the NAT gateway and IGW.

  1. Traffic from the private subnet routes to the NGFW endpoint.
  2. The NGFW inspects and, if allowed, returns traffic to the NGFW endpoint.
  3. The firewall subnet route table forwards to the NAT gateway.
  4. The NAT gateway forwards through the IGW to the internet.

Distributed Inbound

Inbound traffic from the internet enters via the IGW, hits the NGFW endpoint (via IGW edge association route table), is inspected, then forwarded to an ALB and ultimately to application instances.

  1. Traffic arrives at the IGW, which routes to the NGFW endpoint.
  2. The NGFW inspects and, if allowed, returns traffic to the NGFW endpoint.
  3. The endpoint routes to the ALB, which forwards to application targets.
Verification

The Distributed model is per-VPC, no-TGW. Each protected VPC has its own NGFW and endpoints. East-west inspection is intra-VPC only (between subnets), not between separate VPCs.

▶ Isolated Model

The Isolated model shares a single Cloud NGFW resource across multiple standalone VPCs using cross-account NGFW endpoints, without a Transit Gateway. Each VPC operates independently with its own IGW, NAT gateway, and NGFW endpoints.

This model is ideal when:

  • VPCs do not need east-west connectivity between each other.
  • Consolidating NGFW resources reduces cost and management overhead.
  • VPCs span multiple AWS accounts but share a common Cloud NGFW tenant.

Isolated Inbound Flow

  1. The IGW forwards traffic to the ALB.
  2. The ALB subnet route table directs target-group traffic to the inbound NGFW endpoint.
  3. The NGFW inspects and, if allowed, returns traffic to the endpoint.
  4. The firewall subnet route table delivers traffic to the application instances.

Isolated Outbound Flow

  1. EC2 instance traffic routes to the egress NGFW endpoint.
  2. The NGFW inspects and, if allowed, returns traffic to the endpoint.
  3. The firewall subnet route table forwards to the NAT gateway.
  4. The NAT gateway sends through the IGW to the internet.
Verification

The Isolated model has no TGW and no east-west traffic between VPCs. Each VPC has its own endpoints pointing to a shared Cloud NGFW resource. Separate inbound and outbound NGFW endpoints may reside in different firewall subnets.

▶ Cloud WAN Integration

AWS Cloud WAN replaces Transit Gateway as the network backbone. VPCs attach directly to a Cloud WAN core network organized into segments (e.g., ProdSegment, SecuritySegment). The security VPC containing the Cloud NGFW attaches to the security segment, and routing policies steer traffic through it.

Cloud NGFW should be deployed in every AWS region that the Cloud WAN spans to maintain low-latency inspection and regional cost optimization.

Deployment Approaches

  • Federated TGW + Cloud WAN — Replace TGW peering with Cloud WAN while keeping existing TGW attachments. Use this when migrating from TGW.
  • Cloud WAN only — All VPCs connect directly to Cloud WAN. TGW is removed entirely.

East-West Packet Walkthrough (Cloud WAN)

  1. App VPC 1 sends traffic to App VPC 2. The VPC route table has a default route to the Cloud WAN Core Network ARN.
  2. The core network performs a prod segment route table lookup. The default route points to the security VPC attachment.
  3. Traffic arrives at the security VPC's Cloud WAN subnet. The route table forwards to the NGFW endpoint.
  4. The NGFW inspects the traffic. If allowed, it returns to the NGFW endpoint.
  5. The firewall subnet route table has a default route back to the Core Network ARN.
  6. The core network performs a security segment route table lookup. The App VPC 2 CIDR matches a static route, and traffic forwards to App VPC 2.
  7. App VPC 2 receives the traffic via its Cloud WAN subnet.
Important: Cloud WAN Considerations
  • TGW-to-Cloud-WAN peering is supported only within the same region, not across regions.
  • The Cloud WAN core network ASN must differ from any TGW ASNs in the same environment.
  • Enable appliance mode on the security VPC attachment to maintain flow symmetry.
Verification

Cloud WAN replaces TGW as the hub. VPC route tables point to a Core Network ARN instead of a TGW ENI. Segment route tables and sharing policies control which traffic reaches the security VPC for inspection.

Architecture Overview

Cloud NGFW for Azure is a Palo Alto Networks next-generation firewall delivered as a fully managed, cloud-native Azure service (FWaaS). There is no firewall infrastructure to deploy, patch, or scale: Palo Alto Networks manages the underlying compute, and the Cloud NGFW resource scales automatically based on subnet sizing, up to 100 Gbps per resource with appropriately sized subnets.

Cloud NGFW for Azure supports multi-region deployments. Each Cloud NGFW resource is deployed within a specific Azure region with built-in high availability. For multi-region protection, deploy a separate Cloud NGFW resource in each region.

Multi-region deployment, with Cloud NGFW spanning availability zones within each region:

Security Zones on Azure

Azure Cloud NGFW uses delegated subnets (public and private) that provide a natural two-zone model. However, whether you can use these zones in security rules depends on the management mode.

Panorama-Managed

When Cloud NGFW for Azure is managed through Panorama, the firewall exposes two pre-defined zones: public and private. These map directly to the two delegated subnets. You cannot create custom zones; only public and private are available.

Traffic DirectionSource ZoneDest ZoneZone Type
Inbound (internet → spoke)publicprivateInterzone
Outbound (spoke → internet)privatepublicInterzone
East-West (spoke → spoke)privateprivateIntrazone
Override Intrazone Default to DENY

East-west traffic (private → private) is intrazone. PAN-OS defaults intrazone to ALLOW. This means all spoke-to-spoke traffic passes without inspection after deployment unless you change this immediately.

In Panorama: Policies → Security → Default Rules → intrazone-default → Action: Deny. Push the change to the Cloud NGFW device group.

SCM-Managed

When managed through Strata Cloud Manager, security rules use any for both source and destination zones. The zone fields are not editable in the SCM UI. Traffic direction is determined by address objects: use source/destination address groups to distinguish inbound, outbound, and east-west flows.

Logs from SCM-managed Cloud NGFW will still show public/private zone names (the underlying firewall still has zones), but policy rules always use any/any.

Three deployment models exist. The right choice depends on the Azure networking topology and whether cross-VNet (east-west) inspection is required.

Which deployment model?
  • Centralized VNet Hub-and-Spoke — traditional hub VNet with VNet peering to spoke VNets. Traffic steering uses User-Defined Routes (UDRs). Inspects all traffic types including east-west.
  • Virtual WAN (vWAN) — Cloud NGFW deploys directly into a Virtual WAN hub as a SaaS NVA. Traffic steering uses routing intent policies. Inspects all traffic types including east-west.
  • Distributed — each VNet gets its own dedicated Cloud NGFW instance. No hub, no peering. Simplest to deploy but does not inspect east-west traffic between VNets.
▶ Centralized VNet Hub-and-Spoke Model (primary)

Cloud NGFW is deployed into a centralized hub VNet that contains two delegated subnets, public and private. Spoke VNets peer to the hub and use UDRs to steer traffic through the Cloud NGFW private IP for inspection.

Centralized VNet hub-and-spoke topology:

Hub VNet Requirements

  • Minimum hub VNet size: /25 (128 addresses)
  • Two subnets, each minimum /26 (64 addresses): one public, one private
  • Both subnets must have subnet delegation enabled for PaloAltoNetworks.Cloudngfw/firewalls
  • A public IP address associated with the Cloud NGFW for inbound and outbound internet traffic

Traffic Flows

Egress (spoke to internet):

  1. Workload VM in spoke VNet sends traffic destined for the internet.
  2. The spoke subnet's UDR (0.0.0.0/0 → Cloud NGFW private IP) forwards traffic to the Cloud NGFW.
  3. Cloud NGFW inspects the traffic against security policy.
  4. Cloud NGFW performs SNAT — translates the source from the spoke VM's private IP to the Cloud NGFW's public IP.
  5. Traffic egresses to the internet.

Egress traffic flow:

Ingress (internet to spoke):

  1. External client sends traffic to the Cloud NGFW's public IP.
  2. Cloud NGFW performs DNAT — translates the destination from the public IP to the spoke workload's private IP.
  3. Cloud NGFW performs SNAT — translates the source to its private subnet IP to ensure return traffic routes back through the firewall.
  4. Traffic traverses VNet peering to reach the spoke workload.

Ingress traffic flow:

East-West (spoke to spoke):

  1. Workload VM in spoke A sends traffic to a workload in spoke B.
  2. The spoke subnet's UDR forwards traffic to the Cloud NGFW private IP.
  3. Cloud NGFW inspects the traffic against security policy.
  4. Traffic exits via the same private interface and traverses VNet peering to reach spoke B.
  5. No NAT is performed on east-west traffic.

East-west traffic flow:

Ingress via Application Gateway:

  1. External client sends traffic to the Azure Application Gateway's frontend public IP.
  2. Application Gateway terminates the connection and forwards to its backend pool via the app-gw subnet.
  3. A UDR on the Application Gateway subnet routes traffic to the Cloud NGFW private IP for inspection.
  4. Cloud NGFW inspects the traffic against security policy.
  5. Traffic traverses VNet peering to reach the backend workload in the spoke VNet.
  6. Return traffic from the spoke follows the UDR back through Cloud NGFW to the Application Gateway.

Ingress via Application Gateway traffic flow:

Important: SNAT/DNAT behavior

Cloud NGFW performs SNAT on all egress traffic and both SNAT + DNAT on ingress traffic. East-west traffic passes through without NAT translation. When using Application Gateway for ingress, DNAT is handled by the Application Gateway; Cloud NGFW inspects traffic in-line without performing NAT. DNAT rules for direct inbound access (without App Gateway) are configured in the Azure portal under the Cloud NGFW resource's Networking & NAT settings, not in Panorama or SCM.

Verification

Confirm you understand the Centralized VNet model before proceeding. All spoke traffic routes through UDRs to the Cloud NGFW in the hub VNet. Cloud NGFW performs SNAT on egress, DNAT + SNAT on ingress, and no NAT on east-west traffic. Application Gateway ingress uses a UDR on the App Gateway subnet to route through Cloud NGFW for inspection.

▶ Virtual WAN (vWAN) Model (overview)

In the Virtual WAN model, Cloud NGFW deploys directly into an Azure Virtual WAN hub as a SaaS NVA. Spoke VNets connect to the vWAN hub via virtual network connections (not VNet peering). Traffic steering uses routing intent and routing policies instead of UDRs.

Virtual WAN architecture:

vWAN Traffic Flows

Egress (spoke to internet):

  1. A workload VM in a spoke VNet (e.g., App02 at 10.113.2.4) sends traffic to an internet destination.
  2. The vWAN hub's routing intent policy (Internet → Cloud NGFW) directs the traffic to Cloud NGFW.
  3. Cloud NGFW inspects the traffic and performs SNAT — translating the source from the spoke VM's private IP to the Cloud NGFW's public IP (198.51.100.98).
  4. Traffic egresses to the internet destination.

vWAN egress traffic flow:

Ingress (internet to spoke):

  1. An external client sends traffic to the Cloud NGFW's public IP (198.51.100.98).
  2. Cloud NGFW performs DNAT — translating the destination to the spoke workload's private IP (e.g., 10.112.1.4 in App01) — and SNAT — translating the source to the Cloud NGFW's internal IP.
  3. The vWAN hub forwards the traffic to the spoke VNet via the virtual network connection.
  4. Traffic arrives at the destination workload in the spoke VNet.

vWAN ingress traffic flow:

East-West (spoke to spoke):

  1. A workload in App01 (10.112.1.4) sends traffic to a workload in App02 (10.113.2.4).
  2. The vWAN hub's routing intent policy (Private → Cloud NGFW) directs the traffic to Cloud NGFW for inspection.
  3. Cloud NGFW inspects the traffic and returns it to the vWAN hub. No NAT is performed on east-west traffic.
  4. The vWAN hub forwards the traffic to the destination spoke VNet via the virtual network connection.

vWAN east-west traffic flow:

Ingress via Application Gateway (hub VNet):

  1. External client sends traffic to the Azure Application Gateway's frontend public IP. The Application Gateway resides in a separate VNet connected to the vWAN hub.
  2. Application Gateway terminates the connection and forwards to its backend pool.
  3. The vWAN hub's routing intent policy directs traffic from the Application Gateway VNet to Cloud NGFW for inspection.
  4. Cloud NGFW inspects the traffic and the vWAN hub forwards it to the destination spoke VNet.

vWAN ingress via Application Gateway traffic flow:

East-West: On-premises to cloud:

  1. On-premises client sends traffic via ExpressRoute or S2S VPN to the vWAN hub.
  2. The vWAN hub's routing intent policy (Private → Cloud NGFW) directs the traffic to Cloud NGFW for inspection.
  3. Cloud NGFW inspects the traffic and returns it to the vWAN hub.
  4. The vWAN hub forwards the traffic to the destination spoke VNet via the virtual network connection.

▶ Distributed Model

In the Distributed model, each application VNet contains its own dedicated Cloud NGFW instance with public and private delegated subnets. VNets are not connected to each other; there is no hub, no peering, and no shared firewall. Each Cloud NGFW inspects only the traffic within its own VNet.

Distributed architecture with an independent Cloud NGFW per VNet:

Per-VNet Requirements

  • Each application VNet needs four subnets: public and private (delegated to Cloud NGFW, minimum /26 each), workload, and bastion (AzureBastionSubnet)
  • Each Cloud NGFW instance gets its own public IP for inbound DNAT and outbound SNAT
  • UDR on the workload subnet routes 0.0.0.0/0 to the local Cloud NGFW private IP

Traffic Flows

Egress (workload to internet):

  1. Workload VM sends traffic destined for the internet.
  2. The workload subnet's UDR (0.0.0.0/0 → local Cloud NGFW private IP) forwards traffic to the Cloud NGFW within the same VNet.
  3. Cloud NGFW inspects the traffic against security policy.
  4. Cloud NGFW performs SNAT — translates the source to this Cloud NGFW instance's public IP.
  5. Traffic egresses to the internet.

Distributed egress traffic flow:

Ingress (internet to workload):

  1. External client sends traffic to this Cloud NGFW instance's public IP.
  2. Cloud NGFW performs DNAT — translates the destination to the workload's private IP within the same VNet.
  3. Cloud NGFW performs SNAT — translates the source to its private subnet IP to ensure return traffic routes back through the firewall.
  4. Traffic reaches the workload VM within the same VNet (no peering needed).

Distributed ingress traffic flow:

No east-west traffic inspection

Because application VNets are isolated, there is no east-west traffic flow to inspect. If workloads in different VNets need to communicate securely, use the Centralized VNet or Virtual WAN model instead.

Confirm the Distributed model fits your use case. Each VNet gets its own Cloud NGFW instance; there is no hub, no peering, and no east-west inspection between VNets. Choose this model only when application VNets are truly isolated and do not need to communicate with each other.

Architecture Overview

Cloud NGFW for Azure with native rulestack provides a deploy-then-connect approach: infrastructure is provisioned through the Azure portal, and security policy is managed through Strata Cloud Manager (SCM). There is no requirement for Panorama or Terraform; the entire lifecycle is handled through Azure-native tools and the SCM web console.

This approach suits teams that want Azure-native infrastructure management (portal or ARM templates) with cloud-native security policy management through SCM. Zones and NAT stay in the Azure portal; security rules, address objects, and security profiles move to SCM.

The management boundary, showing what is managed where:

Security Zones on Azure Native Rulestack

Azure Native Rulestack uses a single implicit zone. The rulestack policy engine does not expose zone fields; all rules use ANY for source and destination zones. Traffic direction is determined by prefix lists and FQDN lists in the rule definition.

Traffic DirectionSource ZoneDest ZoneHow to Match
InboundANYANYSource = external prefix list; Dest = internal prefix list
OutboundANYANYSource = internal prefix list; Dest = FQDN list or external
East-WestANYANYSource & Dest = different internal prefix lists
Zones in logs

Even though rulestack rules use ANY/ANY, Cloud NGFW logs may still display public or private zone names. This reflects the underlying data plane behavior (the delegated subnets still have a directional nature) but it does not affect rule matching.

VNet Hub-and-Spoke

Cloud NGFW manifests as two private IP addresses (public-facing and private-facing) inside delegated subnets in the hub VNet. User-defined routes (UDRs) on spoke subnets steer traffic through these IPs for inspection.

vWAN (Virtual Hub)

Cloud NGFW deploys as a SaaS NVA into the vWAN virtual hub. Routing intent programs routes automatically; no UDRs are required on spoke VNets. Hub address space determines throughput scaling capacity.
