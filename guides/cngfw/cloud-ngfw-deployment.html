Cloud NGFW Deployment

End-to-end guide: marketplace subscription through verified traffic inspection with Cloud NGFW as a managed firewall service

Phase 1 Prerequisites Phase 2 Mgmt Platform Phase 3 Review Phase 4 Terraform Config Phase 5 Deploy & Verify Phase 6 Spoke VPCs Phase 7 Verify
Guide Approach

This guide follows a management-first approach. Cloud NGFW management — via Panorama or Strata Cloud Manager (SCM) — is configured before any AWS infrastructure is deployed. This ensures Cloud NGFW resources bootstrap into a fully configured management plane on creation.

Design model: Combined Design (TGW hub-and-spoke for east-west + distributed inbound in spoke VPCs) with GWLB endpoints and non-overlay routing.

Deployment method: All AWS infrastructure (Phases 4–6) is deployed with Terraform using the official Palo Alto Networks SWFW Modules — Cloud NGFW Combined Design.

Architecture Overview

Cloud NGFW for AWS is a Palo Alto Networks next-generation firewall delivered as a fully managed, cloud-native service. Palo Alto Networks owns and operates the underlying firewall infrastructure — including scaling, patching, and high availability — while you retain full control over security policy. Traffic reaches the Cloud NGFW through NGFW endpoints (AWS Gateway Load Balancer endpoints) that you place in your VPC subnets and reference in VPC route tables.

Five deployment models exist. Each balances control, complexity, and blast radius differently. Expand the model that matches your environment to study the architecture and traffic flows.

Which model should I pick?
  • Combined — Best for most environments. Centralizes east-west and outbound inspection in a security VPC via TGW, while distributing inbound inspection via cross-account NGFW endpoints in each spoke VPC. Start here if unsure.
  • Centralized — All traffic flows (inbound, outbound, east-west) route through a central security VPC via TGW. Simplifies management but requires an internet-facing ELB in the security VPC for inbound traffic.
  • Distributed — Each VPC has its own Cloud NGFW. No TGW required. Simplest to deploy but does not inspect inter-VPC (east-west) traffic across VPCs.
  • Isolated — Cloud NGFW shared across multiple standalone VPCs via cross-account endpoints. No TGW. Good for independent VPCs that do not need east-west connectivity.
  • Cloud WAN — Replaces TGW with AWS Cloud WAN for global, multi-region connectivity. Use when Cloud WAN is already your backbone.
▶ Combined Model (recommended)

The Combined model uses a hub-and-spoke topology with AWS Transit Gateway at the center. East-west and outbound traffic routes through a centralized security VPC, while inbound traffic enters each spoke VPC directly and is inspected by cross-account NGFW endpoints before reaching application workloads.

This model deploys two logical Cloud NGFW resources:

  • An East-West & Outbound NGFW in the centralized security VPC — inspects all inter-VPC and internet-bound traffic.
  • An Inbound NGFW with cross-account endpoints placed in each spoke VPC — inspects traffic arriving from the internet before it reaches the application load balancer.

Inbound Traffic Flow (Combined)

  1. Client sends a request to the application's public DNS name. DNS resolves to the EIP of the internet-facing ELB in the spoke VPC.
  2. The IGW edge association route table directs traffic to the inbound NGFW endpoint in the ELB's AZ.
  3. The NGFW endpoint tunnels traffic via GWLB to the Inbound Cloud NGFW for inspection.
  4. If allowed, the NGFW returns the packet to the NGFW endpoint.
  5. The NGFW endpoint subnet route table forwards traffic to the ELB's private IP.
  6. The ELB distributes the request to healthy EC2 targets.

Outbound Traffic Flow (Combined)

  1. An instance in a spoke VPC sends traffic to the internet. The instance subnet route table directs it to the TGW attachment.
  2. The TGW spokes route table matches the default route and forwards to the security VPC attachment.
  3. The TGW subnet route table in the security VPC forwards to the NGFW endpoint in the same AZ.
  4. The NGFW endpoint tunnels traffic to the East-West & Outbound Cloud NGFW for inspection.
  5. If allowed, the NGFW returns the packet to the NGFW endpoint.
  6. The NGFW endpoint subnet route table forwards internet-bound traffic to the NAT gateway.
  7. The NAT gateway translates the source IP to its public EIP.
  8. The IGW sends the packet to the internet.

East-West Traffic Flow (Combined)

  1. An instance in App01 VPC sends traffic to an instance in App02 VPC. The instance subnet route table directs it to the TGW attachment.
  2. The TGW spokes route table forwards to the security VPC attachment (no direct spoke-to-spoke routes exist).
  3. The TGW subnet route table in the security VPC forwards to the NGFW endpoint.
  4. The NGFW endpoint tunnels traffic to the East-West & Outbound Cloud NGFW for inspection.
  5. If allowed, the NGFW returns the packet to the NGFW endpoint.
  6. The NGFW endpoint subnet route table matches the App02 CIDR and forwards to the TGW attachment.
  7. The TGW security route table forwards to the App02 VPC attachment.
  8. The TGW attachment in App02 delivers the packet to the destination instance.

▶ Centralized Model

The Centralized model routes all traffic flows — inbound, outbound, and east-west — through dedicated security VPCs connected via Transit Gateway. No NGFW endpoints are placed in spoke VPCs.

This model deploys two security VPCs:

  • An East-West & Outbound Security VPC with NGFW endpoints, NAT gateways, and IGW.
  • A Centralized Inbound Security VPC with NGFW endpoints and an internet-facing ELB that accepts all inbound traffic.

Centralized Design — high-level architecture:

When to Use Centralized

  • Regulatory requirements mandate that inbound traffic is inspected outside the application VPC.
  • A single ingress point is preferred for all applications.
  • Fewer Cloud NGFW resources to manage (one per traffic direction, not one per spoke).

Inbound Traffic Flow (Centralized)

  1. Client sends a request to the application's public DNS name. DNS resolves to the EIP of the internet-facing ELB in the inbound security VPC.
  2. The ELB listener selects a target from the target group (private IPs in spoke VPCs) and forwards the request.
  3. The ELB subnet route table directs traffic to the NGFW endpoint.
  4. The NGFW endpoint tunnels traffic to the Inbound Cloud NGFW for inspection.
  5. If allowed, the NGFW returns the packet to the NGFW endpoint.
  6. The NGFW endpoint subnet route table forwards to the TGW attachment.
  7. The TGW inbound security route table forwards to the spoke VPC attachment.
  8. The spoke VPC TGW attachment delivers the packet to the instance or internal ELB.
Centralized Inbound Limitation

Centralized inbound inspection supports only TCP traffic with IP address targets in the ELB target group. UDP-based or non-ELB inbound workloads require the Combined model instead.

Outbound and east-west traffic flows are identical to the Combined model — they route through the centralized East-West & Outbound security VPC via TGW.

Verification

Confirm the distinction: in the Centralized model, inbound traffic enters at the security VPC's ELB, not at the spoke VPC. The Combined model's inbound traffic enters at each spoke VPC's own IGW and ELB.

▶ Distributed Model

In the Distributed model, each VPC that requires protection deploys its own NGFW endpoints. No Transit Gateway is required. This is the simplest model to deploy but does not provide cross-VPC (east-west) inspection between separate VPCs.

Three traffic patterns are supported within a single VPC:

Distributed East-West (Intra-VPC)

Traffic between subnets within the same VPC routes through NGFW endpoints placed in a firewall subnet. Subnet route tables direct inter-subnet traffic to the endpoint.

  1. Traffic from the source subnet routes to the NGFW endpoint.
  2. The NGFW endpoint tunnels traffic to the Cloud NGFW for inspection.
  3. If allowed, the NGFW returns the packet to the NGFW endpoint, which delivers it to the destination subnet.

Distributed Outbound

Outbound internet traffic from a private subnet routes through the NGFW endpoint before reaching the NAT gateway and IGW.

  1. Traffic from the private subnet routes to the NGFW endpoint.
  2. The NGFW inspects and, if allowed, returns traffic to the NGFW endpoint.
  3. The firewall subnet route table forwards to the NAT gateway.
  4. The NAT gateway forwards through the IGW to the internet.

Distributed Inbound

Inbound traffic from the internet enters via the IGW, hits the NGFW endpoint (via IGW edge association route table), is inspected, then forwarded to an ALB and ultimately to application instances.

  1. Traffic arrives at the IGW, which routes to the NGFW endpoint.
  2. The NGFW inspects and, if allowed, returns traffic to the NGFW endpoint.
  3. The endpoint routes to the ALB, which forwards to application targets.
Verification

The Distributed model is per-VPC, no-TGW. Each protected VPC has its own NGFW and endpoints. East-west inspection is intra-VPC only (between subnets), not between separate VPCs.

▶ Isolated Model

The Isolated model shares a single Cloud NGFW resource across multiple standalone VPCs using cross-account NGFW endpoints — without a Transit Gateway. Each VPC operates independently with its own IGW, NAT gateway, and NGFW endpoints.

This model is ideal when:

  • VPCs do not need east-west connectivity between each other.
  • Consolidating NGFW resources reduces cost and management overhead.
  • VPCs span multiple AWS accounts but share a common Cloud NGFW tenant.

Isolated Inbound Flow

  1. The IGW forwards traffic to the ALB.
  2. The ALB subnet route table directs target-group traffic to the inbound NGFW endpoint.
  3. The NGFW inspects and, if allowed, returns traffic to the endpoint.
  4. The firewall subnet route table delivers traffic to the application instances.

Isolated Outbound Flow

  1. EC2 instance traffic routes to the egress NGFW endpoint.
  2. The NGFW inspects and, if allowed, returns traffic to the endpoint.
  3. The firewall subnet route table forwards to the NAT gateway.
  4. The NAT gateway sends through the IGW to the internet.
Verification

The Isolated model has no TGW and no east-west traffic between VPCs. Each VPC has its own endpoints pointing to a shared Cloud NGFW resource. Separate inbound and outbound NGFW endpoints may reside in different firewall subnets.

▶ Cloud WAN Integration

AWS Cloud WAN replaces Transit Gateway as the network backbone. VPCs attach directly to a Cloud WAN core network organized into segments (e.g., ProdSegment, SecuritySegment). The security VPC containing the Cloud NGFW attaches to the security segment, and routing policies steer traffic through it.

Cloud NGFW should be deployed in every AWS region that the Cloud WAN spans to maintain low-latency inspection and regional cost optimization.

Deployment Approaches

  • Federated TGW + Cloud WAN — Replace TGW peering with Cloud WAN while keeping existing TGW attachments. Use this when migrating from TGW.
  • Cloud WAN only — All VPCs connect directly to Cloud WAN. TGW is removed entirely.

East-West Packet Walkthrough (Cloud WAN)

  1. App VPC 1 sends traffic to App VPC 2. The VPC route table has a default route to the Cloud WAN Core Network ARN.
  2. The core network performs a prod segment route table lookup. The default route points to the security VPC attachment.
  3. Traffic arrives at the security VPC's Cloud WAN subnet. The route table forwards to the NGFW endpoint.
  4. The NGFW inspects the traffic. If allowed, it returns to the NGFW endpoint.
  5. The firewall subnet route table has a default route back to the Core Network ARN.
  6. The core network performs a security segment route table lookup. The App VPC 2 CIDR matches a static route, and traffic forwards to App VPC 2.
  7. App VPC 2 receives the traffic via its Cloud WAN subnet.
Important: Cloud WAN Considerations
  • TGW-to-Cloud-WAN peering is supported only within the same region, not across regions.
  • The Cloud WAN core network ASN must differ from any TGW ASNs in the same environment.
  • Enable appliance mode on the security VPC attachment to maintain flow symmetry.
Verification

Cloud WAN replaces TGW as the hub. VPC route tables point to a Core Network ARN instead of a TGW ENI. Segment route tables and sharing policies control which traffic reaches the security VPC for inspection.

Phase 1: Prerequisites

Complete these prerequisites before configuring any management platform or deploying infrastructure. Each step ends with a verification check — do not proceed until every check passes.

▶ Step 1.1: Confirm AWS Account Requirements and IAM Setup

Cloud NGFW for AWS requires specific AWS account privileges and IAM roles. The CloudFormation template launched during subscription creates four cross-account IAM roles that Palo Alto Networks uses to manage NGFW endpoints, logging, and secrets.

  1. Sign in to the AWS Management Console with an account that has administrator-level IAM privileges.
  2. Navigate to Services → Security, Identity & Compliance → IAM.
  3. Click Access management → Roles.
  4. Search for PaloAltoNetworks.
  5. Confirm four roles exist:
    • PaloAltoNetworksCrossAcco-CustomNotificationLambda
    • PaloAltoNetworksCrossAcco-ServiceManagedEndpointRo
    • PaloAltoNetworksCrossAccountRoleSet-DecryptionRole
    • PaloAltoNetworksCrossAccountRoleSetu-LogMetricRole
Multi-Account Environments

For the Combined model with cross-account NGFW endpoints, a second AWS account associated with the same AWS organization is required. Add the second account to the Cloud NGFW tenant after subscription. Deploy spoke VPCs (App01, App02) on the second account and the security VPC on the subscription (first) account.

Verification

Four PaloAltoNetworks* IAM roles are visible in the IAM Roles list. Each role has a trust policy referencing a Palo Alto Networks-controlled AWS account.

▶ Step 1.2: Subscribe to Cloud NGFW in AWS Marketplace

An active AWS Marketplace subscription creates the Cloud NGFW tenant and grants access to the Cloud NGFW console, where NGFW resources and security configuration are managed.

  1. In the AWS console, navigate to Services → AWS Marketplace Subscriptions.
  2. Click Discover products.
  3. Search for Palo Alto Networks Cloud Next-Generation Firewall.
  4. Select Cloud Next-Generation Firewall (PAYG with 15-Day Free Trial).
  5. Review the product overview, then click View purchase options.
  6. Click Subscribe.
  7. Click Set up your account.
  8. Review the AWS permissions listed in step 1 of the setup page.
  9. Click Login or create vendor account.
  10. Under Create Tenant, enter an email address, first name, and last name, then click Create.
  11. Check email for a temporary password. Log in and set a new password.

▶ Step 1.3: Configure Audit Logging

  8. Navigate to Tenant in the left menu.

  10. Select CloudWatch.

  12. Click Save.
Verification

The Audit Log Settings section in the Cloud NGFW console shows CloudWatch as the destination with the correct Log Group ARN. In CloudWatch, the log group exists and shows recent audit entries after any console action.

Phase 2: Management Platform Configuration

All security policy, device groups, templates, and log forwarding are configured on the management platform before any AWS infrastructure is deployed. This management-first approach ensures that Cloud NGFW resources bootstrap into a fully configured policy on creation.

Cloud NGFW supports three management methods. Select the tab that matches your environment — the selection persists across the page.

Which path should I pick?
  • Panorama — Centralized management with device groups, template stacks, Cortex Data Lake logging, and advanced features (DAGs, DNS Security, WildFire, custom App-IDs). Required for multi-platform environments managing PA-Series, VM-Series, and Cloud NGFW from a single pane.
  • SCM (Strata Cloud Manager) — Cloud-native management with folder-based policy organization. Suitable for cloud-first environments standardizing on SCM.
Native Rulestacks (Local Management)

Cloud NGFW also supports local rulestacks managed directly through the Cloud NGFW console, Terraform, or CloudFormation. Local rulestacks are suitable for proof-of-concept or small deployments. This guide does not cover local rulestack configuration in detail — refer to Cloud NGFW Rules and Rulestacks in TechDocs.

Verification

▶ Step 2A.6: Configure Log Forwarding

When managed by Panorama, Cloud NGFW sends traffic logs to Cortex Data Lake. Configure log forwarding profiles in each device group to ensure all traffic is logged.

  1. In Panorama, navigate to Objects → Log Forwarding.
  2. Select the east-west-outbound device group.
  3. Click Add to create a new log forwarding profile.
  4. Set Name to default.
  5. Add log type match entries for traffic, threat, url, and data.
  6. For each match entry, select Cortex Data Lake as the forwarding destination.
  7. Click OK.
  8. Repeat for the inbound device group.
  9. Attach the log forwarding profile to each security rule: edit the rule, go to the Actions tab, and select the default log forwarding profile.
  10. Click Commit → Commit and Push.
Important: The Magic "default" Keyword

Naming the log forwarding profile exactly default (lowercase) causes PAN-OS to auto-attach it to new security rules created in this device group. This is case-sensitive and not retroactive — existing rules without a log forwarding profile must be updated manually.

Verification

A log forwarding profile named default exists in each device group. Every security rule shows the log forwarding profile attached in the Actions column. Commit-and-push completes without errors.

▶ Step 2B.2: Create Folder Structure

Folders in SCM organize policy hierarchically. Create folders to separate east-west/outbound and inbound policy sets.

Guide Approach

This guide follows a management-first approach. Cloud NGFW management — via Panorama or Strata Cloud Manager (SCM) — is configured before any Azure infrastructure is deployed.

Design model: Centralized VNet (hub-and-spoke with VNet peering and UDRs for traffic steering).

Deployment method: All Azure infrastructure (Phases 4–6) is deployed with Terraform using the official Palo Alto Networks SWFW Modules — Cloud NGFW Centralized VNet.

Architecture Overview

Cloud NGFW for Azure is a Palo Alto Networks next-generation firewall delivered as a fully managed, cloud-native Azure service (FWaaS). There is no firewall infrastructure to deploy, patch, or scale — Palo Alto Networks manages the underlying compute, and the Cloud NGFW resource scales automatically up to 50 Gbps per resource with built-in multi-AZ redundancy.

Two deployment models exist. The right choice depends on whether the Azure environment uses traditional hub-and-spoke VNets or Azure Virtual WAN.

Which deployment model?
  • Centralized VNet Hub-and-Spoke — traditional hub VNet with VNet peering to spoke VNets. Traffic steering uses User-Defined Routes (UDRs). This is the primary model covered in this guide.
  • Virtual WAN (vWAN) — Cloud NGFW deploys directly into a Virtual WAN hub. Traffic steering uses routing intent policies. See the overview below for key differences.
▶ Centralized VNet Hub-and-Spoke Model (primary)

Cloud NGFW is deployed into a centralized hub VNet that contains two delegated subnets — public and private. Spoke VNets peer to the hub and use UDRs to steer traffic through the Cloud NGFW private IP for inspection.

Centralized VNet — hub-and-spoke topology:

Hub VNet Requirements

  • Minimum hub VNet size: /25 (128 addresses)
  • Two subnets, each minimum /26 (64 addresses): one public, one private
  • Both subnets must have subnet delegation enabled for PaloAltoNetworks.Cloudngfw/firewalls
  • A public IP address associated with the Cloud NGFW for inbound and outbound internet traffic

Traffic Flows

Egress (spoke to internet):

  1. Workload VM in spoke VNet sends traffic destined for the internet.
  2. The spoke subnet's UDR (0.0.0.0/0 → Cloud NGFW private IP) forwards traffic to the Cloud NGFW.
  3. Cloud NGFW inspects the traffic against security policy.
  4. Cloud NGFW performs SNAT — translates the source from the spoke VM's private IP to the Cloud NGFW's public IP.
  5. Traffic egresses to the internet.

Egress traffic flow:

Ingress (internet to spoke):

  1. External client sends traffic to the Cloud NGFW's public IP.
  2. Cloud NGFW performs DNAT — translates the destination from the public IP to the spoke workload's private IP.
  3. Cloud NGFW performs SNAT — translates the source to its private subnet IP to ensure return traffic routes back through the firewall.
  4. Traffic traverses VNet peering to reach the spoke workload.

Ingress traffic flow:

East-West (spoke to spoke):

  1. Workload VM in spoke A sends traffic to a workload in spoke B.
  2. The spoke subnet's UDR forwards traffic to the Cloud NGFW private IP.
  3. Cloud NGFW inspects the traffic against security policy.
  4. Traffic exits via the same private interface and traverses VNet peering to reach spoke B.
  5. No NAT is performed on east-west traffic.

Important: SNAT/DNAT behavior

Cloud NGFW performs SNAT on all egress traffic and both SNAT + DNAT on ingress traffic. East-west traffic passes through without NAT translation. DNAT rules for inbound access are configured in the Azure portal under the Cloud NGFW resource's Networking & NAT settings — not in Panorama or SCM.

▶ Virtual WAN (vWAN) Model (overview)

In the Virtual WAN model, Cloud NGFW deploys directly into an Azure Virtual WAN hub as a SaaS NVA. Spoke VNets connect to the vWAN hub via virtual network connections (not VNet peering). Traffic steering uses routing intent and routing policies instead of UDRs.

Virtual WAN architecture:

Key Differences from Centralized VNet

Aspect Centralized VNet Virtual WAN
Cloud NGFW placement Hub VNet (customer-managed) vWAN hub (Azure-managed)
Traffic steering UDRs on spoke subnets Routing intent policies on the vWAN hub
Spoke connectivity VNet peering Virtual network connections
Branch/on-prem connectivity Separate VPN gateway in hub VNet Native vWAN S2S VPN, P2S VPN, ExpressRoute
Multi-region Separate hub VNet per region Hub-to-hub mesh with per-hub Cloud NGFW
East-west NAT No NAT No NAT
Note

The vWAN model is not covered in the step-by-step phases of this guide. For vWAN-specific deployment procedures, refer to the Cloud NGFW for Azure documentation and the companion vWAN deployment guide.

▶ Step 4.4: Create terraform.tfvars

Create a terraform.tfvars file with values specific to the deployment environment. The example below uses the reference IP schema from the Palo Alto Networks deployment architecture.

# terraform.tfvars — Cloud NGFW Centralized VNet Deployment

resource_group_name = "rg-cloudngfw-hub"
location            = "eastus"

# Hub VNet — minimum /25, subnets minimum /26 each, delegated to Cloud NGFW
vnets = {
  hub = {
    name          = "hub-vnet"
    address_space = ["10.10.0.0/16"]
    subnets = {
      public = {
        name             = "public"
        address_prefixes = ["10.10.1.0/24"]
        delegation       = "PaloAltoNetworks.Cloudngfw/firewalls"
      }
      private = {
        name             = "private"
        address_prefixes = ["10.10.2.0/24"]
        delegation       = "PaloAltoNetworks.Cloudngfw/firewalls"
      }
    }
  }
  app01 = {
    name          = "app01-vnet"
    address_space = ["192.168.0.0/16"]
    subnets = {
      app01 = {
        name             = "app01"
        address_prefixes = ["192.168.1.0/24"]
      }
    }
  }
  app02 = {
    name          = "app02-vnet"
    address_space = ["172.16.0.0/16"]
    subnets = {
      app02 = {
        name             = "app02"
        address_prefixes = ["172.16.1.0/24"]
      }
    }
  }
}

# Cloud NGFW resource
cloudngfws = {
  cloudngfw = {
    name            = "cloudngfw-hub"
    management_mode = "panorama"  # Change to "scm" or "rulestack" as needed
    panorama_registration_string = "PASTE_REGISTRATION_STRING_HERE"
    public_ip_name  = "cloudngfw-pip"
    enable_snat     = true
  }
}

# VNet peering — hub to each spoke
vnet_peerings = {
  hub-to-app01 = {
    local_vnet  = "hub"
    remote_vnet = "app01"
  }
  hub-to-app02 = {
    local_vnet  = "hub"
    remote_vnet = "app02"
  }
}
Important: Replace placeholder values

Replace PASTE_REGISTRATION_STRING_HERE with the registration string generated in Step 2A.6 (Panorama path) or configure the appropriate SCM/rulestack parameters. Adjust VNet CIDRs to avoid conflicts with existing address spaces.

Note: Subnet delegation

Both the public and private subnets in the hub VNet must be delegated to PaloAltoNetworks.Cloudngfw/firewalls. The SWFW modules handle this delegation automatically when the delegation attribute is set in the subnet configuration.

Verification

The terraform.tfvars file exists in the working directory with all placeholder values replaced. Running terraform validate after terraform init (Phase 5) should report no syntax errors.

Phase 6: Spoke VNet Onboarding

After the hub infrastructure is deployed, onboard additional spoke VNets by creating the VNet, peering it to the hub, and configuring UDR routing to send all traffic through the Cloud NGFW. This is the most-repeated process in the deployment lifecycle.

Note: Terraform vs. manual

The recommended approach is to add spoke VNets to the Terraform configuration (Phase 4) and re-run terraform apply. The manual steps below are provided for environments where Terraform is not used for spoke management or for one-off testing.

▶ Step 6.1: Create Spoke VNet

Create a new spoke VNet with a non-overlapping address space.

  1. Navigate to Home > Virtual networks and click Create.
  2. Set Resource group to the spoke's resource group (e.g., rg-app03).
  3. Set Name to app03-vnet.
  4. Set Region to the same region as the hub VNet.
  5. On the IP Addresses tab, set the address space (e.g., 10.20.0.0/16).
  6. Add a subnet (e.g., app03 with 10.20.1.0/24).
  7. Click Review + create, then Create.
Verification

Navigate to Home > Virtual networks. The app03-vnet VNet appears with the correct address space and subnet.

▶ Step 6.2: Configure VNet Peering to Hub

Peer the new spoke VNet to the hub VNet to enable connectivity through the Cloud NGFW.

  1. Navigate to Home > Virtual networks > hub-vnet > Peerings.
  2. Click Add.
  3. Set Peering link name (this VNet) to hub-to-app03.
  4. Ensure Allow 'hub-vnet' to access the peered virtual network is checked.
  5. Set Peering link name (remote VNet) to app03-to-hub.
  6. Set Virtual network to app03-vnet.
  7. Ensure Allow 'app03-vnet' to access 'hub-vnet' is checked.
  8. Ensure Allow 'app03-vnet' to receive forwarded traffic from 'hub-vnet' is checked.
  9. Click Add.
Important: Peering checkboxes

The Azure portal shows several similarly named checkboxes. Select only the specific options listed above. Incorrect selections can prevent traffic forwarding through the Cloud NGFW.

Verification

The peerings page shows hub-to-app03 with status Connected.

▶ Step 6.3: Create UDR with Default Route to Cloud NGFW

Create a route table with a default route pointing to the Cloud NGFW private IP address.

  1. Navigate to Home > Route tables and click Create.
  2. Set Resource group to rg-app03.
  3. Set Name to app03-udr.
  4. Set Region to the same region as the spoke VNet.
  5. Set Propagate gateway routes to No (prevents the Azure default internet route from overriding the UDR).
  6. Click Review + create, then Create.
  7. Open the newly created route table and navigate to Routes.
  8. Click Add.
  9. Set Route name to default-to-cloudngfw.
  10. Set Address prefix destination to IP Addresses.
  11. Set Destination IP addresses/CIDR ranges to 0.0.0.0/0.
  12. Set Next hop type to Virtual appliance.
  13. Set Next hop address to the Cloud NGFW private IP address (from Terraform outputs or Azure portal).
  14. Click Add.
Verification

The route table app03-udr shows a route: 0.0.0.0/0 → Virtual appliance → [Cloud NGFW private IP].

▶ Step 6.4: Associate UDR with Spoke Subnets

Associate the route table with the spoke subnet to activate the routing.

  1. Navigate to Home > Route tables > app03-udr > Subnets.
  2. Click Associate.
  3. Set Virtual network to app03-vnet.
  4. Set Subnet to app03.
  5. Click OK.
Verification

The route table app03-udr shows the app03 subnet associated under the Subnets tab.

▶ Step 6.5: Verify Routing from Spoke to Hub

Confirm the effective routes on a spoke VM's NIC show the UDR directing all traffic through the Cloud NGFW.

  1. Navigate to the spoke VM's NIC (e.g., Home > Virtual machines > app03-vm > Networking > Network interface).
  2. Under Help, click Effective routes.
  3. Confirm the 0.0.0.0/0 route shows Source = User, Next Hop Type = Virtual Appliance, Next Hop = Cloud NGFW private IP.

Alternatively, use the Azure CLI:

az network nic show-effective-route-table \
  --resource-group rg-app03 \
  --name app03-vm-nic \
  --output table
Verification

The effective routes show 0.0.0.0/0 with next hop Virtual Appliance pointing to the Cloud NGFW private IP. The VNet peering routes for the hub VNet address space also appear.

Phase 7: Post-Deployment Verification

Verify end-to-end traffic flows through the Cloud NGFW. These tests confirm that egress, east-west, and ingress traffic are inspected and logged correctly.

▶ Step 7.1: Verify Outbound Traffic Flow

Outbound traffic flows from a spoke VM through the Cloud NGFW with SNAT before reaching the internet.

  1. SSH or RDP into a spoke VM (e.g., app01-vm).
  2. Run a curl or wget to an external endpoint:
curl -s https://ifconfig.me
  1. The returned IP address should be the Cloud NGFW public IP — not the VM's private IP or a NAT gateway IP.
  2. Check the management platform for the traffic log:
    • Panorama: Navigate to Monitor > Logs > Traffic. Filter by the Cloud DG. Confirm a log entry shows the spoke VM's private IP as source and the external IP as destination.
    • SCM: Navigate to Monitor > Logs. Filter by the Azure folder. Confirm the same.
Note: SNAT behavior on egress

Cloud NGFW performs SNAT on all outbound traffic, translating the spoke VM's private source IP to the Cloud NGFW's public IP. The returned IP from ifconfig.me confirms this translation is working correctly.

Verification

curl https://ifconfig.me returns the Cloud NGFW public IP. A traffic log entry appears in the management platform with the correct source, destination, and application.

▶ Step 7.2: Verify East-West Traffic Flow

East-west traffic flows between spoke VNets through the Cloud NGFW without NAT translation.

  1. SSH into a VM in spoke A (e.g., app01-vm at 192.168.1.4).
  2. Attempt to reach a VM in spoke B (e.g., app02-vm at 172.16.1.4):
# Test connectivity — use an application allowed by security policy
curl http://172.16.1.4:80
  1. If no east-west allow rule exists for the test application, the connection is denied by the overridden intrazone-default rule. This is expected behavior confirming the Cloud NGFW is inspecting east-west traffic.
  2. Check the management platform for traffic or threat logs showing the connection attempt between the two spoke VMs.
Note: No NAT on east-west

Cloud NGFW does not perform NAT on east-west traffic. Both the source and destination IP addresses in the traffic logs should be the actual spoke VM private IPs.

Verification

Traffic logs show the connection attempt between 192.168.1.4 (app01) and 172.16.1.4 (app02) with no NAT. Allowed applications succeed; denied applications are logged with action deny.

▶ Step 7.3: Verify Inbound Traffic Flow

Inbound traffic arrives at the Cloud NGFW public IP, undergoes DNAT and SNAT, and is forwarded to the spoke workload.

  1. Navigate to the Cloud NGFW resource in the Azure portal: Settings > Networking & NAT.
  2. Under Destination NAT (DNAT), click Add to create a DNAT rule:
Field Value
Name app01-web-inbound
Protocol TCP
Frontend IP Cloud NGFW public IP
Frontend Port 80
Backend IP 192.168.1.4 (app01 VM)
Backend Port 80
  1. Click Save.
  2. Ensure a security rule exists in the management platform allowing web-browsing from zone public to zone private with the destination address matching the spoke VM.
  3. From an external machine (outside Azure), access http://[Cloud NGFW public IP].
  4. Confirm the spoke web server responds.
  5. Check traffic logs in the management platform. The log entry should show:
    • Source: external client IP
    • Destination: spoke VM IP (after DNAT)
    • NAT Source: Cloud NGFW private subnet IP (SNAT)
Important: DNAT configuration location

Inbound DNAT rules are configured in the Azure portal under the Cloud NGFW resource's Networking & NAT settings — not in Panorama or SCM. Security policy (allow/deny) is still managed on the management platform.

Verification

An external client can access the spoke web server via the Cloud NGFW public IP. Traffic logs show the connection with DNAT (destination translated to spoke VM IP) and SNAT (source translated to Cloud NGFW private IP).

▶ Step 7.4: Verify Azure Monitor Diagnostics

Cloud NGFW can send traffic, threat, and decryption logs to an Azure Log Analytics Workspace in addition to (or instead of) Panorama. Verify log delivery if Azure-native logging is configured.

  1. Navigate to the Cloud NGFW resource in the Azure portal.
  2. Under Monitoring, click Diagnostic settings.
  3. If a diagnostic setting exists, confirm it targets a Log Analytics Workspace or Storage Account.
  4. Navigate to the Log Analytics Workspace and run a sample query:
// Query Cloud NGFW traffic logs
PaloAltoNetworksCNGFWTrafficLogs
| where TimeGenerated > ago(1h)
| project TimeGenerated, SourceAddress, DestinationAddress, Application, Action
| take 20
  1. Confirm log entries appear that correspond to the traffic tests performed in Steps 7.1-7.3.
Note: Log types

Cloud NGFW supports three log types for Azure diagnostics: Traffic, Threat, and Decryption. Traffic logs record session start/end for every connection. Threat logs record matches against security profiles. Decryption logs record TLS handshake outcomes.

Verification

The Log Analytics Workspace query returns log entries showing traffic from the verification tests. Source addresses, destination addresses, applications, and actions match expected values.

Troubleshooting

Common issues encountered during Cloud NGFW for Azure deployment, organized by symptom.

▶ VNet Peering Not Connected

Symptom: VNet peering status shows Disconnected or Initiated instead of Connected.

Possible causes:

  • Overlapping address spaces between the hub and spoke VNets.
  • The peering was created from only one side. Azure requires the peering configuration on both sides, but when creating from the hub, Azure auto-creates the remote side.
  • Insufficient permissions to create peering in the remote VNet's subscription.

Resolution:

  1. Navigate to both VNets' peering pages and check the status from each side.
  2. If one side shows Initiated, delete the peering from both sides and recreate it from the hub VNet, ensuring both VNets are in the same subscription or that cross-subscription permissions exist.
  3. Verify no overlapping CIDRs exist between peered VNets.
Verification

Both sides of the peering show status Connected.

▶ UDR Routing Not Working

Symptom: Spoke VMs can reach the internet directly (bypassing Cloud NGFW) or cannot reach any destination.

Possible causes:

  • The route table is not associated with the spoke subnet.
  • The UDR next hop IP does not match the Cloud NGFW private IP.
  • Propagate gateway routes is set to Yes, allowing system routes to override the UDR.
  • The route table is in a different region than the VNet.

Resolution:

  1. Navigate to the route table and confirm the subnet association.
  2. Verify the next hop address matches the Cloud NGFW private IP (visible in the Azure portal under the Cloud NGFW resource overview).
  3. Set Propagate gateway routes to No on the route table.
  4. Use Effective routes on a spoke VM NIC to see the active route table:
az network nic show-effective-route-table \
  --resource-group rg-app01 \
  --name app01-vm-nic \
  --output table
Verification

Effective routes show 0.0.0.0/0 with source User pointing to the Cloud NGFW private IP.

▶ NSG Conflicts Blocking Cloud NGFW Traffic

Symptom: Traffic is blocked even though the Cloud NGFW security policy allows it. NSG flow logs show denied packets.

Possible causes:

  • NSG rules on the spoke subnet or VM NIC are denying traffic before it reaches the Cloud NGFW.
  • NSG rules on the hub public or private subnet are blocking traffic to/from the Cloud NGFW.
  • Missing NSG on a subnet with Standard SKU public IPs (Azure blocks all traffic by default without an NSG).

Resolution:

  1. Review NSG rules on both spoke subnets and hub subnets.
  2. For the hub private subnet, ensure inbound rules allow traffic from VirtualNetwork.
  3. For the hub public subnet, ensure inbound rules allow traffic on the required ports (e.g., 80, 443 for inbound web traffic).
  4. Use Azure Network Watcher NSG diagnostics to test specific traffic flows.
Verification

NSG flow logs show allowed traffic. NSG diagnostics confirm the test traffic flow is permitted by all NSGs in the path.

▶ Terraform Provider Errors

Symptom: terraform init or terraform plan fails with provider-related errors.

Possible causes:

  • Terraform version below the required minimum (1.5).
  • The paloaltonetworks provider is not included in the required_providers block.
  • Azure CLI is not authenticated or is using the wrong subscription.
  • Network connectivity issues preventing provider download from the Terraform registry.

Resolution:

  1. Verify Terraform version: terraform version.
  2. Verify Azure CLI authentication: az account show.
  3. If behind a proxy, set HTTPS_PROXY environment variable.
  4. Run terraform init -upgrade to refresh provider downloads.
Verification

terraform init completes without errors. terraform plan generates a valid execution plan.

▶ Cloud NGFW Resource Health Issues

Symptom: Cloud NGFW resource shows Unhealthy status or Failed provisioning state.

Possible causes:

  • Subnet delegation is missing on the public or private subnet.
  • Subnet size is too small (below /26).
  • The Panorama registration string is invalid or expired.
  • Panorama is unreachable from the Cloud NGFW resource (network connectivity issue).
  • The Azure region does not support Cloud NGFW.

Resolution:

  1. Check the Cloud NGFW resource Activity log in the Azure portal for specific error messages.
  2. Verify subnet delegation: navigate to the hub VNet subnets and confirm both public and private subnets show PaloAltoNetworks.Cloudngfw/firewalls under Subnet delegation.
  3. If using Panorama, verify the registration string is valid and has not expired. Generate a new one if needed.
  4. Verify Panorama network reachability: the Cloud NGFW must be able to reach Panorama's IP address. If Panorama is in a separate VNet, ensure peering or network connectivity exists.
Verification

The Cloud NGFW resource overview page shows Provisioning State: Succeeded and Health Status: Healthy.

▶ Subnet Delegation Issues

Symptom: Terraform fails with an error about subnet delegation, or the Cloud NGFW resource cannot be created in the specified subnets.

Possible causes:

  • The subnet already has resources deployed that conflict with the delegation.
  • The delegation string is misspelled (it must be exactly PaloAltoNetworks.Cloudngfw/firewalls).
  • The subnet has an existing delegation to a different service.

Resolution:

  1. Navigate to Hub VNet > Subnets and check the delegation status of both public and private subnets.
  2. If a conflicting delegation exists, remove it (this may require removing existing resources first).
  3. If no delegation exists, add it:
    • Select the subnet
    • Under Subnet delegation, choose PaloAltoNetworks.Cloudngfw/firewalls
    • Click Save
  4. Ensure no VMs, load balancers, or other compute resources are deployed in the delegated subnets — delegated subnets are reserved for the Cloud NGFW service.
Verification

Both hub subnets show PaloAltoNetworks.Cloudngfw/firewalls under subnet delegation. No conflicting resources exist in either subnet.
