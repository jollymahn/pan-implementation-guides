Cloud NGFW on AWS: Multi-Account Licensing with Panorama

Deploying Cloud NGFW into child AWS accounts when the Marketplace subscription and private-offer credits live in a parent account, and managing the result from an on-premises Panorama.

Cloud NGFW on AWS Cloud NGFW Overview & Deploy

Scope & Verification Status

This guide covers a specific situation: an AWS Organization where the Cloud NGFW Marketplace subscription and any private-offer credits sit in the parent (management) account, while the VPCs that need inspection live in child (member) accounts. It assumes policy is managed from an on-premises Panorama rather than Strata Cloud Manager, and that deployment is automated with the terraform-aws-swfw-modules Terraform modules.

Confidence tagging

Product behaviour changes between releases. Claims in this guide carry a tag so you know how much weight to put on each one:

  • Verified Confirmed by reading the Terraform module source directly. Safe to rely on, subject to the module version noted.
  • Unverified Consistent with how the product works, but not validated against current vendor documentation at the time of writing.
  • Confirm with PAN Materially affects the design, or is potentially destructive. Raise with your SE or TAC before acting. Do not treat these as instructions.

The Panorama integration details and the billing-transfer workflow in Path B are the least certain parts of this document. The Terraform findings are the most certain.

How Cloud NGFW Licensing Actually Works

Teams often arrive at this problem looking for a way to “present the licence” to the child account. That mechanism does not exist for this product, and looking for it wastes time. Cloud NGFW for AWS is a SaaS Marketplace offering, not an AMI offering, and that distinction drives everything else.

Why the AMI mental model misleads here

With VM-Series (an AMI product) you think in terms of licences and auth codes that attach to instances, and AWS License Manager grants that can be shared across an Organization. None of that applies to Cloud NGFW. There is no licence artifact to move, no auth code to present, and no License Manager grant to share. What exists instead is a tenant and a set of cross-account IAM roles.

Four things that get conflated

ThingWhat it isWhere it livesCan it move?
Marketplace subscription The AWS billing agreement that meters usage Parent account Only via Path B, with significant caveats
Private-offer credits Prepaid drawdown against that agreement Parent account, tied to the agreement Confirm with PAN
Cloud NGFW tenant The SaaS control plane, created when the subscription is activated. Owns firewall resources, rulestacks, and account associations. Logically owned by the subscribing account No, and it does not need to
Cross-account IAM roles What actually lets the tenant build endpoints inside another account's VPC Each child account Created per child via CloudFormation

The resolution: the subscription and credits stay in the parent permanently. You associate each child account with the parent's tenant, then deploy a vendor-generated CloudFormation template into each child to establish IAM trust. The tenant provisions firewall endpoints inside the child's VPCs while metering centrally against the parent's credits.

Subscription and credits never leave the parent. Only IAM trust is established in the child. On-prem Panorama reaches the tenant outbound over HTTPS.

The Three Paths

Three approaches circulate for this problem. They are not equivalent, and two carry real risk.

✓ Recommended

Path A: Associate child accounts with the parent's tenant

Subscription and credits stay in the parent. Child accounts are added to the tenant and a CFT establishes IAM trust.

Risk: Low. Additive and reversible.

⚠ Caution

Path B: Move the billing link to the child

Generate a billing code in the management console, subscribe from the child, then cancel the parent subscription.

Risk: High. The final step is destructive and may forfeit credits.

✗ Not applicable

Path C: Share via Organizations / License Manager

The mechanism used for AMI and container products.

Risk: Not applicable. Does not work for SaaS products such as Cloud NGFW. Rule it out early.

A further reason to prefer Path A under Panorama management

The Path B workflow is documented in Strata Cloud Manager terms: generating a billing code from SCM, then supplying a tenant email address during an SCM-flavoured activation wizard. Whether that flow exists, or behaves identically, for a Panorama-managed tenant is unknown. Confirm with PAN

Prerequisites: Tenant Setup in the Parent Account

Everything in Path A starts with “log in to the Cloud NGFW Admin Console”, which assumes something that may not be true yet. This section covers what has to exist first.

Yes, the tenant must be set up in the parent account

The Cloud NGFW tenant is created when someone activates the Marketplace subscription, and whichever AWS account performs that activation becomes the tenant owner. Since the subscription and the private-offer credits are in the parent, the tenant has to be created from the parent. There is no way to subscribe in the parent and have the tenant belong to a child.

This is also why the account-association model exists: the tenant is pinned to the parent, so child accounts are brought to it rather than the other way round.

A common starting state: subscription but no tenant

Accepting a private offer and activating the product are two different actions. Teams frequently accept the offer, see the credits land on the Marketplace agreement, and assume they are done. If nobody has clicked Set up your account, there is a billing agreement but no control plane, no console to log in to, and nothing to associate child accounts with.

Check which state you are in before anything else:

SymptomStateNext action
Marketplace shows an active subscription, but nobody has a Cloud NGFW console loginSubscribed, not activatedRun Prerequisite 2 below
Someone can log in to the Cloud NGFW console and sees a tenantTenant existsConfirm it is owned by the parent, then go to Path A
A tenant exists but was created from a child or a sandbox accountTenant in the wrong accountStop. This is the one scenario where Path B or a tenant rebuild becomes relevant. Raise with PAN.
▶ Prerequisite 1: Permissions and roles for the person doing the activation

Activation touches Marketplace, IAM, and CloudFormation in the parent account. The operator needs, in the parent:

  • aws-marketplace:Subscribe and aws-marketplace:ViewSubscriptions, to see and activate the agreement.
  • CloudFormation stack creation rights, plus iam:CreateRole and iam:AttachRolePolicy, for the onboarding template. CAPABILITY_NAMED_IAM is required.
  • Authority to accept vendor terms on behalf of the organisation. This is a commercial sign-off, not just a technical one.
Two different people, usually

The person with Marketplace and billing authority is rarely the person who will administer firewall policy. Plan for the activation to be done jointly, or for the activator to create a tenant admin account for the security team immediately afterwards. The email address used at activation becomes the initial tenant administrator, so do not use a personal address. Use a monitored distribution list.

Check for Service Control Policies at the OU level that block Marketplace subscriptions or IAM role creation. In tightly governed Organizations these are a frequent and quiet cause of failure.

▶ Prerequisite 2: Activate the subscription and create the tenant

This is the step that produces the console you later log in to.

  1. Sign in to the parent AWS account. Verify the account ID in the top-right before going further, because doing this in the wrong account creates a tenant in the wrong place.
  2. Go to AWS Marketplace > Manage subscriptions and open the Cloud NGFW for AWS subscription. If the private offer has not been accepted yet, accept it first.
  3. Click Set up your account, or Launch product on the purchase page. This hands off to the Palo Alto Networks Cloud NGFW Admin Console.
  4. Complete the registration form. This creates the tenant and the first tenant administrator.
  5. Record the tenant ID, the admin email, and the region you selected.
Decide the management mode here

If policy will be managed from an on-premises Panorama, that choice may need to be made at tenant creation rather than retrofitted. Read On-Premises Panorama Management before completing this step, not after. Confirm with PAN

Verification

You land in the Cloud NGFW Admin Console, a tenant is listed, and the parent account ID appears under Settings > AWS Accounts.

▶ Prerequisite 3: Onboard the parent account itself

Creating the tenant is not the same as onboarding an account to it. The parent also needs the cross-account CloudFormation template deployed, exactly as the child accounts will in Step A.2.

  1. In the Cloud NGFW console, download the CloudFormation template or copy the launch-stack URL generated for the parent account.
  2. Deploy it in the parent via CloudFormation, acknowledging the IAM capability prompt.
  3. Wait for the stack to reach CREATE_COMPLETE.

Deploy this even if no firewalls will ever run in the parent. It establishes the IAM trust the tenant needs for its own home account.

Verification

The parent account shows as Connected or Active under Settings > AWS Accounts. Only once you can see this working for the parent should you start adding child accounts, because you then know what success looks like.

▶ How to reach the console on subsequent visits

After the first activation you do not have to go through Marketplace every time, though that route always works.

RouteWhen to use it
AWS Marketplace > Manage subscriptions > Cloud NGFW > Launch product, from the parent accountAlways available, and the most reliable route. Use this if anyone is unsure which tenant they are landing in.
Direct Cloud NGFW Admin Console URL, signing in with the tenant admin identity created at activationDay-to-day administration, and for people who have no AWS console access at all. Unverified
Strata Cloud ManagerOnly where the tenant is managed through SCM. Not the route for a Panorama-managed estate. Unverified
Console access is not AWS IAM

Cloud NGFW console logins are tenant identities, managed in the Cloud NGFW tenant, not AWS IAM users. Granting someone AWS access to the parent account does not give them firewall administration rights, and revoking their AWS access does not remove their tenant login. Track tenant administrators separately in your joiner and leaver process. Unverified

Path A: Associate the Child Account

This section assumes the tenant exists and the parent is onboarded. If either is not yet true, start at Prerequisites.

▶ Step A.1: Add the child account to the tenant

Log in to the Cloud NGFW Admin Console as a tenant administrator, using one of the routes in Prerequisites. The tenant is the parent's, so there is nothing to log in to from the child account at this stage.

  1. Navigate to Settings > AWS Accounts, which may be labelled Account Linkage.
  2. Click Add Account.
  3. Enter the 12-digit AWS account ID of the child account.

Repeat per child account. There is no need to re-subscribe or re-purchase anything.

Verification

The child account appears in the accounts list with status Pending Setup or Awaiting CFT.

▶ Step A.2: Deploy the CloudFormation template in the child

The console generates a CloudFormation template, or a pre-signed launch-stack URL, scoped to the specific child account ID you entered. It is not generic. Do not reuse one child's template for another.

  1. Download the template, or copy the launch-stack URL.
  2. Log in to the child account's AWS Management Console. Confirm the account ID in the top-right before proceeding.
  3. Open CloudFormation and deploy the stack.
  4. Acknowledge the IAM capability prompt (CAPABILITY_NAMED_IAM).

This creates the cross-account role permitting the parent's tenant to create and manage Gateway Load Balancer endpoints inside the child's VPCs, plus the role used for log delivery.

Verification

In the Cloud NGFW Admin Console under AWS Accounts, the child account status changes to Connected or Active. If it stays pending for more than a few minutes, see Troubleshooting.

▶ Step A.3: Create the programmatic-access roles in the child (required for Terraform)
Commonly missed

Most console walkthroughs stop at the cross-account CFT. That is sufficient for console-driven deployment but not for Terraform. The cloudngfwaws Terraform provider does not use the cross-account role from Step A.2. It authenticates by assuming a separate set of programmatic-access roles. Skip this and terraform plan fails at provider initialisation.

Three role types exist: Unverified

RolePurposeProvider argument
LFALocal Firewall Admin, creates and manages NGFW resourceslfa_arn
LRALocal Rulestack Admin, manages account-scoped rulestackslra_arn
GRAGlobal Rulestack Admin, manages tenant-wide rulestacksgra_arn

Create these in the child account via Settings > Manage Programmatic Access in the Cloud NGFW console. The terraform-aws-swfw-modules examples assume a single role carrying both LFA and LRA permissions, named cloudngfw by default.

Confirm the trust policy requirements

These roles require a specific trust relationship and, in some versions, specific resource tags for the Cloud NGFW service to assume them. Use the exact policy document the console generates rather than hand-writing one. Confirm with PAN

Verification

From a shell holding child-account credentials, aws sts assume-role --role-arn arn:aws:iam::<CHILD_ID>:role/cloudngfw --role-session-name test succeeds, and terraform plan initialises the cloudngfwaws provider without an authentication error.

On-Premises Panorama Management

For an on-prem Panorama shop this is the constraint with the largest blast radius, and it needs settling before any Terraform is written, because it changes what Terraform is allowed to create.

Choose the management mode first

Cloud NGFW for AWS offers more than one policy management plane. The choice determines where rules live and what the Terraform module may own.

Policy is authored in Panorama as Device Groups and Template Stacks, then pushed to the Cloud NGFW tenant. The NGFW resource associates with Panorama via a link identifier rather than a rulestack.

Terraform implication: Terraform must not create rulestacks or security rules. It creates the NGFW resource, the endpoints, and the routing only. Policy belongs to Panorama. The cloudngfw module does the opposite today. See Terraform Changes.

Rules are authored per-account in the Cloud NGFW console or by Terraform. This is what the terraform-aws-swfw-modules cloudngfw module is built for today.

If the Panorama path stalls on version compatibility, this is the fallback that works with the module unmodified.

Cloud-delivered management. Relevant here mainly because the Path B billing-code workflow is documented in SCM terms, so organisations standardised on on-prem Panorama may find that workflow does not apply to them.

Settle this before provisioning anything

The management mode may be fixed at tenant or firewall-resource creation time, and converting a tenant from local-rulestack mode to Panorama-managed mode afterwards may require rebuilding firewall resources. Establish whether an existing tenant is already in the correct mode before associating child accounts. Confirm with PAN

▶ Step P.1: Install and license the Cloud NGFW plugin on Panorama

Panorama manages Cloud NGFW through a dedicated plugin, installed under Panorama > Plugins.

Version compatibility is a hard gate

There is a minimum Panorama PAN-OS version for the Cloud NGFW plugin, and a compatibility matrix between plugin version and the Cloud NGFW tenant. An on-prem Panorama that has not been upgraded recently is the single most likely blocker in a project like this. Check the current Panorama version against the matrix as the very first action item. Confirm with PAN

If Panorama is an HA pair, plan the plugin installation for both members.

▶ Step P.2: Open outbound connectivity from on-prem Panorama

This step is what distinguishes an on-prem Panorama from a cloud-hosted one, and it is where on-prem deployments typically stall.

Panorama initiates an outbound HTTPS (TCP/443) connection to the Cloud NGFW regional API endpoint:

api.<region>.aws.cloudngfw.paloaltonetworks.com

Work through the following with the network team:

  • Egress firewall rules permitting Panorama's management interface outbound to that FQDN on 443.
  • Proxy configuration if corporate egress is proxied. Panorama supports a proxy for plugin traffic, but it must be configured explicitly.
  • DNS resolution of the public endpoint from the management network.
  • TLS inspection exemption. If the egress path decrypts TLS, the API endpoint will likely need an exemption, since certificate pinning or strict validation may reject a re-signed certificate.
  • One endpoint per region. Multi-region deployments have a separate API hostname to permit for each region.
Good news for the firewall team

The connection is Panorama-initiated and outbound. No inbound rules to on-prem, and no requirement to expose Panorama to the internet. Unverified Confirm the direction before promising it to the network team.

Verification

The plugin shows a connected tenant, and the Cloud NGFW tenant appears with a reachable status. For a pre-check before touching Panorama, run curl -sv https://api.<region>.aws.cloudngfw.paloaltonetworks.com from a host on the same egress path.

▶ Step P.3: Link the tenant to Panorama and build the Device Group
  1. In the Cloud NGFW console, generate the credentials or service account the plugin will use to authenticate to the tenant.
  2. In Panorama, add the tenant to the Cloud NGFW plugin configuration.
  3. Create a Device Group for the Cloud NGFW estate, and a Template or Template Stack as required by the plugin.
  4. Author security policy in that Device Group as you would for any managed firewall.
  5. The plugin produces a link identifier associating a Cloud NGFW firewall resource with the Device Group. Terraform needs this value. See Terraform Changes.
Cross-account scope

Whether a single Panorama Device Group can span firewall resources living in multiple child accounts under one tenant, and how that interacts with the tenant's account associations, is a design question worth settling early if you are onboarding more than one child account. Confirm with PAN

▶ Step P.4: Decide where logs go
The most common unwelcome finding

Cloud NGFW writes logs to AWS-native destinations: CloudWatch Log Groups, S3, or Kinesis Data Firehose. It does not behave like a VM-Series forwarding logs to an on-prem Log Collector over the standard log-forwarding path.

A team running on-prem Panorama usually expects unified logging and reporting in Panorama, and with Cloud NGFW that expectation may not be met directly. Whether an on-prem Log Collector is a supported destination, and whether Strata Logging Service is required as an intermediary for Panorama-side log visibility, must be established before anyone is promised a single pane of glass. Confirm with PAN

Plan for one of these outcomes:

  • AWS-native only. Logs land in CloudWatch, S3, or Kinesis in the child account, the SIEM ingests from there, and Panorama manages policy without showing Cloud NGFW traffic logs.
  • Strata Logging Service. Logs go to the cloud logging service with Panorama querying it. There are commercial implications, so raise it with the account team.
  • On-prem Log Collector. If supported, this preserves the existing operational model. Verify before assuming.

The Terraform module already provisions CloudWatch log groups and streams and attaches a log profile, so the AWS-native path is the one with working automation today.

Terraform Changes Required

This section was verified by reading the module source in terraform-aws-swfw-modules, with the cloudngfwaws provider pinned at 2.0.20. Verified Line numbers shift between releases, so treat them as pointers rather than exact addresses.

Finding 1: The provider already supports targeting another account

The Cloud NGFW examples expose the hook you need. From examples/cloudngfw_centralized_design/versions.tf:

locals {
  provider = coalesce(var.provider_account, data.aws_caller_identity.current.account_id)
}

provider "cloudngfwaws" {
  region    = var.region
  host      = "api.${var.region}.aws.cloudngfw.paloaltonetworks.com"
  lfa_arn   = "arn:aws:iam::${local.provider}:role/${var.provider_role}"
  lra_arn   = "arn:aws:iam::${local.provider}:role/${var.provider_role}"
  sync_mode = true
}

Set provider_account to the child account ID and provider_role to the role created in Step A.3. The shipped .tfvars defaults to an empty provider_account and a role named cloudngfw.

Finding 2: The module hardcodes the account ID to the caller

In modules/cloudngfw/main.tf the account ID comes from the AWS caller identity in three places, with no override:

ResourceExpression
cloudngfwaws_ngfw.thisaccount_id = data.aws_caller_identity.current.id
cloudngfwaws_rulestack.thisaccount_id = data.aws_caller_identity.current.id
cloudngfwaws_ngfw_log_profile.thisaccount_id = data.aws_caller_identity.current.id
The failure mode

Run Terraform with parent credentials while pointing provider_account at the child, and the cloudngfwaws provider authenticates into the child while the resources are submitted with the parent's account ID. The resulting error does not obviously point at this mismatch.

Two ways to resolve it:

  • Option 1, no code change. Run Terraform with child-account credentials, or add assume_role into the child on the aws provider. Caller identity then resolves to the child and everything lines up. Least effort, and the right choice for a first deployment.
  • Option 2, parameterise the module. Cleaner for a multi-account pipeline run from a central automation account.
# modules/cloudngfw/variables.tf
variable "account_id" {
  description = "AWS account ID that owns the Cloud NGFW resources. Defaults to the caller's account. Set explicitly when deploying into a child account from a central pipeline."
  type        = string
  default     = null
}

# modules/cloudngfw/main.tf
locals {
  account_id = coalesce(var.account_id, data.aws_caller_identity.current.account_id)
}
# then replace all three occurrences of
#   data.aws_caller_identity.current.id
# with
#   local.account_id
Incidental inconsistency worth fixing at the same time

The module uses data.aws_caller_identity.current.id while the examples use data.aws_caller_identity.current.account_id. Both return the same value for this data source, so it is not a live bug, but account_id is the documented attribute and the inconsistency is confusing. Standardise on account_id.

Finding 3: The module cannot do Panorama-managed mode

This is the blocker, not the account linkage

Searching modules/cloudngfw/ and the Cloud NGFW examples for panorama or link_id returns zero matches. The module is built exclusively for local-rulestack mode.

modules/cloudngfw/main.tf creates:

  • cloudngfwaws_rulestack.this, a rulestack
  • cloudngfwaws_security_rule.this, security rules from var.security_rules
  • cloudngfwaws_commit_rulestack.this, a rulestack commit
  • cloudngfwaws_ngfw.this with rulestack = cloudngfwaws_commit_rulestack.this.rulestack

Under Panorama management none of the first three should exist, since policy comes from the Device Group, and the NGFW resource associates with Panorama by link identifier instead of by rulestack. The required change has roughly this shape:

variable "management_mode" {
  description = "Policy management plane: Rulestack (local) or Panorama."
  type        = string
  default     = "Rulestack"

  validation {
    condition     = contains(["Rulestack", "Panorama"], var.management_mode)
    error_message = "management_mode must be either Rulestack or Panorama."
  }
}

variable "link_id" {
  description = "Panorama link identifier. Required when management_mode is Panorama."
  type        = string
  default     = null
}

locals {
  panorama_managed = var.management_mode == "Panorama"
}

resource "cloudngfwaws_rulestack" "this" {
  count = local.panorama_managed ? 0 : 1
  # ... existing configuration
}

resource "cloudngfwaws_ngfw" "this" {
  name       = var.name
  vpc_id     = var.vpc_id
  account_id = local.account_id

  # Rulestack mode only
  rulestack = local.panorama_managed ? null : cloudngfwaws_commit_rulestack.this[0].rulestack

  # Panorama mode only. VERIFY attribute name against the provider schema.
  link_id = local.panorama_managed ? var.link_id : null
}
Verify the attribute names rather than trusting the snippet

The exact attribute name and semantics for Panorama association in cloudngfwaws_ngfw are not confirmed here. The snippet shows the shape of the change. Read the real schema straight from the pinned provider:

cd examples/cloudngfw_centralized_design
terraform init
terraform providers schema -json \
  | jq '.provider_schemas
        | to_entries[]
        | select(.key | test("cloudngfwaws"))
        | .value.resource_schemas.cloudngfwaws_ngfw.block.attributes
        | keys'

That gives the authoritative attribute list with no guesswork, and works offline once the provider is downloaded.

Finding 4: Global rulestacks need another provider argument

The module exposes rulestack_scope, defaulting to Local and accepting Global. The example provider block sets only lfa_arn and lra_arn, with no gra_arn, so setting rulestack_scope = "Global" against the examples as shipped will fail to authenticate.

This is usually moot under Panorama management, where policy comes from Device Groups and the rulestack question largely falls away. It matters only if the Panorama path is deferred and central rulestacks are adopted as an interim measure.

Path B: Moving the Billing Link to the Child

This workflow circulates informally and is included for completeness. It is not recommended, and should not be executed on the strength of this guide alone.

Three specific problems
  1. It solves a problem you probably do not have. The usual requirement is to deploy firewalls in a child account, and Path A achieves that without touching billing. Path B relocates the billing relationship, which is a different and larger change.
  2. The final step is destructive and may forfeit credits. The workflow advises cancelling the parent's Marketplace subscription once the child is active. Private-offer credits are attached to that agreement. Whether a prepaid balance migrates to a newly linked child subscription or is simply forfeited is the single most important thing to establish, in writing, before anyone clicks cancel. Confirm with PAN and with your AWS account team
  3. The source is unverified. The described console navigation and the billing-code prompt in the Marketplace wizard are not confirmed here, and the claim that the switch is non-disruptive is asserted rather than demonstrated. Confirm with PAN

If you pursue it anyway

Get written confirmation on the credit question first, then rehearse in a non-production tenant if one is available. The outline:

  1. In the management portal, navigate to the subscription or account-linkage page and add a new subscription for the target child account ID. Copy the generated billing code.
  2. From the child account, subscribe to Cloud NGFW for AWS in the Marketplace, choose Set up your account, answer yes to the billing-code prompt, and supply the tenant email plus the code.
  3. Verify the child is listed as an active subscribed account under the tenant.
  4. Stop. Do not cancel the parent subscription until the credit treatment is confirmed and you have run for a full billing cycle.
A safer middle ground

If the real driver is cost allocation rather than deployment, say so explicitly. It is usually solvable with AWS cost allocation tags and chargeback reporting against the parent's consolidated bill, with no change to the subscription at all.

Troubleshooting

▶ Child account stuck at “Pending Setup” after deploying the CFT
  • Confirm the stack was deployed in the child account, not the parent. This is the most common cause: an operator with both consoles open deploys into the wrong one.
  • Confirm the CFT used was the one generated for that specific account ID. Templates are not interchangeable between child accounts.
  • Check the stack actually reached CREATE_COMPLETE rather than rolling back on an IAM capability or name collision.
  • Check for a Service Control Policy at the OU level denying IAM role creation, or denying the sts:AssumeRole trust to an external principal. SCPs are a frequent cause in tightly governed Organizations, and the failure is silent from the console's perspective.
▶ Terraform fails to initialise the cloudngfwaws provider
  • The programmatic-access roles from Step A.3 are missing. The cross-account CFT role is not sufficient. This is the most common cause.
  • provider_account is empty, so it has fallen back to the caller's account via the coalesce() in versions.tf. Verify it holds the child account ID.
  • provider_role does not match the actual role name in the child account. The default is cloudngfw.
  • The host region does not match the region the tenant was onboarded in.
  • Test the role independently with aws sts assume-role --role-arn arn:aws:iam::<CHILD_ID>:role/cloudngfw --role-session-name tf-test.
▶ NGFW resource is created in the wrong account

This is Finding 2. The cloudngfwaws provider points at the child, but the AWS credentials Terraform runs under belong to the parent, so data.aws_caller_identity.current.id resolves to the parent.

Confirm what Terraform actually sees:

aws sts get-caller-identity

Fix by running with child credentials, adding assume_role to the aws provider, or applying the account_id variable patch from Finding 2.

▶ Panorama cannot reach the Cloud NGFW tenant
  • Verify DNS resolution of api.<region>.aws.cloudngfw.paloaltonetworks.com from the Panorama management network.
  • Verify the egress firewall rule exists and is matching. Check the traffic log on the perimeter firewall rather than assuming the rule works.
  • If egress is proxied, confirm the proxy is configured on Panorama for plugin traffic specifically, not just for content updates.
  • If the egress path decrypts TLS, add an exemption for the API endpoint and retest.
  • Confirm the plugin version is in the supported matrix. A version mismatch can present as a connectivity failure rather than a clear version error.
▶ Rulestack commit fails or times out

Relevant only in local-rulestack mode. The module already sets generous timeouts on cloudngfwaws_commit_rulestack (create and update at 20m). If commits still time out, check that the LRA role carries rulestack permissions rather than only firewall-admin permissions.

If you are in Panorama-managed mode and seeing this error at all, the module has not been modified per Finding 3. It is still trying to create and commit a rulestack that should not exist.

Summary

  1. Do not try to move the licence. Keep the subscription and credits in the parent, and associate child accounts with the tenant. That is Path A.
  2. Remember the programmatic-access roles. Console walkthroughs routinely omit them, and Terraform cannot authenticate without them.
  3. The Panorama requirement is the real project risk, not the account linkage. Plugin version compatibility and log destination are the two items most likely to force a design change.
  4. The Terraform module needs work before it can do Panorama-managed mode. It has no concept of it today, and will try to create rulestacks that should not exist.
  5. Treat Path B as out of scope unless someone confirms in writing that the private-offer credits survive.
