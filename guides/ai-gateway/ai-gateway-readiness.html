Customer Readiness — AI Gateway

What your application teams need ready before the first AI Gateway working session

AI Red Teaming AI Gateway API Intercept Model Scanning

This document is for the teams who own the AI Gateway target: the application developers, the platform engineers, and whoever holds the credentials. Work through it before the first working session. Everything here is something only you can supply, and every item left open on the day is a session that stops early.

What this covers, and what it does not

This is the customer side only. Licensing, tenant provisioning, deployment profiles and entitlement are handled separately by Palo Alto Networks and your account team, and none of it is on this list. If you are looking for that side, it is Phase 1 of the AI Gateway core deployment guide.

There is also a Technical Requirements Document for AI Gateway. That is the structured intake form filled in together during the session. This document is what gets you to that session able to answer it.

Three sections follow. Start these now is the one to action first: every item in it has a lead time measured in days rather than minutes, and it is the usual reason a kickoff slips.

Coverage is an inventory problem, not a deployment problem

The gateway is opt-in per application. Nothing forces traffic through it by routing, by DNS, or by a proxy setting. An application that still points at its provider endpoint keeps working exactly as before and stays completely invisible to the gateway.

So the work is not standing the gateway up, which takes very little time. The work is finding every application in your estate that calls a model, converting each one, and stopping new ones bypassing it. Section 2 is that inventory, and it is the item worth starting first.

1. Who needs to be in the room

RoleWhat they must be able to doWhat stalls without them
Owner of each application being routed Change three configuration values in their application and deploy it: the base URL, the credential, and the model reference. Know their release process and whether a change window is needed. No application moves to the gateway. The gateway can be stood up and configured, and still carry zero traffic.
Holder of the provider credentials
often a central AI platform team		 Supply the working provider credential for each model vendor in scope, and later revoke the direct keys that applications currently hold. Integrations cannot be configured, so there is nothing for an application to point at.
Platform or Kubernetes engineer
hybrid deployment only		 Install a Helm chart, or run a container on ECS or Container Apps, and expose it to the applications that will call it. There is no data plane for hybrid, and the engagement defaults to the hosted endpoint whether or not that was the intent.
Network or egress owner
hybrid deployment only		 Confirm the gateway's outbound destinations are permitted, and that TLS inspection is not breaking them. The gateway registers and reports healthy while every inference request fails. This failure looks like a product fault and is not one.
Security or data residency owner Decide hosted or self-hosted, having understood where prompt content travels in each case. A deployment model gets chosen for convenience and then has to be unpicked once someone asks the residency question.
FinOps or budget owner
optional, but useful		 Say how spend should be attributed: per team, per application, per environment. Set budget ceilings. Cost attribution collapses into one bucket, which is usually the reason the gateway was bought.

2. The application inventory

This is the central artifact. Build a row for every application, agent, notebook, pipeline or developer tool in your organization that calls a language model. Include the ones nobody officially approved, because those are the reason a gateway is being deployed.

For every application, recordWhy it is needed
Application name and owning teamBecomes the unit of cost attribution and the scope of its gateway key.
Which provider and model it calls todayDetermines which integrations have to exist before that application can be converted.
Where its provider key lives todayAn environment variable, a secret manager, or hard-coded. This is what gets revoked at cutover, and you cannot revoke what you cannot find.
Which SDK or client it usesMost clients take a base URL and a key. Some, such as Claude Code, send a bare model name and need one extra header to work at all.
Whether it streams responsesStreaming changes where a guardrail can stop a response and where it cannot.
Environment and criticalityPick a low-risk application to convert first. Converting the busiest production service first is a bad first day.
Release process and lead timeThree configuration values is a small change, but a small change in a regulated release process can still take two weeks.
Three values move an application, and no code changes

Converting an application means changing the base URL it calls, swapping its provider key for a gateway key, and prefixing the model name with an integration slug. Some native clients need a fourth value, a header naming the integration, because they send a bare model name the gateway cannot resolve.

No application logic changes. The useful thing to confirm in advance is simply whether those values are configurable at all, or baked into an image that has to be rebuilt.

2.1 — Provider credentials to have in hand

One per model vendor you intend to front. These are held centrally once the gateway is configured, and individual applications stop needing them.

ProviderWhat to bring
OpenAIAn API key, and the Organization ID if your account uses one.
AnthropicAn API key.
Amazon BedrockCredentials for an identity scoped to model invocation only, plus the region, plus confirmation that the models you want are enabled in that region.
Azure AI FoundryThe resource endpoint, the deployment names, the API version, and whichever credential your resource is configured for.
Anything self-hostedThe endpoint, the credential, and which API dialect it speaks.

2.2 — The deployment model decision

Make this before the session. It changes what your platform and network teams need to do, and it is awkward to reverse later.

ModelWhat you runWhere prompt content travels
Hosted Nothing. Applications call a Palo Alto Networks endpoint directly. Prompts transit a Palo Alto Networks hosted endpoint on their way to the provider.
Self-hosted A gateway in your own Kubernetes cluster, or on ECS or Container Apps. You size it, expose it and operate it. Prompt traffic does not transit a Palo Alto Networks endpoint. Prompt and response bodies are still sent to the Strata Cloud Manager backend for logging, so this is not the same as prompts never leaving your environment.
Self-hosted does not mean prompts stay in your environment

This is the single most common misunderstanding, and it surfaces late when it surfaces at all. In the current release the gateway sends full request and response bodies to the Strata Cloud Manager backend whichever endpoint served the call. Self-hosting changes the inference path, not the logging path.

If a data residency requirement is driving the self-hosted choice, get that in front of your security owner now rather than at the cutover review.

3. Start these now

TaskTypical lead timeDetail
Build the application inventory 1 to 3 weeks The longest item on the list, and the one that cannot be compressed. Egress logs to known provider hostnames are the fastest way to find callers nobody declared.
Open outbound egress for the gateway
self-hosted only		 1 to 5 business days The gateway calls its own control plane, its logging endpoint, each provider you integrate, and the Prisma AIRS scan endpoint when a guardrail is attached. Read the authoritative list off a running gateway rather than from any published list, including ours.
Exempt the gateway from TLS inspection
self-hosted only		 1 to 5 business days An inspecting proxy breaks several layers independently, and the symptoms do not point at the proxy. If inspection cannot be lifted, the CA bundle has to be mounted instead. Decide which before the session.
Obtain provider credentials Varies Often slower than expected, because the person who holds a production provider key is rarely the person attending the session.
Size and provision the data plane
self-hosted only		 1 to 2 weeks A cluster, or an ECS or Container Apps environment, plus however it will be exposed to the applications that call it.
Book a change window for the first application Varies Pick a low-risk application. The change itself is three configuration values; the approval around it is the part with the lead time.
Decide how bypass will be prevented Discussion Once applications are converted, what stops a new one calling a provider directly? The two levers are egress policy to the provider endpoints, and revoking the direct provider keys. Both need an owner.

4. What happens in the session

  1. The gateway is enabled, or the self-hosted data plane is installed and registered.
  2. An integration is configured per provider, using the credentials from section 2.1. Each gets a slug that applications reference.
  3. A gateway key is created for the first application, scoped and tagged so its cost is attributable.
  4. The first application is pointed at the gateway and a real request is proven end to end.
  5. Guardrails and logging are configured, and you see your own prompts in the log.
  6. The remaining applications are scheduled, which is where the inventory from section 2 earns its keep.

Readiness checklist

People confirmed
  • Owner of the first application to convert is attending
  • Holder of the provider credentials is attending or has handed them over
  • Platform engineer attending, if self-hosting
  • Network or egress owner attending, if self-hosting
  • Security owner has signed off the deployment model
  • Budget owner has stated how cost should be attributed
Inventory
  • Every application that calls a model is listed, including unofficial ones
  • Provider and model recorded for each
  • Location of each application's current provider key recorded
  • SDK or client recorded, and native clients needing an extra header flagged
  • Streaming applications flagged
  • A low-risk first application chosen
  • Release process and lead time known for that first application
Credentials and decisions
  • A working credential in hand for every provider in scope
  • Bedrock region confirmed and the required models enabled in it
  • Azure endpoint, deployment names and API version recorded
  • Hosted or self-hosted decided and signed off
  • Residency position understood, including that self-hosting does not keep bodies out of the backend
Lead-time items started
  • Egress rules raised, if self-hosting
  • TLS inspection exemption raised, or a CA bundle plan agreed
  • Cluster or container environment provisioned, if self-hosting
  • Change window booked for the first application
  • An owner named for preventing bypass after cutover
Check your connectivity before the session

The connectivity validator generates the commands to prove your environment can reach the gateway and authenticate to it, and decodes the output to tell you what is broken. For a self-hosted deployment it is worth running from inside the cluster as well as from a laptop.
