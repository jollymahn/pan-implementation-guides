Guide Approach

This guide deploys the Prisma AIRS AI Gateway, the Palo Alto Networks native gateway managed through Strata Cloud Manager (SCM). You pick how the data plane runs once (SaaS, hosted by Palo Alto Networks, or Hybrid, hosted in your own Kubernetes cluster), and the guide tailors the enablement phase to that choice. The selector is sticky: choose it in any section and the whole page follows.

Design model: every AI interaction in your organization (LLM prompts, Model Context Protocol traffic, and agent-to-agent communication) routes through the gateway, which applies guardrails, budgets, rate limits, and model allowlists while logging everything to a single dashboard.

Deployment method: configuration-driven. The SaaS gateway needs no infrastructure at all; the Hybrid data plane is a containerized deployment installed with Helm charts and still managed centrally from SCM. No infrastructure-as-code is required for the SCM configuration itself.

Architecture Overview

AI Gateway provides a centralized security and observability layer for all AI traffic in your organization. It sits between your applications, agents, and MCP clients on one side and your LLM providers, MCP servers, and privately hosted models on the other. Strata Cloud Manager is the control plane: licensing, configuration, access control, and dashboards all live there.

▶ What the gateway secures — prompts, MCP, and A2A

The gateway monitors and audits three classes of AI traffic from a single dashboard:

  • LLM prompts — requests and responses between your applications and model providers.
  • MCP interactions — Model Context Protocol traffic between agents and MCP servers, including servers authenticated with API keys or static tokens via custom headers.
  • Agent-to-agent (A2A) communication — traffic exchanged directly between AI agents.

All three classes are metered by token consumption against your flex credit allocation, and all three appear in the unified AI Gateway dashboard.

Verification

You can name the three traffic classes the gateway secures and know that all of them are metered and logged the same way.

▶ Key capabilities in this release
  • Unified AI traffic visibility — monitor and audit all AI interactions across prompts, MCP, and A2A traffic from a single dashboard.
  • Flexible logging — event logs stream to SIEM and SOAR tools via OpenTelemetry-compatible endpoints; prompt logs are stored natively with 1-year retention and, on Hybrid deployments, can be exported to a customer-owned S3 bucket.
  • Guardrails — Basic and third-party guardrails are supported out of the box; Check Language and Detect Gibberish are included in the Basic tier.
  • Flex credit licensing — metered by token consumption (1 token equals 4 characters), with identical pricing across both deployment models.
  • SCM-managed — full lifecycle management through Strata Cloud Manager with role-based access control via SBAC, the scoped role model Strata Cloud Manager uses to grant administrators access to specific tenants and folders. Palo Alto Networks does not expand the acronym in the official documentation. You do not configure SBAC in this guide; you only need an SCM account whose role can open AI Security in the left navigation, which Step 1.1 verifies.

Each tenant starts with a single default workspace. Multiple workspaces are supported, as is Strata Logging Service (SLS) integration for Threat Logs. SLS is where Threat Logs land; it is not required to deploy or use the gateway, and Step 1.1 explains what to do if your tenant has no SLS instance.

Verification

You understand the five capability pillars: visibility, logging, guardrails, flex credit licensing, and SCM management.

▶ Where AI Gateway ends and AI Runtime begins

AI Gateway is one pillar of Prisma AIRS, and its guardrails are intentionally scoped. Two detection families are not part of the gateway guardrail set:

  • PII (personally identifiable information) detection — handled by AI Runtime, which provides advanced DLP (Data Loss Prevention).
  • Moderation — handled by AI Runtime, which provides advanced threat detection.

Palo Alto Networks routes those to AI Runtime because it provides more comprehensive threat detection and DLP capabilities than guardrails cover. If you need inline scanning for prompt injection, data leaks, or malicious content, pair the gateway with the AIRS API Intercept pillar.

Verification

You know which detections the gateway guardrails supply and which belong to AI Runtime, so nothing is assumed covered that is not.

Choose Your Deployment Model

AI Gateway ships in two deployment models. The control plane is always SCM; the choice is where the data plane (the component your AI traffic actually flows through) runs. Pick once here and the rest of the guide follows your choice; the selection persists across the page and between visits.

The two models side by side:

Which path should I pick?
  • SaaS — the default. Choose it when you want zero infrastructure work, automatic scaling, and built-in high availability. It is enabled as soon as licensing completes.
  • Hybrid — choose it when AI traffic must stay inside your own environment (any public cloud, private cloud, or on-premises Kubernetes cluster), or when you need prompt logs written to storage you own. You operate the data plane; SCM still manages it.

Pricing is identical for both models. There is no cost penalty for choosing one over the other, and no additional cost for using multiple gateways or distributing the data plane.

For most deployments this is an either/or decision, and the rest of this guide treats it that way. Technically, though, the two are not mutually exclusive: the SaaS gateway stays enabled per TSG even after you deploy a Hybrid data plane, so a tenant can run both at once. That is useful for piloting Hybrid alongside existing SaaS traffic, and it is something to switch off deliberately if your reason for choosing Hybrid was that no AI traffic may leave your environment. Phase 2, Step 2.1 (Hybrid) covers the toggle; you will find it on the Hybrid tab of that phase, since the toggle lives on the same Gateway Registration page the Hybrid flow uses.

▶ Step 1.2: Size your license by monthly token consumption

All AI Gateway metering is token-based. Every AI transaction through the gateway (prompts, MCP interactions, and A2A traffic) draws down flex credits by token usage, and you license the instance against your maximum expected monthly token consumption.

The token conversion is the industry standard:

1 token = 4 characters of text

estimated monthly tokens = total characters sent and received per month / 4

billion tokens per month = estimated monthly tokens / 1,000,000,000

Example: 12,000,000,000 characters per month
  tokens   = 12,000,000,000 / 4 = 3,000,000,000
  billions = 3,000,000,000 / 1,000,000,000 = 3

To build the estimate, inventory the applications, agents, and MCP servers that will route through the gateway, and for each one approximate: requests per month, average prompt size (including system prompts and context), and average response size. Sum the character counts, divide by 4, and add headroom for growth.

Both directions count

Metering covers the full transaction, not just what you send. Long model responses and large context windows (retrieved documents, tool schemas, conversation history) dominate token counts in most real workloads.

Verification

You have a single number in billions of tokens per month (with growth headroom) to type into the Billion tokens per month field in the next step. If your estimate comes to under one billion tokens, check whether the field accepts a decimal such as 0.5 before rounding up.

▶ Step 2.4 (Hybrid): Confirm what the cluster has to provide
The underlying Kubernetes infrastructure does not matter

The data plane is an ordinary container workload delivered as a Helm chart, so it does not know or care what is underneath it. EKS, AKS, GKE, OpenShift, Rancher, k3s, or a self-built cluster on bare metal are all equally valid, and none of them change a single value in the file SCM generated for you. Any cluster that meets the requirements below can run the data plane.

Check these before you install, because every one of them fails at a different and confusing point later if it is missing:

RequirementWhy the data plane needs it
A conformant Kubernetes cluster you can deploy toThe data plane runs as normal pods. Any distribution that passes upstream conformance is fine; there is no minimum managed-service tier and no cloud-specific integration.
Helm, with permission to install a releaseThe chart is the only supported delivery mechanism. Your account needs enough RBAC to create the release's resources in the target namespace.
Outbound HTTPS on 443 to api.portkey.aiThe pods pull configuration every 30 seconds and push analytics in batches. All management traffic is outbound only, so no inbound path into the cluster is required.
Image pull access to registry.portkey.aiThe gateway image is pulled from here with the credentials in your values.yaml. The chart's optional bundled components pull from docker.io and quay.io as well, so a mirrored or air-gapped cluster needs all three mirrored.
An object store and a Redis the pods can reachRequest and response logs go to an object store, and cached configuration and rate-limit state go to Redis. Step 2.5 configures both; the chart can supply Redis itself but the object store is yours.
CPU and memory you can allocate to the podsGateway scale is dependent on the CPU and memory allocated to the Data Plane, so the resources you request set your throughput ceiling. Size against the AI traffic volume you estimated in Step 1.2.
Traffic is outbound only

The data plane opens connections to the management plane; the management plane never opens connections to your cluster. That means no inbound firewall rule, no public load balancer, and no VPN back to Palo Alto Networks is needed for management. The chart documents the full list of outbound calls in OutboundAPIs.md.

Verification

You can run kubectl get nodes against the target cluster, helm version returns a v3 client, and you have confirmed with whoever runs your network that the cluster can reach api.portkey.ai and registry.portkey.ai on 443.

▶ Step 2.5 (Hybrid): Add your storage backends to values.yaml

The values.yaml SCM generated is not ready to deploy as-is. Its environment.data block arrives empty: the file carries your identity and image pull credentials, but says nothing about where logs and cache state go. Two backends have to be filled in before the install.

Do not skip straight to helm install

Installing the downloaded file unmodified gives the gateway nowhere durable to put request and response logs. The log store is the one you must configure; the cache store has a working in-cluster default you can accept, and the vector store and OpenTelemetry export at the bottom of this step are genuinely optional.

Both backends are set the same way, as keys under environment.data in the file you downloaded:

  • Log store — an object store holding raw LLM request and response bodies. This is the mechanism behind the prompt logs you will read in Phase 4.
  • Cache store — a Redis holding cached configuration, rate limit counters, and budget state, refreshed from the management plane roughly every 30 seconds.
Merge into the existing environment block, do not add a second one

The downloaded file already contains a top-level environment: key holding create, secret, and an empty data. Add your LOG_STORE_* lines underneath that existing data:. YAML does not merge duplicate top-level keys: pasting a second environment: block silently discards the first, taking your gateway's environment secrets with it, and the failure surfaces later as a gateway that cannot authenticate rather than as a parse error. Blocks with their own top-level key, such as minio: and redis:, can be appended anywhere in the file.

This choice is about your storage, not your cluster

Step 2.4 established that the Kubernetes platform underneath makes no difference. Storage is the one place where the environment genuinely does change what you type, because each provider has its own service names, environment variables, and authentication model. Pick the tab matching the storage you already own, which is usually but not always the platform your cluster runs on. Nothing stops an on-premises cluster from writing to S3, or an EKS cluster from writing to in-cluster MinIO.

In every tab, the environment: fragment shows only the keys you add. It is not the whole block. Two ways to reach an external Redis — pick one

The chart accepts external Redis settings in two places: as Helm values under redis.external, and as environment keys (CACHE_STORE, REDIS_URL) under environment.data. Use one or the other, not both.

Whichever you use, also set redis.external.enabled: true. The chart deploys its bundled Redis whenever that value is false, which is the default, so setting only the environment keys leaves a bundled Redis running alongside the external one you actually want. That surplus pod is what causes the Service selector overlap described in Step 3.7.

Log store — in-cluster MinIO

Enable the bundled MinIO and point the log store at it. MinIO is disabled by default, so both blocks below are required. Open the downloaded values.yaml in an editor: the lines marked KEEP AS-IS are already in your file with real values, so do not retype or paste over them.

  name: "minio"

    create: true
    accessKey: "<Enter access key here>"   # you choose this
    secretKey: "<Enter secret here>"       # you choose this
  persistence:
    enabled: true
    size: 10Gi

# ADD these keys under the environment.data already in your file

  data:
    PORTKEY_CLIENT_AUTH: ...     # KEEP AS-IS, already in your file with a real value
    ORGANISATIONS_TO_SYNC: ...   # KEEP AS-IS, already in your file with a real value
    PORT: "8787"                 # KEEP AS-IS if present, otherwise add
    # add the log store keys below, alongside the ones above
    LOG_STORE: s3_custom
    LOG_STORE_REGION: "us-east-1"                    # placeholder value; see note below
    LOG_STORE_ACCESS_KEY: "<Enter access key here>"   # same as above
    LOG_STORE_SECRET_KEY: "<Enter secret here>"       # same as above
    LOG_STORE_GENERATIONS_BUCKET: "<Enter bucket name here>"   # chart creates this bucket
    LOG_STORE_BASEPATH: "<Enter bucket name here>"             # same bucket name
Region is a placeholder here

There are no regions in a single in-cluster MinIO, but LOG_STORE_REGION should still be set to a plausible value rather than left blank. Region is part of the S3 signature scope, so an empty string can produce signing failures depending on the client. Use us-east-1, the conventional default for S3-compatible storage, and keep the same value everywhere you point a client at this MinIO. A mismatch between what the client signs with and what the server expects is a common cause of SignatureDoesNotMatch errors.

The bucket creates itself, but only if you name it

You do not need to create the bucket by hand. On startup the MinIO pod runs an init step that waits for MinIO to come up, then issues mc mb --ignore-existing for the bucket named in LOG_STORE_GENERATIONS_BUCKET.

Set that key even though the chart's own s3_custom example omits it. That example lists only LOG_STORE_BASEPATH, but the MinIO init step reads LOG_STORE_GENERATIONS_BUCKET, and with it unset the command renders as mc mb --ignore-existing minio/ and no bucket is created. Giving both keys the same bucket name satisfies the init step and the gateway's own path handling at once. The key is documented in the chart's Configuration reference as the bucket for generation logs.

Find your cluster's storage class with kubectl get storageclass and use the one marked (default). On K3s and RKE2 that is typically local-path, the Rancher local-path provisioner. The MinIO console can be reached without exposing it, using kubectl port-forward svc/minio 9001:9001, then signing in at http://localhost:9001 with the same access key and secret key you set above.

Node-local storage pins your pods

Check the provisioner before treating this as production storage. A local-path or hostPath provisioner writes to a directory on whichever node the pod lands on, so the volume cannot move: if that node goes away, the data goes with it, and the pod cannot reschedule elsewhere. That is fine for a lab or a first deployment, and it directly conflicts with the multi-replica, spread-across-failure-domains posture described in Step 2.6. For production on-premises, back MinIO with networked storage (Ceph, Longhorn, or an NFS or iSCSI class) so volumes follow their pods.

A related detail worth knowing: a class with VOLUMEBINDINGMODE: WaitForFirstConsumer leaves the PersistentVolumeClaim in Pending until a pod actually schedules against it. Seeing Pending immediately after install is expected with that mode, not a failure.

Cache store — bundled Redis

The chart deploys its own Redis when redis.external.enabled is false, and that is already the default. You do not have to add anything for the cache store: omit the redis block entirely and you get a working in-cluster Redis.

The one default worth reconsidering is persistence, which is off, making the bundled Redis ephemeral. Cache contents rebuild from the management plane on restart, so this is survivable, but a pod restart drops rate limit and budget counters along with the cache. To keep it across restarts:

redis:
  statefulSet:
    persistence:
      enabled: true
      size: 2Gi
      storageClassName: "<Enter storage class here>"
Why some external keys still apply to the bundled Redis

The naming is misleading. When redis.external.enabled is false, the chart composes the connection URL itself from the release name and ignores connectionUrl, but it still reads tlsEnabled, mode, and store from under redis.external and writes them into the Redis Secret. Those three are shared settings that happen to live under an external key, not external-only ones. Their defaults ("false", "standalone", "redis") are correct for the bundled instance, which is why nothing above needs to set them. Only connectionUrl and existingSecretName are genuinely external-only.

To use a Redis you operate yourself instead of the bundled one, set redis.external.enabled: true and give it a connectionUrl such as redis://my-redis:6379, turning on tlsEnabled and authentication if your instance requires them. Setting enabled: true is what stops the chart from deploying its own bundled Redis, so do not omit it.

▶ Step 2.6 (Hybrid): Install the chart with Helm

With storage configured, the install is four commands. Run them from the directory holding your edited values.yaml, with your kubectl context pointed at the target cluster.

helm repo add airs-gw https://portkey-ai.github.io/airs-gw-helm
helm repo update

helm upgrade --install airs-gw airs-gw/airs-gw \
  -f ./values.yaml \
  -n airs-gw \
  --create-namespace

The three airs-gw values in that command are different things: the Helm release name (the first argument), the repo/chart (airs-gw/airs-gw), and the namespace (-n airs-gw). If your organization requires a different namespace or release name, change them here and use the same values in every kubectl command that follows, including the in-cluster DNS name in Step 3.7, which is built as <release-name>.<namespace>.svc.cluster.local.

Then confirm the pods came up:

kubectl get pods -n airs-gw

Optionally, reach the gateway locally without exposing it, to prove it is listening before you wire any client to it:

kubectl port-forward -n airs-gw pod/<gateway-pod-name> 8787:8787

Take <gateway-pod-name> from the kubectl get pods output above, choosing a pod whose name starts with your release name and is not a Redis pod. Target the pod directly rather than svc/airs-gw: Step 3.7 explains why forwarding the Service can land on the bundled Redis pod instead and fail with a confusing named-port error.

upgrade --install is deliberate

The same command installs the release the first time and upgrades it afterwards, so re-running it after editing values.yaml is the normal way to change configuration. To remove the release entirely, use helm uninstall airs-gw --namespace airs-gw.

Plan for more than one replica

The chart ships with replicaCount: 1, which is a starting point rather than a production posture. Palo Alto Networks' resiliency guidance describes three or more gateway pods, and the chart exposes autoscaling (defaulting to a range of 2 to 20 replicas when enabled), pod disruption budgets, and topologySpreadConstraints. Spreading pods across failure domains is what buys availability: Availability Zones on a cloud-managed cluster, or your own labeled racks, rooms, or sites on-premises. Confirm the spread with kubectl get pods -n airs-gw -o wide.

If pods do not reach Running

Check the logs first: kubectl logs -n airs-gw deployment/airs-gw. Image pull failures point at registry egress or the credentials in values.yaml; crash loops shortly after start usually point at the log store or Redis settings from Step 2.5.

▶ Step 3.5: Set up workspace provisioning, budgets, and rate limits

Workspace provisioning determines which teams and projects can access this integration. This is crucial for maintaining security boundaries and ensuring teams only access approved AI resources. Sharing credentials with a workspace means:

  • That workspace sees the integration as an AI Provider in their Model Catalog.
  • They can use it immediately; there is no need to enter credentials again.
  • You can set different budgets and rate limits for each workspace.
  • You can revoke access at any time.
  1. On the Workspace Access, Budget & Rate Limits stage, check the box next to each workspace that gets access (the toolbar offers Select All, Deselect All, and a search filter).

Understand the consequence before enabling it: limit values cannot be edited after they are applied (see the warning below), so the only way to change a limit for a workspace is to remove that workspace's access and provision it again with new values, which interrupts that workspace's traffic while access is removed. You can turn the automatic provisioning off at any time, and doing so does not change workspaces already provisioned. On a first deployment, leave it off until your limit values are settled.
  3. Optionally, for each workspace, click Set Value (or select several and use Set Value for All Selected) to open the Set Budget and Rate Limits panel, covered below.

The workspace stage with one workspace selected and its Set Value action:

Set Value opens the budget and rate limit panel for that workspace:

Add Budget: budget limits act as financial guardrails that prevent unexpected AI costs, and they cascade down to all AI Providers created from this integration.

  1. In the panel, switch on Add Budget.
  2. Choose the budget type with the Cost or Tokens selector (the same pair appears on the API key form in Step 3.7):
    • Cost — a budget in dollars entered in the Budget Limit ($) field. Once reached, the gateway blocks further usage for that workspace through this integration until the budget resets.
    • Tokens — a maximum number of tokens that can be consumed, controlling usage independent of cost fluctuations.
  3. Optionally fill the Alter Threshold ($) field with a dollar amount below the budget limit.
  4. Set the reset cadence dropdown:
    • No Periodic Reset — the budget limit applies until exhausted, with no automatic renewal.
    • Reset Weekly — resets at the beginning of each week (Sunday at 12 AM UTC).
    • Reset Monthly — resets on the 1st calendar day of the month at 12 AM UTC, irrespective of when the budget limit was set.
What Alter Threshold means

The field carries no description in the UI, but it maps to the underlying gateway platform's alert threshold; the on-screen label is a typo, and the API key form in Step 3.7 labels the same control Alert Threshold ($). When spend crosses this amount, the gateway raises an alert without blocking traffic; requests are blocked only when the Budget Limit itself is reached. Example: a Budget Limit of 500 with a threshold of 400 warns at $400 of spend and cuts off at $500. A common practice is to set it at 80% of the budget.

Add Rate Limit: rate limits control the velocity of API usage, protecting against runaway processes and ensuring fair resource distribution across teams.

  1. In the panel, switch on Add Rate Limit.
  2. Choose the limit type with the Request or Token selector:
    • Request-based — limit the number of API calls (for example, 1000 requests per minute).
    • Token-based — limit the token consumption rate (for example, 1M tokens per hour).
  3. Enter the limit in Set Rate Limit and choose the time window in the unit dropdown next to it (shown as Requests/Minute):
    • Per Minute — limits reset every minute, ideal for fine-grained control.
    • Per Hour — limits reset hourly, providing balanced usage control.
    • Per Day — limits reset daily, suitable for broader usage patterns.

Whether you set a budget, a rate limit, or both, click Apply to save the panel. Clicking Cancel or closing the panel discards everything you entered.

Key considerations for both limit types:

  • The minimum cost limit is $1; the minimum token limit is 100 tokens.
  • Budget limits apply only to requests made after the limit is set (never retroactively) and hold until exhausted or reset; they cover all AI Providers created from this integration.
  • Rate limits apply immediately and cover all organization members who use the provider.
  • Setting a rate limit to 0 disables the provider.
  • After a rate limit is reached, requests are rejected with a specific error code until the time window resets; error messages clearly indicate that the rate limit has been exceeded.

Together the limits cover cost control, consistent performance, fair distribution across teams, abuse mitigation, and staying within the rate limits your providers impose.

Budget and rate limits cannot be edited once set

Once set, neither budget limits nor rate limits can be edited by any organization member. Decide the budget amount, type, and reset cadence deliberately, model your peak legitimate traffic before committing a rate value, and remember that 0 turns the provider off entirely.

Hybrid only — building your own base URL

Skip this callout entirely if you deployed the SaaS gateway. It applies only to Hybrid, and it changes what item 2 of the list below means for you.

The Gateway URLs value SCM shows is the hosted SaaS endpoint. If you deployed a Hybrid data plane in Phase 2, that endpoint is not where your traffic should go: your gateway is the service running in your own cluster, and requests should be sent to it directly. Everything else in this step is unchanged, since the API key and the model reference come from the same SCM tenant either way.

The address depends on how you exposed the release. Find the service with:

kubectl get svc -n airs-gw

The gateway service publishes two ports: the LLM traffic port (the chart's service.port, defaulting to 8787) and an MCP port on 8788 used in Step 3.9. Your base URL is built from the first one, reached whichever way suits the cluster:

  • ClusterIP — the in-cluster DNS name, for callers running in the same cluster: http://airs-gw.airs-gw.svc.cluster.local on the service port.
  • NodePort — any node's address on the high-numbered port shown in the PORT(S) column.
  • LoadBalancer — the address in EXTERNAL-IP, once one is assigned.
  • Port-forward — no cluster changes at all, for a quick test from your workstation.
kubectl port-forward -n airs-gw pod/<gateway-pod-name> 8787:8787

With the forward running, http://localhost:8787 is your base URL. Sending traffic straight to your own data plane is the point of Hybrid: prompts and responses never transit a Palo Alto Networks hosted endpoint, while the gateway still reports usage and logs back to SCM exactly as Step 2.7 verified.

Port-forward the pod, not the service

Running kubectl port-forward against svc/airs-gw can fail with Pod 'airs-gw-redis-0' does not have a named port 'gateway'. The bundled Redis pod carries the same base selector labels as the gateway, and the gateway Service does not narrow its selector by component, so the Service matches the Redis pod as well. Port-forwarding resolves the Service to whichever pod it picks first, and that can be Redis.

Target the gateway pod directly, using the name from kubectl get pods -n airs-gw. Note the container listens on 8787 even when the Service publishes port 80. The same overlap means the Service can route live traffic to Redis, so confirm which pods are actually behind it:

kubectl get endpoints -n airs-gw airs-gw

If a Redis pod's address appears in that list, requests to the Service will intermittently fail. Using an external Redis, as recommended for production in Step 2.5, avoids the overlap entirely because no Redis pod is deployed.

LoadBalancer stays pending without a controller

On-premises clusters have nothing to satisfy a LoadBalancer service unless you have installed a bare-metal load balancer such as MetalLB, so EXTERNAL-IP sits at <pending> indefinitely. The service still works: Kubernetes allocates a NodePort alongside it, visible in the PORT(S) column as 80:31707/TCP, and that high port is reachable on any node. Use the NodePort or a port-forward, or switch the service to ClusterIP and put your own ingress in front of it.

▶ Step 3.8: Route Claude Code through the gateway

Claude Code reads three environment variables for gateway routing: ANTHROPIC_BASE_URL for the gateway endpoint, ANTHROPIC_AUTH_TOKEN for the credential (sent as an Authorization: Bearer header), and ANTHROPIC_CUSTOM_HEADERS to pin the integration (explained below). Test with shell exports first, then persist the values in a settings file.

Trim the /v1 suffix for Anthropic-native clients

The Gateway URLs field displays the address with a /v1 suffix (https://aigw.portkey.ai/v1). Anthropic-native clients such as Claude Code append their own /v1/messages path, so set ANTHROPIC_BASE_URL to the address without the suffix: https://aigw.portkey.ai. The underlying gateway platform documents the same rule for its own endpoint. The curl test in step 2 confirms the form your tenant accepts.

  1. Open a terminal. Every placeholder in this step maps to a value recorded in Step 3.7:
    • <gateway-base-url> — the Gateway URLs value with the /v1 suffix removed: https://aigw.portkey.ai
    • <gateway-api-key> — the User key copied from the Save your Gateway API Key dialog
    • <model-reference> — the slug and model name combined, for example @default-anthropic/claude-fable-5
    • <integration-slug> — the slug alone, for example default-anthropic
    Copy the block below, then replace all three angle-bracket placeholders with your own values before pressing Enter. The shell accepts the placeholder text without complaining, and the curl test in the next item then fails in a way that is hard to trace back to here. Keep the surrounding double quotes. 
    export ANTHROPIC_BASE_URL="<gateway-base-url>"
export ANTHROPIC_AUTH_TOKEN="<gateway-api-key>"
export ANTHROPIC_CUSTOM_HEADERS="x-portkey-provider: @<integration-slug>"

    Confirm the substitution took before moving on:

    echo "$ANTHROPIC_BASE_URL"

    That must print your gateway address. If it prints a string containing angle brackets, the placeholders were never replaced; re-run the exports with real values.

    Why the third variable

    Claude Code sends bare model names (claude-fable-5), not @slug/model references, so the gateway cannot tell which integration should serve the request and rejects prompts with 400 Either x-portkey-config or x-portkey-provider header is required. ANTHROPIC_CUSTOM_HEADERS attaches the x-portkey-provider header to every request, pinning this session to your integration. Direct API callers that already use the full @slug/model reference (like the curl test below) do not need it.

    Exports live only in this terminal

    These variables exist only in the terminal window where you ran the exports. Run everything else in this step, including claude itself, from this same window. A Claude Code session started anywhere else still uses your normal login and never touches the gateway; its /status output will show no base URL line.

  2. Confirm the gateway answers before opening Claude Code: 
    curl -X POST "$ANTHROPIC_BASE_URL/v1/messages" \
  -H "Authorization: Bearer $ANTHROPIC_AUTH_TOKEN" \
  -H "anthropic-version: 2023-06-01" \
  -H "content-type: application/json" \
  -d '{"model": "<model-reference>", "max_tokens": 32,
       "messages": [{"role": "user", "content": "Say OK"}]}'
    A JSON response starting with {"id":"msg_ and containing a "content":[...] field proves the URL and credential work. An error naming an unknown model still proves both, because the gateway authenticated the request before rejecting the model name.
  3. In the same terminal, run claude, then run /status inside the session. The output includes an Anthropic base URL line (shown only when a gateway address is set) and an Auth token line confirming which credential is active.
  4. Send any prompt, then open AI Security → AI Gateway → Observability in SCM (the page you verified in Phase 2: Step 2.1 on the SaaS path, Step 2.7 on the Hybrid path) and check the Logs tab: the request appears with its model, token counts, and cost, and the Analytics panels tick up from zero.
  5. Persist the configuration so every future session routes through the gateway. If ~/.claude/settings.json does not exist, create it with exactly the block below. If it already exists, add the "env" key inside the existing top-level object, alongside your other settings, rather than pasting the whole block; the file must remain a single JSON object: 
    {
  "env": {
    "ANTHROPIC_BASE_URL": "<gateway-base-url>",
    "ANTHROPIC_AUTH_TOKEN": "<gateway-api-key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-portkey-provider: @<integration-slug>"
  }
}

Not using Claude Code? Change the endpoint in your code instead

Claude Code is only the worked example. For a custom AI application, apply the same three values where the code constructs its LLM client: point the base URL at the gateway and swap the provider key for the gateway key. With the Anthropic Python SDK that is two constructor arguments:

from anthropic import Anthropic

client = Anthropic(
    base_url="<gateway-base-url>",
    auth_token="<gateway-api-key>",
)

message = client.messages.create(
    model="<model-reference>",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Hello through the gateway"}],
)

The SDK also reads ANTHROPIC_BASE_URL from the environment, so the exports from step 1 work without any code change. Any other SDK that accepts a base URL override (the OpenAI SDK's base_url argument, for example) follows the same pattern: no application logic changes, only the endpoint and credential.

Keep the key out of shared settings files

Never put the gateway key in a project's .claude/settings.json; that file is committed and shared with everyone who clones the repository. Use the user-level ~/.claude/settings.json shown above, or the gitignored .claude/settings.local.json for a single project.

How the gateway credential interacts with your claude.ai login

While ANTHROPIC_AUTH_TOKEN is set, it takes precedence over a saved claude.ai login or Console key; the login stays saved and unused. Unset the variable and Claude Code returns to it. When a shell export and a settings-file env block set the same variable, the settings-file value wins; /status shows which source is active. ▶ Step 4.5: Final end-to-end verification

Walk the whole chain once before handing the gateway to teams:

  1. License — in the Customer Support Portal under Products → Software NGFW Credits, the AI-GW profile row's consumed meter reflects test traffic. Consumption may not appear immediately after a request; the update latency has not been measured, so allow time before treating a flat meter as a failure.
  2. Gateway — the data plane is active (SaaS) or registered and healthy in SCM (Hybrid).
  3. Integration — a provisioned workspace sees the provider in its Model Catalog and can invoke an allowed model without holding provider credentials.
  4. Controls — a request to a model outside the allowlist fails, and traffic past a rate limit is rejected with a clear rate-limit error until the window resets.
  5. Logs — the interaction appears as an event log and a prompt log, and Threat Logs reach SLS.
Verification

Deployment is complete. AI traffic routes through the Prisma AIRS AI Gateway with credentials centralized, models allowlisted, spend guarded by budgets and rate limits, and every interaction logged to the dashboard, SLS, and your SIEM.
