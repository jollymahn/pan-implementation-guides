Authentication and Identity

Chapter 2 of 13. Attaching an identity provider to the organization, gating which email domains may enter it, automating provisioning, and issuing the keys that machines use

Configuration Hub Previous: Registration Next: Secret References Agent Identity with Entra ID

Three ways in

Three distinct populations authenticate to the gateway, and each uses a different mechanism. Configuring one does nothing for the other two.

WhoMechanismConfigured in
People opening the consoleSingle sign-on over OIDC or SAML, gated by allowed domainsSteps 1 and 2
Applications calling the inference APIAPI keys, either organization-scoped or workspace-scopedStep 5
Agents and services presenting a tokenJWT validated against JWKS configured on the organizationStep 4

Automated provisioning sits alongside these. It does not authenticate anyone; it creates and removes the accounts that single sign-on then admits.

Allowed domains come first, and the reason is not cosmetic

Provisioning only creates users whose email domain is verified on the organization. Running a provisioning sync before step 1 produces no users and no error that explains why, which is a long way to travel for a silent result. Set the domains first.

Prerequisites

  • Chapter 1 complete, with an organization you own
  • The Organization Owner role, because authentication settings are owner-level
  • Administrative access to your identity provider, for creating an application registration
  • The list of email domains your organization uses, including any acquired or legacy domains
  • For the Cloud Identity Engine path, a Strata Cloud Manager tenant with Cloud Identity Engine activated and at least one directory synced
Keep a non-SSO route open while you work

Configure single sign-on in a session where you still hold a working console login through another browser or profile. A misconfigured issuer URL or redirect URI locks everyone out of the organization, and recovering from that means contacting support rather than fixing a field.

Step 1 — Set the allowed domains

Allowed domains restrict which email domains may authenticate into the organization. They also decide which users provisioning is permitted to create.

▶ 1.1 — Add every domain your users sign in with
  1. Go to Admin Settings → Authentication Settings.
  2. Find the Allowed Domains section.
  3. Add each domain, for example example.com.
  4. Repeat for every domain in use, including domains from acquisitions and any domain your contractors sign in with.
A missing domain fails quietly

Users on an unlisted or unverified domain are skipped during provisioning rather than reported as errors. If a sync later reports fewer users than the directory group holds, an absent domain is the first thing to check.

Verification

Every domain that appears in your users' email addresses is listed. Count the distinct domains in the directory group you plan to sync and compare the two lists.

Step 2 — Configure single sign-on

The gateway accepts either OIDC or SAML. Pick one. The choice usually follows whatever your identity provider team already standardized on, and the selection below persists as you move through the page.

Which path should I pick?
  • OIDC — the default choice for Okta and Entra ID. It needs an issuer URL, a client ID, and a client secret, and it supports refresh tokens through the offline_access scope.
  • SAML — use when your identity provider team requires SAML or when an existing SAML application is being reused. It needs either a metadata URL or metadata XML.

The gateway needs three values from your identity provider: the issuer URL, the client ID, and the client secret. The OIDC well-known configuration document must be reachable at the issuer URL.

▶ 2.1 — Create the application in your identity provider

The gateway requires these scopes on the application:

  • openid
  • profile
  • email
  • offline_access

The redirect URI is the Strata Cloud Manager console address, https://stratacloudmanager.paloaltonetworks.com/.

▶ Okta
  1. In the Okta dashboard, open Applications and create a new app integration.
  2. Select OIDC - OpenID Connect as the sign-in method.
  3. Select Web Application as the application type.
  4. Set the sign-in redirect URI to https://stratacloudmanager.paloaltonetworks.com/.
  5. Check both Authorization code and Refresh Token as grant types, then create the application.
  6. Open the application's General section and edit General Settings. Set Login initiated by to Either Okta or app, and set the initiate login URI to the same console address.
  7. Open the Sign On section, edit it, select Okta URL as the issuer, and save.

Collect three values: the issuer from the Sign On section, the client ID, and the client secret from General → Client Credentials → Client Secrets.

▶ Entra ID
  1. Sign in to the Azure portal and open Microsoft Entra ID.
  2. Under Manage, select App registrations → New registration.
  3. Enter a name and choose the supported account types your organization requires.
  4. Under Redirect URI, select Web as the platform and enter https://stratacloudmanager.paloaltonetworks.com/.
  5. Register the application.
  6. Open Certificates & secrets → Client secrets → New client secret. Set an expiry that matches your rotation policy and add it.

Collect three values from Overview: the OpenID Connect metadata document URL from Endpoints, the Application (client) ID from Essentials, and the client secret you just created.

Record the secret expiry date now

Entra client secrets expire. When the secret expires, every console sign-in through this application fails at once. Put the expiry date in the same calendar you use for certificate renewals.

▶ 2.2 — Enter the values in the console
  1. Go to Admin Settings → Authentication Settings → OIDC.
  2. Enter the Issuer URL, the Client ID, and the Client Secret Key.
  3. Save.
Verification

Open a private browser window and sign in to Strata Cloud Manager. The identity provider prompts for credentials and returns you to the console signed in. Keep your original session open until this works.

▶ 2.3 — Change the client authentication method, if your provider requires it

By default the gateway authenticates to the token endpoint with client_secret_basic. Change it only when your identity provider rejects that method.

  • Set token_endpoint_auth_method in the OIDC settings to the method your provider expects, for example client_secret_post or private_key_jwt.
  • For private_key_jwt, also supply a jwks object holding your client's private key set, and register the matching public JWKS with your identity provider.

Supplying a JWKS without naming a method selects private_key_jwt automatically.

Self-hosted management planes use environment variables

A self-hosted deployment running in single-organization SSO mode sets the same behavior through OIDC_TOKEN_ENDPOINT_AUTH_METHOD and OIDC_CLIENT_JWKS on the backend service. Air-gapped deployments add custom scopes through OIDC_CUSTOM_SCOPES as a comma-separated list.

Verification

A sign-in from a private browser window completes. A failure here appears as a token exchange error rather than a credential prompt, which distinguishes it from a wrong password.

SAML needs either a provider metadata URL or the metadata XML. The gateway supplies two values your identity provider needs in return, and both are shown in the console before you start.

▶ 2.1 — Collect the two values the gateway publishes
  1. Go to Admin Settings → Authentication Settings → SAML.
  2. Copy the SAML Redirect/Consumer Service URL.
  3. Copy the SAML Entity ID.

Your identity provider application needs both before it can be created, so collect them first rather than switching back and forth.

Verification

You have both values recorded. Nothing has changed in the console yet.

▶ 2.2 — Create the application in your identity provider
▶ Okta
  1. In the Okta dashboard, open Applications and create a new app integration.
  2. Select SAML 2.0 as the sign-in method.
  3. In Configure SAML, set Single sign-on URL to the SAML Redirect/Consumer Service URL you copied.
  4. Set Audience URI (SP Entity ID) to the SAML Entity ID you copied.
  5. Create the application.
  6. Open Sign On, then the SAML 2.0 tab, then Metadata details, and copy the Metadata URL.
▶ Entra ID
  1. Sign in to the Azure portal and open Microsoft Entra ID.
  2. Under Manage, select App registrations → New registration.
  3. Enter a name and choose the supported account types your organization requires.
  4. Under Redirect URI, select Web as the platform and enter the SAML Redirect/Consumer Service URL.
  5. Register the application.
  6. Select Endpoints at the top of the page and copy the Federation metadata document URL.
  7. In the left panel, select Expose an API. Next to Application ID URI, select Add, enter the SAML Entity ID, and save.
▶ 2.3 — Enter the metadata in the console
  1. Go to Admin Settings → Authentication Settings → SAML.
  2. Paste the metadata URL into Provider Metadata URL, or paste the XML into Provider Metadata XML.
  3. Save.

A metadata URL is preferable to pasted XML, because the gateway re-reads it when your identity provider rotates its signing certificate. Pasted XML has to be replaced by hand at every rotation.

Verification

Open a private browser window and sign in to Strata Cloud Manager. The identity provider prompts for credentials and returns you to the console signed in. Keep your original session open until this works.

Step 3 — Automate user provisioning

Provisioning creates and removes accounts from your directory instead of by hand. Which path you take is decided by your deployment rather than by preference.

Which path should I pick?
  • Cloud Identity Engine directory sync — the path for a Strata Cloud Manager tenant. It pulls users and groups from Entra ID, Okta, or on-premises Active Directory through the Cloud Identity Engine, and it replaces standalone SCIM.
  • SCIM provisioning — the path for a deployment that is not on a Strata Cloud Manager tenant. Directory sync is not available there.

Directory sync has two halves. The directory connection, the identity attribute, and the auth profile are configured here. Mapping directory groups to workspaces happens in chapter 8, because a mapping needs a workspace that already exists.

▶ 3.1 — Confirm a directory is connected in the Cloud Identity Engine
  1. In Strata Cloud Manager, open the Cloud Identity Engine console.
  2. Go to Directory Sync → Directories.
  3. Confirm at least one directory is listed with a successful sync status.

To add one, click Add New Directory and choose the type:

Directory typeProviderNotes
Cloud DirectoryEntra ID, Okta, GoogleThe most common setup.
On-Premises DirectoryActive DirectoryRequires a Cloud Identity agent installed on-premises.
CIE DirectoryCloud Identity EngineA local directory managed entirely within the Cloud Identity Engine.
Verification

The directory listing shows your directory with a sync status of success, a user count, and a group count. A directory with zero groups gives chapter 8 nothing to map.

▶ 3.2 — Select the connected directory
  1. In the AI Gateway, go to Admin Settings → Authentication → Directory Sync.
  2. Open the Connected Directory dropdown. It lists every directory available from the Cloud Identity Engine with its provider type and entity counts.
  3. Select your directory.

The Configure in CIE button on this page returns you to the Cloud Identity Engine console if the directory you expect is missing.

Verification

The dropdown shows your directory with non-zero user and group counts.

▶ 3.3 — Choose the user identity attribute

This setting decides which directory attribute becomes the user's email address in the gateway.

AttributeUse when
UPN (User Principal Name)The user principal name matches the user's email address. This is the default choice.
Mail (Primary Email)The user principal name differs from the email address, for example a principal name on an onmicrosoft.com domain against a real mail domain.
Pick the attribute that is populated for everyone

A user missing the selected attribute is skipped during sync rather than reported. Check the attribute is populated across the whole directory before choosing it, and remember that the resulting domain must appear in the allowed domains from step 1.

Changing it later is safe

Changing the attribute after setup triggers an automatic full re-sync that updates every user's email address. No users are removed by that re-sync.

Verification

The selected attribute matches the domains you listed in step 1.

▶ 3.4 — Save and select an auth profile
  1. Click Save to persist the connected directory and the identity attribute. The background sync scheduler starts at this point.
  2. Open the Auth Profile dropdown and select a profile. These profiles come from the authentication profiles configured in the Cloud Identity Engine.

The auth profile validates user identity during MCP inbound authentication, which chapter 10 builds on. Selecting it now means chapter 10 has one fewer dependency to resolve.

Verification

The Directory Sync State section shows a status of Success or In Progress, with a Last Updated timestamp. A status of Failed here blocks everything downstream, so resolve it before continuing.

▶ 3.5 — Know the sync cadence before you troubleshoot

Three timings explain most of what looks like a broken sync:

  • Delta sync — group membership changes are pulled every 15 minutes, so a directory change can take that long to appear.
  • Automatic full sync — when the Cloud Identity Engine rebuilds its cache, roughly weekly, the gateway performs a full sync on its own.
  • Manual full sync — the Full Sync button forces a complete pull. If a sync is already running, the forced one starts when the current one finishes.
Verification

Click Full Sync and watch Objects Synced and Last Updated change. Until chapter 8 maps a group to a workspace, the object count reflects mapped objects only, so a low number here is expected rather than a fault.

SCIM automates user creation, updates, deprovisioning, and workspace group membership from your identity provider. Entra ID and Okta are the supported providers.

▶ 3.1 — Collect the SCIM base URL and generate a token
  1. Go to Admin Settings → Authentication Settings → SCIM Provisioning.
  2. Copy the SCIM URL.
  3. Generate an API token on the same page and copy it.

Your identity provider sends the token as a bearer credential on every SCIM request:

Authorization: Bearer <your-api-token>
The token is shown once

Store it in your secrets manager as you generate it. Recovering it later means generating a new one and updating the identity provider, which interrupts provisioning until both sides match again.

Verification

You hold both the SCIM URL and the bearer token, and the token is stored outside the console.

▶ 3.2 — Configure the identity provider

In your identity provider's provisioning configuration, supply two fields:

FieldValue
SCIM Base URLThe SCIM URL copied in step 3.1
Bearer TokenThe API token generated in step 3.1

The gateway supports the full set of operations, so provisioning, updates, and deprovisioning all flow through for both users and groups:

  • User provisioning, updates, and deprovisioning
  • Group provisioning, updates, and deprovisioning, where a group maps to a workspace
Verification

Run the identity provider's test or validation action for the connection. It authenticates against the SCIM URL and returns success before any user is provisioned.

▶ 3.3 — Provision a first user and confirm
  1. Assign one test user to the application in your identity provider.
  2. Run a provisioning cycle, or wait for the scheduled one.
  3. Check the organization user list in the gateway for the new account.
No user and no error means the domain is not allowed

SCIM only provisions users whose email domain is verified in Allowed Domains. A user on an unlisted domain is skipped silently. Return to step 1 and add the domain, then run the cycle again.

Verification

The test user appears in the organization user list. Removing the user's application assignment and running another cycle removes the account, which confirms deprovisioning works as well as provisioning.

Step 4 — Configure JWT validation

Clients can present a JWT instead of an API key, in either the x-portkey-api-key header or an Authorization: Bearer header. The gateway validates it against JWKS held on the organization. Configure this when agents or services authenticate with tokens from your identity provider rather than with static keys.

Skip this step if every client uses an API key

JWT validation is additive. Leaving it unconfigured changes nothing for API key clients, and step 5 covers the keys those clients need.

▶ 4.1 — Check your tokens meet the hard requirements

These constraints are rejections rather than preferences. Confirm them against a real token before configuring anything, because a token that fails one of them is refused with no partial behavior.

ElementRequirement
alg headerMust be RS256. Symmetric algorithms such as HS256 are refused.
typ headerMust be JWT.
kid headerRequired, and must match a kid present in your JWKS.
Key type and sizeRSA, 2048 bits or larger.
JWKS contentsPublic key parameters only. Private key material must never appear.
Verification

Decode one real token from your identity provider and confirm the three header fields. A missing kid is the most common cause of a token that looks correct and is still refused.

▶ 4.2 — Add the JWKS to the organization
  1. Go to Admin Settings → Organisation → Authentication.
  2. Supply one of the two forms:
    • JWKS URL — public keys are fetched dynamically. Several URLs may be given as a comma-separated list, which the gateway fetches and merges. This is what you use while rotating between identity providers.
    • JWKS JSON — a static document holding the public keys.
  3. Save.

Prefer the URL form. A static document has to be replaced by hand every time your identity provider rotates its signing key, and a missed rotation refuses every token at once.

Verification

Step 4.4 performs the end-to-end check. Saving the JWKS on its own proves only that the field accepted the value.

▶ 4.3 — Confirm the claims your tokens carry

Required claims:

ClaimMeaning
portkey_oid or organisation_idThe organization identifier recorded in chapter 1.
portkey_workspace or workspace_slugThe workspace the token acts in. Chapter 8 creates the workspaces these refer to.
scope or scopesThe permissions the token grants.
expExpiry as a UNIX timestamp in seconds. Mandatory. A token with no exp, or an expired one, is refused, with a small tolerance for clock skew.

Optional claims add per-token behavior: defaults applies default settings to every request made with the token, and usage_limits and rate_limits enforce caps on it. The iat and nbf claims are recommended and not required.

The gateway attributes usage to a user by taking the first claim present, in this order: email_id, then sub, then uid. Attribution in logs and metrics follows that precedence, so a token carrying only sub reports a subject identifier where you may expect an address.

Hosted against hybrid

The hosted gateway validates JWTs on the management plane and requires both portkey_oid and portkey_workspace. Hybrid and air-gapped deployments can enable gateway-local validation so tokens are checked at the gateway, in which case the organization and workspace can be resolved from deployment configuration and a standard identity provider token works unmodified. The agent identity guide walks the hybrid claim path in detail.

Verification

A decoded token shows all four required claims, and the organization identifier matches the one recorded in chapter 1.

▶ 4.4 — Make a call with a token

Send one request to the gateway with the JWT in place of an API key. Until chapter 9 configures an integration there is no model to reach, so at this stage a rejected credential and a missing model are different outcomes and you are only checking the credential.

  • An authentication error means the token, the JWKS, or a claim is wrong.
  • An error about the model or the integration means authentication passed.
Verification

The response is anything other than an authentication failure. Re-run this check after chapter 9 to confirm the full path.

Step 5 — Understand and issue API keys

API keys authenticate requests to the inference API. They are not accepted on the Admin API, which uses a Strata Cloud Manager access token issued to a service account instead.

▶ 5.1 — Choose the right kind of key
Key typeScopeIssued to
Admin API keyThe whole organization, reaching across every workspaceAdministrative automation only. Owners and organization admins create them.
Workspace API keyOne workspaceApplications and services. This is what application teams receive.

An admin key can target a specific workspace by naming a workspace identifier when it updates an entity, which is why its reach is wider than it first appears.

Do not hand an admin key to an application

An admin key carries organization-wide scope including user management, guardrail changes, and key rotation. An application that only needs to call a model needs a workspace key. Chapter 8 issues those once the workspaces exist.

Verification

You can state which key type each planned consumer will hold. Issuing the workspace keys themselves waits for chapter 8.

▶ 5.2 — Create the first admin key
  1. Go to Admin Settings and open the API keys section for the organization.
  2. Create a key, name it for the automation that will hold it rather than for the person creating it, and record it in your secrets manager.

Name keys after their consumer. A key called ci-pipeline-provisioning can be rotated with confidence; a key called admin-key-2 cannot, because nobody knows what breaks when it changes.

Verification

The key appears in the list with the name you gave it, and the value is stored outside the console.

▶ 5.3 — Plan rotation before keys are in use

Keys support rotation, which regenerates the value in place. Agreeing the cadence now is easier than agreeing it during an incident.

  • Decide a rotation interval per key type and write it down with the key inventory.
  • Record which system holds each key, so rotation has a known blast radius.
  • Rotate the admin key you just created once, before anything depends on it, to confirm the process works while nothing breaks.
Verification

A rotation of the unused admin key completes and produces a new value. Your inventory records the interval and the holder for every key issued so far.

Step 6 — Verify the chapter

▶ 6.1 — Confirm identity works end to end
  • Every email domain in use appears under Allowed Domains.
  • A sign-in from a private browser window completes through the identity provider.
  • Provisioning shows a successful state, whether through directory sync or SCIM.
  • A test user provisioned from the directory appears in the organization user list.
  • If tokens are in use, a call carrying a JWT fails for a reason other than authentication.
  • At least one named admin key exists and is recorded in your secrets manager.
Verification

All six hold. Sign out completely and sign back in through the identity provider as a final check that no fallback session is masking a broken configuration.
