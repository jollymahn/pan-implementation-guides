Plugins

Chapter 7 of 13. Connecting partner security platforms to the gateway, configuring the Prisma AIRS check in full, and wiring in a guardrail you already run

Configuration Hub Previous: Guardrails Next: Workspaces Prisma AIRS Platform

What a plugin is

A plugin connects an outside platform to the gateway by holding its credential. Once enabled, that platform's checks appear in the same guardrail catalog as the built-in ones and are built, actioned, and attached exactly as chapter 6 describes.

Two kinds exist, and they do opposite things:

KindDoesExamples
Guardrail partnersInspects a request or response and returns a verdict. Can block.Prisma AIRS, Pangea, Patronus, Mistral, AWS Bedrock Guardrails
Capability pluginsAdds content to a request before it reaches the model. Does not block.Exa and Tavily online search
A capability plugin is a guardrail that never says no

Exa and Tavily are configured through the guardrail machinery because that is where the gateway's request interception lives, not because they gate anything. They enrich the prompt and pass it on. Setting deny on one has nothing to act upon.

This is not the same as the AIRS Integrations guides

The AIRS Integrations family covers Prisma AIRS scanning inside other platforms: Claude Code, Kong, LiteLLM, Azure API Management, Apigee, and CI/CD pipelines. This chapter is the opposite direction, bringing partner platforms into the gateway. If the gateway is your enforcement point, you are in the right place.

Prerequisites

  • Chapter 6 complete, because a plugin produces checks and the actions model is covered there
  • An account with the partner, and an API key from it
  • A Production plan or above, since partner checks are not available on Developer
  • For Prisma AIRS, an activated AIRS tenant in Strata Cloud Manager with at least one security profile
Hold partner credentials in your vault

Partner API keys are credentials like any other. Chapter 3 set up secret references so they live in your vault rather than in the gateway, which is the reason that chapter came before this one.

Step 1 — Enable a plugin and add its credential

▶ 1.1 — Find the plugin surface

Partner credentials are entered in one of two places, depending on the partner and the gateway version:

  • Settings → Plugins — find the partner in the list, click Enable, and enter the API key.
  • Settings → Integrations — click the edit control on the partner's row and add the credential there.
Check both before concluding a partner is missing

The upstream documentation uses both names, and which one your console shows depends on the partner and the version you are running. The outcome is identical: a stored credential that makes the partner's checks selectable. Look in the other place before raising a support case.

Verification

The partner shows as enabled with a credential stored. Nothing is enforced yet; the plugin only makes checks available.

▶ 1.2 — Confirm the checks appeared
  1. Go to the Guardrails page and click Create.
  2. Search the check sidebar for the partner's name.

Its checks now sit alongside the BASIC and PRO ones. From here the partner check behaves like any other: same actions, same direction constraint, same status codes.

Verification

The partner's checks are listed and selectable. Checks that do not appear after enabling usually mean the plan does not include partner guardrails.

Step 2 — Configure the Prisma AIRS check

Prisma AIRS blocks a prompt or response when AI Runtime Security returns a block action. It is the partner most deployments of this gateway start with, and it carries parameters the other partners do not.

▶ 2.1 — Prepare Prisma AIRS itself

Three things must exist on the AIRS side before the gateway can use it:

  1. Prisma AIRS onboarded and activated in Strata Cloud Manager.
  2. At least one security profile carrying the threat detection rules you want applied.
  3. The profile name or profile ID recorded, if you intend to target a specific profile.
Targeting a profile is optional

Leaving both profile fields empty makes AIRS use the profile linked to your API key in Strata Cloud Manager. That is a reasonable default for a single-profile deployment and ambiguous for a multi-profile one, where naming the profile explicitly documents the intent.

Verification

The security profile exists in Strata Cloud Manager, and you hold the API key plus the profile name or ID.

▶ 2.2 — Add the credential and the check
  1. Open the plugin surface from step 1 and edit the Palo Alto Networks Prisma AIRS entry.
  2. Add your Prisma AIRS API key from Strata Cloud Manager, and save.
  3. Go to the Guardrails page and click Create.
  4. Search for PANW Prisma AIRS Guardrail and click Add.

The check runs on both hooks, so one guardrail can be built for the input and a second for the output.

Verification

The check is added to a guardrail and its parameter fields are editable.

▶ 2.3 — Set the parameters

Every parameter is optional, and the defaults are worth knowing because several of them show up later in reporting.

ParameterDefaultWhat it does
Profile NameNoneThe AIRS security profile to apply.
Profile IDNoneThe same selection by ID. Usable instead of or alongside the name.
AI Modelunknown-modelModel identifier used for tracking and reporting.
Application Userportkey-gatewayUser identifier in AIRS audit logs and user-level analytics.
Application NameNoneApplication name for tracking, which AIRS prefixes with Portkey-.
Scan Scopelast_messageWhich messages are scanned. See 2.4.
Strip ScaffoldingfalseRemoves known agent-harness wrappers before scanning. See 2.4.
Leaving the defaults makes AIRS reporting useless for attribution

Without AI Model and Application User, every request in the AIRS console arrives as unknown-model from portkey-gateway. The security team then sees threats with no way to tell which application or user produced them. Set all three tracking fields even though none is required.

Verification

The three tracking parameters carry real values, and the profile selection matches the profile you built in 2.1.

▶ 2.4 — Tune scan scope, especially for agentic clients

Scan Scope is the one parameter that changes what the gateway can detect, and it is the exception to the last-message rule stated in chapter 6.

ScopeScans
last_messageThe last message only. The default, and the same behavior as the gateway's own checks.
last_user_messageThe most recent message from the user, skipping assistant and tool turns after it.
user_messagesEvery user message in the conversation.
all_messagesThe entire conversation.

Agentic clients such as Claude Code, Cursor, and Cline inject scaffolding into messages: system reminders, MCP tool instructions, and mode markers. That scaffolding reads like an instruction injection to a security scanner, so it generates false positives on traffic that is entirely normal.

Two settings address it together:

  • Set Scan Scope to last_user_message, so the scan targets what the human actually sent.
  • Turn Strip Scaffolding on, which removes known harness wrappers before scanning.
Widening the scope costs more than latency

all_messages re-scans the whole conversation on every turn, so a long session rescans the same early messages repeatedly. That raises both the time per request and the volume AIRS processes. Widen the scope because a threat model requires it, not as a precaution.

Verification

Run an ordinary agentic session through the gateway and check the AIRS console for blocks. Scaffolding false positives appear as blocks on requests the user would call routine, and they disappear once scope and stripping are set.

Step 3 — Add a capability plugin

▶ 3.1 — Enable online search

Exa and Tavily give an offline model current information by searching the web and adding the results to the prompt. The sequence is:

  1. A caller sends a prompt that needs up-to-date information.
  2. The gateway intercepts it and sends a search query to the provider.
  3. The provider returns results.
  4. The gateway adds those results to the prompt as context.
  5. The enriched prompt goes to the model.

To set it up:

  1. Go to Settings → Plugins, find the provider, and click Enable.
  2. Enter the API key from the provider's dashboard and save.
  3. On the Guardrails page, click Create, search for the provider's online search check, and add it.
This sends prompt content to a third party and brings untrusted text back

Two exposures arrive together. The search query derived from your prompt leaves your boundary, and the web content returned is injected into the prompt the model then reads, which is a prompt injection path by design. Pair online search with an input guardrail that runs after it, and do not enable it on workspaces handling confidential prompts.

Verification

Ask a question whose answer postdates the model's training cutoff. A current answer confirms the plugin fired; a refusal or a stale answer means it did not.

Step 4 — Bring your own guardrail

A guardrail pipeline you already run becomes a gateway check through a webhook. The gateway sends the request or response to your endpoint, your endpoint returns a verdict, and the gateway applies your configured actions to it.

▶ 4.1 — Configure the webhook check

Add a Webhook check to a guardrail and complete these fields:

FieldTypeNotes
Webhook URLstringYour endpoint. Must be reachable from the gateway.
HeadersJSONHeaders sent with each request, which is where your own authentication goes.
Timeoutnumber, millisecondsHow long the gateway waits for a verdict.
Fail on ErrorbooleanWhether a non-200 response or a timeout counts as a failed check.
Forward Headersarray of stringsClient headers to pass through to your webhook.
Execute on ProxybooleanWhether the webhook also runs on proxy requests to /v1/*.
Fail on Error decides whether your control fails open or closed

Left off, a webhook that times out or errors produces a passing check, so an outage in your own service silently disables the guardrail. Turned on, an outage blocks traffic. Neither is automatically right, and the choice has to be made deliberately rather than discovered during an incident. Set the timeout low enough that a hung endpoint does not hold requests open.

Self-hosted gateways need private endpoints allowlisted

On a self-hosted gateway, a webhook on a private network must be listed in TRUSTED_CUSTOM_HOSTS. Without it the call is refused regardless of network reachability, which looks like a connectivity fault and is not one.

Verification

Send a request that should fail your webhook's logic and confirm the verdict arrives. Then stop the webhook service and confirm the Fail on Error behavior matches what you chose, because that is the case nobody tests until it happens.

Step 5 — Verify the chapter

▶ 5.1 — Confirm the partner path end to end
  • Each partner you need shows as enabled with a stored credential.
  • The partner's checks appear in the guardrail check list.
  • For Prisma AIRS, the tracking parameters carry real values rather than the defaults.
  • Scan scope and scaffolding stripping are set for any workspace serving agentic clients.
  • Any webhook check has a deliberate Fail on Error setting that has been tested.
A partner block has two consoles

When a partner check blocks a request, the gateway log shows the guardrail verdict and the partner's own console shows why. Confirm you can see both and that someone owns watching the second one. A verdict with no visible reason is hard to act on.

Firing the check needs a model to call

As with chapter 6, proving a check fires needs an integration from chapter 9. Record it as an open item and run it alongside the chapter 6 verification.

Verification

All five hold, and the live-fire test is recorded against chapter 9.
