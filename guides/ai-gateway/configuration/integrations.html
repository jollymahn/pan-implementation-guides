Integrations and the Model Catalog

Chapter 9 of 13. Connecting providers, deciding which models anyone may call, handing them to workspaces, and finally making a request that proves the whole set works

Configuration Hub Previous: Workspaces Provider Prerequisites

Integration, provider, model

Three words that sound interchangeable and are not. Getting them straight makes the rest of the chapter obvious.

TermLives atIs
IntegrationThe organizationA stored credential for one provider, plus the list of models it exposes and the workspaces allowed to use it.
ProviderA workspaceWhat an integration looks like once it has been provisioned to that workspace. The team uses it without ever seeing the credential.
ModelThe model catalogAn individual model, available only if the integration enabled it.

The flow runs one way: store the credential once as an integration, choose which models it exposes, share it with workspaces, and each workspace gets the same credential under its own budget and rate limits.

Credentials are never exposed to the teams using them

A workspace sees a usable provider, not an API key. Keys are encrypted at rest and decrypted in memory inside sandboxed workers at the moment a request is made. That is the reason to centralize integrations rather than let each team enter its own.

The model allowlist is set here and nowhere else

Workspaces see only the models their integration enabled. A team asking for access to a model is asking you to change the integration, not their workspace. Set this deliberately in step 2, because leaving it open means every workspace can call the most expensive model the provider offers.

Prerequisites

  • Chapters 1 to 8 complete, with at least one workspace holding an API key
  • Provider credentials, or a secret reference from chapter 3 that holds them
  • The list of models each team is approved to use
  • For pricing adjustments, gateway 2.7.0 or higher, and on air-gapped deployments backend 1.15.0 and frontend 1.8.1 or higher
Per-provider preparation is its own exercise

Each provider wants different things: an API key for OpenAI, an access key pair or an assumed role for Bedrock, a deployment name for Azure OpenAI, a service account for Vertex AI. The model provider prerequisites guide lists what to collect for each one. Have it in hand before step 1.

Step 1 — Create an integration

▶ 1.1 — Find the provider
  1. Go to Integrations in the organization settings.
  2. Click Create New Integration, or find the provider on the All tab and click Connect.

The page has three tabs, and they answer different questions:

TabShows
AllEvery provider the gateway supports. The starting point for a new connection.
ConnectedIntegrations connected at the organization level. Your main management view.
Workspace-CreatedIntegrations created by workspace admins for their own workspaces. Covered in the governance section below.
Verification

Your provider appears on the All tab. A provider that is not listed is a candidate for a custom model with a custom host, covered in step 2.

▶ 1.2 — Set the details, and choose the slug carefully
FieldNotes
NameDescriptive, for humans. For example Bedrock Production.
SlugThe unique identifier used in API calls. For example bedrock-prod.
DescriptionOptional context about what this integration is for.
Endpoint TypePublic or private.
The slug ends up in application code

Callers reference the integration by slug, so it is effectively a public interface. Changing it later means changing every application and every config that names it. Decide the convention now, across all your integrations, rather than naming the first one and improvising the rest.

A convention that holds up: provider and environment, lowercase, hyphenated. openai-prod, openai-dev, bedrock-prod. Avoid team names, which change, and avoid model names, since one integration carries many models.

Verification

The slug follows a convention you have written down and can apply to every integration you are about to create.

▶ 1.3 — Supply the credential, by vault reference if you can

This is where chapter 3 pays off. The credential field carries a toggle.

  1. Switch the toggle to Secret Ref.
  2. Select the secret reference you created in chapter 3.
  3. If the reference points at a secret holding several values, supply a Secret Key to pick the right one.

The alternative is pasting the key directly, which stores it in the gateway rather than in your vault.

Why the toggle is worth using even though both work

A referenced credential rotates in your vault with no change here, and the five-minute data plane cache picks it up. A pasted credential has to be re-entered on every integration that uses it at every rotation. The difference compounds with the number of integrations.

Provider-specific fields can also be referenced

It is not only the main API key. Provider configuration fields such as an AWS secret access key or an Entra client secret can each resolve from a reference. If a provider needs two secrets, both can come from the vault rather than one of each.

Verification

The integration saves. This still does not prove the vault can be read, which is the check chapter 3 deferred and step 5 finally runs.

Step 2 — Decide which models exist

▶ 2.1 — Set the allowlist
  1. In the integration, go to Model Provisioning.
  2. Choose one:
    • Allow All Models gives access to everything the provider offers, including models released after you configured this.
    • Allow Specific Models builds an allowlist.

Whatever you choose applies to every provider created from this integration, in every workspace it reaches.

Allow All includes models that do not exist yet

A provider adding a new flagship model makes it immediately callable by every workspace on this integration, at whatever it costs, with no action from you. On an allowlist, the same release is invisible until you add it. The allowlist is more work and it is the only one of the two that is a cost control.

Verification

The enabled models match what you approved. Count them: an allowlist that quietly matches the provider's full list is not an allowlist.

▶ 2.2 — Add a custom model

The catalog is not limited to a provider's standard list. Three cases need this:

  • Fine-tuned models, such as a fine-tune of an OpenAI or Anthropic base model.
  • Self-hosted or internal models running on your own infrastructure.
  • Models from a provider the gateway does not natively support, mapped onto a compatible API signature.
  1. In Model Provisioning, click Add Model.
  2. Set a Model Slug, lowercase and unique. This is what callers put in their request.
  3. Add a short description and the model type.
Per-model routing

A custom model can carry its own custom_host and custom_headers, so different models under one integration reach different upstreams. Model-level headers override integration-level ones. This is how a self-hosted model sits in the same catalog as a hosted one.

Verification

The custom model appears in the catalog with the same governance controls as a standard one. Step 5 confirms it is reachable.

Step 3 — Make the cost figures true

The gateway calculates cost from standard list pricing. If what you pay differs, every cost figure in every dashboard is wrong until you tell it. Two mechanisms, at different levels.

▶ 3.1 — Override pricing for one model
  1. In Model Provisioning, find the model.
  2. Click the edit control on its row.
  3. Set your pricing values and save.

Subsequent requests cost out at the new rates. Use it for a negotiated rate on a specific model, for internal chargeback, or to price a private model that has no list rate at all.

Verification

Make a call after saving and check the cost on the log entry against a hand calculation. Pricing changes are not retroactive, so earlier entries keep the old rate.

▶ 3.2 — Apply a multiplier to the whole integration

Pricing adjustments scale every model on an integration at once, which suits a contract discount better than editing models one at a time.

  1. Open the integration at the Integration Details step.
  2. Toggle Pricing Adjustments on.
  3. Choose a multiplier mode: Default for the common token types, or Custom for a JSON editor covering reasoning, audio, image and additional units.
  4. Enter the multipliers. Empty fields inherit from the default.
  5. Save.
MultiplierEffect
1Unchanged.
0.8A 20 percent discount, for a negotiated rate.
1.2A 20 percent markup, for internal showback that includes platform overhead.
Check the version before planning around this

Pricing adjustments need gateway 2.7.0 or higher, and on air-gapped deployments backend 1.15.0 and frontend 1.8.1. Below those the toggle is absent and per-model overrides from 3.1 are the only route.

Two integrations of the same provider can price differently

A discounted production integration and a standard-rate sandbox can sit side by side, each reporting its own effective cost. That is the cleanest way to stop sandbox spend distorting production figures.

Verification

A call through the integration reports a cost matching list price times your multiplier.

Step 4 — Hand the integration to workspaces

▶ 4.1 — Choose which workspaces get it
  1. In the integration, go to Workspace Provisioning.
  2. Choose All Workspaces or Specific Workspaces.

Each provisioned workspace sees the integration as a provider in its model catalog and can use it immediately, with no credential to enter.

All Workspaces includes workspaces that do not exist yet

Like the model allowlist, this setting reaches forward. A workspace created in six months inherits the integration without anyone deciding it should. Where an integration carries a production credential, name the workspaces explicitly.

Separate integrations per environment

One integration for development and another for production, each provisioned to its own workspaces, keeps the credentials separate and lets you price, limit and revoke them independently. Sharing one integration across both means a credential rotation touches production and development together.

Verification

Open a provisioned workspace and confirm the provider appears in its model catalog, showing only the models enabled in step 2.

▶ 4.2 — Set per-workspace limits

Each provisioned workspace can carry its own limits on this integration.

  1. Click the Edit Budget & Rate Limits control on a workspace row.
  2. Set budget limits, rate limits, and model access for that workspace.
  3. Optionally select the option to apply the same limits to every workspace where this integration is enabled.
An integration budget cascades to every provider created from it

This is the broadest of the three limit levels. A budget here governs all usage of the integration in that workspace, across every provider derived from it. The same rules as chapter 5 apply: it is not retroactive, and once set it cannot be edited by anyone.

Verification

Each workspace row shows the limits you intended, and you can explain why a given workspace has the number it has.

Step 5 — Make the first model call

Everything up to here has been configuration you could not test. One request now exercises the whole stack: the credential, the vault, the allowlist, the workspace key, the guardrails, and the logging mode.

▶ 5.1 — Send one request

Use the workspace API key from chapter 8 and name a model the allowlist permits. The gateway's own playground or a simple request from your workstation both work.

Read the result against this table before changing anything:

OutcomeMeans
A model responseThe whole path works. Continue to 5.2.
Authentication rejected at the gatewayThe workspace key is wrong, or it lacks the completions permission from chapter 8.
Gateway error fetching the secretThe secret reference path or the vault permission is wrong. This is the chapter 3 check finally reporting.
Provider rejects the credentialThe secret resolved but holds the wrong value, or the wrong key within a multi-value secret.
Model not found or not permittedThe model is not on the step 2 allowlist, or the integration is not provisioned to this workspace.
HTTP 400 naming an inline elementSaved-only mode from chapter 4 is on and the request passed an inline provider or config. Reference a saved resource instead.
HTTP 446A guardrail denied it. The configuration is working; the request failed a check.
Every row is a different chapter reporting back

This is the first moment the set can fail honestly. Work the table rather than guessing, because each outcome points at exactly one earlier decision.

Verification

A model response comes back through the gateway, made with a workspace key, naming an allowlisted model.

Step 6 — Clear the deferred checks

Five earlier chapters recorded verifications they could not run. They can all run now, and they should be run together while the first call is fresh.

▶ 6.1 — Work the backlog
FromCheckPasses when
Chapter 3The secret reference resolvesThe call in step 5 succeeded using a referenced credential rather than a pasted one.
Chapter 5The request logging mode behavesIn Full Logging the log entry shows prompt and response. In Metrics Only it shows tokens, latency and cost with no content.
Chapter 5The default config appliesA call made with no config reference behaves as the config attached to the key specifies.
Chapter 6A guardrail firesA request designed to fail returns 200, 246 or 446 according to its async and deny settings, and a passing request succeeds.
Chapter 6Redaction worksA prompt containing a test value is stored with the replacement text rather than the original.
Chapter 7The partner check firesThe gateway log shows the verdict and the partner console shows the reason.
Chapter 8Workspace guardrails applyA request in that workspace is evaluated by its guardrails as well as the organization baseline.
Run the passing case for every one of them

Each of these has a failing case that is easy to produce and a passing case that is easy to skip. A guardrail that blocks everything, a redaction pattern that matches everything, an allowlist that permits nothing: all three look like working controls until normal traffic arrives.

Verification

Every row passes, in both directions. Anything that does not points at a specific earlier chapter rather than at the gateway.

▶ 6.2 — Attach the default config now that it can exist

Chapter 5 decided the policy and could not write the config, because a config needs a provider to route to. That is now resolved.

  1. Create the config, naming the integration slug as its provider and the guardrail IDs from chapter 6 under input_guardrails and output_guardrails.
  2. Attach it to the workspace API keys from chapter 8 as their default config.
  3. Repeat the step 5 call with no config named by the caller.
This is what makes the governance hold

With a default config on the key and saved-only mode from chapter 4 enabled, the caller cannot route around the policy: they cannot supply their own config, and the one they get is yours. Neither half achieves that alone.

Verification

A request naming no config is still subject to the retries, guardrails and routing the config specifies.

Workspace-created integrations

Workspace admins can create integrations for their own workspace. Those appear on the Workspace-Created tab, giving you visibility and an audit trail over credentials you did not provision.

Check this tab before declaring the deployment governed

A team that wanted a model you had not approved may already have connected the provider themselves, with its own credential, outside your allowlist and your pricing. The integration is visible here and nowhere in your Connected view. Review it on the same schedule you review workspace membership.

If workspace-created integrations are not wanted at all, the integration write permissions on the Security tab from chapter 4 are where that is turned off.

The three limit levels, in one place

Budgets and rate limits exist at three levels, configured in three places across three chapters. This is the consolidated view.

LevelSet inScopeChapter
API keyThe key's own settingsOne credential5
WorkspaceWorkspace Control, Budget Allocation tabEvery key in the workspace, rejected together8
Integration, per workspaceWorkspace Provisioning, Edit Budget and Rate LimitsAll use of that integration in that workspace, cascading to every provider from it9
Pick one level per control

Setting all three produces overlapping ceilings and no clear answer to which one stopped a request. A workable default: integration limits for provider spend, workspace limits for team fairness, and key limits only where one application needs a cap its neighbors do not.
