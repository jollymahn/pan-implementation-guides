Security and Access Control

Chapter 4 of 13. The organization and workspace role models, the per-resource permissions that tune them, and the audit trail that records every change

Configuration Hub Previous: Secret References Next: Organization Properties

Two role models

The gateway has two independent role models. The organization model decides who administers the deployment. The workspace model decides what a team can do inside its own space. A user holds a role in each.

Two rules connect them, and both surprise people:

Organization owners and admins hold admin rights in every workspace

There is no workspace a user with an organization admin role cannot administer. Granting that role is a decision about the whole deployment, not about one team, and no workspace-level setting restricts it.

Organization membership comes first

A user must exist as an organization member before any workspace can invite them. Workspace admins and managers invite from the pool of organization members rather than from your directory, which is why chapter 2 set up provisioning before this chapter assigns roles.

Prerequisites

  • Chapters 1 to 3 complete
  • The Organization Owner role, because the permission settings in step 3 are owner-level and admin-level
  • The list of teams that will hold workspaces, even in draft, because the permission decisions here shape what those teams can do
  • Your organization's position on whether engineers should read prompt and response payloads in logs
Some settings have a version floor

Data visibility filtering needs gateway 2.2.4 or later, and on air-gapped deployments also backend 1.11.0 and frontend 1.6.4 or later. Only logs written after that version are filtered, so older logs stay visible to whoever could already see them. On SaaS the setting applies to logs from 19 February 2026 onward.

Step 1 — Assign organization roles

▶ 1.1 — Understand what each organization role carries

Owner and Admin are close to identical. Billing is the practical difference.

FeatureOwnerAdminMember
Logs and analyticsView, filter, groupView, filter, groupView, filter, group
PromptsList, view, create, update, delete, publishList, view, create, update, delete, publishList, view, create, update
ConfigsList, view, create, update, deleteList, view, create, update, deleteList, view, create
GuardrailsList, view, create, update, deleteList, view, create, update, deleteList, view, create, update
IntegrationsList, create, edit, duplicate, delete, copyList, create, edit, duplicate, delete, copyList, copy
Model catalog providers and modelsList, create, edit, duplicate, delete, copyList, create, edit, duplicate, delete, copyList, copy
TeamAdd users, assign rolesAdd users, assign rolesNone

Admin is not a reduced Owner

An organization admin can create and delete guardrails, rotate API keys, change organization settings, and assign roles. Treat the role as equivalent to Owner for every purpose except paying the bill, and grant it on that basis.

Verification

You can name every account that should hold Owner or Admin, and the list is short enough to read aloud. A deployment with more admins than workspaces has usually granted the role as a convenience.

▶ 1.2 — Review the workspace roles you will assign later

Workspaces do not exist until chapter 8. Decide the shape now, because step 3 configures what Manager and Member can actually do and those settings apply to every workspace.

Workspace roleCarries
AdminComplete control of workspace configuration and team management, including assigning the Admin role to others and creating workspace API keys.
ManagerTeam and resource management. By default a manager holds the same permissions as an admin, which step 3 is where you change.
MemberRead-only on workspace resources: logs, prompts, configs, providers, and models. No create, update, or delete.
Manager equals Admin until you say otherwise

Workspace admins and managers hold the same permissions by default. If your model expects a manager to be a lighter role, step 3 is the only place that becomes true, and skipping it leaves two names for one level of access.

Verification

You can state, for each of the three workspace roles, what you intend it to be able to do. Step 3 turns that intent into settings.

▶ 1.3 — Assign organization roles
  1. Go to Admin Settings and open the organization user list.
  2. Set each account's role to Owner, Admin, or Member.
  3. Leave everyone who only needs to work inside a workspace as a Member. The workspace role is what gives them their access, and chapter 8 assigns it.
Verification

Every account shows the role you intended. Users arriving later through directory sync land as members, so re-check this list after the first full sync rather than assuming it stays as you left it.

Step 2 — Audit the master API key

▶ 2.1 — Find the key the organization was created with

A new organization is provisioned with a master API key that has every permission enabled. Nobody chose that; it comes with the organization. Find it before anything starts using it.

  1. Open the API keys list for the organization in Admin Settings.
  2. Identify the key created at the same time as the organization.
  3. Decide whether anything needs it. In most deployments nothing does, because the keys created in chapter 2 and chapter 8 are scoped to their consumers.
  4. Either restrict its permissions to what one named consumer needs, or delete it.
A fully permissioned key with no owner is the weakest point in a new deployment

The master key can read logs, change guardrails, manage users, and rotate other keys. Leaving it in place unexamined means an unattributed credential with complete access exists for the life of the organization.

Verification

Every key in the list has a named purpose and a recorded holder. No key remains whose only description is that it came with the organization.

Step 3 — Configure the Security tab permissions

One page holds the permission model for every workspace. Go to Admin Settings → Security, where each section below appears in turn. Settings here apply organization-wide, so a workspace cannot loosen them locally.

Organization owners and admins are never restricted by these settings

Every section tunes what workspace managers and workspace members can do. Owners and admins see everything regardless, which is the same observation made at the top of this chapter arriving in a second place.

▶ 3.1 — Logs Management

Six switches, split across three roles and two levels of detail.

PermissionGrants
Managers View LogsWorkspace managers see full log entries.
Managers View Logs MetadataWorkspace managers see log metadata.
Members View LogsWorkspace members see full log entries.
Members View Logs MetadataWorkspace members see log metadata.
Org-Admin View LogsOrganization admins see full log entries inside workspaces.
Org-Admin View Logs MetadataOrganization admins see log metadata inside workspaces.

The distinction between the two is the whole point of the section:

  • Logs — complete entries, including request and response payloads. Prompts and model output are readable.
  • Logs metadata — timestamps, model used, tokens consumed, and other metrics, with no content.

All six are enabled by default, so every role reads payloads until you decide otherwise.

Payload access is a data protection decision, not a convenience one

Prompts routinely carry customer records, source code, and internal documents. Granting metadata without payloads gives a team everything it needs for cost and latency work while keeping content out of reach. Make this call with whoever owns data protection rather than defaulting it.

Verification

Each of the six switches matches a decision you can explain. Step 6 confirms the effect with a real account.

▶ 3.2 — Data Visibility

Logs Management decides whether a role sees logs at all. Data Visibility decides whose logs it sees.

PermissionWhen enabled
Managers View All DataWorkspace managers see logs, analytics, and traces from every user in the workspace.
Members View All DataWorkspace members see logs, analytics, and traces from every user in the workspace.

Both are enabled by default. Disabling one restricts that role to data generated by its own API keys, across logs, analytics, and traces alike.

The restriction applies to browser sessions and to workspace user API keys. Organization-level and workspace-level service API keys are not affected, and a workspace user key fetching analytics or exporting logs through the API is filtered by the role of the user it belongs to.

This is per-user scoping, not redaction

A member with this disabled still reads their own payloads in full. Use Logs Management to remove payload access; use Data Visibility to narrow whose requests are in scope. The two settings answer different questions and are often confused for each other.

Verification

Check the version floor from the prerequisites. On a deployment below it, the setting is present and has no effect, which looks identical to a setting that is working.

▶ 3.3 — API Key Management

Four switches controlling who may see and issue keys inside a workspace.

PermissionGrants
View Keys (Workspace Managers)Managers see both user and service API keys in their workspace, limited to those created by workspace administrators.
Manage Keys (Workspace Managers)Managers create, update, and delete user and service keys, including creating keys on behalf of another user.
View Keys (Workspace Members)Members see user keys only, and only ones created for them.
Manage Keys (Workspace Members)Members create, update, and delete their own user keys.

Two kinds of key are involved. Service keys drive automated processes and integrations and are not tied to a person. User keys belong to an individual and carry that person's scope.

Creating keys for other people is an attribution problem

A manager with Manage Keys can issue a key on behalf of another user. Usage then attributes to that user rather than to the manager who created it, so the audit trail for key creation and the attribution in logs point at different people. Grant it where a team genuinely onboards its own members, and know the trade.

Verification

The four switches match your intent for manager and member autonomy. Chapter 8 exercises them against a real workspace.

▶ 3.4 — The remaining resource sections

The rest of the Security tab follows one pattern: a view switch and a write switch, for managers and for members, per resource.

SectionSwitchesDefault
AnalyticsManagers View Analytics, Members View AnalyticsBoth enabled.
GuardrailsManagers View, Managers Write, Members View, Members WriteManagers view and write; members view only.
PromptsManagers View, Managers Write, Members View, Members WriteManagers view and write; members view only.
IntegrationsManagers Write Workspace Integrations, Managers Write MCP Integrations, Managers Write MCP ServersChapters 9 and 10 depend on these.
ProvidersView Providers, Manage ProvidersMembers view; managers view and manage.
Guardrail write access deserves a second look

A role that can write guardrails can also weaken or delete them. Leaving write access with workspace managers means a team can remove a control the organization put in place for it. Chapter 6 covers organization-level guardrails, which managers cannot touch, and that is the right home for anything that must hold.

Verification

Every section on the Security tab has been read and set deliberately. A section left at its default because you agreed with the default is a decision; one left because you did not scroll to it is not.

Step 4 — Set saved-only mode

Saved-only mode, shown as Block Inline Configs, stops callers supplying a provider, endpoint, or config in the request itself. Requests must reference a saved resource by slug, which is the only way the allowlists, budgets, guardrails, and attribution attached to those resources reliably apply.

▶ 4.1 — Find out what your organization already does

The default depends on when the organization was created, so check rather than assume.

Organization createdDefault
On or after 19 June 2026Enabled. Inline provider configuration is rejected out of the box.
Before 19 June 2026Disabled, to preserve existing traffic. Nothing changes until an administrator turns it on.

New workspaces inherit the organization setting as it stands when they are created.

Hybrid deployments need gateway 2.11.0 or later

Below that version the setting exists and does nothing. Inline configuration is not blocked, and the console gives no indication that enforcement is inactive.

Verification

You know the current state of the setting and the gateway version behind it.

▶ 4.2 — Enable it
  1. Go to Admin Settings → Security.
  2. Find Block Inline Configs and enable it.

Enforcement is a data-plane check that runs once at the start of request processing, before routing. A request carrying an inline provider, endpoint, or config is rejected with HTTP 400 and an error code naming what was blocked, and it never reaches an upstream provider.

Turning this on can break live applications immediately

Any caller that currently passes a provider name, a base URL, or an ad-hoc config object starts failing on the next request. On an organization created before 19 June 2026 with traffic already flowing, inventory what your callers send before enabling it, and give application teams a date.

Verification

Send one request with an inline provider and confirm it returns HTTP 400 with an error code identifying the blocked element. Send one referencing a saved resource by slug and confirm it proceeds. Before chapter 9 creates an integration there is no saved resource to reference, so run the second half of this check again then.

Step 5 — Confirm audit logging

▶ 5.1 — Open the audit log and find your own changes

Audit logs collect automatically across every workspace. There is nothing to switch on.

  1. Go to Admin Settings → Audit Logs.
  2. Find the changes you made earlier in this chapter.

Each entry records:

FieldHolds
TimestampWhen the action occurred.
UserWho performed it.
WorkspaceThe workspace context, where one applies.
ActionCreate, update, delete, and so on.
ResourceThe entity affected.
Response StatusThe HTTP status the action returned.
Client IPWhere the request came from.
CountryThe geographic location associated with the request.

Filters cover HTTP method, request ID, resource type, and action. Resource types include workspaces, API keys, integrations, model catalog, configs, prompts, guardrails, collections, labels, and the organization itself.

Access is limited to owners and admins

Nobody else reads the audit log, and no Security tab setting changes that. If your security operations team needs the data, they need an organization role or an export path, which chapter 13 covers.

Verification

Your own permission changes from step 3 appear as entries, attributed to your account, with a successful response status. An empty audit log after a chapter of changes means you are looking at the wrong organization.

Step 6 — Verify the chapter

▶ 6.1 — Prove the model with a real account

Settings pages show intent. Only a sign-in shows effect.

  • The Owner and Admin list is short and every entry is deliberate.
  • The master API key has been scoped or deleted.
  • Every section of the Security tab has been read and set.
  • Saved-only mode matches your decision, and you know the gateway version supports it.
  • Audit log entries exist for the changes you just made.
The real test waits for chapter 8

Manager and member permissions cannot be exercised until a workspace exists with someone in it. Carry this check forward: once chapter 8 creates the first workspace, sign in as a member and confirm they see what you intended and nothing else.

Verification

All five hold, and the deferred member sign-in is recorded as an open item against chapter 8.
