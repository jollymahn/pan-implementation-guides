Secret References

Chapter 3 of 13. Pointing the gateway at credentials held in your own vault, so no provider key is ever stored in the gateway

Configuration Hub Previous: Authentication Next: Security Building a Key Vault

How a reference works

A secret reference tells the gateway where to fetch a credential rather than holding the credential itself. Instead of pasting an OpenAI key into an integration, you create a reference that names your vault, the path, and the key, and the gateway resolves it when a request arrives.

The work is split across the two planes:

  1. You create the reference. The management plane stores the configuration only: the manager type, the secret path, and the authentication details. It never stores the secret value.
  2. At request time the data plane reads that configuration and fetches the secret directly from your vault.
  3. The data plane caches the fetched value for five minutes, so your vault is not called on every request. After the cache expires, the next request triggers a fresh fetch.
The five-minute cache is also the rotation delay

Rotating a secret in your vault takes effect on the gateway within five minutes, with no change needed on the gateway side. The same window means a revoked credential keeps working for up to five minutes, which matters when you are revoking in response to an incident.

Do this before chapters 7 and 9

Plugins and integrations both accept a reference in place of a literal credential. Creating them first and migrating later means editing every one of them by hand, so set up the references your deployment needs while nothing depends on them yet.

Prerequisites

  • Chapter 2 complete, with an owner or admin account
  • Gateway version 2.2.4 or higher
  • For air-gapped deployments, backend version 1.12.0 or higher
  • A vault already holding the credentials, in AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault
  • The exact secret path, and the key within the secret when the secret holds several key-value pairs
  • Credentials or a role that lets the gateway read from the vault, which step 2 covers per vault
No vault yet?

The LLM provider API key management guide builds one from scratch with Azure Key Vault and Entra ID, including storage layout, access grants, and rotation alerting. Return here once the secrets are stored and readable.

Check the version before planning around this

Secret references do not exist below gateway 2.2.4. On an older gateway the Secret References area is absent and integrations take literal credentials only. Confirm the version first, because the alternative is a different credential design rather than a slightly different click path.

Step 1 — Create a secret reference

▶ 1.1 — Open Secret References and start a new one
  1. In the admin panel, open Secret References.
  2. Click Create.
Verification

The create form opens. If the Secret References area is missing entirely, re-check the gateway version against the prerequisites.

▶ 1.2 — Name the reference
FieldRequiredNotes
NameYes1 to 255 characters. This is what you will pick from a list in chapters 7 and 9.
SlugNoUnique identifier, generated from the name when omitted. Must match ^[a-zA-Z0-9_-]+$.
DescriptionNoUp to 1024 characters.

Name the reference after the credential and the environment, not after the vault. A reference called prod-openai-key is legible in an integration dropdown six months later; aws-sm-ref-1 is not.

Verification

The name is accepted and a slug is shown. A rejected slug means a character outside the allowed pattern, usually a space or a dot.

▶ 1.3 — Choose the vault

Select the external manager holding the secret:

  • AWS Secrets Manager
  • Azure Key Vault
  • HashiCorp Vault

The authentication fields on the next part of the form change with this choice, which step 2 covers.

Verification

The authentication section redraws with fields belonging to the manager you picked.

▶ 1.4 — Set the secret location
FieldRequiredWhat goes in it
Secret PathYesThe secret name as the external manager knows it, for example prod/openai/api-key.
Secret KeyNoThe specific key inside the secret, used when the secret holds several key-value pairs, for example OPENAI_API_KEY.
A secret holding several pairs needs the key

Leaving Secret Key empty against a multi-pair secret resolves the whole object rather than the value you want, and the failure surfaces later as a provider rejecting the credential rather than as an error here.

Verification

The path matches the secret name in your vault exactly, including case and any prefix. Step 3 confirms the gateway can actually read it.

Step 2 — Configure vault authentication

Each vault offers several authentication types. Choosing between them is a security decision rather than a convenience one, because two of the three vaults support a mode that needs no stored credential at all.

Which path should I pick?
  • AWS Secrets Manager — three types, of which assumed role and service role avoid storing a long-lived key.
  • Azure Key Vault — three types, of which managed identity avoids storing a client secret.
  • HashiCorp Vault — three types, of which Kubernetes auth avoids storing a static token.
▶ 2.1 — Pick an AWS authentication type
TypeWhat it needsUse when
Access keyAccess key ID, secret access key, regionNothing better is available. This stores a long-lived credential in the gateway to fetch credentials from a vault, which weakens the point of the exercise.
Assumed roleRole ARN, region, optional external IDThe gateway should assume a role in your account. This is the usual production choice.
Service roleRegion, optionalThe gateway uses its own service role. Your secret's resource policy must grant that role access.
Set an external ID on the assumed role

The external ID is optional in the form and worth setting anyway. Without it, a role trusting the gateway's account is open to the confused deputy problem that external IDs exist to close.

Verification

The chosen type's required fields are all populated. For assumed role, the role ARN resolves in your AWS account and its trust policy names the gateway.

▶ 2.2 — Grant the read permission in AWS

Whichever type you chose, the identity reaching the vault needs permission to read the specific secret rather than the whole manager. Grant secretsmanager:GetSecretValue scoped to the secret ARN, and no more.

For the service role type, the grant goes on the secret's resource policy rather than on an identity policy in your account.

Verification

A policy simulation or a read from the role succeeds against the named secret and fails against a different one, which confirms the scope is tight rather than broad.

▶ 2.1 — Pick an Azure authentication type

All three types need the vault URL. They differ in how the gateway proves who it is.

TypeWhat it needsUse when
Entra service principalTenant ID, client ID, client secret, vault URLThe gateway runs outside Azure, or no managed identity is available. The client secret expires, so track the date.
Managed identityVault URL, and a client ID only for a user-assigned identityThe gateway runs on Azure. This is the strongest option because no secret is stored.
Default credentialsVault URLThe hosting environment already supplies a credential chain the gateway can use.
Verification

The vault URL is the full resource address and resolves from a browser. A truncated or wrong-region URL fails at fetch time rather than at save time.

▶ 2.2 — Grant the read role in Azure

Assign Key Vault Secrets User to the identity on the vault, which grants read access to secret values and nothing else. Avoid Key Vault Secrets Officer here, because the gateway never needs to write.

On a vault using the legacy access policy model rather than role-based access control, grant the Get permission on secrets instead.

Verification

The role assignment appears on the vault against the identity you configured. Azure role assignments can take a few minutes to take effect, so a failure immediately after assignment is worth retrying once.

▶ 2.1 — Pick a HashiCorp Vault authentication type

All three types need the Vault address, and all three accept an optional namespace for Vault Enterprise.

TypeWhat it needsUse when
TokenVault address, tokenTesting, or a short-lived credential you intend to replace. A static token stored in the gateway inherits whatever lifetime Vault gave it.
AppRoleVault address, role ID, secret IDMachine-to-machine access outside Kubernetes. The usual production choice for a gateway not running in a cluster.
KubernetesVault address, roleThe gateway runs in Kubernetes. The service account token authenticates it, so nothing static is stored.
Verification

The Vault address includes the scheme and port as your Vault expects them, and the namespace is set if your deployment uses Vault Enterprise namespaces.

▶ 2.2 — Bind a policy to the role

The role the gateway authenticates as needs a policy granting read on the secret path alone. Confirm the policy path matches the engine mount, because a KV version 2 mount stores data under a data/ segment that the policy path must include.

Verification

Authenticating as the role from a workstation and reading the path returns the secret. A permission denied at this point is a policy path problem rather than a gateway problem.

Step 3 — Verify the reference resolves

▶ 3.1 — Save and confirm the reference exists

Save the reference. It appears in the Secret References list with its name and slug.

Saving proves the form was valid, not that the vault can be read

The management plane stores configuration without contacting your vault, so a reference pointing at a wrong path or a role with no permission saves cleanly. The fetch happens on the data plane at request time, which is where a mistake shows up.

Verification

The reference is listed. Proving it resolves needs step 3.2.

▶ 3.2 — Resolve it through a real request

A reference is only exercised when something consumes it. Confirm it works by attaching it to the first integration you build in chapter 9 and making one model call.

  • A successful model response proves the whole path: the gateway reached the vault, read the secret, and the provider accepted it.
  • An authentication failure from the provider points at the wrong secret key or a stale value in the vault.
  • A gateway-side error fetching the secret points at the vault path or the permission grant.
Why this check is deferred

There is no way to exercise a reference from the Secret References page alone. Rather than leave you with an untested configuration, chapter 9 returns to this check as the first thing it verifies after creating an integration.

Verification

Recorded as an open item until chapter 9. Note which reference you expect each integration to use, so the check is quick when you get there.

Update and delete

▶ Updating a reference

Edit only the fields that changed. Authentication details are merged rather than replaced, so changing a region does not require re-entering the credential alongside it.

Rotating the underlying secret in your vault needs no change here at all. The data plane picks the new value up when its five-minute cache expires.

Verification

After a vault-side rotation, a request made more than five minutes later succeeds with the new value.

▶ Deleting a reference

Deletion fails while any integration still uses the reference. Remove those associations first, then delete.

The refusal is a safety net

This is the one place the gateway stops you from breaking a live path by accident. Treat a failed deletion as useful information about what still depends on the reference rather than as an obstacle.

Verification

The reference disappears from the list, and the integrations that used it have been repointed rather than left broken.

Workspace scoping

A new reference is reachable from every workspace in the organization by default. That is the right setting for a shared credential and the wrong one for a credential belonging to a single team.

Restricting a reference to named workspaces has no console path today

The create and edit forms cover the reference identity, the vault, the authentication, and the location. Limiting a reference to specific workspaces is driven through the Admin API instead, by supplying the list of workspaces the reference may be used from. Setting that list turns off organization-wide access automatically, and reverting to organization-wide access clears the list.

Plan for this when you design the credential layout in chapter 9. Where a credential must not be reachable organization-wide and you want to stay inside the console, a separate integration per workspace achieves the same separation without the API.

Platform encryption

Secret references control where credentials live. They sit alongside the encryption the platform applies regardless of configuration.

LayerWhat appliesConfigurable
In transitTLS 1.2 or higher on all traffic to and from the gatewayNo
At restAES-256 on stored dataNo
Provider credentialsHeld in your vault and fetched at request timeYes, this chapter
Customer-managed keys are arranged, not configured

Bringing your own key management service key is possible and is set up with Palo Alto Networks rather than through the console, so it is not a procedure in this set. Raise it with your account team if your controls require customer-managed keys, and raise it early, because it affects data written before it is in place.
