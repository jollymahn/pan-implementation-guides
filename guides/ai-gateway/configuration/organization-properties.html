Organization Properties

Chapter 5 of 13. What every workspace and every key inherits: the logging mode, mandatory metadata, enforced configs, and spending controls

Configuration Hub Previous: Security Next: Guardrails

What inheritance means here

The settings in this chapter are the defaults a workspace is born with and the rules a key is bound by. Chapter 4 decided who may change things. This chapter decides what they inherit before they change anything.

Timing matters more than usual, for two reasons that work differently:

  • Metadata schemas apply to new objects only. Existing API keys and workspaces are untouched when you add a schema. It binds new keys, new workspaces, and existing keys at the point they are next updated.
  • Budget limits are not retroactive and not editable. A limit applies to requests made after it is set, and once set it cannot be changed by anyone in the organization.
A budget limit is a one-way decision

Budget limits cannot be edited after they are set, by any organization member including the owner. Work out the number before you type it. An over-tight limit on a production key is corrected by replacing the key, not by raising the limit.

Prerequisites

  • Chapters 1 to 4 complete
  • The Organization Owner role, since request logging and metadata schemas are owner-level
  • A decision from whoever owns data protection about whether payloads may be stored at all
  • The metadata fields your organization needs for cost attribution, for example team, cost center, environment, or service
  • A monthly spending figure per key you are willing to commit to, because the limit cannot be changed later

Step 1 — Set the request logging mode

This setting decides what the gateway stores for every LLM request in the organization. It is the single largest privacy control in the product.

▶ 1.1 — Choose between full logging and metrics only
ModeStoresSuits
Full LoggingComplete request payloads, full response content, and all associated metrics and metadataDebugging, prompt engineering, and investigating model behavior. You can see what was asked and what came back.
Metrics OnlyUsage statistics such as tokens, latency, and cost, plus request metadata. No payloads.Regulated data, or any environment where prompts carry information that must not be stored.
  1. Go to Admin Settings → Organisation Properties.
  2. Find Request Logging.
  3. Select the mode and save.
Metrics Only cannot be applied backwards

Switching to Metrics Only stops new payloads being stored. Payloads already written stay written. If the organization has been running in Full Logging while this decision was pending, raise retention of the existing data separately rather than assuming the switch cleaned up behind it.

This is a different control from the one in chapter 4

Logs Management on the Security tab decides who may read stored payloads. Request Logging decides whether payloads are stored at all. Metrics Only makes the Security tab question moot, because there is no content for anyone to read.

Verification

Make one model call after chapter 9 and open its log entry. In Full Logging the prompt and response are readable. In Metrics Only the entry shows tokens, latency, and cost with no content. Record this as an open check until an integration exists.

▶ 1.2 — Decide whether workspaces may override it

The same section controls whether workspace managers can change the organization logging setting for their own workspace.

  • Override allowed — a workspace handling sensitive data can tighten to Metrics Only without asking. A workspace can also loosen, which is the risk.
  • Override restricted — the organization setting holds everywhere and only an owner changes it.
Allowing override means a team can turn payload logging back on

If Metrics Only exists because of a regulatory position rather than a preference, restrict the override. A control a workspace manager can undo is not a control you can describe to an auditor.

Verification

The override setting matches the strength of the reason behind your logging mode. Chapter 8 confirms the effect from inside a workspace.

Step 2 — Require metadata on keys and workspaces

Metadata schemas make specific fields mandatory when an API key or a workspace is created. Without them, attribution depends on whoever created the key remembering to fill something in, which is to say it depends on nothing.

▶ 2.1 — Decide the fields before writing the schema

Pick fields that answer a question someone will actually ask. The usual set:

  • team_id — who owns the spend.
  • cost_center — where it is charged.
  • environment — development, staging, or production.
  • service_id — which application the key belongs to.

Every field adds friction to key creation, so require only what you will use. A field nobody queries is a field people fill with a placeholder.

Verification

For each field, you can name the report or the question it serves.

▶ 2.2 — Write the schema

Schemas follow JSON Schema draft-07 with three constraints the gateway enforces:

RequirementWhy
"type": "object" at the top levelMandatory. The schema describes a metadata object.
"additionalProperties": trueMandatory, and must be true. Teams may add their own fields beyond the ones you require.
Every property typed "string"Other types are not accepted. A numeric cost center is still a string here.

A schema that defines fields without requiring them:

{
  "type": "object",
  "properties": {
    "team_id": {
      "type": "string"
    },
    "environment": {
      "type": "string"
    }
  },
  "additionalProperties": true
}

Add a required array to make them mandatory:

{
  "type": "object",
  "required": ["team_id", "service_id"],
  "properties": {
    "team_id": {
      "type": "string"
    },
    "service_id": {
      "type": "string"
    },
    "environment": {
      "type": "string"
    }
  },
  "additionalProperties": true
}
Defining a property does not require it

Only names listed in required are enforced. A schema with properties and no required array documents the fields and mandates none of them, which is a reasonable first step while teams get used to the idea.

Verification

The schema validates as JSON and carries all three mandatory elements.

▶ 2.3 — Apply the schemas
  1. Go to Admin Settings → Organisation Properties.
  2. Select API Key Metadata Schema or Workspace Metadata Schema.
  3. Paste the schema and save.

The two schemas are independent. A key schema and a workspace schema usually share fields and do not have to.

Existing keys and workspaces are not retrofitted

Enforcement starts at the next creation. Existing API keys and workspaces keep working without the fields, and an existing key picks up the requirement only when someone next updates it. A deployment that adds schemas late ends up with two populations, and only a deliberate pass over the old keys merges them.

This is why the schema belongs before chapter 8

Every workspace created in chapter 8 and every key issued there will carry the fields. Adding the schema afterwards leaves exactly the gap described above.

Verification

Create a throwaway API key and confirm the form demands the required fields, then delete the key. A key that saves without them means the schema was accepted but the required array is missing or misspelled.

Step 3 — Attach default configs to keys

A default config attached to an API key applies to every call made with that key. The caller writes no config ID, and you change the policy later by editing the config rather than by asking an application team to ship code.

▶ 3.1 — Understand what a default config can carry

A config holds routing and governance behavior, so attaching one by default lets you enforce:

  • Which models and providers a key may reach.
  • Fallbacks, retries, and timeouts.
  • Guardrails and content moderation.
  • Caching behavior.

The separation this creates is the point: application teams build applications, and governance lives in an object administrators control.

Pairs with saved-only mode

Chapter 4 can block callers supplying their own config inline. Combining that with a default config on every key means the policy you set is the policy that runs, with no path for a caller to route around it.

Verification

You can name the behavior the default config will carry for each key population.

▶ 3.2 — Create the config, then attach it

A config has to exist before a key can point at it, and a useful config references integrations and guardrails that chapters 6 and 9 create.

  1. Create a config in Strata Cloud Manager with the settings you want.
  2. Note its config ID.
  3. Open the API key and attach the config as its default.
This step completes after chapters 6 and 9

A config written now can only reference what exists now, which is nothing to route to and no guardrail to apply. Decide the policy here, write the config once integrations and guardrails are in place, and attach it to keys before those keys reach an application team.

Verification

Recorded as an open item against chapter 9. When it completes, a call made with the key and no config reference behaves as the config specifies.

Step 4 — Set budget limits on API keys

▶ 4.1 — Choose cost or tokens

When creating or editing an API key, toggle on Add Budget Limit and pick one:

TypeSetBehaves
CostA maximum spend in USD, minimum 1 dollarTracks what the usage costs, so model price changes move the ceiling in real terms.
TokensA maximum token countTracks consumption independently of price, which keeps the limit stable when pricing shifts.

Pick tokens when you are protecting capacity, and cost when you are protecting a budget line.

Verification

The limit type matches what you are actually trying to control. A cost limit on a key whose risk is a runaway loop will trip late.

▶ 4.2 — Choose the reset period
PeriodBehavior
No periodic resetThe limit applies until exhausted. The key stops working at that point and stays stopped.
Reset weeklyResets every Sunday at midnight UTC.
Reset monthlyResets on the first of each month at midnight UTC.
Midnight UTC is not midnight where your finance team sits

A monthly reset lands at midnight UTC on the first, which is the previous evening in the Americas and mid-morning in Asia. Teams reconciling spend against a local calendar month see a boundary that does not line up. Say so once rather than explaining it every month.

A budget limit with no reset stops a production key permanently

Reaching the limit expires the key. There is no raising it afterwards, because budget limits cannot be edited once set. For anything production-facing, choose a reset period or set the ceiling high enough that reaching it is genuinely an incident.

Verification

Every key with a limit has a reset period you chose deliberately, and the production keys are not on the no-reset setting by accident.

Step 5 — Set rate limits on API keys

▶ 5.1 — Pick a limit type and a window

Rate limits control velocity rather than total spend. Toggle on Add Rate Limit when creating or editing a key.

  • Requests — a cap on the number of API calls.
  • Tokens — a cap on token consumption rate.

Three windows are available:

WindowSuits
Per minuteHigh-frequency applications where a runaway loop must be caught quickly.
Per hourModerate usage, and the usual starting point.
Per dayBroad usage management, closer to a soft quota than a throttle.

When the limit is reached, further requests are rejected until the window resets. Unlike a budget limit, this is temporary and self-clearing.

A per-minute limit is the one that catches a loop

A daily cap on a runaway process is reached after the damage. Where the risk is an application retrying in a tight loop, the minute window is the one that helps, and a daily cap alongside it bounds the worst case.

Verification

Each key's limit reflects its expected traffic with headroom. A limit set below normal peak turns into an incident on the first busy day.

Step 6 — Turn on notifications

▶ 6.1 — Add recipients who can act
  1. Toggle on Email Notifications when creating or editing a key with budget limits.
  2. Type a recipient address and press Enter or click New.
  3. Add as many as needed.

Organization owners and admins are notified automatically when a limit is reached or a threshold is crossed. Recipients you add are in addition to them.

Notify the team that owns the key, not only the administrators

The default recipients are the people who administer the gateway. The people who can stop a runaway job are usually the application team. Add them, or the first warning reaches someone with no ability to act on it.

Verification

Each key with a budget limit lists at least one recipient outside the administrator group.

Step 7 — Verify the chapter

▶ 7.1 — Confirm what every new workspace will inherit
  • The request logging mode is set, and the override decision matches the reason behind it.
  • Both metadata schemas are applied, and a throwaway key creation demanded the required fields.
  • The default config policy is decided and recorded as an open item against chapter 9.
  • Budget limits, where set, have a deliberate reset period.
  • Rate limits reflect expected traffic with headroom.
  • Notification recipients include the teams that own the keys.
Verification

All six hold. Stage 1 of the configuration set is complete: the organization has an identity, an identity provider, vault-backed credentials, a role model, and the defaults every workspace will inherit.

Limits set elsewhere

Budgets and rate limits exist at three levels, configured in three places. Setting one does not set the others.

LevelSet inCovered by
API keyThe key's own settingsThis chapter
WorkspaceWorkspace settingsChapter 8
Integration, per workspaceIntegration settings, under Workspace Provisioning, then Edit Budget and Rate LimitsChapter 9
Integration limits cascade, key limits do not

A budget set on an integration applies to every provider created from that integration, which makes it the broadest of the three. A key limit binds one credential. Decide which level each control belongs at before setting any of them, or you end up with three overlapping ceilings and no clear answer to which one stopped a request.
