Routing and Reliability

Chapter 12 of 13. The config object, and the retries, fallbacks, load balancing, conditional routing, circuit breakers and caching that live inside it

Configuration Hub Previous: Agent Gateway Integrations

One object, three strategies

Everything in this chapter is one thing: a JSON config object, created once and referenced by ID. There is no separate fallback feature and no separate load balancer. There is a config, and the config has a strategy.

Three strategy modes exist, and they are mutually exclusive at any single level of the object.

ModePicks a target byUse for
fallbackOrder. First target, then the next on failure.Surviving a provider outage
loadbalanceWeight. A relative share of traffic each.Spreading load, pooling rate limits, canary testing
conditionalA rule evaluated against the request.Routing by user plan, region, or request parameter

Retries, circuit breakers and caching are not modes. They are settings that sit alongside a strategy and modify how it behaves.

Strategies nest, which is where the real designs come from

Any target inside a strategy can itself be another strategy. A fallback whose primary target is a load balancer survives single-endpoint failures inside the cluster and only fails over on a full outage. A conditional router whose branches are fallback chains keeps EU traffic on EU infrastructure even while failing over. Reach for nesting once the flat version stops expressing what you mean.

Prerequisites

  • Chapters 1 to 11 complete, with at least two providers in the model catalog from chapter 9
  • A second provider or a second API key for the same provider, since most of this chapter needs somewhere to route to
  • For semantic caching, a vector database
Provider slugs come from chapter 9

Targets are written as @provider-slug or @provider-slug/model-name, and the slug is the one set on the integration. A config referencing a slug that does not exist fails at request time rather than when saved, so have the catalog open while writing one.

Step 1 — Create and attach a config

▶ 1.1 — Create the config
  1. Go to the Configs page in Strata Cloud Manager.
  2. Click Create.
  3. Write the config JSON. Start with a single retry block if you have nothing else in mind, because it is useful on its own.
  4. Save, and note the Config ID.
{
  "retry": { "attempts": 3 },
  "override_params": { "model": "@openai-prod/gpt-4o" }
}
Verification

The config is saved and has an ID. Nothing is using it yet.

▶ 1.2 — Attach it per request

Send the ID in the x-portkey-config header, either as a client default or on individual requests.

curl https://aigw.portkey.ai/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "x-portkey-api-key: $API_KEY" \
  -H "x-portkey-config: $CONFIG_ID" \
  -d '{
    "model": "@openai-prod/gpt-4o",
    "messages": [{ "role": "user", "content": "Hello" }]
  }'
A request-level config replaces the client default, it does not merge with it

Where a client sets a default config and an individual request also names one, the request wins outright for that call. Nothing from the default survives into it. A config that appears to lose half its settings on certain calls is usually this.

Verification

The call succeeds, and the log entry for it shows the Config ID.

▶ 1.3 — Or attach it to an API key as a default

A config attached to a key applies to every request made with that key, with no header and no application change. This is the governance path, and it is the mechanism chapter 9 relies on.

  1. Open API Keys and edit the key.
  2. Set the default config.
  3. Save.

Three cases make this the right choice rather than the header:

  • Clients that cannot send custom headers at all, such as Open WebUI and LibreChat
  • Organization-wide policy that must not depend on application code being changed
  • Shared routing and caching rules across every application using one key
A default config is not an enforced config on its own

A caller who sends their own x-portkey-config header replaces yours for that request. Pairing the default with the saved-only config restriction from chapter 4 is what makes it binding. Chapter 9 sets this out as the combination that makes governance hold, and neither half achieves it alone.

Verification

A request sending no config header is still subject to the config's behavior.

Step 2 — Retries

The cheapest reliability win here, and the only one that needs no second provider. Up to five attempts, with exponential backoff.

{
  "retry": { "attempts": 3, "on_status_codes": [429, 503] },
  "override_params": { "model": "@openai-prod/gpt-4o" }
}
AttemptWait
InitialImmediate
1st retry1 second
2nd retry2 seconds
3rd retry4 seconds
4th retry8 seconds
5th retry16 seconds
on_status_codes replaces the defaults rather than adding to them

The default retry codes are 429, 500, 502, 503, 504 and 529. Setting on_status_codes to [408] means retrying on 408 and nothing else, silently dropping the five defaults. If you want to add a code, list the defaults alongside it.

Setting use_retry_after_headers makes the gateway honour the provider's own retry-after headers instead of the backoff table, falling back to the table when the provider sends none.

Cumulative retry wait is capped at 60 seconds

The cap applies across the whole request, not per attempt. A first retry waiting 20 seconds followed by a provider asking for 50 more exceeds it, and the request fails rather than waiting. Any single Retry-After above 60 seconds fails immediately. On a provider that returns long backoff under load, retries therefore stop helping at exactly the moment the provider is most congested, and a fallback is the better answer.

Retries are one log entry, not several

Attempts are not logged individually and the response times are summed, so a slow entry may be four quick failures and a success. Read x-portkey-retry-attempt-count on the response to tell them apart: -1 means every retry was exhausted and the request failed, 0 means no retries were configured, and any positive number is the attempt that succeeded.

Verification

Send a request that provokes a retryable code and confirm x-portkey-retry-attempt-count is greater than zero on the response.

Step 3 — Fallbacks

A prioritized list. The gateway tries the first target, and moves down the list on failure.

{
  "strategy": { "mode": "fallback", "on_status_codes": [429, 503] },
  "targets": [
    { "override_params": { "model": "@openai-prod/gpt-4o" } },
    { "override_params": { "model": "@anthropic-prod/claude-3-5-sonnet-20241022" } }
  ]
}

By default a fallback triggers on any non-2xx response. Narrowing it with on_status_codes is usually right: a 400 caused by a malformed request will fail identically on every target, and falling through the whole chain to discover that costs latency and money for no benefit.

One request can bill against several providers

Each target in a chain that gets tried is a real call. Latency and price differ per target, so a fallback that looks free in testing shows up in the cost analytics the first time the primary has a bad hour. Check that every model in the chain is actually acceptable for the use case, not merely available, because a request silently answered by a weaker model is worse than a failed one in some applications.

Tracing a chain in the logs

Filter by Config ID to see every request using the config, and by Trace ID to see all the attempts belonging to one original request. The second is the one that shows the chain.

Verification

Force a failure on the primary, by revoking its credential or pointing it at a model it cannot serve, and confirm the response arrives from the second target with both attempts under one Trace ID.

Step 4 — Load balancing and canary testing

Weights, not order. Each target takes a relative share of the traffic.

{
  "strategy": { "mode": "loadbalance" },
  "targets": [
    { "provider": "@openai-prod", "weight": 0.7 },
    { "provider": "@azure-prod", "weight": 0.3 }
  ]
}
PatternWhat it does
Between providersSpread across providers, with the model taken from the request
Multiple API keysSeveral keys for one provider, pooling their separate rate limits
Cost optimizationMost traffic to a cheaper model, a reserved share to the premium one
Gradual migrationA small weight on a new model, increased as confidence grows
Canary testing is this, with a small weight

There is no separate canary feature. Putting 5 percent on a new model and 95 percent on the incumbent is a canary test, and the analytics from chapter 13 are what turn it into a decision. Treating it as its own mechanism leads people to look for a feature that does not exist.

Verification

Send enough requests to exceed the smallest weight several times over, then group the logs by model. The distribution should approach the weights. A handful of requests proves nothing, because the split is probabilistic rather than a strict rota.

Step 5 — Conditional routing

A rule evaluated against each request decides the target. Both conditions and default are required.

{
  "strategy": {
    "mode": "conditional",
    "conditions": [
      { "query": { "metadata.user_plan": { "$eq": "paid" } }, "then": "premium" }
    ],
    "default": "standard"
  },
  "targets": [
    { "name": "premium",  "override_params": { "model": "@openai-prod/gpt-4o" } },
    { "name": "standard", "override_params": { "model": "@openai-prod/gpt-4o-mini" } }
  ]
}

Three things can be matched against, and each query key has exactly two segments.

PathMatches
metadata.<key>Custom key-value pairs sent with the request
params.<key>Any parameter in the request body, such as model or temperature
url.pathnameThe request path, for routing a whole route such as /v1/embeddings

Operators are $eq, $ne, $in, $nin, $regex, $gt, $gte, $lt and $lte, combined with $and or $or.

Nested keys are not supported, and the failure is silent

Only two-segment keys work. metadata.user_plan is valid; metadata.features.new_model_enabled is not. Values must be primitives. A nested key does not raise an error, it simply never matches, so every request quietly takes the default target and the routing appears to be ignored rather than misconfigured.

An invalid regex evaluates to false

$regex uses JavaScript regular expressions with no flags, so matching is case-sensitive. A pattern that fails to compile does not error either: the condition is simply false. Between this and the nested-key rule, a conditional config that always falls through to its default is the characteristic failure of this strategy. Test each branch by sending a request you know should match it.

Verification

Send one request per branch, each carrying metadata that should select it, plus one that should match nothing. Confirm in the logs that all three reached different targets, including the default.

Step 6 — Circuit breakers

Retries and fallbacks both react per request. A circuit breaker remembers, taking a failing target out of rotation so later requests do not pay the timeout at all.

{
  "strategy": {
    "mode": "fallback",
    "cb_config": {
      "failure_threshold_percentage": 20,
      "minimum_requests": 10,
      "cooldown_interval": 60000,
      "failure_status_codes": [401, 429, 500]
    }
  },
  "targets": [
    { "override_params": { "model": "@openai-prod/gpt-4o" } },
    { "override_params": { "model": "@anthropic-prod/claude-3-5-sonnet-20241022" } }
  ]
}
FieldMeaning
failure_thresholdFailure count that opens the circuit
failure_threshold_percentageFailure rate that opens it, as an alternative
minimum_requestsRequests needed before a rate is judged at all
cooldown_intervalMilliseconds before retrying the target. Minimum 30 seconds.
failure_status_codesWhich codes count as failures. Defaults to above 500.

The circuit opens when the count or the rate is exceeded, and closes automatically once the cooldown passes. Strategies inherit cb_config from their parent, and targets inherit from their strategy, so one block at the top covers a nested design.

Conditional strategies are not evaluated by the circuit breaker

A conditional mode strategy is skipped entirely. Putting cb_config on one has no effect, and a design that routes conditionally to several providers has no breaker protection at that level however it is written. Place the breaker on fallback or loadbalance strategies nested inside the conditional branches instead.

When every target is open, the breaker is bypassed

Rather than failing all requests, the gateway ignores the breaker and tries anyway. This is deliberate, and it means a total provider outage looks like no protection at all: latency returns to full timeouts on every request. The breaker buys you nothing in exactly the scenario people imagine buying it for, and what helps there is a fallback to a different provider family.

Not the same as the MCP circuit breakers in chapter 10

Circuit breakers for MCP servers are announced and not shipped. These, for model routing, are available now. Same name, two features, different states.

Verification

Drive a target past its threshold and confirm later requests skip it without waiting, then confirm it is used again after the cooldown elapses.

Step 7 — Caching

{ "cache": { "mode": "semantic", "max_age": 60 } }
ModeMatchesAvailable on
simpleAn exact match on the requestAll routes, including image generation
semanticRequests with similar meaning, by cosine similarity/chat/completions and /completions only

Simple cache hits when the entire request body matches a stored entry, along with the metadata and cache namespace if used, and the entry is still inside max_age. One changed character anywhere in the body is a miss.

Semantic cache is a superset: the gateway checks for an exact match first and only runs a similarity search on a miss. The default similarity threshold is 0.95, and it works on requests under 8,191 tokens with four messages or fewer.

Semantic cache ignores the system prompt

Similarity is judged on the user text. Changing the system prompt does not change the cache key, so two requests with the same question and deliberately different system instructions can return the same cached answer. Where the system prompt is what distinguishes two use cases, separate them with x-portkey-cache-namespace or use simple mode, because semantic caching will otherwise merge them.

Two headers that change caching behavior

x-portkey-cache-force-refresh: true forces a miss and refreshes the entry, which is the way to test a change without waiting out the TTL. Separately, caching does not work at all when x-portkey-debug: "false" is sent, which is an easy thing to have set globally in a client and then spend an afternoon wondering why nothing caches.

Verification

Send one request twice and confirm the second is markedly faster and its log entry shows a cache hit. For semantic mode, send a reworded version of the same question and confirm it also hits.

Composing strategies

Targets are fully composable. Any strategy can nest inside any other, which is how the patterns worth deploying are actually built.

ShapeBehavior
Fallback over load balancersEndpoint failures stay inside the cluster. Only a full outage triggers the cross-provider backup.
Fallback into a conditional routerThe backup is chosen by request context, so EU traffic stays on EU infrastructure during failover
Load balancer of fallback chainsEach slot has its own independent backup, so one model family failing does not pull in another's
Build these one layer at a time

Each layer is individually testable and the combined object is not. Get the inner strategy behaving correctly on its own, then wrap it, rather than writing three levels and trying to work out which one swallowed a request.

What runs when

Several controls can act on one request, and knowing the order explains most surprising behavior.

  • A cache hit returns before any provider is called, so no strategy, retry or breaker runs at all
  • The strategy selects a target, by order, weight or condition
  • The circuit breaker removes targets it currently considers unhealthy, except under a conditional strategy and except when all of them are open
  • Retries apply to the attempt against the selected target
  • Fallback moves to the next target once that target is exhausted
Retries multiply against fallback targets

Three retries on each of three fallback targets is nine possible upstream calls for one client request, each with its own backoff. The worst case is slower and more expensive than either setting suggests on its own, and it is bounded by the 60-second cumulative retry cap rather than by anything in the fallback configuration. Keep retry counts low where a fallback chain is long.
