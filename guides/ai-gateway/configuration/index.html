AI Gateway Configuration

Configuring a licensed AI Gateway from an empty organization to a governed, multi-workspace deployment, in the order the product requires

Start: Organization Registration Deployment Guide Customer Readiness AIRS Integrations

What this covers

This set configures the gateway itself. It assumes the data plane already exists, whether that is the hosted SaaS plane or a self-hosted hybrid plane you installed from the hybrid infrastructure guide. Nothing here deploys infrastructure.

Every step is a click path in Strata Cloud Manager. Where a capability has no console path today, the chapter says so and says what the alternative is rather than switching you to an API workflow for one setting.

Relationship to the deployment guide

The AI Gateway Deployment Guide takes a licensed tenant to a first working model call, with one integration and a basic guardrail. That is the shortest path to proving the gateway works. This set is the full build: the same ground covered in depth, plus identity, access control, governance defaults, workspaces, the MCP and agent gateways, routing behavior, and observability.

Why the order matters

The chapters run in sequence because several settings bind only what comes after them. Working out of order produces a tenant that looks configured and behaves inconsistently.

GateSet inWhat breaks if you skip ahead
Allowed DomainsChapter 2SCIM provisions nobody. The gateway only creates users whose email domain is verified on the organization, so a provisioning run against an empty domain list silently yields zero users.
Secret referencesChapter 3Integrations and plugins store raw credentials. Moving them to vault references later means editing every integration by hand.
Roles and permissionsChapter 4Users arrive before the model that governs them and inherit whatever the default allows.
Organization defaults and guardrailsChapters 5 and 6Workspaces created earlier do not pick up an enforced default config or an organization guardrail retroactively for traffic already flowing.
WorkspacesChapter 8Integrations are provisioned to workspaces. With no workspaces, provisioning has no target and every integration lands organization-wide.

Stage 1 — Foundation

Five chapters that establish who the organization is, who may sign in, how credentials are held, who may change what, and what every workspace inherits.

▶ Chapter 1 — Organization registration and gateway URLs

Licensing and activation, confirming the organization, the Organisation ID, and pointing the console at a self-hosted gateway so generated code snippets and playground calls use your endpoint instead of the cloud default.

Open Chapter 1

▶ Chapter 2 — Authentication and identity

OIDC and SAML single sign-on with per-provider setup for Okta and Entra ID, allowed domains, SCIM provisioning, Cloud Identity Engine directory sync, JWT validation for agent traffic, and the two kinds of API key.

Open Chapter 2

▶ Chapter 3 — Secret references

Pointing the gateway at credentials held in AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault instead of storing provider keys in the gateway, with the authentication variants for each vault.

Open Chapter 3

▶ Chapter 4 — Security and access control

Organization and workspace roles, the per-resource permission settings for logs, analytics, providers and keys, data visibility, saved-only mode, and audit logs.

Open Chapter 4

▶ Chapter 5 — Organization properties

Request logging mode, mandatory metadata schemas, enforced default configs, and budget and rate limits on API keys.

Open Chapter 5

Stage 2 — Protection

Two chapters covering what inspects traffic before any traffic exists.

  • Chapter 6 — Guardrails. The built-in deterministic and LLM checks, synchronous against asynchronous evaluation, streaming behavior, PII redaction, and organization-level enforcement. Open Chapter 6.
  • Chapter 7 — Plugins. Partner guardrail plugins including Prisma AIRS, credential configuration, capability plugins, and bringing your own guardrail. Open Chapter 7.

Stage 3 — Tenancy

  • Chapter 8 — Workspaces. Creating workspaces, adding members by directory mapping or invitation, workspace API keys, workspace-level guardrails, and workspace budgets and rate limits. Open Chapter 8.

Stage 4 — Supply

  • Chapter 9 — LLM integrations and the model catalog. Provider integrations, model provisioning, pricing overrides and adjustments, custom models and hosts, workspace provisioning, and the first model call that proves the whole set works. Open Chapter 9.
  • Chapter 10 — MCP gateway. The registry, internal and external servers, upstream authentication, user identity forwarding, access provisioning, tool provisioning, the first tool call, rate limits, and guardrails. Open Chapter 10.
  • Chapter 11 — Agent gateway. Scoping the key for agents, registering an A2A agent and validating it by fetching its card, provisioning workspaces, controlling skills, and swapping a client onto the virtual server. Open Chapter 11.

Stage 5 — Runtime and visibility

  • Chapter 12 — Routing and reliability. The config object and how it attaches, then retries, fallbacks, load balancing and canary testing, conditional routing, circuit breakers, and simple and semantic caching. Open Chapter 12.
  • Chapter 13 — Observability. Metadata, traces and feedback going in, then the logs, filters, analytics, log export and OpenTelemetry ingest coming out, plus how cost figures are calculated. Open Chapter 13.

Who can do what

Most of this set requires the organization Owner or Admin role. Workspace-scoped settings can be delegated once chapter 8 creates the workspaces and chapter 4 establishes the role model.

ChaptersMinimum roleNotes
1, 2, 3, 5Organization OwnerAuthentication settings and organization defaults are owner-level changes.
4Organization OwnerRole assignment and permission configuration.
6, 7Organization Owner or AdminOrganization guardrails are owner-level; workspace guardrails follow the workspace role.
8 to 13Organization Admin, or Workspace Admin within a workspaceDelegable once the workspace exists.

Outside this set

  • Data plane deployment. Installing the hybrid gateway is covered by the Kubernetes and ECS and Container Apps guides.
  • Customer-managed encryption keys. Bringing your own KMS key is arranged with Palo Alto Networks rather than configured in the console, so it is not a procedure in this set. Platform encryption applies regardless: traffic uses TLS 1.2 or higher, and stored data uses AES-256.
  • Client application setup. Pointing developer tools at the gateway is covered by the client applications guide.
