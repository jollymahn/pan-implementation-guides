Observability

Chapter 13 of 13. Metadata, traces and feedback going in, then logs, analytics, export and OpenTelemetry coming out

Configuration Hub Previous: Routing and Reliability Organization Properties

Metadata is the hinge

Every other chapter configured something the gateway does. This one is about what it records, and it divides cleanly in two: what you put in at request time, and what you can read afterwards.

The division matters because the first half gates the second.

Sent with the requestMakes possible afterwards
MetadataFiltering, grouped analytics, cost attribution by team or feature, and the conditional routing in chapter 12
Trace IDSeeing a multi-step workflow as one thing rather than scattered calls
Feedback, after the factQuality analytics, which no amount of latency and cost data substitutes for
None of it can be added retroactively

A request logged without metadata is logged without metadata forever. The analytics dashboards can group by any key you sent and by nothing you did not, so the question "what is the marketing team spending" is answerable only if marketing's requests carried an identifier at the time they were made. Decide the metadata scheme before traffic starts, because the alternative is a quarter of logs you cannot break down.

Prerequisites

  • Chapters 1 to 12 complete, with live traffic through the gateway
  • An agreed set of metadata keys, which is a conversation with whoever will ask the reporting questions
  • For log export on self-hosted enterprise, the Data Service enabled
  • For OpenTelemetry ingest, a Server key

Step 1 — Send metadata

Metadata travels in the x-portkey-metadata header as a JSON object.

curl https://aigw.portkey.ai/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $API_KEY" \
  -H 'x-portkey-metadata: {"_user":"user-123","environment":"prod","feature":"chat-assist"}' \
  -d '{ "model": "@openai-prod/gpt-4o", "messages": [{"role":"user","content":"Hello"}] }'
Every value must be a string of 128 characters or fewer

Not a number, not a boolean, not a nested object. There is no limit on how many keys you send, but a value that is not a string is the usual reason metadata appears to be dropped. Cast request IDs and numeric tenant IDs to strings before sending them.

_user is the one key with behavior attached

It powers the user analytics described in step 6. If your request body already carries OpenAI's user field, the gateway copies it into _user automatically, and an explicit _user in metadata wins where both exist. Everything else is a plain string you choose, so agree on environment, team and feature spellings now rather than discovering three variants of "production" in the dashboards later.

Two mechanisms exist for not relying on every caller to remember. On self-hosted deployments with gateway 2.5.0 or higher, HEADERS_TO_METADATA injects named request headers into metadata automatically, matching header names case-insensitively.

HEADERS_TO_METADATA=x-request-id,x-caller-service,x-environment

Separately, metadata can be defined at the API key and workspace levels, not only per request, and required keys can be enforced through the API key metadata schema from chapter 5. Enforcement is the only version of this that survives contact with a team under deadline.

Verification

Send a request with metadata, open its log entry, and confirm the keys appear. Then filter the logs by one of them and confirm the request comes back.

Step 2 — Trace multi-step work

A trace groups related calls into one chronological view. For a single question and answer it adds little. For an agent making eight calls to finish one task, it is the difference between a readable record and eight unrelated rows.

The model is OpenTelemetry's. Spans form a tree, children point at parents, and parentless spans become roots.

FieldPythonRequired
traceIdtrace_idYes
spanIdspan_idNo
spanNamespan_nameNo
parentSpanIdparent_span_idNo

The gateway returns a trace ID on every request in the x-portkey-trace-id response header whether you sent one or not, which is what step 3 needs.

Already running OpenTelemetry? Send the standard headers

The gateway accepts W3C Trace Context, so an instrumented application can pass traceparent and baggage rather than gateway-specific headers. The trace ID and parent span are extracted from traceparent, a span ID is generated for the gateway's own span, and the span name is set to the method and path. Where both forms are present, the gateway-specific headers win, which is worth knowing before you spend an afternoon wondering why your traceparent is being ignored.

Verification

Send two requests sharing a trace ID and confirm the Traces view shows them as one trace with two spans, not two traces.

Step 3 — Collect feedback

Cost and latency are measured for you. Whether the answer was any good is not, and feedback is the only input that carries it.

curl --location 'https://aigw.portkey.ai/v1/feedback' \
  --header 'Authorization: Bearer $API_KEY' \
  --header 'Content-Type: application/json' \
  --data '{
    "trace_id": "YOUR_TRACE_ID",
    "value": -10,
    "weight": 0.5,
    "metadata": { "text": "title was irrelevant", "_user": "fef653" }
  }'
KeyRequiredAccepts
trace_idYesThe trace the feedback attaches to
valueYesAn integer from -10 to 10
weightNoA float from 0 to 1, default 1.0
metadataNoAny JSON. _user, _organisation, _prompt and _environment are indexed by default.

Weight exists for collecting several signals on one trace. An explicit thumbs-down from a user and an automated quality check should not count equally, and weighting is how you say so.

Feedback can also be added by hand from a log

Reviewers working through the Logs page can attach feedback to individual entries without any API call. It lands in the same analytics as the API route, which makes a manual review pass a usable way to seed quality data before any instrumentation exists.

Verification

Post feedback against a known trace ID and confirm it appears on the feedback analytics for that request.

Step 4 — The logs

A chronological list of every request, with timestamp, type, model, tokens, thinking tokens and cost. Clicking an entry opens the full raw request and response. Each log has its own URL, so a confusing one can be pasted to a colleague directly.

The Status column is where chapter 12 gets verified

Every strategy you configured reports its actual state here, per request. This is the answer to "is the cache even on", and it is faster than reasoning about the config.

FeatureInactiveActive states
CacheCache DisabledCache Miss, Cache Refreshed, Cache Hit, Cache Semantic Hit
RetryRetry Not TriggeredRetry Success on N Tries, Retry Failed
FallbackFallback DisabledFallback Active
LoadbalanceLoadbalancer DisabledLoadbalancer Active

Config and prompt IDs appear in the log detail and are clickable, taking you to the config or the prompt playground. The Replay button reruns a request in a fresh playground, which is the quickest route from a bad response to a fixed one.

Replay is unavailable in three cases

The endpoint is something other than /chat/completions, /completions or /embeddings; the provider used has since been archived; or the request came from a prompt template invoked inside a config target. A greyed-out Replay button is one of these three rather than a fault.

DO NOT TRACK, and the caching side effect from chapter 12

Sending x-portkey-debug: false processes the request without logging its content. Tokens, cost and latency are still recorded; the request and response bodies are not. That is the right control for genuinely sensitive traffic, and it is also the explanation for the caching behavior flagged in chapter 12: caching does not work on a request that is not being tracked. If a client sets debug: false globally, it has silently turned off both.

Verification

Send one request through a config carrying a cache and a retry, then find it in the logs and read both states off the Status column.

Step 5 — Filters

Logs and analytics share one filter set. The dimensions worth knowing are model, provider, cost, tokens, status, metadata, average weighted feedback, config ID, trace ID, API key, prompt ID, cache status, workspace and time range.

Which of them you see depends on your role, so a filter a colleague describes may genuinely not be on your screen.

Saved filters are shared and anyone can change them

A saved filter is visible to every member of the organization, and any of them can edit, rename or delete it. That makes them good for standardizing a team's views and bad for anything you depend on being stable without telling people. Name them so their purpose is obvious, because an unexplained saved filter is the sort of thing somebody tidies away.

Verification

Filter the logs by a metadata key from step 1, save the filter, reload the page and apply it from the saved list.

Step 6 — Analytics

TabAnswers
OverviewCost, tokens, mean latency, request volume, top models. The starting point.
UsersActivity by _user. See the warning below about who that means.
ErrorsError rates, and how many requests the routing strategies rescued
CacheLatency improvement and cost saved by caching
FeedbackWhatever step 3 collected
SummaryGroup by any dimension, including any metadata key
The Users tab means your application's end users, not your staff

It is built from the _user metadata key and OpenAI's user field, which identify whoever is using the application you built. The gateway does not provide analytics on usage by individual members of your own organization. Anyone opening this tab expecting to see which colleague is spending the budget will misread it, and the numbers will look plausible while answering a different question.

The Summary tab is the one that repays the metadata discipline from step 1. Grouping by any key gives total requests, total cost, average latency, success rate, average tokens and last seen for each value, which is how questions like "which feature costs the most" and "which model has the worst success rate" get answered without an export.

The Errors tab quantifies chapter 12

It reports how many requests were rescued by retries, fallbacks and load balancing. That number is the return on the reliability work, and it is the figure worth putting in front of whoever asked whether the routing complexity was justified.

Verification

Open Summary, group by a metadata key you have been sending, and confirm each value shows a sensible request count and cost.

Step 7 — Log export

  1. Open Exports in the sidebar.
  2. Click Request Data.
  3. Set the time range, a log limit or custom offset, and the fields to include.
  4. Click Request Export.

Selectable fields include the log and trace IDs, timestamp, full request and response payloads, provider and model, request, response and total tokens, cost and currency, response time and status code.

Self-hosted enterprise needs the Data Service enabled

Without it the export feature is unavailable. This is a deployment-time dependency rather than a setting on this page, so if Exports is missing or inert, that is the thing to check first.

Verification

Export a narrow time range, open the file, and confirm the rows match what the logs show for that window.

Step 8 — OpenTelemetry

Everything so far observes requests that went through the gateway. OpenTelemetry ingest reverses the direction: the gateway becomes a backend for telemetry from the rest of your stack, so application, service and database spans sit alongside the LLM calls they triggered.

OTEL_EXPORTER_OTLP_ENDPOINT="https://aigw.portkey.ai/v1/otel"
OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer YOUR_API_KEY"
It must be a Server key

A workspace user key will not authenticate the OTLP exporter. Since exporters typically fail quietly and simply drop spans, the symptom is no data rather than an error, and the key type is the first thing to check.

Any OTel-compatible source works, which includes the instrumentation already present in tools like the Vercel AI SDK, LlamaIndex, OpenLLMetry and Logfire. Correlation with gateway traffic comes free when the application propagates the same trace IDs as step 2.

Verification

Emit one span from an instrumented service and find it in the Traces view alongside the LLM call it wrapped.

Cost and pricing data

Costs are computed from a central pricing file covering every provider and model the gateway prices, applied to input and output tokens per request. How current that file is depends on the deployment.

DeploymentPricing updates
SaaSInstant, fully managed
HybridAutomatic every 24 hours, needs gateway 1.12 or higher
Air-gappedLegacy, not offered to new customers. Customer-managed, automatic only with outbound access.
Pricing is cached for 24 hours

A provider's price change will not appear in your cost figures immediately, and on hybrid deployments below gateway 1.12 it will not appear until someone updates the file by hand. Reconcile against the provider's own billing before treating gateway cost figures as authoritative for chargeback.

What it will not tell you

Four limits are worth knowing before anyone builds a process on top of these dashboards.

LimitConsequence
Metadata cannot be backfilledAny breakdown you did not instrument for is unavailable for all past traffic
Retry attempts are not logged individuallyOne entry per request with response times summed. Read x-portkey-retry-attempt-count to see the attempts.
The Users tab is end users onlyNo analytics on usage by members of your own organization
debug: false omits contentDeliberate, but it removes the request and response bodies that make a log worth opening, and disables caching with it
