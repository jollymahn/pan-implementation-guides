Checks, actions, configs

A guardrail is two things assembled: a set of checks that each return yes or no, and a set of actions that decide what the gateway does with those verdicts. Creating one does not make it active. It becomes active either by being enforced at the organization level, or by being named in a config that a request uses.

Four constraints shape every guardrail you build, and all four surprise people who expect a content filter:

The gateway's own checks evaluate only the last message

Input guardrails built from the catalog below look at the last message in the request body, not the whole conversation. A prompt injection planted three turns earlier is not re-examined on this turn. Design these checks around the newest message.

Some partner checks are the exception and take a scope parameter of their own. The Prisma AIRS check, for instance, scans anything from the last message up to the entire conversation. Chapter 7 covers that setting, and it is the route to full-conversation analysis.

One guardrail validates input or output, never both

The direction is fixed when you create it, and the actions you set apply only to that direction. Covering both means building two guardrails. A single guardrail with checks for both directions is a configuration that cannot work.

A check returns a boolean and nothing else

Every check answers yes or no. There is no score, no confidence, and no partial result to threshold on. Orchestration comes from the actions in step 2, not from the checks.

Guardrails are text-only

Image inputs, whether base64 or URLs in a multimodal message, are not evaluated. Only the text portions of a message reach the checks.

Which checks you can use depends on the plan:

PlanAvailable checks
DeveloperBASIC only
ProductionBASIC, PARTNER, and PRO
EnterpriseAll of the above plus custom guardrails

Prerequisites

  • Chapters 1 to 5 complete
  • The Organization Owner role for step 4, since organization guardrails are owner-level
  • A decision on which checks are advisory and which must block, because step 2 turns that into behavior
  • For partner checks, the partner credential, which chapter 3 can hold as a vault reference
Why this comes before workspaces

An organization guardrail applies to every request in the organization, including requests from workspaces created later. Setting the baseline now means every workspace in chapter 8 inherits it rather than being retrofitted one at a time.

Step 1 — Create a guardrail and add checks

▶ 1.1 — Decide the direction first

Before opening the console, settle which direction this guardrail covers, because it cannot be changed into the other one later.

DirectionRunsTypical job
Input, meaning the promptOn the user's prompt before the model is calledPrompt injection, PII in the prompt, model allowlisting, required metadata
OutputOn the model's generated text after the callSchema conformance, PII in the response, content moderation, leaked code

Most deployments need one of each, so expect to run this step twice.

Verification

You can state the direction and name the checks that belong to it. A check that only supports the other direction, which the catalog marks, is a sign the split is wrong.

▶ 1.2 — Create it and add the checks
  1. Open the Guardrails page and click Create.
  2. Add checks from the sidebar. Each one has its own input fields, so fill them in and save the check.
  3. Add as many checks as the guardrail needs. There is no limit.
  4. Name the guardrail and save it.

Saving produces a guardrail ID. Record it: steps 4 and 5 both reference it.

Name for the direction and the intent

A guardrail called input-pii-block is obvious in a config six months later. One called guardrail-2 means reading its checks to find out what it does, every time.

Verification

The guardrail appears in the list with its ID, and every check within it supports the direction you chose.

Step 2 — Set the actions

Actions are where a guardrail becomes either an observation or a control. There are four settings, and the defaults are deliberately passive: a freshly created guardrail logs and blocks nothing.

▶ 2.1 — Async: observe or gate
SettingBehaviorLatency
Async true, the defaultChecks run in parallel with the model call. Results are logged and change nothing.None
Async falseChecks run before the request reaches the model, or before the response reaches the caller. Results can deny or modify.Adds the time the checks take
A guardrail left on the default never blocks anything

Async true is the shipped state. A team that creates a guardrail, attaches it, and assumes traffic is now controlled has built a logger. Setting async to false is what makes it a control.

Verification

Each guardrail's async setting matches whether you intend it to observe or to gate.

▶ 2.2 — Deny: what a failure costs
SettingOn a failed checkStatus returned
Deny trueThe request is killed.446
Deny false, the defaultThe request proceeds anyway, and the failure is recorded.246
Either, all checks passThe request proceeds.200

Those two status codes are specific to the gateway and replace the provider's own code when async is false. Anything consuming the gateway needs to handle them.

Tell application teams about 246 and 446 before you enable deny

A client written against standard HTTP semantics treats 246 as a success in the 2xx range and 446 as an unrecognized failure. Neither is handled sensibly by default. Roll deny out on a subset of traffic first and confirm the callers cope.

Verification

For every guardrail with deny true, the teams calling through it know what 446 means and have agreed how their application responds.

▶ 2.3 — Sequential: ordering and cost
SettingBehavior
Sequential false, the defaultAll checks run at once. Faster when the checks are independent.
Sequential trueChecks run one after another, each starting when the previous finishes. Adds latency.

Leave it parallel unless the checks genuinely depend on each other or you need predictable ordering.

Verification

Sequential is on only where you can name the dependency that requires it.

▶ 2.4 — Feedback on success and failure

Two further actions append custom feedback to the request, one when every check passes and one when any check fails. Both are worth setting.

Over time this builds a dataset of guardrail verdicts against real traffic, which is the only practical way to find out whether a check is tuned correctly before you set deny on it.

This is how you earn the right to turn deny on

Run a new guardrail with async true and feedback configured for a period. The feedback record shows how often it would have fired and on what. Enable deny once that rate is one you can defend to the teams it will affect.

Verification

Both feedback actions are configured on every guardrail you intend to enforce later.

Step 3 — Turn on PII redaction

Redaction replaces sensitive values in the request before it reaches the model, rather than rejecting the request. It is the right answer when the prompt is legitimate and the data in it is not.

▶ 3.1 — Enable it on a PII check

On the guardrail creation page, PII checks carry a Redact PII toggle. Enabling it redacts matches instead of only reporting them.

Five providers support redaction:

ProviderRedacts
Prisma AIRS AI Gateway Pro PIIPhone numbers, email addresses, location information, IP addresses, social security numbers, names, and credit card information.
Patronus AIConfidential business content, based on an enterprise PII dataset covering meeting notes, contracts, marketing email, and performance reviews.
PangeaGeographic locations, payment card data, and other sensitive types, with customizable rules.
AWS Bedrock GuardrailsPredefined PII types, plus custom types defined with regular expressions.
PromptfooPII exposures in session data, through social engineering, and through direct exposure.
Verification

Step 6 sends a prompt containing a test value and confirms the stored log shows the redacted form rather than the original.

▶ 3.2 — Redact a pattern of your own

For identifiers specific to your organization, such as an internal account number, use the Regex Match check with redaction rather than a PII provider.

  1. On the Guardrails page, click Create.
  2. Choose Regex Match from the BASIC category.
  3. Enter the pattern in Regex Rule, for example \b\d{3}-\d{2}-\d{4}\b for a social security number shape.
  4. Set Replacement Text, for example [REDACTED].
  5. Toggle Redact on.
  6. Leave Inverse off, unless you intend to redact everything except the pattern.
Inverse redacts the opposite of what you matched

Turning Inverse on replaces everything that does not match the pattern. On a prompt, that removes the prompt. It has uses, and none of them is the one you reached this step for.

Verification

Test the pattern against a sample string before saving. A regex that matches nothing produces a guardrail that passes everything and looks healthy doing it.

Step 4 — Enforce a baseline organization-wide

Organization guardrails apply to every API request in the organization, with no config needed and nothing for a caller to opt into. This is the baseline that holds regardless of what a workspace or an application does.

▶ 4.1 — Set the input and output guardrails
  1. Go to Admin Settings → Organisation Guardrails.
  2. Add your input guardrail, your output guardrail, or both.
  3. Save.

The guardrails offered here are the same ones built in step 1, including partner checks.

Keep the organization baseline small

Every request in the deployment pays for these checks. A heavy organization guardrail with async false adds its latency to all traffic, including traffic that never needed it. Put the universal minimum here and the specific controls in workspace guardrails, which chapter 8 covers.

Verification

The setting saves and both slots show the guardrail you intended. Step 6 confirms enforcement with a real request.

▶ 4.2 — Know what you cannot exempt from the console

Some workspaces have a genuine reason to run without the organization baseline, an internal evaluation sandbox being the usual one.

Workspace exclusions have no console path today

Exemptions are managed per guardrail direction through the Admin API, authorized with a Strata Cloud Manager access token belonging to a service account that can administer the organization. Console support is stated as coming, and is not present.

If you want to stay inside the console, the alternative is to leave the organization slots empty and set the same guardrail on each workspace that needs it in chapter 8. That trades one setting for several and keeps every control visible in the interface.

Verification

You have decided between an organization baseline with API-managed exemptions and per-workspace guardrails, and recorded which one this deployment uses.

Step 5 — Attach a guardrail through a config

Beyond the organization baseline, a guardrail becomes active by being named in a config. This is how a specific application gets a specific control.

▶ 5.1 — Name the guardrails in the config

A config takes two keys, each holding a list of guardrail IDs:

KeyApplies to
input_guardrailsThe input, before the model is called
output_guardrailsThe output, after the model responds
 
{
  "retry": {
    "attempts": 3
  },
  "cache": {
    "mode": "simple"
  },
  "provider": "@openai-xxx",
  "input_guardrails": ["guardrails-id-xxx"],
  "output_guardrails": ["guardrails-id-yyy"]
}
An older hook syntax still works

The same effect can be written as before_request_hooks and after_request_hooks, each taking objects of the form {"id": "$guardrail_id"}. You will meet it in existing configs and in raw JSON guardrails. Prefer the two keys above for anything new.

Verification

The config saves and names the guardrail IDs recorded in step 1.

▶ 5.2 — Make the config reach the request

A config applies when a request references it, or when it is attached to an API key as that key's default. The second is what chapter 5 set up, and it is the stronger option because the caller writes nothing.

This step completes in chapter 9

A config needs a provider to route to, and the integration that provides it does not exist until chapter 9. Build the guardrails now, enforce the organization baseline now, and attach configs once there is something to call.

Verification

Recorded as an open item against chapter 9. The organization baseline from step 4 is already active and does not wait for it.

Step 6 — Verify the chapter

▶ 6.1 — Prove a guardrail fires

A guardrail that has never fired is a guardrail you have not tested. Prove it deliberately.

  1. Send a request that should fail the check, for example a prompt containing a test value your PII check targets.
  2. Open the log entry for that request and read the guardrail result.
  3. Send a request that should pass, and confirm it does.

What you should see:

ConfigurationExpected result
Async trueStatus 200, with the failure recorded in the log. The request completes normally.
Async false, deny falseStatus 246. The request still completes.
Async false, deny trueStatus 446. The request is killed and never reaches the model.
Redaction enabledStatus 200, and the stored prompt shows the replacement text rather than the original value.
Both halves matter

A check that fires on everything looks identical to a working control until the day it blocks legitimate traffic. Confirm the passing case as carefully as the failing one.

This needs a model to call

Until chapter 9 creates an integration there is nothing to route to. Record this check as an open item and run it as the first thing you do once an integration exists.

Verification

Both the failing and the passing request behave as the table predicts, for each guardrail you intend to rely on.

Two checks worth noticing

Model Whitelist and Required Metadata Keys are governance controls wearing a guardrail's clothing. Enforcing model choice and metadata through an organization guardrail reaches traffic that a config-based control would miss.

▶ PRO — LLM-based checks

An LLM check means a second model call

PRO checks evaluate with a model, so they cost tokens and add latency that a regular expression does not. With async false they sit directly in the request path. Measure one before enabling it across all traffic.

Bring your own

A custom guardrail is a webhook. The Webhook check in the BASIC catalog calls your endpoint and uses its answer as the verdict, which is how a model or rules engine you already run becomes a gateway guardrail.

Where guardrails do not run

Guardrails evaluate on inference endpoints where the gateway can extract text. Knowing the gaps matters, because an endpoint that runs no guardrail is a path around every control in this chapter.

EndpointInputOutput
/v1/chat/completionsYesYes
/v1/completionsYesYes
/v1/messages, AnthropicYesYes
/v1/responses, on POSTYesYes
/v1/prompts/{promptId}/completionsYesYes
/v1/embeddingsYesNo model output exists to evaluate
These endpoints run no guardrails at all

Assistants and threads, audio, images, files, batches, fine-tuning, moderations, models, prompt rendering without a model call, and retrieving a stored response with GET /v1/responses. If your applications use any of them, the controls in this chapter do not apply to that traffic and something else has to.

▶ Streaming, and what an output guardrail can actually do

Input and output guardrails behave very differently on a streamed response.

TypeOn a streaming request
Input guardrailsEvaluated before the stream starts. A failure with deny true blocks the stream with 446 before any token is sent.
Output guardrailsEvaluated on the full response after the stream completes. Results are informational only.
An output guardrail cannot stop a streamed response

By the time the full text is assembled and checked, the caller already has every token. No fallback or retry is triggered. An output control that must actually prevent delivery cannot be built on streaming, and the only enforcement point left is the input side.

Results arrive as a hook_results chunk after the [DONE] marker. To see them, set:

x-portkey-strict-open-ai-compliance: false

The header defaults to true, which hides those chunks. Input guardrail results appear in the first chunk on /chat/completions, or as a separate event on /messages. For Anthropic /messages streaming, hook_results are not reachable through the Anthropic SDK, so use raw HTTP to see them.

The streaming, caching, and A2A guide covers the streaming path in more depth.
