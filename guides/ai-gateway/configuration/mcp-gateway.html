MCP Gateway

Chapter 10 of 13. Putting MCP servers behind one authenticated endpoint, deciding which teams and which tools they reach, and governing the calls that result

Configuration Hub Previous: Integrations Workspaces

Client, gateway, server

Connected directly, every agent needs its own credentials and its own configuration for every MCP server it touches. Ten agents and six servers is sixty credential decisions, and no record of which agent called what.

The MCP gateway sits between them as a proxy. Clients authenticate once to the AI Gateway. The gateway checks whether that identity may reach the requested server and tool, injects the credential the upstream server expects, proxies the call, and logs it.

Two authentication layers do that work, and they are independent of each other.

LayerWho proves whatOptions
GatewayThe client proves its identity to the AI GatewayAPI key, AI Gateway OAuth 2.1 with PKCE, or an external IdP such as Okta, Entra ID or Auth0
UpstreamThe AI Gateway proves its identity to the MCP serverNone, OAuth 2.1, Client Credentials, or Headers
Users never see the upstream credential

A developer holds a gateway API key or an OAuth session. The token for GitHub, Slack or your internal API is held by the gateway and injected at call time. Revoking a person's access is a gateway change, not a credential rotation, and that is the whole reason to centralize the registry rather than let each team wire its own servers.

A public server still needs gateway authentication

The two layers are genuinely separate. A server whose upstream auth type is None is open at the far end, but reaching it through the gateway still requires a valid gateway identity. Setting upstream auth to None does not make the server anonymous to your organization, and it does not exempt the calls from logging, access control or guardrails.

Prerequisites

  • Chapters 1 to 9 complete, with at least one workspace holding an API key
  • Org Admin or Org Owner to add servers to the registry and provision workspaces
  • Workspace Manager or Workspace Admin to control which users inside a workspace reach a server
  • Each server reachable over HTTP, speaking MCP over Streamable HTTP transport
  • For rate limits, gateway 2.18.0 or higher and backend 1.24.0 or higher
STDIO servers need an HTTP front door first

The gateway proxies remote servers over HTTP. A local STDIO server cannot be registered as it stands: expose it as an HTTP endpoint, then register that endpoint. This is the most common reason a server that works on a laptop cannot be added to the registry.

Step 1 — Add the server to the registry

▶ 1.1 — Open the registry
  1. Go to MCP Registry in the organization settings sidebar.
  2. Click Add MCP Server.

The registry is the organization-wide catalog. Everything a workspace can see later has to exist here first.

Verification

The add server form is open. Nothing has been created yet.

▶ 1.2 — Describe the server
FieldWhat to enter
NameThe display name teams will see, such as Internal Documentation
Short DescriptionOne line on what the server is for. Developers browsing the workspace MCP page read this before anything else.
SlugThe URL identifier, such as internal-docs
Server URLThe server's own MCP endpoint
Server TypeHttp
Auth TypeHow the gateway authenticates to this server. Step 2 covers the choice.
The slug becomes part of every client configuration

The connection URL is built from it as https://aigw.portkey.ai/m/{slug}/mcp, and that string gets pasted into every developer's client config. Changing it later means every client breaks until each one is edited. Choose it as deliberately as a hostname.

Verification

Every field is populated and the slug is the one you intend to live with.

▶ 1.3 — Test the connection, then save
  1. Click Test Connection.
  2. When the test succeeds, click Add Server.

Testing before saving is worth the extra click. A server saved with an unreachable URL looks identical in the list to one that works, and the difference only surfaces when a developer's first tool call fails.

Verification

The server appears in the registry list. Open it and the Overview tab reports a health score, uptime and average response time rather than an error.

Step 2 — Authenticate the gateway to the server

This is the upstream layer from the table above. It answers one question: what does this particular MCP server want to see before it will accept a call?

Auth TypeUse whenToken scope
NonePublic servers that require no credentialNot applicable
OAuth 2.1Services holding user-specific data, such as Linear, GitHub or SlackPer user. One person's access is separate from another's.
Client CredentialsService accounts and shared resourcesShared across all users
HeadersServers using a static API key or tokenShared across all users
▶ 2.1 — OAuth servers that support dynamic client registration

Many MCP servers implement OAuth 2.1 with Dynamic Client Registration. For these there is nothing to prepare.

  1. Select OAuth 2.1 as the auth type.
  2. Save the server.

The gateway registers itself as an OAuth client automatically. The first time a user calls a tool, the gateway returns an authorization URL, the user completes consent, and the gateway stores and refreshes that user's token from then on.

Verification

The server's Overview tab shows the auth type as OAuth and a grant type. No client ID was required from you.

▶ 2.2 — OAuth servers that need an app created by hand

Some services, GitHub among them, do not support dynamic client registration. These need an OAuth app created on the service side first.

  1. Create an OAuth App in the service's own developer settings.
  2. Set its callback URL to https://aigw.portkey.ai/m/oauth/upstream-callback.
  3. In the gateway, open the server's Advanced Configuration.
  4. Enter the client_id, client_secret and redirect_uri from the app you just created.
  5. Save.
The callback URL is fixed

It is the gateway's own endpoint, identical for every server you register this way. A mistyped callback produces a consent screen that completes and then fails on redirect, which reads like a credential problem and is not.

Verification

Trigger the OAuth flow once as a test user. Consent completes and returns you to the gateway rather than to an error page.

▶ 2.3 — Static tokens with Headers
  1. Select Headers as the auth type.
  2. Enter the header name and the token value the server expects.
  3. Where the token already exists as a secret reference from chapter 3, use the reference rather than pasting the value.
Header auth is shared, so logs are the only attribution

Every user of this server presents the same upstream token, which means the upstream service cannot tell your users apart. If that server needs to know who is calling, either use per-user OAuth or forward identity explicitly with step 3. Gateway logs still attribute each call correctly, but the upstream server's own logs will not.

Verification

The credential is stored and the server's Overview tab reports the auth type as Headers.

Step 3 — Forward user identity to internal servers

Skip this step for third-party servers. It applies when the server is yours and needs to know which person is behind a call, which is the usual case for anything that enforces its own per-user authorization.

Configure it under the server's Advanced Configuration. Three methods are available, and they trade verification strength against implementation effort.

MethodWhat the server receivesChoose when
jwt_headerA JWT signed by the gateway, carrying the claims you listThe server must be able to prove the identity was not forged
claims_headerThe same claims as plain JSON, unsignedThe server sits in a private network and trusts the gateway already
bearerThe original token, unchangedThe server validates tokens from the same IdP the user authenticated against
▶ 3.1 — Signed JWT, the verifiable option 
{
  "user_identity_forwarding": {
    "method": "jwt_header",
    "include_claims": ["sub", "email", "workspace_id"],
    "header_name": "X-User-JWT"
  }
}

Your server verifies the signature against the gateway's public keys, published at:

GET https://aigw.portkey.ai/m/.well-known/jwks.json
Verification

Call a tool and have the server log the header it received. The JWT is present, and verifying it against the JWKS endpoint succeeds rather than merely parsing.

▶ 3.2 — Plain claims, the simple option 
{
  "user_identity_forwarding": {
    "method": "claims_header",
    "include_claims": ["sub", "email", "workspace_id"],
    "header_name": "X-User-Claims"
  }
}
Unsigned claims are a trust assertion, not proof

Anything that can reach your server directly can set this header itself. That is acceptable only where the server is unreachable except through the gateway. If the server has any other ingress path, use jwt_header instead, because a header a caller can forge is not an authorization control.

Verification

The server receives the claims and, separately, you have confirmed it cannot be reached except through the gateway.

Step 4 — Provision access

▶ 4.1 — Choose the workspaces, at the organization level
  1. Click MCP Registry in the sidebar.
  2. Click the server.
  3. Open the Access Control tab.
  4. Toggle on each workspace that should reach this server.

The tab also offers Automatically provision this integration for new workspaces, which includes every workspace created from then on.

Auto-provisioning is a standing decision, not a convenience

Enabled, it means a workspace created next quarter reaches this server on its first day, without anyone revisiting the question. That is right for a general-purpose documentation server and wrong for anything touching production or customer data. Decide per server rather than setting it once as a default.

Verification

The intended workspaces are enabled and no others. Count them against your intended list rather than scanning for the ones you remember enabling.

▶ 4.2 — Choose the users, at the workspace level

Granting a workspace access does not mean every member of it should have access. This second level is set by a Workspace Manager or Workspace Admin.

  1. Go to the MCP page in the workspace sidebar.
  2. Click the server.
  3. Use the User Access tab to toggle individual users.
Verification

A user you did not enable cannot see the server on their own MCP page.

Step 5 — Decide which tools exist

A server exposes tools, resources and prompts. Reaching the server is not the same decision as being allowed to call everything on it, and the Capabilities tab is where the difference is set.

  1. Open the server and select the Capabilities tab.
  2. Toggle individual tools, or use Enable All and Disable All for bulk changes.
Set atByScope
MCP Registry → server → CapabilitiesOrg Admins and OwnersOrganization-wide
MCP → server → CapabilitiesWorkspace Managers and AdminsThat workspace only
Disabled tools are hidden, not merely refused

A disabled capability does not appear in tool listings, so an agent never learns it exists and will not plan around it. Called directly by something that knew the name already, it returns an error. That combination is what makes this usable for blocking destructive operations rather than only discouraging them.

Verification

List the tools from a connected client. The disabled ones are absent from the response, not merely greyed out in the console.

Step 6 — Make the first tool call

▶ 6.1 — Copy the connection URL
  1. Open the MCP page in the workspace sidebar.
  2. Copy the connection URL for the server.

It follows the slug chosen in step 1.2:

https://aigw.portkey.ai/m/{server-slug}/mcp
Verification

The URL contains the slug you intended. If the server is absent from this page, access was not provisioned in step 4.

▶ 6.2 — Option A, OAuth with no credential in the file 
{
  "mcpServers": {
    "internal-docs": {
      "url": "https://aigw.portkey.ai/m/internal-docs/mcp"
    }
  }
}

On first use the client prompts for authentication through OAuth 2.1 with PKCE. The session is stored and refreshed after that. This is the right default for people working interactively in Claude Desktop, Claude Code, Cursor or VS Code, because there is no key to create, rotate or leak.

Verification

The client prompts once, then lists the server's enabled tools.

▶ 6.3 — Option B, an API key for non-interactive callers 
{
  "mcpServers": {
    "internal-docs": {
      "url": "https://aigw.portkey.ai/m/internal-docs/mcp",
      "headers": {
        "Authorization": "Bearer <API_KEY>"
      }
    }
  }
}

Use a workspace user API key. Pipelines, backend services and scheduled agents cannot complete an interactive OAuth flow, so this is their path.

The key needs MCP Invoke permission explicitly

A workspace key that works perfectly for model calls will be refused here if MCP Invoke was not enabled on it. The failure arrives as an authorization error on the first tool call rather than at connection time, which sends people looking at the server configuration instead of the key. Check the key before debugging anything else.

Verification

Call one tool and confirm two things: the client receives the result, and the call appears in Logs attributed to the right user, workspace and tool.

Step 7 — Rate limit the tool calls

Version floor

MCP rate limits require gateway 2.18.0 or higher and backend 1.24.0 or higher. Below those versions the policy is accepted and silently never enforced, so confirm the version before relying on a limit you have configured.

MCP rate limits run on the same policy engine as the model rate limits from earlier chapters, distinguished by a target of mcp_tools. Existing model policies are unaffected, and the two sets do not interact.

Policies are workspace-scoped and limit either request count or token consumption, per minute, hour, day or week.

KeyMatches on
api_keyA specific API key ID
workspace_idA workspace
mcp_serverA server slug
mcp_toolAn individual tool name
metadata.*Any request metadata key, such as metadata._user

Conditions decide which requests a policy covers and combine with AND. Group-by keys decide how the counter is bucketed, so grouping by user gives each person their own allowance rather than a shared pool.

{
  "name": "Per-user MCP rate limit",
  "target": "mcp_tools",
  "type": "requests",
  "unit": "rpm",
  "value": 50,
  "conditions": [
    { "key": "metadata._user", "value": "*" }
  ],
  "group_by": [
    { "key": "metadata._user" }
  ],
  "status": "active"
}
api_key does not exist in OAuth flows

Requests authenticated through OAuth or an external IdP carry no API key, so a policy conditioned on api_key never matches them and they pass unlimited. If any of your users connect the way step 6.2 describes, condition on mcp_server, mcp_tool or metadata.* instead. This is the most common way an MCP rate limit appears configured and turns out to cover nobody.

Verification

Exceed the limit deliberately with a test caller. The request is rejected with a rate limit error, and a caller in a different group-by bucket is still served.

Step 8 — Guardrail the tool inputs and outputs

Tool arguments can carry sensitive data outward and tool results can bring confidential data back. Guardrails intercept tools/call at either end, again using target: "mcp_tools" to stay separate from the model guardrails in chapter 6.

run_onInspectsRuns
inputThe arguments sent to the toolBefore the tool executes
outputThe result the tool returnedAfter the tool executes

Set both with ["input", "output"]. Guardrails apply at the workspace level as a default for every server, or at the server level for a specific one. Where both exist, the server-level guardrail runs in addition to the workspace default rather than replacing it.

Checks available for MCP tool calls include regex match and replace, contains, ends with, webhook, JSON schema, JSON keys, sentence, word and character counts, contains code, valid URLs, case checks, not null, and the required metadata key checks.

The model-side checks are not available here

PII detection, content moderation, language detection and the third-party provider checks apply to llm targets only. They cannot be mapped to mcp_tools. A guardrail strategy that relies on PII detection for model traffic therefore has no equivalent on the MCP path, and the nearest substitute is a regex check or a webhook to your own service. Plan for that gap rather than discovering it after a tool starts returning records.

By default a mapping covers every tool on the server. Pass mcp_integration_capability_ids to narrow it to specific tools.

Verification

Call a tool with an argument the guardrail should stop. The call is refused at the input stage, before the upstream server is reached, and the refusal is visible in the logs.

Circuit breakers

Not yet available

Circuit breakers for MCP servers are announced but not shipped. There is no configuration to apply, and nothing in this chapter depends on them. Early access is handled through Palo Alto Networks support.

The published intent is automatic detection of unhealthy upstream servers by failure rate and response time, fast failure instead of waiting on a timeout, periodic recovery checks, configurable per-server thresholds, and circuit state visible in the dashboard as closed, open or half-open.

Until it ships, an unhealthy upstream server fails per request. If a server's reliability is a live concern, the Overview tab's health score and average response time are the available signal, and they are observed rather than enforced.

The three access levels

Access to an MCP tool is decided three times, and the model is subtractive. Each level can only remove what the level above granted, so no level can widen access beyond its parent.

LevelSet inDecidesRole needed
OrganizationMCP RegistryWhich servers exist at allOrg Admin or Owner
WorkspaceAccess Control tabWhich teams reach a serverOrg Admin or Owner
UserUser Access tabWhich people in a team reach itWorkspace Manager or Admin
Troubleshoot downward, in that order

When a developer cannot see a server they expect, the question is which level removed it, and checking in order settles it in three looks. Capabilities sit underneath all three: a user with full access to a server still cannot call a tool disabled in step 5.
