Workspaces

Chapter 8 of 13. Creating the team boundaries, filling them from your directory, issuing the keys applications actually use, and closing the checks deferred from chapters 2, 4 and 5

Configuration Hub Previous: Plugins Next: Integrations Chapter 2: Identity

What a workspace is

A workspace is a sub-organization: a boundary around a team's data, members, resources, and visibility. Everything you built in chapters 1 to 7 was organization-wide. This is where the deployment divides.

One fact shapes everything else in this chapter:

Completion APIs are always workspace-scoped

Model calls can only be made with a workspace API key. There is no organization-level key that calls a model. Until a workspace exists and holds a key, no application can use the gateway at all, which is why this chapter blocks every application team waiting on you.

This chapter also closes three items held open earlier:

You already have one workspace

Every organization carries a default Shared Team Workspace. It cannot be deleted. Treat it as the catch-all it is, and avoid letting production traffic settle there by default, because a workspace you cannot remove is a poor place for anything you may later need to separate.

Prerequisites

  • Chapters 1 to 7 complete
  • An Organization Owner or Organization Admin account, because only those roles create workspaces
  • The team structure you want to reflect, from step 1
  • Values for any fields the workspace metadata schema from chapter 5 marks required
  • For directory mapping, a successful sync state from chapter 2 and the names of the groups to map

Step 1 — Plan the layout before creating anything

▶ 1.1 — Choose what a workspace represents

Pick one axis and hold to it. Mixing axes produces a list nobody can reason about six months later.

AxisWorks whenWatch for
By teamBudgets and access follow organizational lines. The most common choice.Teams that share an application end up splitting its traffic across two workspaces.
By applicationCost attribution per product matters more than per team.The count grows quickly, and each one needs members and keys maintained.
By environmentDevelopment, staging and production need different guardrails and budgets.Three workspaces per team multiplies the administration.
One-to-one with directory groups, if you are mapping

A directory group maps to exactly one workspace, and a workspace takes exactly one group. If membership will be driven from your directory, the workspace layout has to mirror a group layout that already exists, or someone has to create the groups first.

Verification

You have a written list of workspaces, the axis they follow, and for each one the directory group it will map to or the fact that it will be populated by hand.

Step 2 — Create a workspace

▶ 2.1 — Create it
  1. Open the workspace dropdown in the sidebar.
  2. Create a new workspace and give it a name matching your plan from step 1.
  3. Complete any metadata fields the schema from chapter 5 requires.
The metadata schema proves itself here

If chapter 5 defined a workspace metadata schema with required fields, the creation form demands them now. A form that does not is the signal that the schema saved without its required array, and this is the cheapest moment to find that out.

Verification

The workspace appears in the dropdown, and it inherited the organization defaults: the request logging mode from chapter 5, the saved-only setting from chapter 4, and the organization guardrails from chapter 6.

▶ 2.2 — Confirm what it inherited

A new workspace takes the organization settings as they stand at the moment of creation. Confirm rather than assume, because anything set after this point does not reach back.

InheritedSet inChangeable per workspace
Saved-only modeChapter 4No, it follows the organization
Request logging modeChapter 5Only if the organization allows the override
Organization guardrailsChapter 6No, exemptions are Admin API only
Metadata requirementsChapter 5No
Verification

Each inherited setting reads as you expect from inside the new workspace. A mismatch means the organization setting changed after an earlier workspace was created, and the two now differ.

Step 3 — Add members

Membership arrives one of two ways. Both require the person to be an organization member first, which is what chapter 2 set provisioning up to do.

Which path should I pick?
  • Directory mapping — membership follows a directory group automatically, including removals. This is the deferred work from chapter 2 and the right answer for anything long-lived.
  • Manual invitation — a workspace admin or manager invites named organization members. Right for small or short-lived workspaces, and for people who are not in a suitable group.
▶ 3.1 — Map a directory group to the workspace
  1. Go to Admin Settings → Authentication → Directory Sync.
  2. In Group Mappings, click Add Mapping.
  3. Select a CIE Group from the dropdown, which lists the groups in your connected directory.
  4. Select the Workspace to map it to.
  5. Click Add.

Members of that group are provisioned into the workspace automatically from the next sync.

The mapping is strictly one to one

A group maps to one workspace, and a workspace accepts one group. A team whose membership spans two directory groups cannot be assembled this way, and the usual fix is a new group in the directory rather than a second mapping.

Verification

The mapping appears in the list. Members take up to 15 minutes to arrive on the delta sync, or press Full Sync to force it.

▶ 3.2 — Confirm the members arrived
  1. Go to AI Gateway → Workspace Control.
  2. Open the workspace and go to the Members tab.

Each entry shows the display name from the directory's common name attribute, the email derived from the identity attribute you chose in chapter 2, when the user was provisioned, and when their membership last changed.

Fewer members than the group holds means an allowed domain is missing

Users whose email domain is not verified on the organization are skipped silently, and users missing the selected identity attribute are skipped too. Both were set in chapter 2, and both fail quietly here rather than at the point you configured them.

Verification

The member count matches the directory group. Add a user to the group in your directory, force a sync, and confirm they appear, which proves the ongoing path rather than just the initial load.

▶ 3.3 — Understand what removing a mapping does

Deleting a mapping with the trash icon removes every user it provisioned from that workspace, immediately.

There is no undo

Recovery means re-creating the mapping and waiting for a sync to re-provision everyone. Anything those users held in the workspace is inaccessible to them in the meantime, and a mapping deleted to tidy up during business hours takes a team offline.

Verification

Nobody removes a mapping without knowing this. Say it out loud to whoever else administers the organization.

▶ 3.1 — Invite organization members

Workspace admins and managers invite from the pool of existing organization members and assign a workspace role as they do.

RoleGrants
AdminFull control of the workspace, including assigning the Admin role and creating API keys.
ManagerTeam and resource management, bounded by the Security tab settings from chapter 4.
MemberRead-only on workspace resources.
Someone not in the organization cannot be invited

The invitation list contains organization members only. A person who does not appear has not been provisioned yet, which is a chapter 2 problem rather than a workspace one.

Verification

Each invited person appears on the Members tab with the role you assigned.

▶ 3.2 — Record who maintains the list

Manual membership has no leaver process attached to it. When someone changes team or leaves, nothing removes them from the workspace unless a person does it.

Name an owner for every manually populated workspace

Directory-mapped workspaces deprovision on their own. Manual ones accumulate former members indefinitely. If you cannot name who reviews the list and how often, map the workspace to a directory group instead.

Verification

Every manually populated workspace has a named owner and a review cadence recorded outside the console.

Step 4 — Issue workspace API keys

These are the keys applications use. Both types are scoped to the workspace and can only act within it.

▶ 4.1 — Choose service or user
TypeTied toUse for
ServiceNobody. A shared key.Applications, automated processes, and integrations.
UserA specific workspace member.Individual access, and per-person attribution in logs and analytics.
User keys are what make per-user data visibility work

The Data Visibility settings in chapter 4 scope what a manager or member sees to data generated by their own API keys. That only separates anything if people hold user keys. A workspace where everyone shares one service key gives every member the same view whatever those settings say.

Verification

You can state which type each planned consumer gets, and the choice is consistent with the visibility model from chapter 4.

▶ 4.2 — Create a key
  1. Select the workspace from the Workspace dropdown at the top of the page.
  2. Go to AI Gateway → Security Keys. The page has a Service tab and a User tab.
  3. Click + Create New.
  4. Choose the API Key Type. For a user key, pick the member under Select User, which lists only people already in this workspace.
  5. Enter an API Key Name, which is required.
  6. Optionally add a short description, a configuration, and metadata.
  7. Click Next: Set Permissions and set permissions per resource: Agents, Completions, Logs, MCP and Prompts, each with actions such as invoke, write and render.
  8. Click Create Gateway API Key.
  9. Copy the key.
The key is shown once

It cannot be retrieved afterwards. Put it in your secrets manager before clicking Copy and Close. Recovering a lost key means creating a replacement and updating whatever held the old one.

Attach the default config here if chapter 5 defined one

The Configuration field is where the enforced default config from chapter 5 attaches. That config needs an integration to reference, so it arrives in chapter 9, and keys issued before then are updated once it exists.

Verification

The key appears on the correct tab with the name you gave it, and the value is stored outside the console. A user key shows the member it belongs to.

Step 5 — Set workspace guardrails

▶ 5.1 — Choose a default input and output guardrail
  1. In the sidebar, click the workspace and select the edit option.
  2. In Edit Workspace, choose an Input Guardrail and an Output Guardrail.
  3. Save.

These apply to every request made within the workspace, on top of any organization guardrail from chapter 6.

Only guardrails created in this workspace are offered

The dropdowns list guardrails belonging to the workspace, not the organization's library. A guardrail built at the organization level for everyone is not selectable here, so a control you want in several workspaces is either an organization guardrail or a guardrail rebuilt in each one.

This is the console-only route around the exclusion gap

Chapter 6 noted that exempting a workspace from an organization guardrail needs the Admin API. If you want every control visible in the console, leave the organization slots empty and set guardrails per workspace here. You trade one setting for several and gain the ability to leave a sandbox uncovered without an API call.

Verification

Both slots show the guardrail you intended. Proving they fire needs a model to call, which arrives in chapter 9.

Step 6 — Set budgets and rate limits

Workspace limits sit between the key limits from chapter 5 and the integration limits in chapter 9. They stop one team consuming a disproportionate share regardless of how many keys it holds.

▶ 6.1 — Open the budget controls
  1. In the sidebar, click Workspace Control for the workspace.
  2. Select the Budget Allocation tab.

Who can do this:

  • Organization owners and organization admins
  • Workspace admins
  • Workspace managers, but only if an organization admin enabled workspace management permissions in Admin Settings
Verification

The tab opens. If it does not and you expected it to, check the workspace management permission rather than the role.

▶ 6.2 — Set a rate limit
  1. Toggle on Add Rate Limit.
  2. Choose Requests or Tokens.
  3. Enter the value in Set Rate Limit.
  4. Choose an interval: per minute, per hour, or per day.
A workspace rate limit rejects every key at once

When the workspace reaches its limit, all subsequent requests are rejected whichever key made them. A single misbehaving application therefore takes out every other application in the same workspace. Where one noisy workload must not affect its neighbors, separate workspaces rather than a shared limit is the answer.

Verification

The limit is above the combined expected peak of everything in the workspace, not above the peak of its largest consumer.

▶ 6.3 — Set a budget and an alert threshold
  1. Toggle on Add Budget.
  2. Choose Cost or Tokens.
  3. Enter the amount in Budget Limit.
  4. Set an Alert Threshold, which notifies before the full budget is consumed while the workspace keeps running.
  5. Choose a periodic reset.
ResetBehavior
No periodic resetApplies until exhausted.
Reset weeklyEvery Sunday at midnight UTC.
Reset monthlyThe first of each month at midnight UTC.
Custom reset daysAny interval from 1 to 365 days. Admin API only, and mutually exclusive with the options above.
Always set the alert threshold

Without one, the first signal that a workspace is out of budget is the workspace stopping. The threshold is the only warning between normal operation and a hard stop, and notifications go to organization administrators and owners.

Custom reset intervals are an API-only option

The console offers none, weekly and monthly. A custom interval, and a specific first-reset date, are set through the Admin API. Where a console-only deployment needs a different cycle, monthly is the closest available and the difference is worth stating to whoever owns the budget.

Verification

Each workspace with a budget has an alert threshold and a reset period, and the recipients of those alerts know what the workspace does.

  • Members arrived, by mapping or by invitation, and the count matches the source.

Deleting a workspace

▶ Removing a workspace you no longer need

A workspace cannot be deleted while it holds resources. Prompts, prompt partials, providers, configs and guardrails all have to go first.

  1. Open the workspace menu in the sidebar.
  2. Select the workspace.
  3. Click the delete option next to its name.
  4. If a warning lists remaining resources, remove those and return.
  5. Type the workspace name in the confirmation field.
Deletion is permanent

There is no undo and no recovery. Export anything in the workspace you may need, including logs, before starting.

The Shared Team Workspace cannot be deleted

The default workspace is permanent. If traffic has accumulated there that belongs elsewhere, the move is to create the proper workspace and repoint the applications, not to remove the original.

Verification

The workspace is gone from the dropdown, and any directory group mapped to it has had its mapping removed too, since the mapping has nowhere left to point.
