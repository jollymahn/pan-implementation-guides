Agent Gateway

Chapter 11 of 13. Registering A2A agents, putting a virtual server in front of each one, and deciding which workspaces reach which skills

Configuration Hub Previous: MCP Gateway Workspaces

Registry and virtual server

The agent gateway is the same shape as the MCP gateway from chapter 10: a proxy between your clients and an upstream server, holding the credentials and the access decisions. Two components make it up.

ComponentWhat it does
Agent RegistryThe catalog of every agent provisioned in the organization, with access control over the agent and over the individual skills it exposes
Agent ServersVirtual servers. Each one is a client to your upstream agent server and a server to your downstream agent clients.
The agent catalog and the Agent Registry are the same thing

Two names appear in the documentation for one surface. The catalog is the registry viewed as a list. There is no second place to visit and nothing to keep in step between them.

The protocol is A2A. Agents that speak it can be registered; the gateway fetches each agent's card to discover what it offers, then exposes it on a virtual URL of its own.

The agent path is not the MCP path

An MCP server is reached at /m/{slug}/mcp and an agent at /agent/{slug}. The two are easy to transpose when configuring both in the same sitting, and the resulting 404 says nothing about which half is wrong. On self-hosted deployments, substitute your own gateway hostname for aigw.portkey.ai in both.

Prerequisites

  • Chapters 1 to 10 complete
  • An A2A agent server, reachable at a public http or https endpoint
  • Organization admin rights to register agents and provision workspaces
  • For the upstream URL protections described below, backend 1.16.1 or higher
No agent of your own yet

Two public A2A agents exist for exactly this, and registering one is the fastest way to prove the path end to end before your own agent is ready. A hello-world agent is published at hello.a2aregistry.org, and the A2A project's Python tutorial covers hosting your own.

Step 1 — Scope the API key

Do this first. An agent registered perfectly still refuses every call if the key invoking it was never scoped for agents, and the error arrives at call time rather than at registration.

▶ 1.1 — Enable the Agent Gateway toggle and the invoke scope
  1. Open the API Keys page and create or edit the key.
  2. Turn on the Agent Gateway toggle in the key's permissions.
  3. Enable the agents.invoke scope on any key that will actually call an agent.
  4. Save.
Two separate switches, and both are needed to invoke

The toggle admits the key to the agent gateway at all. The agents.invoke scope permits calling agents with it. A key carrying the toggle but not the scope reaches the gateway and is refused at invocation, which reads like an agent configuration fault and is not.

Verification

The key's permission summary lists the Agent Gateway toggle as on and agents.invoke among its scopes.

Step 2 — Register the agent

▶ 2.1 — Point the registry at the upstream server
  1. Open the Agent Registry.
  2. Add an agent and enter the upstream agent server URL.
  3. Give it a slug. As in chapter 10, the slug becomes the URL clients use, so choose it as deliberately as a hostname.
Verification

The upstream URL is entered and the slug is the one you intend to live with.

▶ 2.2 — Fetch the agent card
  1. Click Fetch Agent Card.

This is the validation step, not a convenience. Fetching the card is how the gateway discovers the agent's transport and authentication schemes and confirms the upstream server is reachable and genuinely speaks A2A.

A card that will not fetch is a registration that will not work

Resist saving past a failed fetch to come back to it. The agent appears in the registry either way, and the difference only surfaces when someone's first invocation fails. The common causes are an upstream URL that is not public, an authentication scheme the gateway was not given credentials for, and a server that answers HTTP but does not implement A2A.

Verification

The card returns and the form shows the discovered transport and authentication schemes rather than an error.

Step 3 — Provision workspaces

Registration makes the agent exist. Provisioning decides who reaches it, and the two are separate on purpose: an agent can sit registered and unprovisioned while it is being evaluated.

  1. On the agent's configuration, select the workspaces that should have access.
  2. Save.
Verification

The agent appears on the Agents tab for a user in a provisioned workspace, and is absent for a user in one you did not select.

Step 4 — Control the skills

An agent exposes skills and capabilities, and reaching the agent is not the same decision as being allowed to use everything it can do. This mirrors the capabilities model for MCP tools in chapter 10.

  1. Open the registered agent.
  2. Enable or disable individual skills and capabilities.
Skill control is organization-wide today

Access to the agent and to its skills is set once, for the organization. Per-user access and per-workspace skill control are announced but not shipped, which the reference section below sets out. Where one team needs a narrower set of skills than another, the available answer today is registering the upstream agent twice under two slugs with different skills enabled.

Verification

The agent card fetched through the virtual server in step 5 lists only the skills you left enabled.

Step 5 — Call the agent

▶ 5.1 — Get the virtual server URL
  1. Open the Agents tab.
  2. Copy the agent server URL.

It is built from the slug:

https://aigw.portkey.ai/agent/{agent-slug}
Verification

The URL carries your slug. If the agent is missing from this tab, step 3 did not provision your workspace.

▶ 5.2 — Swap the URL and fetch the card through the gateway

Integration is a substitution. Replace the upstream agent server URL in your client with the virtual one, and add the API key from step 1.

curl --location --request POST \
  'https://aigw.portkey.ai/agent/{agent-slug}/.well-known/agent.json' \
  --header 'Content-Type: application/json' \
  --header 'Authorization: Bearer {API_KEY}'

Fetching the card through the virtual server is the cleanest first call, because it exercises the key, the registration and the skill configuration in one request without invoking any agent logic.

Verification

Three things at once. The card returns, it lists only the skills left enabled in step 4, and the request appears in Logs attributed to the right key and workspace.

▶ 5.3 — Point the real client at it

With the card returning, change the base URL in the application itself. An A2A client resolves the card from the base URL, so no other change is normally required.

BASE_URL = "https://aigw.portkey.ai/agent/{agent-slug}"
Every request through the virtual server is logged

This is the point of the substitution. Calls that went directly to the upstream agent were invisible; calls through the virtual server carry the key, workspace and skill into the same log stream as the model and MCP traffic from earlier chapters.

Verification

The application behaves as it did against the upstream server directly, and its traffic now appears in the gateway logs.

Upstream URL restrictions

From backend 1.16.1 the gateway applies SSRF protections when fetching an agent card. The upstream URL must be a public http or https endpoint, and three categories are rejected outright.

RejectedWhy
Private IP addressesAn agent registered against an internal address would turn the gateway into a probe for your private network
Cloud metadata hostsThe classic SSRF target, reachable from inside a cloud network and holding instance credentials
URLs containing a # fragmentFragments let a crafted URL read as one host to a validator and another to a fetcher
An agent on a private network cannot be registered as it stands

This is a deliberate protection rather than a gap, and it has the same shape as the STDIO restriction for MCP servers in chapter 10. Give the agent a public endpoint, with its own authentication, and register that. Do not reach for a workaround that makes the gateway fetch from inside your network.

Not available yet

Three access controls are announced and not shipped. None of them has a configuration surface today, and a design that depends on any of them is a design waiting on a release.

  • Access control for specific users, as distinct from workspaces
  • Skill-level access scoped to a particular workspace
  • Skill-level access scoped to a particular user

The practical consequence is in step 4. Skills are enabled or disabled for the organization as a whole, so two teams needing different subsets of one agent's skills is not expressible in a single registration. Registering the upstream agent twice under two slugs is the available answer, at the cost of two entries to keep in step.

Compare the MCP model before assuming parity

Chapter 10's three access levels, including per-user control through the workspace User Access tab, do not have equivalents here yet. Agent access is organization and workspace scoped only. Carrying the MCP mental model across is the likeliest source of a wrong assumption in this chapter.
