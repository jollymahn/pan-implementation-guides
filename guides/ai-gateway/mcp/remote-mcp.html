Remote MCP

The AI Gateway feature that lets a model provider use MCP tools during inference, the two places those tools can run, the @portkey-mcp prefix that keeps execution inside your own environment, and the security consequences of letting the provider run the tool instead

All MCP Guides MCP Registry Remote MCP Observability Troubleshooting Configuration Chapter 10 Provider Integrations

What this covers

Remote MCP is not the MCP Gateway. The MCP Gateway proxies an MCP client, such as an IDE or an agent framework, to an MCP server that an administrator registered. Remote MCP sits on the inference path instead: an application sends a model request to the AI Gateway, the request names MCP tools, and the model calls those tools while it is answering. The two features share the letters MCP and nothing else about their surface, their configuration or their audience.

This page covers the inference-path feature. It sets out the two places an MCP tool can execute, the request fields and the beta header that choose between them, how a request reaches a server that already exists in the MCP Registry, and the case where a private server leaves only one option open.

How this differs from the MCP Gateway

Where the tool runs

A remote MCP request executes its tools in one of two places, and the request body decides which. Gateway execution runs the tool inside your own environment and is selected with the @portkey-mcp prefix. Provider execution hands the model provider a server_url and lets the provider's own infrastructure call the server.

PropertyGateway execution, @portkey-mcpProvider execution, server_url
Where tools run Within your own VPC. On provider servers.
Data exposure MCP credentials stay in your environment. Tokens may reach provider training data and audit pipelines.
User attribution Attributed through your service or user API key. None.
Audit and logging Executions are logged and auditable. No execution logging and no security controls.

The three rows below the first are the reason a customer cares. Under provider execution the credential the server needs travels to the provider, and the tokens exchanged with that server may reach provider training data and provider audit pipelines. No per-user attribution is recorded, so a tool call cannot be traced back to the person whose request triggered it. No execution logging exists, so the gateway's own observability surfaces show the model call without the tool calls that happened inside it.

Provider execution removes the controls the gateway exists to apply

A tool executed on provider infrastructure passes through none of the gateway's logging, none of its guardrails and none of its attribution. An organization that adopted the AI Gateway to get an auditable record of model use loses that record for every tool call made this way, while the model call itself still appears in the logs and looks complete.

Provider execution against Anthropic

Anthropic gates its own MCP client behind the header anthropic-beta: mcp-client-2025-04-04 and takes the servers in an mcp_servers array. Each entry carries:

  • type — url is the only supported value.
  • url — must start with https.
  • name — unique per request, and the value that identifies the server in mcp_tool_call blocks.
  • tool_configuration — optional, holding enabled and allowed_tools.
  • authorization_token — optional.

Responses add two content block types, mcp_tool_use and mcp_tool_result. Everything in the right-hand column of the table above applies to this path.

Gateway execution

Two things select gateway execution: a beta header on the request, and a prefix on the server name inside the tool definition.

  • The header — x-portkey-beta: server-side-mcp-2026-06-01 on every request that uses the feature.
  • The prefix — @portkey-mcp/ in front of the server name, on server_label for the Responses API or on mcp_server_name for the Messages API.
Three fields are ignored once the prefix is present

With @portkey-mcp/ on the server name, the gateway ignores server_description, server_url and require_approval if the request passes them. A request that carries both the prefix and a server_url is accepted, and the server_url has no effect. Removing those three fields from the body makes the request say what it does.

▶ Step 1 — Call a tool through the gateway on the Responses API

The tool definition is an ordinary Responses API MCP tool with one change: the server label carries the prefix. The provider slug travels in x-portkey-provider and the model field holds a bare model name, which is the same pattern an ordinary model call uses.

curl --location 'https://api.portkey.ai/v1/responses' \
--header 'Content-Type: application/json' \
--header 'x-portkey-provider: @your-provider-slug' \
--header 'x-portkey-api-key: $PORTKEY_API_KEY' \
--header 'x-portkey-beta: server-side-mcp-2026-06-01' \
--data-raw '{
    "model": "gpt-5.5",
    "tools": [
        {
            "type": "mcp",
            "server_label": "@portkey-mcp/your-mcp-server-label",
            "allowed_tools": ["tool_name_1", "tool_name_2"]
        }
    ],
    "input": "what is portkey gateway"
}'

Export PORTKEY_API_KEY first so the value stays out of shell history. https://api.portkey.ai is the SaaS host; a self-hosted deployment substitutes its own gateway base URL. allowed_tools is optional, and omitting it exposes every tool the server offers, so name the tools explicitly when the model should reach only some of them.

Dropping the @portkey-mcp/ prefix and supplying a server_url instead moves execution to the provider and loses every property in the left column of the table above.

Verification

A response comes back and the tool call appears in the gateway's own logs with the user or service identity attached. A response that answers without calling the tool, or a tool call absent from the logs, means the request reached the provider-execution path. Re-read the request for a missing x-portkey-beta header or a missing @portkey-mcp/ prefix, in that order.

▶ Step 2 — Call the same tool on the Messages API

The Messages API carries the prefixed name twice: on name inside mcp_servers, and on mcp_server_name inside the tools object. The beta header is identical to the Responses API call.

curl --location 'https://api.portkey.ai/v1/messages' \
--header 'Content-Type: application/json' \
--header 'x-portkey-api-key: $PORTKEY_API_KEY' \
--header 'x-portkey-beta: server-side-mcp-2026-06-01' \
--data-raw '{
    "messages": [
        { "role": "user", "content": "what is Portkey-AI gateway repository?" }
    ],
    "model": "@anthropic/claude-haiku-4-5",
    "max_tokens": 10000,
    "mcp_servers": [
        {
            "type": "url",
            "url": "https://aigw.portkey.ai/m/server-name/mcp",
            "name": "@portkey-mcp/deepwiki"
        }
    ],
    "tools": {
        "type": "mcp_toolset",
        "mcp_server_name": "@portkey-mcp/deepwiki",
        "default_config": { "enabled": true },
        "configs": { "specific_tool_name": { "enabled": true } }
    },
    "stream": false
}'

The vendor example includes url and also states that url is not required when @portkey-mcp is in use, which matches the three fields the prefix already overrides. Leave it out for a gateway-executed call and the request still names the server through the prefixed name.

default_config sets the enabled state every tool inherits, and configs overrides it for one named tool. The rest of the body stays the provider's own, and the gateway does not change it, which is the behavior the Anthropic integration page documents for a plain model call on this path.

Verification

The response contains the tool result and the gateway logs show a tool call of the same shape the Responses API produced in Step 1. A 400 naming mcp_server_name means the field went into the wrong place in the body; a successful response with no logged tool call means the prefix did not take effect.

Reaching a server that is already in the registry

A server registered in the MCP Registry is also reachable by its gateway connection URL, named in server_url. The credential that authorizes the call depends on how that server authenticates. Header-based and no-auth servers take the Portkey API key inside headers. OAuth servers take the user's token in authorization.

These two bodies carry no prefix, so they follow the provider-execution column

The vendor examples below set server_label to a plain name and pass server_url, server_description and require_approval, all of which the @portkey-mcp/ prefix would override. Sending them as written therefore accepts the right-hand column of the comparison table in Where the tool runs. Prefix server_label to keep execution on the gateway.

▶ Step 3 — Authorize the call against a registry server

For a server registered with the Headers authentication option or with None, pass the Portkey API key as x-portkey-api-key inside the tool's headers object. The key appears twice in the request: once as a transport header on the HTTP call, and once inside the tool definition.

{
  "model": "@OPENAI_PROVIDER/gpt-4.1",
  "tools": [
    {
      "type": "mcp",
      "server_label": "dmcp",
      "server_description": "deepwiki mcp",
      "server_url": "https://aigw.portkey.ai/m/deepwiki/mcp",
      "headers": { "x-portkey-api-key": "{{PORTKEY_API_KEY}}" },
      "require_approval": "never"
    }
  ],
  "input": "what is portkey gateway"
}

For a server registered with OAuth 2.1, the body is identical except that authorization replaces the headers object.

{
  "model": "@OPENAI_PROVIDER/gpt-4.1",
  "tools": [
    {
      "type": "mcp",
      "server_label": "dmcp",
      "server_description": "deepwiki mcp",
      "server_url": "https://aigw.portkey.ai/m/deepwiki/mcp",
      "authorization": "{{OAUTH_TOKEN}}",
      "require_approval": "never"
    }
  ],
  "input": "what is portkey gateway"
}

Which of the two shapes applies is decided by the Authentication option chosen when the server was registered, and the registry page sets out all four options and what each one exposes. A server registered as OAuth 2.1 is per-user, so the token belongs to the person the request is made for and a shared value does not substitute for it.

The Responses API stores neither the header values nor the URL path

It discards the value of every string in the headers object, and it discards the path portion of server_url in responses, so example.com/mcp comes back as example.com. Nothing is retained between calls. Send the full server_url path and every header the server needs on every single request, because a second call that relies on the first having registered them reaches the server unauthenticated or reaches the wrong path.

Not verified in a tenant

Whether the key used here must also carry the mcp.invoke permission was not established. That permission is required for tool calls made through the MCP Gateway, as the registry page records, and nothing read for this page states whether the inference path applies the same check. Grant it before testing, then remove it to find out.

Verification

The tool returns data the server could only produce for an authorized caller. A 401 means the credential went into the wrong field for the server's authentication option: move a header-shaped value into headers, or an OAuth token into authorization. A 404 against a URL that works elsewhere means the /mcp path was dropped on a retry.

Private servers

A model provider can only call a server its own infrastructure can route to. A server behind a corporate firewall, bound to localhost, or published on a private network with no public DNS record is unreachable from provider infrastructure, whatever the request body says. Provider execution against such a server fails at the provider end, and no change to the credential or the tool definition fixes it.

Gateway execution is therefore the only option for a private server, rather than the better of two. The gateway runs inside your environment and reaches the server over the same network path any internal client would use.

Providers without remote MCP execution

Several upstream providers do not support executing MCP tools remotely at all. Amazon Bedrock and Google Vertex AI are the named cases. A request that asks one of them to call an MCP server has nothing to call it with, so the feature would be unavailable to every application routed to those providers.

The @portkey-mcp prefix answers that by moving execution off the provider entirely. The gateway performs the tool call and returns the result into the model exchange, so an application written against the Responses API or the Messages API uses MCP tools with a provider that has no MCP support of its own, and the application code does not change when the model behind the slug changes.
