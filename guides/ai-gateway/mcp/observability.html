MCP Observability

What the gateway records for every MCP tool call without any setup, the metadata fields that attribute a call to a person, a team and a key, how to filter the log view while debugging a reported failure, and what the source material does not answer about retention, export and redaction

All MCP Guides MCP Registry Remote MCP Observability Troubleshooting Configuration Chapter 10 Provider Integrations

What this covers

Every request that passes through the MCP Gateway is logged automatically. No agent is installed, no exporter is configured, no logging profile is attached, and no setting has to be switched on first. A server registered this morning is producing tool call records as soon as the first client calls it.

That changes what an administrator has to do. The work here is reading and filtering what already exists rather than instrumenting anything, and the first question a customer asks is usually what the gateway captured rather than how to make it capture.

This page documents the record itself: the fields on a tool call, the metadata attached to every request, the filters that find one call among thousands, and the procedure for taking a reported failure down to a cause.

What the neighboring pages own
  • Registering a server — MCP Registry and the Add MCP Server wizard covers the registry, the two-step wizard and all four authentication options, field by field.
  • The configuration procedure — Configuration chapter 10 is the short path through the whole feature, including the identity forwarding step this page refers to.
  • Credentials and attribution on the model side — Identity and clients explains why a given call logs a person or logs a workspace. The metadata fields below are the same argument seen from the logging end.

Tool call logs

What a tool call records

Nine fields are captured per request. Six of them answer who called what and how it went; two of them hold the content of the call.

FieldWhat it holds
ToolThe name of the tool that was invoked.
ParametersThe full request payload, meaning every argument the calling agent constructed for the tool.
ResponseThe full response data the MCP server returned.
UserThe person the call attributes to, where the credential carried one.
TeamThe team the caller belongs to.
TimestampWhen the call was made.
LatencyHow long the call took.
StatusWhether the call succeeded or failed.
MCP ServerThe registered server the tool belongs to.
Tool arguments are logged in full

Parameters is the complete request payload and Response is the complete response data. A tool that takes a customer record, a file path, a database query or a support ticket body as an argument puts that value into the log, and a tool that returns records returns them into the log as well. Raise this before a customer connects a server that touches regulated data, because the capture happens by default and nothing on the registration form mentions it.

Whether the capture can be narrowed, disabled or redacted for a given server is not answered by the source material behind this page. Not yet verified records that as an open question rather than as a product limitation.

Where to look and how to filter

Tool calls appear under Logs, alongside the model requests the same gateway handled. Six filters narrow the list: MCP server, team, user, tool name, time range and status. Clicking an entry opens the exact parameters that were sent, the response that came back, and a timing breakdown for the call.

▶ Open the log view and narrow it to one server

Start wide and remove rows. A filter set that returns nothing is as often a wrong workspace or a wrong time range as it is an absent call.

  1. Confirm the workspace selector at the top left names the workspace the call was made in. A tool call logged in one workspace is not visible from another.
  2. Go to AI Security → AI Gateway → Observability → Logs.
  3. Set the time range to a window that contains the call. The view opens on a recent window, so a call from yesterday is filtered out before you have typed anything.
  4. Filter by MCP server to leave only calls against the server in question.
  5. Add a tool name, a user, a team or a status to reach a single entry.
  6. Click the entry to open the parameters, the response and the timing breakdown.

Aggregate analytics

Beyond individual records, the gateway reports aggregates across tool calls:

  • Requests over time — call volume across a window.
  • Requests by server — which registered servers carry the traffic.
  • Requests by team — which teams are using tools.
  • Requests by user — which individuals are using them.
  • Error rates — the proportion of calls that fail.
  • Latency percentiles — the response time distribution rather than an average.
  • Most used tools — which tools account for the volume.

Two of these change a rollout conversation. Requests by server shows a registered server that nobody calls, which is a candidate for removal rather than for more provisioning. Most used tools shows the handful of tools worth guardrailing first, which chapter 10 covers.

Request metadata

Nine metadata fields ride on every request, for calls authenticated with an API key and for calls authenticated through OAuth alike. These are the fields that make a tool call attributable to somebody rather than merely visible.

FieldWhat it carries
organisation_idIdentifier of the organization the call belongs to.
organisation_nameDisplay name of that organization.
workspace_idIdentifier of the workspace the call was made in.
workspace_nameDisplay name of that workspace.
workspace_slugSlug form of the workspace, which is the value URLs and configuration files carry.
user_idThe individual the call attributes to, where the credential identified one.
api_key_idThe gateway API key that made the call.
mcp_server_idThe registered MCP server the tool belongs to.
mcp.auth.typeHow the caller authenticated, with the value api_key or Bearer.
The field names keep the vendor's British spelling

The first two fields are organisation_id and organisation_name as the product emits them. Query them with that spelling. An analytics job that looks for an organization field with a letter z finds nothing and reports no results rather than an error.

Five things become possible once these fields are on every record:

  • Per-user usage tracking — which individuals call which tools, from user_id.
  • Per-team cost allocation — tool usage grouped by the team the caller belongs to.
  • Compliance auditing — a record of who invoked what, when, against which server.
  • Chargeback reporting — usage rolled up by workspace, from workspace_id and workspace_slug.
  • Authentication flow analysis — the split between key-authenticated and OAuth-authenticated traffic, from mcp.auth.type.
A shared Service key gives you the workspace and not the person

api_key_id and user_id are how a tool call is attributed, and user_id is only populated when the credential carried an identity. A Service key is tied to nobody, so a team sharing one produces records that resolve to the workspace while every individual behind it is indistinguishable. That is the same behavior Identity and clients describes on the model side, and the fix is the same: issue User keys where per-person attribution is a requirement, and decide it before the keys are distributed, because a key type cannot be changed after issue.

Per-user OAuth servers force the question. A server registered with OAuth 2.1 cannot be called with a Service key at all, as the OAuth 2.1 section sets out, so every call against one carries a person.

Debugging a reported failure

A user reports that an agent cannot do something. The log view turns that into a specific field on a specific record.

▶ Take a reported failure down to a cause
  1. Filter the log view by the user who reported the problem, and set the time range around the window they described.
  2. Add the MCP server, and the tool name where they named one, to reduce the list further.
  3. Find the failing request by its status.
  4. Open the entry and read the parameters that were sent and the response that came back.
  5. Match the symptom against the table below and read the field that answers it.
SymptomWhat to read on the entry
The tool returns errorsThe response data, which carries the error message the MCP server itself produced. That message belongs to the server, so the fix is usually on the server rather than in the gateway configuration.
The tool returns the wrong resultsThe parameters the agent sent. The agent constructs them, and a plausible wrong argument produces a successful call with a useless answer.
Responses are slowThe latency breakdown, which separates time spent inside the MCP server from time spent on the network.
Access is deniedThe user and team on the entry, checked against the tool permissions configured for that server.

Access denials have a second source that the log entry does not show. A tool that is disabled on the server's Capabilities tab never reaches a permission check, because it does not exist for the caller to invoke. Chapter 10 covers that tab, and the access provisioning step covers the three levels a denial can come from.

Verification

You can name which of the four symptoms applies and point at the field on the entry that says so. A failure that matches none of them, or a report with no corresponding log entry at all, did not reach the gateway, which moves the investigation to the client configuration and to MCP troubleshooting.

Forwarding identity to the MCP server

Gateway logs attribute every call correctly on their own. The MCP server behind the gateway sees only the gateway unless user context is forwarded to it, and forwarding changes four things at the server:

  • Server-side logging — the server records its own entries with the gateway context attached.
  • Server-side access control — the server enforces its own per-user rules rather than treating every caller as the gateway.
  • Personalization — the server tailors a response to the individual who asked.
  • Attribution of actions — an action the tool performs is recorded against a person in whatever system the server writes to.

The procedure belongs to chapter 10, step 3, which sets out the methods available and which kind of server each one suits. Configure it there rather than from this page.

Correlating tool calls with model output

Model requests and tool calls are recorded in the same dashboard, and traces span both. A tool call can therefore be read next to the model output that triggered it, which is what an investigation into an agent's behavior needs: the argument a tool received is a consequence of the completion that produced it, and reading either one alone leaves the cause out of frame.
