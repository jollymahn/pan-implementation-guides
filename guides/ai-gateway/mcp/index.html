MCP Gateway

Putting the gateway between an MCP client and the MCP servers it calls, so that credentials, access and tool-call logging are held in one place rather than configured per agent

All MCP Guides MCP Registry Remote MCP Observability Troubleshooting Configuration Chapter 10 Provider Integrations

What this covers

The MCP Gateway proxies MCP clients to MCP servers. A client authenticates once to the gateway, and the gateway injects the upstream credential, checks whether that user may reach the requested server and tool, and logs the call. Connecting agents directly to servers instead means every agent carries its own credential for every server.

This set is the depth behind configuration chapter 10. Chapter 10 is the shortest path from nothing to a working tool call. These pages carry the registry form field by field, the four authentication options and what each one costs you, the separate Remote MCP feature, what the logs hold, and the failure modes with their fixes.

Client, gateway, server

Two authentication hops carry every tool call, and keeping them apart is the difference between a five-minute fix and an afternoon.

HopWhat authenticatesConfigured where
Client to gatewayA gateway API key, or an OAuth or identity provider loginSecurity Keys, covered by identity and client configuration
Gateway to MCP serverWhichever option the registry entry selectsThe registry entry
Most authorization errors come from the second hop

A client usually reports a generic failure, so the message you see describes the hop that did not fail. Check the gateway to server configuration first. Troubleshooting is organized around that assumption.

Authentication options

The registry form offers four, under a control labeled simply Authentication. Two of them take no fields at all, for opposite reasons.

OptionFieldsUse when
OAuth 2.1None. Each user signs in to the upstream service themselves.Each person needs their own upstream account, as with a personal GitHub or Slack
OAuth Client CredentialsToken Endpoint, Client ID, Client Secret, ScopeOne machine identity serves everyone
NoneNone. The server is open.Public servers that require no credential
HeadersHeader and value pairsThe server takes a static API key or token in a header
A Service key cannot drive an OAuth 2.1 server

OAuth 2.1 is per-user, so the request must arrive carrying a user identity. A Service gateway key is tied to nobody and there is no user to sign in, so the call fails. The other three options work with either key type.

The key type is chosen when the key is created and cannot be converted afterwards, so this decision precedes the registry entry rather than following it. The identity and client guide covers the Service against User choice, and the OAuth 2.1 section carries the full compatibility table.

Streamable HTTP or SSE

A separate control from authentication, with two options. Streamable HTTP is selected by default and the form recommends it for most integrations. SSE is the older server-sent events transport, for servers that only speak it.

The server decides this, not you. Pick what the server implements, and change it only when a connection fails in a way that points at the transport. The registry page shows both states.
