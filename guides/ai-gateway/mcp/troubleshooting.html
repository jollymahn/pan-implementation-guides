MCP Troubleshooting

Status code triage for MCP Gateway, the API key type that blocks per-user OAuth without saying so, the Advanced Settings box that swallows a pre-registered OAuth client, token lifetimes and hourly reconnects, and the port routing that breaks a self-hosted gateway

All MCP Guides MCP Registry Remote MCP Observability Troubleshooting Configuration Chapter 10 Provider Integrations

What this covers

MCP Gateway authenticates in two places. A client authenticates to the gateway with a gateway API key, and the gateway authenticates to the MCP server with whatever that server requires. Most messages that read as an authorization failure come from the second hop, even when the client shows nothing more specific than a connection error. Check the gateway-to-server hop first, then the client-to-gateway hop.

The sections below are organized by symptom. Each one names the error as a client or the gateway reports it, states the cause, and gives the correction. Registration procedure stays on MCP Registry and the Add MCP Server wizard, which documents every field on the form as a tenant renders it, and on configuration chapter 10, which is the short path through the whole feature.

Common failures

Start with the status code, because it separates a credential problem from a routing problem in one step. Work down the remaining sections only when the code and the first check do not resolve it.

▶ Triage by status code

Four responses cover most failures. Read the code the client reports, then take the first check in the matching row before changing anything on the registration.

StatusMeaningFirst check
401 The token is missing or expired, or the upstream server wants a sign-in. Re-authenticate the client and complete the server sign-in.
403 The call authenticated and is not allowed. Check the workspace and the server slug in the URL, and check that the key holds access to that server. See The gateway URL.
404 No such server. Check the slug, and check that the server is provisioned to this workspace.
500 with Unable to verify user access The gateway could not confirm who is calling. Check the API key type. See Access denied and the API key type.
A 500 here is a configuration answer, not a gateway fault

The string Unable to verify user access arrives as a server error and reports a mismatch between the key type and the server's authentication option. Raising a support case on the 500 alone sends the case down the wrong path, so read the key type first.

Verification

The failing call reproduces on demand and returns one status code every time. A call that returns a different code on each attempt points at a stale cached connection instead of a configuration fault, which Configuration changes not taking effect covers.

Access denied and the API key type

▶ Access denied, 500 Unable to verify user access, or a tool call refused on a key that works for models

Two separate properties of the gateway API key cause this symptom, and both look like a permissions problem on the server.

The first is the permission. A gateway API key that calls models successfully is refused on a tool call when it does not carry mcp.invoke. Set the permission on the key under Settings → API Keys. Chapter 10 names the same permission as MCP Invoke.

The second is the key type, and it is the higher-value check of the two because nothing in the message mentions it.

MCP server authenticationService keyUser key
None, Custom Headers, Client CredentialsWorksWorks
OAuth 2.1, per-userDoes not workWorks
A Service key cannot drive an OAuth 2.1 server

A Service key belongs to no person, and per-user OAuth has nobody to sign in. A call made with a Service key against a server registered as OAuth 2.1 fails, and the symptom reads as a permissions problem on the server while the cause sits on the key. Issue a User key instead. The key type is fixed at issue, so moving a consumer from a Service key to a User key means a new key and a redeploy of whatever holds it.

Identity and clients sets out the Service and User distinction in full, and OAuth 2.1 on the registry page shows the registration side of the same constraint.

  1. Open the key under Settings → API Keys and confirm that mcp.invoke is present.
  2. Read the key type on the same page.
  3. Open the server in the MCP Registry and read its Authentication option.
  4. Issue a User key where the two disagree, and update the client configuration to use it.
Verification

The same tool call that returned Unable to verify user access now returns a tool result, and the call appears under Logs attributed to the signed-in user rather than to a service identity. A call that still fails on a User key carrying mcp.invoke has a second cause, so return to the status code table.

The gateway URL

▶ 403 or 404 on connect, with the slug or the workspace wrong in the URL

The managed gateway endpoint follows one pattern, and the only variable in it is the registry slug.

https://aigw.portkey.ai/m/{slug}/mcp

The client sends the gateway API key as a bearer token on the same connection:

{
  "mcpServers": {
    "portkey": {
      "url": "https://aigw.portkey.ai/m/{server-slug}/mcp",
      "headers": { "Authorization": "Bearer YOUR_API_KEY" }
    }
  }
}

The value in {slug} is the Slug field set on the registration form, and it is never a UUID. A UUID pasted into that position produces a 404 every time. Step 1 of the Add MCP Server wizard sets the slug.

A 403 or a 404 has three usual causes:

  • A wrong slug — the registry row holds the authoritative value. Copy it rather than retyping it.
  • A server not provisioned to the workspace — the server exists in the organization registry and no workspace toggle was enabled for it. Workspace provisioning is where that is set.
  • A key from a different workspace — the key authenticates and carries no access to the server in the workspace named in the URL.
Two endpoint patterns appear in the vendor material

The help-center troubleshooting page gives https://aigw.portkey.ai/m/{slug}/mcp, and both chapter 10 and the registry page give https://aigw.portkey.ai/m/{server-slug}/mcp. The /m/ prefix is the documented form for a gateway running in unified mode, which suggests the two describe different deployments. Copy the connection URL the workspace MCP page shows for your own tenant instead of choosing between them.

Verification

The client completes a connection and lists the server's enabled tools. A connection that succeeds and lists nothing is a Capabilities setting rather than a URL fault, and chapter 10 covers it.

Incompatible auth server

▶ Incompatible auth server: does not support dynamic client registration

Per-user OAuth registers the gateway as an OAuth client automatically. Snowflake, and anything fronted by Okta or Entra ID, rejects automatic registration and returns this error. The correction is to pre-register an OAuth client with the service by hand and supply its credentials to the gateway.

  1. Create an OAuth client in the identity provider or the service's own admin console.
  2. Set its redirect URI to https://aigw.portkey.ai/m/oauth/upstream-callback exactly. A self-hosted gateway uses its own host, covered in Self-hosted gateways.
  3. Record the issuer, client ID, client secret, authorization endpoint, token endpoint and the scope the service requires.
  4. Open the server in the MCP Registry, expand Advanced Settings, and paste the wrapped object into Advanced Configuration.
{
  "oauth_metadata": {
    "issuer": "https://<your-idp>/...",
    "client_id": "YOUR_CLIENT_ID",
    "client_secret": "YOUR_CLIENT_SECRET",
    "redirect_uri": "https://aigw.portkey.ai/m/oauth/upstream-callback",
    "authorization_endpoint": "https://<your-idp>/.../authorize",
    "token_endpoint": "https://<your-idp>/.../token",
    "scope": "<the exact scope you need>"
  }
}
Advanced Configuration and OAuth Metadata take different shapes

Advanced Configuration merges its top-level keys into the integration configuration, so OAuth metadata goes into that box wrapped as {"oauth_metadata": { ... }}. OAuth Metadata stores its contents as the OAuth metadata directly, so that box takes the inner object only, starting at "issuer", with no wrapper.

Paste the wrapped object into the OAuth Metadata box and the whole structure nests one level too deep. The gateway then finds no client_id, falls back to Dynamic Client Registration without reporting it, and the original error repeats while the form shows credentials that look correct. The two boxes sit next to each other under Advanced Settings, and neither carries helper text or a placeholder.

The inner object, for the OAuth Metadata box:

{
  "issuer": "https://<your-idp>/...",
  "client_id": "YOUR_CLIENT_ID",
  "client_secret": "YOUR_CLIENT_SECRET",
  "redirect_uri": "https://aigw.portkey.ai/m/oauth/upstream-callback",
  "authorization_endpoint": "https://<your-idp>/.../authorize",
  "token_endpoint": "https://<your-idp>/.../token",
  "scope": "<the exact scope you need>"
}
Verification

A user reconnecting the server reaches the identity provider's own sign-in page instead of the registration error, and the authorization URL in the browser address bar carries the client_id you pre-registered. A repeat of the registration error after saving means the credentials landed in the wrong box, so move them and reconnect again.

invalid_scope at sign-in

▶ invalid_scope, or a sign-in that asks for the wrong permissions

The identity provider rejects a scope that does not exist, and it also rejects a scope that exists and is not allowed for the application. Both produce the same error at the authorization step, before any tool runs.

  1. Start a sign-in from the client and stop at the identity provider's page.
  2. Read the scope= parameter in the browser address bar.
  3. Compare it character for character against the scopes the service publishes.
  4. Confirm in the identity provider that the pre-registered application is allowed to request each one.
  5. Correct the scope value in Advanced Configuration or in the Scope field on the registration form, depending on which authentication option the server uses.
Scope lives in two places on the form

OAuth Client Credentials exposes its own optional Scope field, documented under OAuth client credentials. Per-user OAuth has no such field, so its scope comes from the metadata object described under Incompatible auth server.

Verification

The sign-in reaches the consent screen, and the permissions listed on that screen match what the server needs to do its work. A consent screen asking for more than the server needs means the scope string is too broad and should be narrowed before the connection is handed to users.

Protected resource mismatch

▶ Protected resource ... does not match expected ...

The server publishes the exact resource identifier it expects, and the registered URL has to match it. The registered URL is almost always missing its path, and that path is almost always /mcp.

Ask the server for the value it expects:

curl https://<server>/.well-known/oauth-protected-resource
  1. Read the resource value out of the response.
  2. Open the server in the MCP Registry.
  3. Set the URL field to that value exactly, including its path and excluding any trailing slash the response does not carry.
  4. Save, then have a user disconnect and reconnect.
URL and Slug are different fields

URL is the MCP server's own endpoint and Slug is the short identifier that forms the client connection URL. They sit on the same row of the form, and step 1 of the wizard covers the distinction. Editing the slug to fix a resource mismatch breaks every client configuration and does not change what the gateway sends upstream.

Verification

The URL field in the registry reads back identical to the resource value returned by the curl above, and a fresh sign-in completes without the mismatch error.

Configuration changes not taking effect

▶ A corrected registration behaves as it did before the correction

Configuration and upstream connections are both cached for a short period, and an established connection can keep using the values it was created with. A correct edit therefore produces no visible change for a while.

  1. Wait, then retry the call. A short cache interval clears on its own.
  2. Disconnect the server in the client, reconnect, and complete the sign-in again. This drops the stale upstream connection.
  3. Confirm that the integration you edited sits in the same workspace the client connects through. An edit applied to a server in another workspace saves cleanly and changes nothing for that client.
A new slug as a diagnostic

A server registered under a brand new slug always picks up the current configuration, with no cache to clear and no connection to drop. Use that to establish whether the edit itself was wrong or whether a cached value is hiding a correct edit. Treat it as a test rather than as the repair, because every client configuration has to change with the slug.

Verification

A reconnected client shows the behavior the edit intended, such as the new scope on the consent screen or the new tool in the listing. The same result on a throwaway slug and not on the original one confirms a cached connection, so disconnect and reconnect the original rather than editing it further.

Frequent reconnects

▶ Users sign in again roughly every hour

Access tokens last about 1 hour and refresh tokens last about 30 days. The gateway refreshes an access token automatically while it holds a refresh token, so a connection that survives the first hour normally lasts a month. A connection that dies every hour has no refresh token behind it.

Google is the common case. A Google authorization server returns a refresh token only when the authorization request carries access_type=offline, and it omits the parameter unless the client asks for it. Add the parameters to the OAuth metadata for the server:

"authorization_params": {
  "access_type": "offline",
  "prompt": "consent"
}

The authorization_params key sits alongside the other OAuth metadata keys shown under Incompatible auth server, inside the oauth_metadata object when the Advanced Configuration box is used.

Existing connections have to be rebuilt by each user

Connections created before the change hold no refresh token, and adding the parameters does not retrofit one. Each user has to disconnect and reconnect. prompt: consent is part of the fix rather than an extra: Google skips the consent screen for a user who already granted access, and a skipped consent screen returns no refresh token even with access_type=offline present.

Verification

A user who reconnects sees the Google consent screen again, and that user's connection survives past the first hour without a further sign-in prompt. A user who reconnects without seeing a consent screen still has no refresh token, so revoke the application's access in that user's Google account and reconnect.

OAuth discovery returns 404

▶ A client cannot discover the OAuth endpoints

Discovery reads two well-known documents from two different hosts, and a 404 on either one stops the sign-in before it starts. Run both checks and note which host fails.

On the gateway host:

curl -i https://<gateway-host>/.well-known/oauth-authorization-server

On the MCP server itself:

curl -i https://<server>/.well-known/oauth-protected-resource

A 404 from the server means the server does not publish the document, and the server owner has to add it. A 404 from the gateway host on a self-hosted deployment usually means the request never reached the MCP Gateway process, covered under Self-hosted gateways.

Verification

Both commands return 200 with a JSON body. The gateway document names an authorization endpoint and a token endpoint, and the server document carries the resource value that the registered URL has to match.

Self-hosted gateways

▶ Invalid API Key. Error Code: 03, or OAuth failing only on a self-hosted gateway

A self-hosted deployment changes four things that a managed tenant hides, and each one has its own failure.

  • The client URL — it uses your own host, as https://<host>/{slug}/mcp.
  • The OAuth callback — it becomes https://<host>/oauth/upstream-callback, and every upstream OAuth app has to register that value instead of the managed one.
  • MCP_GATEWAY_BASE_URL — it has to hold the public gateway URL with its scheme and no path. A wrong value breaks OAuth and discovery. The process reads it at startup, so a change needs a pod restart.
  • Ingress — it has to forward the Host header, because the gateway builds discovery and callback URLs from it.

Port routing is the fourth and the one that produces the most misleading error. Which mode the deployment runs in decides the answer.

ModePortsRouting
SERVER_MODE=unified One shared port Needs gateway 2.20.0 or later. The client URL becomes https://<host>/m/{slug}/mcp, and /.well-known/* and /oauth/* stay at the root rather than moving under /m.
SERVER_MODE=all or mcp MCP Gateway on 8788, AI Gateway on 8787 Every path on the MCP host routes to 8788. That includes /.well-known/* and /oauth/*, not only /{slug}/mcp.
Invalid API Key. Error Code: 03 is the AI Gateway answering for the MCP Gateway

That string during client registration means a request meant for port 8788 reached port 8787. The AI Gateway received a request it does not serve, read the bearer token as one of its own API keys, and rejected it. The message names a key and the fault is in the ingress rule, so no amount of key regeneration changes it. Route the whole MCP host to 8788.

Confirm which process answers a well-known path:

curl -i https://<host>/.well-known/oauth-authorization-server

Then read the ports the service exposes and the paths the ingress sends to them:

kubectl -n <namespace> get svc -o wide
kubectl -n <namespace> describe ingress <ingress-name>
kubectl -n <namespace> set env deployment/<deployment> --list | grep -E 'SERVER_MODE|MCP_GATEWAY_BASE_URL'
Restart after changing MCP_GATEWAY_BASE_URL

The value is read once at startup. A corrected environment variable on a running pod leaves the old value in effect, which presents as a fix that did nothing.

Verification

The curl returns 200 with the OAuth authorization server document, and the URLs inside it carry your public host rather than an internal service name or localhost. A client then registers without Invalid API Key. Error Code: 03.

External Auth Configuration returns 403

▶ 403 on saving or using external_auth_config

The External Auth Configuration box maps to external_auth_config, which has the gateway broker your identity provider directly. The capability is restricted to self-hosted and enterprise deployments, and a managed SaaS tenant returns 403 for it. The 403 reports the plan and the deployment type rather than a fault in the JSON.

On managed SaaS, use oauth_metadata with a pre-registered OAuth client instead. Incompatible auth server carries the procedure and the worked example, and it reaches the same outcome for every case that does not need the gateway to broker the identity provider itself.

Three boxes, three different contracts

OAuth Metadata takes the inner metadata object. Advanced Configuration takes a wrapper whose top-level keys merge into the integration configuration. External Auth Configuration takes external_auth_config and is unavailable on SaaS. Advanced settings shows all three as the tenant renders them, with no helper text on any of them.

Verification

The External Auth Configuration box is empty, the pre-registered client sits in Advanced Configuration under an oauth_metadata key, and a user sign-in completes without a 403.

Collect this before opening a support case
  • Workspace ID — the workspace the client connects through, not the organization.
  • Server slug — the value from the Slug column of the registry.
  • The full error message and its request_id — copied verbatim, including the trailing identifier that lets support find the call.
  • The MCP client in use — the product and its version, because clients differ in how they drive the OAuth flow.
