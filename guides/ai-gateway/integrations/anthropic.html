Anthropic Integration

Connecting the gateway to Anthropic: the Claude Console API key and the federation path through a federation issuer and a federation rule, including the two Anthropic settings that reject an otherwise correct configuration

All Provider Integrations Identity and Clients OpenAI Anthropic Azure OpenAI Azure Foundry AWS Bedrock

What this covers

This page takes Anthropic through the Add LLM Integration wizard and out the other side to a verified model call. It covers the credential each authentication path needs, where that credential comes from on the Anthropic side, what the gateway asks for, and the two client-side details that decide whether the first Anthropic request succeeds.

Anthropic's federation path differs from OpenAI's in both shape and failure mode. OpenAI exchanges a subject token against a Workload Identity Provider and a service account mapping. Anthropic presents a JWT bearer assertion against a federation issuer and a federation rule, and two settings on the Anthropic side reject a configuration that is correct everywhere else. Most of this page is that path.

Relationship to the configuration chapter set

Chapter 9 of the configuration set owns everything that is the same for every provider: the three tabs on the Integrations page, the slug convention, the model allowlist, workspace provisioning, and budget and rate limits. Read it once. This page covers only what is specific to Anthropic, and hands the reader back to chapter 9 at steps 3 and 4 of the wizard.

The model provider prerequisites page is the pre-engagement checklist for what to ask the customer to collect. This page is the session itself.

Prerequisites

Two sets of prerequisites apply: what the gateway needs before any integration can be created, and what Anthropic needs for the path you chose.

  • Gateway side — an AI Gateway organization in Strata Cloud Manager, an administrator who can create organization-level integrations, at least one workspace holding an API key, and the list of models each team is approved to use. Chapter 9 prerequisites has the full list.
  • Vault, if you use one — a secret reference created in configuration chapter 3, so the credential field can point at your vault instead of storing the value in the gateway.
  • Anthropic side — the table below, by path.
PathAnthropic sideYour side
API key A user who can create an API key in the Claude Console for the organization and workspace the gateway should use. Somewhere to hold the key. A vault reference is preferable to pasting the value.
Workload Identity Federation An Anthropic organization admin, a service account, a federation issuer, and a federation rule. An OIDC identity provider that meets the four requirements below, plus a client application and secret inside it.
Federation needs an Anthropic organization admin in the room

Workload identity is configured in the Claude Console under organization administration, or through the Anthropic Admin API. A workspace member cannot create a federation issuer or a federation rule. Book the organization admin for the session, because the gateway fields cannot be filled until the federation rule exists and its ID has been copied out.

The identity provider used for federation has to meet four requirements, and an identity provider that fails any of them cannot be used for this path:

  • It supports the client_credentials grant with client_secret_post.
  • It returns a signed JWT access token rather than an opaque token.
  • It publishes OIDC discovery at /.well-known/openid-configuration.
  • It publishes a JWKS on a public HTTPS URL, or Anthropic accepts an uploaded or linked JWKS instead.

Choose a path

The Anthropic tile offers two authentication paths and no others. Its Authentication Type control holds exactly two options, API Key and Workload Identity Federation, with API Key selected by default. The OpenAI tile's third option, OAuth Client Credentials, does not appear here, so a design that assumes plain client credentials against Anthropic has to move to federation. The choice between the two turns on what the gateway stores, what rotation costs, and how fast access can be withdrawn.

PathWhat the gateway storesRotationRevocation
API key The Anthropic key, encrypted, or a reference to it in your vault. Manual, on whatever schedule you enforce. A vault reference makes rotation a vault operation. Delete the key in the Claude Console.
Workload Identity Federation A client ID and secret for your own identity provider. No Anthropic key exists. The Anthropic token is short-lived and refreshed automatically. Only the identity provider secret needs rotating. Disable the federation rule. Cached tokens expire within 15 minutes.
The API key path remains a defensible choice

Federation removes the stored Anthropic key, and it adds an identity provider, a federation issuer, a federation rule and a second token exchange to the list of things that can break. A customer without an existing OIDC identity provider will spend the first session building one. Where the key can live in a vault and rotate on a schedule, the API key path reaches a reasonable position with far less to maintain. The comparison across all four providers is on the provider integrations hub.

API key

One key from the Claude Console, held in a vault where possible, pasted into the wizard where not. This is the shortest path to a working integration and the one most engagements start with.

▶ A.1 — Create the key in the Claude Console

The key carries the organization and workspace it was created under, so create it where the spend should land rather than wherever the first admin happens to be working.

  1. Sign in to the Claude Console with an account that can create API keys for the target organization.
  2. Switch to the workspace the gateway should use before creating the key.
  3. Create an API key and give it a name that identifies the gateway, for example prisma-airs-ai-gateway.
  4. Copy the value at the moment the console shows it.
Verification

The Claude Console lists the new key under the intended workspace, and the copied value is held somewhere you can paste from once, which is the vault entry in the next step or the wizard field in the step after it.

▶ A.2 — Put the key in a vault first

A referenced credential rotates in the vault with no change in the gateway. A pasted credential has to be re-entered on every integration that uses it at every rotation.

  1. Store the key in the vault backend configured in configuration chapter 3.
  2. Create or confirm the secret reference that points at it.
  3. If the secret holds several values, note which key within it holds the Anthropic value, because the wizard asks for that separately.

Skip this step only when no vault is in scope for the engagement. The credential field in the wizard accepts a pasted value as the alternative.

Verification

The secret reference appears in the gateway's reference picker. Resolution is not proven yet: that is the check chapter 3 defers, and the first model call is where it reports.

▶ A.4 — Record the two client details Anthropic callers need

These two apply to every Anthropic integration regardless of authentication path, and both of them break the first call rather than the configuration. Record them now, while the slug is in front of you, and hand them to whoever owns the calling application.

DetailWhat to tell the application owner
Base URL Do not add /v1 to the gateway address. The Anthropic SDK adds its own path, so an address ending in /v1 produces a doubled path and the gateway answers 404.
Provider header A client that sends a bare model name needs x-portkey-provider set to @<integration-slug>. Claude Code is one such client. Without the header the gateway answers 400 and names x-portkey-config or x-portkey-provider in the response.

A client that can name the model in full does not need the header, because the model reference @<slug>/<model-name> already identifies the integration. The client applications guide covers Claude Code and the other tools in detail.

Verification

The gateway base URL you are handing out has no /v1 suffix, and the application owner has either the x-portkey-provider header value or the full @<slug>/<model-name> reference written down.

Workload Identity Federation

Federation removes the stored Anthropic credential. Instead of holding a key, the gateway proves its identity to your identity provider, then presents that proof to Anthropic and receives a short-lived token for an Anthropic service account.

The exchange is two hops, not one. Both hops have to be configured, and each one fails with its own error.

HopFrom the gateway toWhat happens
1 Your identity provider token endpoint A client_credentials request returns a signed JWT access token for the gateway's client application.
2 https://api.anthropic.com/v1/oauth/token The gateway presents that JWT as an RFC 7523 JWT bearer assertion. Anthropic verifies the signature against the issuer's keys, matches iss, aud and sub against a federation rule, and returns an access token for the mapped service account.
Anthropic and OpenAI do not use the same grant

OpenAI uses RFC 8693 token exchange against https://auth.openai.com/oauth/token, and its provider-side objects are a Workload Identity Provider and a service account mapping, surfaced in the wizard as an Identity Provider ID and a Service Account ID. Anthropic uses the RFC 7523 JWT bearer grant, and its provider-side objects are a federation issuer and a federation rule, surfaced as a Federation Rule ID, an Organization ID, a Service Account ID and an optional Workspace ID. The identity provider work is shared between the two. Nothing after it is.

Both tokens are cached, and provider tokens are cached for no more than 15 minutes. That figure is also the revocation window: disabling the federation rule takes effect within 15 minutes.

▶ W.1 — Confirm the identity provider can issue the right kind of token

Anthropic verifies a signature against keys it fetches from the issuer, so an identity provider that returns an opaque token or hides its discovery document cannot be used. Check this before building anything, because the alternative is discovering it after the federation rule is already written.

curl -s <issuer-url>/.well-known/openid-configuration \
  | jq '{issuer, token_endpoint, jwks_uri, grant_types_supported}'
  1. Run the command against the issuer you intend to use.
  2. Confirm grant_types_supported includes client_credentials.
  3. Confirm jwks_uri is a public HTTPS URL that resolves from outside your network.
  4. Note the issuer value exactly as printed. Anthropic matches on that string.
Verification

The discovery document returns JSON, client_credentials appears in grant_types_supported, and fetching the jwks_uri returns a key set.

The identity provider build differs between Microsoft Entra ID and Okta. Pick the tab for the customer's identity provider; the choice persists across this page and across the other provider guides in this set.

Which tab applies
  • Microsoft Entra ID — two app registrations, one acting as the audience and one as the gateway's identity.
  • Okta — a custom authorization server plus an API Services application.
▶ W.2 — Register the two Entra applications

Entra needs two app registrations for this pattern. The API app exists to be the audience of the token. The client app is the gateway's identity and holds the secret.

Create the API app:

  1. Register an application named portkey-wif-api.
  2. Under Expose an API, set the Application ID URI to api://<api-app-client-id>.
  3. Open the manifest and set requestedAccessTokenVersion to 2. In the legacy manifest the same property is named accessTokenAcceptedVersion.

Create the client app:

  1. Register a second application named portkey-wif-client.
  2. Under Certificates & secrets, create a client secret and copy the value.
  3. Optionally add an app role on portkey-wif-api with Allowed member types set to Applications, grant it to portkey-wif-client under API permissions, then grant admin consent.
Token version 2 is what makes the issuer stable

With requestedAccessTokenVersion set to 2, Entra issues v2 tokens whose iss is https://login.microsoftonline.com/<tenant-id>/v2.0. That is the string registered as the Anthropic federation issuer. Leaving the default produces a different issuer and the federation rule never matches.

Verification

Both app registrations exist, portkey-wif-api shows an Application ID URI of api://<api-app-client-id>, its manifest shows 2, and the client secret value is copied into the vault or the secret manager you are using.

▶ W.2 — Create the Okta authorization server and the client application

Client credentials with custom scopes require a custom authorization server. The Okta org authorization server does not support them, so an attempt to use it fails at the scope rather than at the credential.

Create or configure the authorization server:

  1. Go to Security, then API, then Authorization Servers.
  2. Use the default server or create one named portkey-wif.
  3. Set its Audience, for example api://portkey-wif.
  4. Add a scope, for example portkey.wif.
  5. Under Access Policies, add a policy assigned to the client application with a rule that allows the Client Credentials grant and that scope.

Create the client application:

  1. Go to Applications, then Create App Integration, then API Services.
  2. Name it portkey-wif-client.
  3. Use client secret authentication so the application accepts client_secret_post, and copy the secret.
The access policy is what grants the scope

An authorization server with the scope defined but no policy rule allowing it to the client application returns invalid_scope on the first token request. Assign the policy to the application explicitly rather than relying on a default rule.

Verification

The authorization server lists the scope, its access policy names portkey-wif-client and allows the Client Credentials grant, and the API Services application exists with its client secret copied into the vault or secret manager you are using.

▶ W.3 — Record the Okta values the gateway and Anthropic need

Five values go into the gateway, and three claims go into the Anthropic federation rule. Write all eight down before moving on.

Gateway fields:

Resulting token claims, which the Anthropic side matches on:

Okta tokens carry a jti claim

Note this now and act on it in W.6. Okta includes a jti in the access token, and Anthropic's replay protection rejects a second presentation of a token it has already seen. The gateway reuses its cached identity provider token, so the second exchange presents the same jti and is refused.

Verification

All five gateway values and all three claim values are written down, and the sub value is the client ID of the API Services application rather than any user or group identifier.

▶ W.4 — Decode one real token before configuring Anthropic

The Anthropic federation rule matches on exact values. Reading iss, aud and sub out of a real token takes one command and removes the guesswork from every step that follows.

curl -s -X POST "<token-endpoint>" \
  -d grant_type=client_credentials \
  --data-urlencode client_id="<client-id>" \
  --data-urlencode client_secret="<client-secret>" \
  --data-urlencode scope="<scope>" \
  | jq '.access_token | split(".")[1] | gsub("-"; "+") | gsub("_"; "/") | . + ("=" * ((4 - length % 4) % 4)) | @base64d | fromjson | {iss, aud, sub, iat, exp}'

The JWT payload is unpadded base64url, which is why the filter pads it before decoding. Subtract iat from exp while the output is on screen: that number is the token lifetime, and it decides the value of the Anthropic max JWT lifetime setting in W.6.

Do not paste a production token into a JWT website

A token pasted into a third-party decoder has been handed to that site. Decode locally with the command above. The same applies to any token captured from a log during troubleshooting.

Verification

The command prints iss, aud, sub, iat and exp, and all three matched values are identical to what the previous step predicted. A sub that differs from the recorded value is the Entra service principal mistake, and correcting it here saves a failed exchange later.

▶ W.5 — Create the Anthropic service account

The federation rule maps an incoming token to a service account, so the service account has to exist first. Work in the Claude Console as an organization admin, or through the Anthropic Admin API.

  1. Create a service account dedicated to this gateway integration.
  2. Add it to the workspace the gateway should use.
  3. Copy the Service Account ID.

Use one service account per integration and per environment. A shared service account makes the Anthropic audit trail unable to distinguish which gateway integration made a call.

Verification

The service account appears in the intended workspace's member list, and its Service Account ID is written down with the values from W.3.

▶ W.6 — Register the federation issuer

The federation issuer tells Anthropic which identity provider to trust and how to fetch its keys. Configure it under workload identity in the Claude Console, using the column for the identity provider in use.

FieldMicrosoft Entra IDOkta
Issuer URL https://login.microsoftonline.com/<tenant-id>/v2.0 https://<okta-domain>/oauth2/<auth-server-id>
JWKS OIDC discovery OIDC discovery
Max JWT lifetime 5400 or higher Default (3600)
Check JTI (replay protection) Not applicable: Entra tokens carry no jti Disable
Max JWT lifetime must be 5400 or higher for Entra ID

Entra access tokens last 60 to 90 minutes. A max JWT lifetime left at the 3600 second default rejects any token whose exp minus iat exceeds one hour, which includes most Entra tokens. The configuration is otherwise correct, the error is a rejected subject token, and nothing in the message points at the lifetime. Set 5400 or higher, and compare it against the lifetime measured in W.4.

JTI replay protection must be disabled for Okta issuers

The gateway reuses its cached identity provider token while that token is still valid, including when it refreshes the Anthropic token. Okta tokens carry a jti. With JTI checks enabled, Anthropic treats the second exchange as a replay and refuses it, so the integration works once and then fails. Disable the JTI check on an Okta issuer. The protection it provides is replaced by the short Anthropic token lifetime and by the exact subject match on the rule.

Verification

The issuer saves with an Issuer URL byte-for-byte identical to the iss claim printed in W.4, with max JWT lifetime at 5400 or higher on Entra, and with the JTI check off on Okta.

▶ W.7 — Create the federation rule

The rule is the match. It names which token claims are accepted and which service account the resulting access token belongs to.

No wildcard and no prefix match. An exact subject is what keeps the rule bound to the one client application built for this integration, and it is the control that makes a disabled rule a complete revocation.

The rule saves, is enabled, and its subject and audience are copy-pastes of the values W.4 printed rather than values retyped from the identity provider console.

▶ W.10 — Create the same integration through the Admin API

The Admin API accepts the same configuration, which is the path to use when the integration is built by automation rather than by hand. Set provider_auth_type to wif inside configurations, and send no key: a federated integration has no provider API key.

{
  "name": "Anthropic (WIF)",
  "ai_provider_id": "<anthropic-provider-id>",
  "configurations": {
    "provider_auth_type": "wif",
    "wif_identity_source": "configuredIdp",
    "oauth_token_endpoint": "https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token",
    "oauth_client_id": "<client-id>",
    "oauth_client_secret": "<client-secret>",
    "oauth_scope": "api://<api-app-client-id>/.default",
    "anthropic_federation_rule_id": "<federation-rule-id>",
    "anthropic_organization_id": "<organization-id>",
    "anthropic_service_account_id": "<service-account-id>"
  }
}

Add anthropic_workspace_id when the federation rule spans multiple workspaces. wif_identity_source defaults to configuredIdp, which is the only supported value, so sending it is optional and sending anything else fails.

Not verified in a tenant

The ai_provider_id string for Anthropic is not recorded in any source read for this page. The captured example for OpenAI uses open-ai. Read the value from an existing Anthropic integration through the API before relying on a guess.

Verification

The API returns the created integration, and the Connected tab in Strata Cloud Manager shows it with the slug and authentication type you sent.

Hardening the federation path
  • A dedicated identity provider client application and a dedicated Anthropic service account per integration and per environment.
  • An exact sub match on the federation rule. No wildcard and no prefix.
  • The rule's OAuth scope limited to workspace:inference rather than anything broader.
  • The identity provider client secret held in a secret reference and rotated on a schedule.
  • For immediate revocation, disable the federation rule. Cached tokens expire within 15 minutes.

Provision the integration and set the model allowlist

Steps 3 and 4 of the wizard are the same for every provider, so they belong to configuration chapter 9 rather than to this page. What follows is the Anthropic-specific part of those two steps.

▶ P.1 — Finish the wizard
  1. On Workspace Provisioning, select the workspaces that should receive the integration, and set each workspace's budget and rate limits. Minimums are $1 for cost and 100 tokens.
  2. On Model Provisioning, enable only the Claude models the customer has approved. Workspaces see nothing that is not enabled here.
  3. Save the integration.
  4. Record the model reference form the applications will use: @<slug>/<model-name>.
Budget and rate limits cannot be edited after they are set

Decide the numbers before saving. A rate limit of 0 disables the provider for that workspace, which is a deliberate way to stage an integration but an unwelcome surprise when it was a typo.

The allowlist is where Claude model access is decided

A workspace asking for a newly released Claude model is asking for a change to this integration, not to their workspace. Chapter 9 covers the governance of that request and the workspace-created integrations path that bypasses it.

Verification

The integration appears on the Connected tab, each intended workspace is listed against it with the limits you set, and the enabled model list matches what the customer approved.

Step 4 of the wizard decides which models this integration exposes. The header reads Select Models to Provision, and the count beside Models is everything Anthropic publishes through the gateway. A tenant capture showed 389. Workspaces see only what is enabled here, so this list is the allowlist.

▶ Enable the approved models
  1. Use Search... to find each approved model by name.
  2. Set the toggle on each model card to on. The toggle sits in the top right of the card.
  3. Leave every other model off.

Select All and Deselect All sit above the list. On a list of several hundred models, start from Deselect All and add what was approved, rather than starting from everything and removing what was not.

The expensive models are enabled by the same click as the cheap ones

Nothing in this list distinguishes a model that costs cents from one that costs dollars for the same prompt. Budgets and rate limits are set per workspace in step 3, so they cap spend without capping which model spends it. The allowlist is the only control that decides that, and it is set here and nowhere else.

Verification

Every approved model shows an enabled toggle, and the count of enabled models matches the list the customer approved.

▶ Decide what happens to models released later

Below the model list is a toggle reading Automatically enable new models from this provider, described as making new models from the provider available on this integration. It is off by default.

Leaving it off means a model released next month is unavailable until someone enables it. Turning it on means that model is callable the day it ships, under the budgets already in place, with no review.

Off suits a governed tenant, on suits a lab

An organization that approves models through a review process wants this off, because the toggle quietly bypasses that process. A team that wants the newest model the day it lands wants it on. Record which was chosen and why, because the setting is invisible until an unexpected model appears in the logs.

Verification

The toggle reflects a decision somebody made, rather than the default nobody looked at.

▶ Set per-model pricing, where the published rate is wrong

Each model card carries a Set Pricing button. It opens a drawer titled Update Base Model on the right of the page.

The drawer opens with Add custom pricing for this model? switched off, explained as using default public model pricing from the base model when nothing is specified, with fine tuned models using public fine tuned model pricing. Leave it off and the gateway costs the model at the published public rate.

Switch it on and the drawer accepts:

Custom pricing changes the reported cost, not the invoice

These figures drive what the gateway reports in analytics and what it counts against a budget. The provider still bills its own rate. Entering a negotiated rate here makes internal reporting match the contract; entering a wrong number makes every budget and every cost report wrong in the same direction, and nothing in the console flags the discrepancy.

Custom Host and Custom Headers are per model

Both sit on the individual model rather than the integration, so two models under one integration can route to different upstreams and send different headers. A model-level header overrides an integration-level header of the same name.

Verification

Each model that needed a negotiated rate shows custom pricing applied, and every model left alone still reports the public rate. A later test call produces a cost figure consistent with the rate entered here.

Make the first model call

Everything so far is configuration that could not be tested. One request exercises the whole path: the workspace key, the credential or the two-hop exchange, the allowlist, and the guardrails. On the federation path this is also the first moment the identity provider and Anthropic actually talk to each other.

▶ F.1 — Send one request with curl

Use a workspace API key, not an organization key, and name the model with the full reference so no provider header is needed.

curl <gateway-base-url>/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "x-portkey-api-key: $AIGW_API_KEY" \
  -d '{
        "model": "@<slug>/<model-name>",
        "messages": [{"role": "user", "content": "Reply with the word ready."}]
      }'

The gateway also accepts the Anthropic protocol at POST /v1/messages, which is what the Anthropic SDK and Claude Code send. The request body is the provider's own body and the gateway does not change it.

Read the result against this table before changing anything:

OutcomeMeans
A model responseThe whole path works, federation included.
Authentication rejected at the gatewayThe workspace key is wrong, or it lacks the completions permission.
Gateway error fetching the secretThe secret reference path or the vault permission is wrong. This is the chapter 3 check finally reporting.
Provider rejects the credentialOn the API key path, the secret resolved but holds the wrong value. On the federation path, see Troubleshooting.
Model not found or not permittedThe model is not on the allowlist, or the integration is not provisioned to this workspace.
HTTP 446A guardrail denied the request. The integration is working.
Verification

A Claude response comes back through the gateway, made with a workspace key, naming an allowlisted model, and the request appears in the gateway log in Strata Cloud Manager with a token count against it.

▶ F.2 — Call it from the Anthropic SDK

The Anthropic Python SDK needs version 0.20 or later, which is where a configurable base URL arrived. Confirm the minimum against the release notes of the version the customer uses rather than quoting it as a product statement.

from anthropic import Anthropic

client = Anthropic(
    base_url="<gateway-base-url>",   # no /v1
    api_key="<gateway-api-key>",
)

message = client.messages.create(
    model="@<slug>/<model-name>",
    max_tokens=64,
    messages=[{"role": "user", "content": "Reply with the word ready."}],
)

print(message.content[0].text)
The base URL has no /v1 and the model name is not bare

The SDK appends its own path, so /v1 on the base URL produces a doubled path and a 404. The model reference @<slug>/<model-name> tells the gateway which integration to use; a bare model name needs the x-portkey-provider header instead. Claude Code sends a bare name, which is why the client applications guide sets that header through ANTHROPIC_CUSTOM_HEADERS.

Verification

The script prints the model's reply, and the gateway log shows a second request against the same integration.

Troubleshooting

The caller sees only the OAuth error code

On the federation path the gateway returns the standard OAuth error, such as invalid_client. The full identity provider or Anthropic response stays in the gateway logs and never reaches the caller. Debugging this from the client side is working blind by design, so read the gateway log rather than inferring from the status code.

▶ T.1 — The first call fails
SymptomCauseFix
HTTP 404 from the gateway The base URL ends in /v1 and the SDK added its own path. Remove /v1 from the base URL.
HTTP 400 naming x-portkey-config or x-portkey-provider The client sent a bare model name. Set x-portkey-provider to @<integration-slug>, or send the full @<slug>/<model-name> reference.
Model not found or not permitted The model is off the allowlist, or the integration was never provisioned to this workspace. Enable the model on the integration, or provision the integration to the workspace.
HTTP 446 A guardrail denied the request. Nothing on this page. The integration is working and a policy stopped the content.
Gateway error fetching the secret The secret reference path or the vault permission is wrong. Correct the reference in chapter 3 and retry.
Verification

The retried request returns a Claude response, and the gateway log shows the request with a token count rather than an error.

▶ T.2 — The first hop fails at the identity provider

These errors happen before Anthropic is ever contacted. The command in W.4 reproduces the same request from your workstation, which is the fastest way to confirm a fix.

ErrorCauseFix
OAuth token acquisition failed: invalid client credentials The identity provider rejected the client ID or the secret. Check the secret value and its expiry. In Okta, confirm the application allows client_secret_post.
OAuth token endpoint returned 400 (invalid_scope) The scope is not allowed for this client. Entra: use api://<api-app-client-id>/.default. Okta: add the scope to the access policy rule.
WIF config incomplete: ... required A required field is empty. Fill in every required field from the W.9 table, including the Anthropic group.
Invalid or unsafe URL The token endpoint is private or uses HTTP. Use the public HTTPS endpoint, or add the host to the gateway's egress allowlist.
Verification

The W.4 command returns a token and prints its claims, which proves the first hop works independently of anything on the Anthropic side.

▶ T.3 — Anthropic rejects a token that looks correct

The error is Anthropic WIF token exchange failed: subject token rejected. It means the JWT reached Anthropic and no federation rule accepted it. Work the four causes in this order, because the last two produce exactly the same message as the first two.

  1. Issuer mismatch. Compare the federation issuer URL against the iss claim from W.4, character for character. On Entra, a missing /v2.0 suffix means requestedAccessTokenVersion was never set to 2.
  2. Subject or audience mismatch. Compare the rule's subject and audience against the sub and aud claims from W.4. On Entra, a subject taken from the app registration rather than the Enterprise applications service principal is the usual cause.
  3. Max JWT lifetime, on Entra. Subtract iat from exp. A value above the issuer's max JWT lifetime is rejected with no mention of the lifetime. Set the issuer to 5400 or higher.
  4. JTI replay protection, on Okta. An integration that works on the first call and fails afterwards is this. Disable the JTI check on the issuer.
Allow 15 minutes before concluding that a fix failed

Tokens are cached for up to 15 minutes. A corrected rule or issuer can take that long to take effect, and the same window applies in reverse when disabling a rule to revoke access.

Verification

A repeated request returns a Claude response, and a second request sent several minutes later also succeeds, which is what distinguishes a fixed configuration from the JTI failure mode.
