Azure OpenAI Integration

Connecting the gateway to an Azure OpenAI resource: the resource name and the deployment entries, the four authentication modes and the two a hosted gateway cannot use, the role assignment on the Azure side, and a verified first call

All Provider Integrations Identity and Clients OpenAI Anthropic Azure OpenAI Azure Foundry AWS Bedrock

What this covers

Azure OpenAI serves models from a resource inside the customer's own Azure subscription. The gateway does not call a shared provider endpoint for this tile. It calls https://<resource-name>.openai.azure.com, names a deployment the customer created, and pins an API version. That changes what the integration asks for and it changes what has to be true in Azure before the integration works at all.

This page covers the Azure side and the provider-specific half of the wizard: the resource name, the deployment entries, the four authentication modes, and the role assignment that grants the credential permission to run inference. Steps 3 and 4 of the wizard are the same for every provider and belong to configuration chapter 9.

What Azure OpenAI asks forWhy the other provider tiles have no equivalent
Resource nameThe endpoint host is per-customer. OpenAI and Anthropic each have one global endpoint, so neither asks.
One entry per deploymentA model becomes callable in Azure only once it is deployed and named. The gateway mirrors that list rather than discovering it.
An API version per deploymentAzure OpenAI versions its REST surface with an api-version query parameter. The value is part of the request, not a property of the model.
A role assignment on the resourceEntra ID and managed identity credentials carry no permission of their own. Authentication and authorization are separate in Azure, and the role supplies the second one.
Deployment names in the model referenceCallers address @<slug>/<deployment-name>. Every other tile in this set takes a model name.
Where the field labels on this page come from

Every Azure OpenAI field label, placeholder and field order quoted here was read from the Add LLM Integration wizard in a tenant on 2026-11-17, with all four authentication modes selected in turn. Four details on the form were not opened and stay unresolved, and the open items at the foot of the page name them. Everything else is what the console shows.

Azure OpenAI, Azure Foundry and Copilot Studio are three different products

Azure OpenAI and Azure Foundry are separate tiles in the provider catalog with separate configurations. A customer who says "Azure AI" has not said which one. Azure Foundry exposes one API across a range of foundation models and its field list is not covered here or on the model prerequisites page.

Neither tile is Microsoft Copilot Studio. Copilot Studio is a different product on a different runtime, and no configuration transfers between it and either Azure tile.

Prerequisites

Four things have to be known before the wizard is opened. Three of them come from Azure and one of them decides which authentication paths are available at all.

▶ Step 1 — Record the resource name

The resource name is the first label of the endpoint host. For an endpoint of https://contoso-eastus-aoai.openai.azure.com the resource name is contoso-eastus-aoai. The integration takes the label on its own.

  1. Open the Azure OpenAI resource in the Azure portal.
  2. Go to Resource Management > Keys and Endpoint and read the Endpoint value.
  3. Take the first label of the host and write it down.

The same value comes from the Azure CLI:

az cognitiveservices account show \
  --name "<RESOURCE_NAME>" \
  --resource-group "<RESOURCE_GROUP>" \
  --query "properties.endpoint" -o tsv
The whole URL is the most common wrong value

Pasting https://contoso-eastus-aoai.openai.azure.com/ into a field that wants contoso-eastus-aoai produces a host the gateway cannot resolve, and the failure surfaces at the first call rather than at save time. Record the label, and record the full endpoint separately so the two never get confused.

Verification

The recorded value contains no scheme, no dots and no trailing slash, and appending .openai.azure.com to it reproduces the host shown on the Keys and Endpoint pane exactly.

▶ Step 2 — List every deployment and its API version

The integration carries one entry per deployment, each with a deployment name and an API version, with one entry marked as the default. Build that list before the session, because the deployment names are chosen by whoever deployed the models and they are rarely the model names.

  1. Open the Azure OpenAI resource and go to its model deployments list, or run the command below.
  2. Record the deployment name of each deployment the gateway should expose.
  3. For each one, record the api-version value the customer's existing applications already send to that deployment.
  4. Mark one deployment as the default.
az cognitiveservices account deployment list \
  --name "<RESOURCE_NAME>" \
  --resource-group "<RESOURCE_GROUP>" \
  --query "[].{deployment:name, model:properties.model.name, version:properties.model.version}" \
  -o table
A deployment name is not a model name

In Azure the model gets a name when it is deployed, and that name is what every caller sends. A resource can hold a deployment called chat-prod running gpt-4o and another called chat-canary running the same model at a different version. The gateway inherits this: the model reference is @<slug>/<deployment-name>, so a caller that sends gpt-4o gets a model-not-found error even though the model exists.

Write down the deployment names. Record the model names beside them for context, and never substitute one for the other.

Match the API version the applications already use

The api-version query parameter selects a version of the Azure OpenAI REST surface, and features such as structured outputs and tool calling appear at different versions. Setting a version the applications have not been tested against changes request handling for every caller on that deployment at once. Take the value from a working application request, not from a release note.

Verification

The list names every deployment the customer wants exposed, each row carries both a deployment name and an api-version value, exactly one row is marked default, and every api-version value was read from a request an application makes today.

▶ Step 3 — Establish which gateway the integration runs on

This answer decides whether two of the four modes exist for this customer. Ask it before offering any of them.

GatewayModes available
SaaS gatewayDefault and Azure Entra. Managed and Workload Identity both need the gateway to run on Azure compute, so neither is available.
Hybrid data plane running on AzureAll four.
Hybrid data plane running anywhere elseDefault and Azure Entra. The other two are unavailable for the same reason.

Check the Strata Cloud Manager gateway list. The Total Gateways count on the AI Gateway page counts Hybrid data planes only, so a tenant with no Hybrid data plane reads zero there and is a SaaS deployment.

Verification

You can name the gateway this integration will run on, and for a Hybrid data plane you can name the Azure compute it runs on. An answer of "both" means the integration has to work on the SaaS gateway too, which rules out Managed and Workload Identity.

▶ Step 4 — Line up the Azure permissions the session needs

Two separate Azure permissions are needed, and they usually sit with two different people. A session that has one and not the other stalls halfway through.

To do thisSomeone needs
Read the resource keyPermission to read keys on the Azure OpenAI resource. Needed for the Default mode only.
Register an application in Entra IDThe Application Developer role, or an Entra tenant that permits users to register applications. Needed for the Azure Entra mode only.
Create a user-assigned managed identityWrite permission in the resource group holding the identity. Needed for the Managed and Workload Identity modes.
Add a federated credential to that identityWrite permission on the managed identity itself. Needed for the Workload Identity mode only.
Assign a role on the Azure OpenAI resourceOwner or User Access Administrator on the resource or its scope. Needed for every mode except Default.
Role assignment is the one that gets forgotten

Creating an app registration is a directory operation and assigning a role is a subscription operation. An engineer who can do the first frequently cannot do the second, and the integration saves cleanly either way. The gap shows up only when the first call returns an authorization failure.

Verification

For the path chosen in the next section, you can name the person in the room who holds each permission in its row, or you have a change request raised for the one nobody holds.

Choose a path

Azure OpenAI does not use the three-card Authentication Type control that the OpenAI tile uses. It has its own control named Azure Authentication Mode, with four options in this order: Default, Managed, Azure Entra and Workload Identity. The control sits directly below Slug, and no parent control sits above it. An Azure Resource Name field follows the mode-specific fields in every mode, and the Foundation Model block follows that.

The mode control, with Managed selected:

The vendor documentation is wrong about federation here

The product documentation states that Workload Identity Federation is supported for OpenAI and Anthropic only. The tile offers a Workload Identity mode, so do not tell a customer that Azure OpenAI cannot federate. That mode asks for a client ID and a tenant ID, and it is Azure AD workload identity rather than the token-exchange federation the OpenAI tile performs.

ModeWhat the gateway storesWhat Azure needsRotation and revocation
Default One of the resource's two keys, or a reference to it in a vault Nothing beyond the resource itself. The key carries inference permission on its own. Regenerate the key in the portal, which breaks every other consumer of that key at the same moment. Revoke by regenerating.
Azure Entra A tenant ID, a client ID and a client secret An app registration, and a Cognitive Services OpenAI User role assignment on the resource Rotate the client secret in Entra on the expiry you set. Revoke by removing the role assignment, which takes effect without touching the gateway.
Managed Nothing. A client ID only, and only when the identity is user-assigned. The field is Azure Managed ClientID (optional), which confirms it is omitted for a system-assigned identity. A managed identity on the Azure compute the gateway runs on, and a Cognitive Services OpenAI User role assignment on the resource No secret exists, so nothing rotates. Revoke by removing the role assignment.
Workload Identity A client ID and a tenant ID. No secret. A user-assigned managed identity carrying a federated credential for the gateway's workload, and a Cognitive Services OpenAI User role assignment on the resource No secret exists, so nothing rotates. Revoke by deleting the federated credential or removing the role assignment.
Two of the four modes work only for a self-hosted gateway running on Azure

A managed identity belongs to the Azure compute resource it is attached to. It is issued by the Azure instance metadata endpoint to code running on that virtual machine, scale set, container app or AKS node. The SaaS gateway does not run on the customer's Azure compute, so there is no identity for it to present and no way to attach one. Workload Identity rests on the same requirement by a different mechanism: the gateway's workload has to present a token Azure AD already trusts, which again means the gateway runs inside the customer's Azure estate.

This is the most common wrong promise in an Azure engagement, because "keyless with managed identity" reads as a property of Azure OpenAI rather than a property of where the gateway runs. A SaaS customer who wants no stored provider key gets the Azure Entra mode, which still stores a client secret, or moves to a Hybrid data plane on Azure. Settle this in Step 3, before any option is named out loud.

The API key path remains a defensible choice

The resource key reaches a reasonable position when it lives in Azure Key Vault and the integration resolves it by reference, as configuration chapter 3 describes. Its real weakness is shared blast radius: the resource has two keys for the whole resource, so regenerating one to rotate the gateway's credential also cuts off every application still holding it. Where the customer already shares that key widely, the Azure Entra mode gives the gateway a credential it can rotate alone.

Default mode, an API key

Default is the first card on the Azure Authentication Mode control and it is the API key path. Selecting it exposes one credential field, API Key, with the placeholder Enter API Key. This is the fastest route and the one to use for a first connection that proves the resource name and the deployment names are right before identity is added on top.

The three steps that follow Step A1 are shared. Every other mode on this page enters the wizard the same way, fills in the same Azure Resource Name and Foundation Model fields, and differs only in what the mode control exposes above them.

▶ Step A1 — Copy a key from the Azure OpenAI resource

The resource carries two keys, and both grant the same access. Taking the second one leaves the first untouched for the applications already using it, which makes a later rotation possible without a simultaneous cutover.

  1. Open the Azure OpenAI resource in the Azure portal.
  2. Go to Resource Management > Keys and Endpoint.
  3. Copy KEY 2 if it is unused, and record which key was taken.
az cognitiveservices account keys list \
  --name "<RESOURCE_NAME>" \
  --resource-group "<RESOURCE_GROUP>" \
  --query "key2" -o tsv
Put the key in a vault now rather than later

Store the key in Azure Key Vault and create the secret reference described in configuration chapter 3 before creating the integration. Converting a pasted key to a reference afterwards means editing the integration again, and the pasted copy has already been typed into a browser in the meantime.

Verification

The key is in the vault or on the clipboard, you can state which of the two resource keys it is, and the resource name recorded in Step 1 matches the endpoint shown on the same pane.

▶ Step A3 — Enter the resource name and the Foundation Model entries

These are the fields that make the Azure OpenAI tile different from every other provider in this set, and they sit in the same place in every mode. Azure Resource Name follows whatever credential fields the mode exposes, and the Foundation Model block follows that. Both are on the main form. This tile has no Optional Fields section, so nothing here is hidden behind a collapsed control.

  1. Enter the resource name recorded in Step 1 into Azure Resource Name, as the bare label. The placeholder reads Enter Azure Resource Name.
  2. In the Foundation Model block, fill in the first entry from the Step 2 list, then click Save on that entry.
  3. Click + Add Model in the block header and repeat for each remaining deployment.
  4. Leave Make it default model checked on exactly one entry and clear it on the others.

Azure Entra mode, a service principal

Azure Entra is the third card on the Azure Authentication Mode control. The gateway holds a client ID and a client secret for an Entra application, exchanges them for a token, and calls the resource with that token. Nothing about the resource's own keys is involved, so rotating the gateway's credential does not disturb any other consumer, and withdrawing access is a role assignment change rather than a key regeneration.

This mode works on the SaaS gateway and on a Hybrid data plane anywhere. It needs work on two Azure surfaces: a registration in the directory, and a role assignment on the subscription.

▶ Step S1 — Register the application in Microsoft Entra ID

Register one application for this integration rather than reusing an existing one. A shared registration means the role assignment that grants Azure OpenAI access also lands on everything else using that application, and removing the gateway's access later removes theirs.

  1. In the Azure portal, go to Microsoft Entra ID > App registrations > New registration.
  2. Set a name that identifies the consumer and the environment, such as aigw-azure-openai-prod.
  3. Leave the supported account types at single tenant and leave the redirect URI empty. The gateway uses the client credentials flow, which has no redirect.
  4. Click Register.
  5. On the Overview page, copy the Application (client) ID and the Directory (tenant) ID.

The equivalent from the Azure CLI, which creates the application and its service principal together:

az ad sp create-for-rbac \
  --name "aigw-azure-openai-prod" \
  --skip-assignment

az account show --query tenantId -o tsv
The registration and the service principal are two objects

An app registration creates a directory object and a separate service principal object in the tenant, and they have different object IDs. The role assignment in Step S3 targets the service principal, which the portal lists under Enterprise applications. Using the app registration object ID there produces an assignment that resolves to nothing.

Verification

The application appears under App registrations and under Enterprise applications, and you have recorded both the Application (client) ID and the Directory (tenant) ID.

▶ Step S2 — Create a client secret and record its expiry
  1. In the registration, go to Certificates & secrets > Client secrets > New client secret.
  2. Set a description naming the consumer, and an expiry that matches the customer's rotation policy rather than the longest option offered.
  3. Copy the Value immediately. Azure shows it once and never again.
  4. Store it in Azure Key Vault and create the secret reference described in configuration chapter 3.
A client secret expires, and the integration will not warn you

The expiry is a date in Entra that nothing in Strata Cloud Manager can see. On that date every call through this integration begins failing authentication, and the gateway reports an OAuth error rather than an expiry. Record the date in whatever the customer uses to track certificate and credential renewals before leaving this step, and record who owns the renewal.

Verification

The secret value is in the vault, the expiry date is recorded in the customer's renewal tracker with a named owner, and the Client secrets list shows exactly one secret for this registration.

▶ Step S3 — Assign Cognitive Services OpenAI User on the resource

The client ID and secret authenticate the gateway to Entra. They grant no access to anything. The role assignment is what authorizes inference calls against this specific resource, and without it the credential is valid and useless.

  1. Open the Azure OpenAI resource in the Azure portal.
  2. Go to Access control (IAM) > Add > Add role assignment.
  3. Select the Cognitive Services OpenAI User role.
  4. Assign access to User, group, or service principal, and select the service principal created in Step S1.
  5. Review and assign.

The equivalent from the Azure CLI, resolving the service principal object ID from the application client ID:

SP_OBJECT_ID=$(az ad sp show \
  --id "<APPLICATION_CLIENT_ID>" \
  --query id -o tsv)

AOAI_RESOURCE_ID=$(az cognitiveservices account show \
  --name "<RESOURCE_NAME>" \
  --resource-group "<RESOURCE_GROUP>" \
  --query id -o tsv)

az role assignment create \
  --role "Cognitive Services OpenAI User" \
  --assignee-object-id "$SP_OBJECT_ID" \
  --assignee-principal-type ServicePrincipal \
  --scope "$AOAI_RESOURCE_ID"
Cognitive Services OpenAI User, not Contributor and not Owner

Cognitive Services OpenAI User permits inference calls against the resource with an Entra token. It does not permit reading the resource keys, creating or deleting deployments, or changing the resource. That boundary is the point of using identity here at all.

Contributor and Owner both include the ability to read the resource keys. Granting either turns a credential that can only run inference into a credential that can extract the long-lived key the API key path uses, which is the exact exposure this path was chosen to avoid. Owner adds the ability to grant that access to others. Neither role fixes a failing call: a 403 after this step means the scope or the principal is wrong, and widening the role hides the mistake rather than fixing it.

Role assignments take time to apply

An Azure role assignment is not always effective the instant the portal confirms it. A call made immediately afterwards can still return an authorization failure. Wait, then retry, before investigating the assignment itself.

Verification

The assignment is listed at the resource scope with the principal from Step S1:

az role assignment list \
  --scope "$AOAI_RESOURCE_ID" \
  --query "[?roleDefinitionName=='Cognitive Services OpenAI User'].{Principal:principalName, Scope:scope}" \
  -o table

The scope column ends in the Azure OpenAI resource name. A scope that stops at the resource group or the subscription grants more than this integration needs.

Managed mode, a managed identity

Read this before offering the mode to a customer

A managed identity is attached to an Azure compute resource and is presented by code running on that resource. The gateway can use one only when the gateway itself runs on Azure compute that has one, which means a Hybrid data plane on an Azure virtual machine, scale set, container app or AKS cluster. The SaaS gateway runs outside the customer's subscription, so this mode does not exist for it under any configuration.

Where the customer runs the SaaS gateway and the requirement is no stored provider key, the Azure Entra mode is the available answer. It removes the resource key and replaces it with a client secret, which is a smaller improvement than the customer may have been promised. Say so plainly rather than at the first call.

Where the gateway does run on Azure, this mode stores no secret at all. Azure issues the token to the compute resource, the role assignment authorizes it against the Azure OpenAI resource, and there is nothing to rotate and nothing to expire.

▶ Step M1 — Confirm the gateway runs on Azure compute with an identity

Two facts have to hold together. The gateway has to be a Hybrid data plane, and the Azure compute hosting it has to carry a managed identity the gateway process can use.

  1. Confirm in Strata Cloud Manager that the integration will be used by a Hybrid data plane, using the check in Step 3.
  2. Identify the Azure compute it runs on: a virtual machine, a scale set, a container app, or an AKS cluster.
  3. For AKS, confirm the gateway workload has an identity through workload identity. The identity section of the Kubernetes deployment guide covers building that for the Azure Kubernetes Service path.
Verification

You can name the Azure compute resource the gateway runs on and the managed identity attached to it, and that identity is the one the gateway process already uses to reach its cache or log store.

▶ Step M2 — Identify the identity and its client ID

Azure has two kinds. A system-assigned identity is created with the compute resource and dies with it, and the gateway finds it without being told. A user-assigned identity is its own resource that can be attached to several compute resources, and a host carrying more than one of them needs to be told which to use, by client ID.

For a user-assigned identity, read both IDs:

az identity show \
  --name "<IDENTITY_NAME>" \
  --resource-group "<RESOURCE_GROUP>" \
  --query "{clientId:clientId, principalId:principalId}" -o table

For a system-assigned identity on a virtual machine, read the principal ID:

az vm identity show \
  --name "<VM_NAME>" \
  --resource-group "<RESOURCE_GROUP>" \
  --query principalId -o tsv
Two IDs, two uses

The principal ID is the service principal object ID, and it is what the role assignment in Step M3 targets. The client ID is what the gateway is given when it has to pick between several user-assigned identities on one host. Swapping them produces a role assignment on an object that does not exist, or a gateway asking for an identity Azure does not recognize.

Verification

You have the principal ID for Step M3, and for a user-assigned identity you also have its client ID. For a system-assigned identity no client ID is needed.

▶ Step M3 — Assign Cognitive Services OpenAI User to the identity

The role assignment is identical to the one the Azure Entra mode uses, and it carries the same least privilege reasoning. The identity authenticates by itself; the role is what lets it run inference against this resource.

AOAI_RESOURCE_ID=$(az cognitiveservices account show \
  --name "<RESOURCE_NAME>" \
  --resource-group "<RESOURCE_GROUP>" \
  --query id -o tsv)

az role assignment create \
  --role "Cognitive Services OpenAI User" \
  --assignee-object-id "<IDENTITY_PRINCIPAL_ID>" \
  --assignee-principal-type ServicePrincipal \
  --scope "$AOAI_RESOURCE_ID"
Cognitive Services OpenAI User, not Contributor and not Owner

A managed identity on shared compute is reachable by anything running on that host. Granting it Contributor gives every workload on the host the ability to read the resource keys and change deployments, and Owner adds the ability to hand that out further. Scope the assignment to the Azure OpenAI resource, and keep the role at Cognitive Services OpenAI User.

A managed identity that already has roles on other resources

Reusing the identity the gateway already uses for its cache and log store is reasonable, and it means this role assignment joins others on the same principal. Check what else is assigned before adding to it, because a principal that has accumulated broad roles elsewhere carries them into the Azure OpenAI call path: az role assignment list --assignee <IDENTITY_PRINCIPAL_ID> --all -o table.

Verification

az role assignment list --scope "$AOAI_RESOURCE_ID" -o table lists the identity against Cognitive Services OpenAI User, and the scope column ends in the Azure OpenAI resource name rather than the resource group.

▶ Step M4 — Select Managed in the wizard

The console marks the client ID field optional, which matches the Azure behavior: a host with one identity needs no disambiguation and a host with several does. The integration saves with no secret entered anywhere, and the only field the mode exposed was Azure Managed ClientID (optional). A form asking for a secret means the Azure Entra card is selected rather than Managed.

Workload Identity mode, a federated credential

Workload Identity is the fourth card on the Azure Authentication Mode control. It exposes two fields, Azure Workload ClientID and Azure Workload Tenant ID, and no secret.

Azure AD workload identity, a different mechanism from the OpenAI token exchange

A reader who has configured Workload Identity Federation on the OpenAI tile arrives expecting a token endpoint, a client secret, an Identity Provider ID and a Service Account ID. None of those fields exist here. The Azure OpenAI mode asks for a client ID and a tenant ID, which are the two identifiers of an Azure user-assigned managed identity, so the credential is Azure AD workload identity: the gateway's workload presents a token its own platform issued, Azure AD trades it for an Azure AD token under a federated credential, and the role assignment on the resource authorizes the call.

Nothing about an external identity provider is involved, so neither the OpenAI federation steps nor the Anthropic ones transfer. The two things this mode does need, an issuer the gateway's workload can prove and a federated credential that trusts it, are both Azure-side objects created in the steps below.

The gateway still has to run inside the customer's Azure estate

A federated credential trusts a specific issuer and subject, which in practice means a Kubernetes service account on a cluster whose OIDC issuer Azure AD can reach. The SaaS gateway presents no such token, so this mode is self-hosted in practice for the same reason Managed is. Settle the deployment model in Step 3 before offering either.

Choosing between the two keyless modes comes down to the host. Managed reads a token from the Azure instance metadata endpoint, which a virtual machine, scale set or container app exposes directly. Workload Identity suits an AKS pod, where the metadata endpoint is not the identity boundary and each workload gets its own service account token instead.

▶ Step W1 — Create a user-assigned managed identity

The federated credential attaches to a user-assigned managed identity, so the identity comes first. Create one for this integration rather than reusing a shared identity, because the role assignment in Step W3 lands on everything that identity is attached to.

az identity create \
  --name "aigw-azure-openai-prod" \
  --resource-group "<RESOURCE_GROUP>" \
  --location "<LOCATION>"

az identity show \
  --name "aigw-azure-openai-prod" \
  --resource-group "<RESOURCE_GROUP>" \
  --query "{clientId:clientId, principalId:principalId, tenantId:tenantId}" -o table

Record all three values. The client ID and the tenant ID go into the wizard in Step W4. The principal ID is what the role assignment in Step W3 targets, and it is a different GUID from the client ID.

Verification

The command prints three distinct GUIDs, and the identity appears in the Azure portal under Managed Identities in the chosen resource group.

▶ Step W2 — Add a federated credential for the gateway workload

The federated credential tells Azure AD which external token it should accept in place of a secret. It names three things: the issuer that signs the token, the subject inside the token, and the audience the token is addressed to.

  1. Read the OIDC issuer URL of the cluster the gateway runs on. For AKS, az aks show --name "<CLUSTER>" --resource-group "<RESOURCE_GROUP>" --query "oidcIssuerProfile.issuerUrl" -o tsv returns it, and the cluster needs the OIDC issuer and workload identity features enabled first.
  2. Read the namespace and service account name the gateway pods run under.
  3. Create the credential on the identity from Step W1.
az identity federated-credential create \
  --name "aigw-gateway" \
  --identity-name "aigw-azure-openai-prod" \
  --resource-group "<RESOURCE_GROUP>" \
  --issuer "<OIDC_ISSUER_URL>" \
  --subject "system:serviceaccount:<NAMESPACE>:<SERVICE_ACCOUNT>" \
  --audience "api://AzureADTokenExchange"
The subject string is matched exactly

Azure AD compares the sub claim character for character and supports no wildcards. A credential written for system:serviceaccount:portkey:default rejects a pod running as system:serviceaccount:portkeyai:gateway, and the failure reads as an authentication error rather than a mismatch. Read the namespace and service account from the running deployment rather than from the Helm values file.

Pods also need the workload identity label

On AKS the service account carries the annotation azure.workload.identity/client-id naming the identity from Step W1, and the pod template carries the label azure.workload.identity/use: "true". Without both, the projected token is never mounted and the gateway falls back to whatever other credential it can find. The identity section of the Kubernetes deployment guide covers the gateway's own chart values.

Verification

az identity federated-credential list --identity-name "aigw-azure-openai-prod" --resource-group "<RESOURCE_GROUP>" -o table lists one credential whose issuer matches the cluster OIDC issuer URL and whose subject matches the namespace and service account the gateway pods actually run under.

▶ Step W3 — Assign Cognitive Services OpenAI User to the identity

The federated credential proves who the workload is. It grants no access to anything. The role assignment is what authorizes inference against this resource, and it targets the identity's principal ID from Step W1.

AOAI_RESOURCE_ID=$(az cognitiveservices account show \
  --name "<RESOURCE_NAME>" \
  --resource-group "<RESOURCE_GROUP>" \
  --query id -o tsv)

az role assignment create \
  --role "Cognitive Services OpenAI User" \
  --assignee-object-id "<IDENTITY_PRINCIPAL_ID>" \
  --assignee-principal-type ServicePrincipal \
  --scope "$AOAI_RESOURCE_ID"
Cognitive Services OpenAI User, not Contributor and not Owner

Cognitive Services OpenAI User permits inference calls against the resource and nothing else. Contributor and Owner both include the ability to read the resource keys, which hands a keyless credential the long-lived key this mode was chosen to remove, and Owner adds the ability to grant that to others. A 403 after this step means the principal or the scope is wrong, and widening the role hides the mistake instead of fixing it.

Verification

az role assignment list --scope "$AOAI_RESOURCE_ID" -o table lists the identity against Cognitive Services OpenAI User, and the scope column ends in the Azure OpenAI resource name rather than the resource group.

▶ Step P1 — Provision the integration to workspaces
  1. On Workspace Provisioning, select the workspaces that should reach this Azure OpenAI resource.
  2. Set a budget and a rate limit on each, following configuration chapter 9.
Budget and rate limits cannot be edited once set

Verification

Each selected workspace shows a budget and a rate limit, and the workspace the first call will be made from is on the list.

▶ Step P2 — Allowlist the deployments, not the models

The allowlist is set on the integration and nowhere else, and it applies to every workspace the integration reaches. For Azure OpenAI the entries are the deployment names recorded in Step 2, because the deployment name is what a caller sends.

  1. On Model Provisioning, choose Allow Specific Models rather than Allow All Models.
  2. Add one entry for each deployment that should be callable.
  3. Count the entries against the Step 2 list.
Allow All behaves differently here

For a provider with a global catalog, Allow All Models admits models the provider releases in future. For Azure OpenAI the callable set is whatever the customer has deployed, so the same setting admits any deployment created on that resource later, by anyone with Contributor on it. Both are a cost control question and the allowlist is the answer to it.

▶ Enable the approved models
  1. Use Search... to find each approved model by name.
  2. Set the toggle on each model card to on. The toggle sits in the top right of the card.
  3. Leave every other model off.

The expensive models are enabled by the same click as the cheap ones

Nothing in this list distinguishes a model that costs cents from one that costs dollars for the same prompt. ▶ Decide what happens to models released later

Below the model list is a toggle reading Automatically enable new models from this provider, described as making new models from the provider available on this integration. It is off by default.

Leaving it off means a model released next month is unavailable until someone enables it. Turning it on means that model is callable the day it ships, under the budgets already in place, with no review.

Off suits a governed tenant, on suits a lab

An organization that approves models through a review process wants this off, because the toggle quietly bypasses that process. A team that wants the newest model the day it lands wants it on. Record which was chosen and why, because the setting is invisible until an unexpected model appears in the logs.

Verification

The toggle reflects a decision somebody made, rather than the default nobody looked at.

▶ Set per-model pricing, where the published rate is wrong

Each model card carries a Set Pricing button. It opens a drawer titled Update Base Model on the right of the page.

The drawer opens with Add custom pricing for this model? switched off, explained as using default public model pricing from the base model when nothing is specified, with fine tuned models using public fine tuned model pricing. Switch it on and the drawer accepts:

FieldWhat it takes

Make the first model call

One request exercises the resource name, the deployment entry, the API version, the credential, the role assignment, the allowlist and the workspace key together. Everything configured so far has been untested until this point, and on the identity paths the role assignment has had no opportunity to fail yet.

Two values are needed. The gateway base URL is the address the gateway was given at deployment, and the client applications guide covers where applications get it. The API key is a workspace key from the gateway, not the Azure key.

▶ Step F1 — Call a deployment with curl

Name the deployment in the model field, prefixed with the integration slug. The example uses the slug azure-openai-prod and a deployment named chat-prod.

export GATEWAY_BASE_URL="https://<your-gateway-address>"
export PORTKEY_API_KEY="<workspace-api-key>"

curl "$GATEWAY_BASE_URL/v1/chat/completions" \
  -H "Authorization: Bearer $PORTKEY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "@azure-openai-prod/chat-prod",
    "messages": [{"role": "user", "content": "Reply with the single word ready."}]
  }'

Read the result against this table before changing any configuration. Each outcome points at one earlier decision.

OutcomeWhat it means
A model responseThe resource, the deployment, the API version, the credential and the role assignment all work.
Model not found or not permittedThe model value names a model rather than a deployment, or the deployment is missing from the allowlist in Step P2, or the integration is not provisioned to this workspace.
Authentication rejected at the gatewayThe workspace API key is wrong or lacks the completions permission. This failure happens before Azure is contacted.
Azure returns 401In Default mode, the key is wrong or belongs to a different resource. In Azure Entra mode, the client ID, secret or tenant ID is wrong, or the secret has expired. In the two keyless modes, the identity or the federated credential is wrong.
Azure returns 403The credential authenticated and has no permission. The Cognitive Services OpenAI User assignment is missing, is scoped to the wrong resource, or targets the wrong principal object.
Azure returns 404The resource name is wrong, or the deployment name does not exist on that resource.
Azure rejects the API versionThe api-version on the deployment entry is not one this resource accepts.
HTTP 446A guardrail denied the request. The integration is working and the content failed a check.
Verification

A model response comes back, made with a workspace key, naming @<slug>/<deployment-name>. The request appears in the gateway logs with a non-zero token count and a non-zero cost.

▶ Step F2 — Call the same deployment from the OpenAI Python SDK

Azure OpenAI reaches the gateway through the OpenAI SDK rather than the Azure OpenAI SDK, because the application now talks to the gateway and the gateway talks to Azure. The application sends no resource name, no API version and no Azure credential.

import os
from openai import OpenAI

client = OpenAI(
    base_url=f"{os.environ['GATEWAY_BASE_URL']}/v1",
    api_key=os.environ["PORTKEY_API_KEY"],
)

response = client.chat.completions.create(
    model="@azure-openai-prod/chat-prod",
    messages=[{"role": "user", "content": "Reply with the single word ready."}],
)

print(response.choices[0].message.content)
print(response.usage)

An application migrating off a direct Azure OpenAI connection changes three values: the base URL becomes the gateway address with /v1, the API key becomes the workspace key, and the model becomes @<slug>/<deployment-name>. The request body and the response body do not change.

Clients that send a bare model name

Some clients cannot put a slug in the model field and send the deployment name on its own. Those clients need the header x-portkey-provider: @<slug> as a fourth value. The client applications guide lists which ones.

Verification

The script prints the model's reply and a usage object carrying prompt and completion token counts. A usage object of None means the response arrived without usage data, which Step F3 addresses.

▶ Step F3 — Confirm a streaming call still records tokens

Azure OpenAI is OpenAI-compatible, which means it inherits the streaming behavior that silently zeroes out cost tracking. With stream: true and nothing else, the provider sends no usage data, the gateway records zero tokens and zero cost, and the budget set in Step P1 never sees the money. The calls succeed, the dashboards look healthy, and the spend is invisible.

The caller has to send stream_options: {"include_usage": true} alongside stream: true.

curl "$GATEWAY_BASE_URL/v1/chat/completions" \
  -H "Authorization: Bearer $PORTKEY_API_KEY" \
  -H "Content-Type: application/json" \
  -N \
  -d '{
    "model": "@azure-openai-prod/chat-prod",
    "stream": true,
    "stream_options": {"include_usage": true},
    "messages": [{"role": "user", "content": "Name three cities."}]
  }'
stream = client.chat.completions.create(
    model="@azure-openai-prod/chat-prod",
    messages=[{"role": "user", "content": "Name three cities."}],
    stream=True,
    stream_options={"include_usage": True},
)

for chunk in stream:
    if chunk.usage is not None:
        print(chunk.usage)
This is an application change, not a gateway setting

No switch in the integration fixes it. Every application that streams has to send the option, so the list of applications built during the engagement is also the list of code changes this requires. Raise it with the application owners at the same time as the three connection values, because a customer who finds out later has already lost the cost record for everything streamed in between.

Verification

The final chunk of the stream carries a usage object with non-zero token counts, and the request appears in the gateway logs with a non-zero cost rather than zero.

Troubleshooting

▶ The call returns a model-not-found error and the model exists in Azure

The request named the model rather than the deployment. Azure OpenAI addresses a deployment, and the deployment name is whatever the person who deployed the model chose.

  1. Read the model value the caller sent. A value of @azure-openai-prod/gpt-4o is a model name and fails even when gpt-4o is deployed.
  2. Compare it against the deployment list from Step 2.
  3. Check the allowlist from Step P2 contains that deployment.
  4. Check the integration is provisioned to the workspace the key belongs to.
Verification

The same call with the deployment name substituted returns a model response, and the deployment appears in the allowlist.

▶ Azure returns 403 and the credential is correct

A 403 after a successful authentication is a role assignment problem. The credential proved who it is and holds no permission to run inference on this resource. Three causes account for most of them.

CauseCheck
Assignment targets the wrong objectThe role was assigned to the app registration object ID instead of the service principal object ID. Re-read it with az ad sp show --id <client-id> --query id -o tsv and compare.
Assignment is on the wrong scopeThe scope string must end in the Azure OpenAI resource. An assignment on a different resource in the same group looks correct in a list view.
Assignment has not applied yetWait and retry before changing anything. Azure role assignments are not always effective the moment the portal confirms them.
Do not widen the role to clear a 403

Assigning Contributor makes the call succeed and gives the credential the ability to read the resource keys and change deployments. The original problem is still there, now hidden behind a permission the integration was supposed to avoid. Fix the principal or the scope.

Verification

az role assignment list --scope "$AOAI_RESOURCE_ID" -o table shows one Cognitive Services OpenAI User row for the expected principal, and the call from Step F1 returns a model response.

▶ Azure returns 401 on an integration that worked yesterday

In Azure Entra mode the usual cause is an expired client secret. Entra sets an expiry when the secret is created and nothing in Strata Cloud Manager reports it approaching.

  1. Open the app registration and check Certificates & secrets for the expiry date of the secret in use.
  2. Create a new secret, store it in the vault, and update the vault secret the integration references.
  3. Delete the expired secret so the next engineer does not read its expiry as current.
  4. Record the new expiry in the customer's renewal tracker.

In Default mode, check whether the resource key was regenerated. Regenerating a key invalidates it everywhere at once, and the gateway is one of several consumers that will have stopped at the same moment.

Verification

The call from Step F1 returns a model response, and the renewal tracker holds the new expiry date with a named owner.

▶ The managed identity option does not work, or is not offered

Confirm the deployment model first. A SaaS gateway cannot use a managed identity, and no configuration on either side changes that.

  1. Check the gateway the integration is used by, using Step 3.
  2. For a Hybrid data plane, confirm the identity is attached to the compute hosting the gateway rather than to a different resource in the same group.
  3. For a host carrying several user-assigned identities, confirm the client ID supplied in Step M4 is the client ID and not the principal ID.
  4. For AKS, confirm the workload identity binding reaches the gateway's service account, following the identity section of the Kubernetes deployment guide. An AKS gateway usually belongs in the Workload Identity mode instead, where the subject string in Step W2 has to match the running service account exactly.
Verification

Either the call from Step F1 returns a model response with no secret stored anywhere, or the customer has been told the mode is unavailable on a SaaS gateway and the Azure Entra mode has been agreed instead.

▶ Calls succeed and every cost figure reads zero

The callers are streaming without stream_options. The gateway records what the provider sends, and a streamed OpenAI-compatible response carries no usage data unless the caller asks for it.

  1. Check a zero-cost request in the gateway logs for stream: true in its body.
  2. Reproduce it with Step F3, first without the option and then with it.
  3. Give the application owners the one-line change and the list of applications that stream.
The historical records cannot be recovered

Requests already recorded at zero tokens stay at zero. The budget consumed nothing for them and the cost reporting for that period understates the spend permanently. Compare the Azure resource's own billing for the period against the gateway's figure so the customer knows the size of the gap.

Verification

A streamed call now records a non-zero token count and a non-zero cost in the gateway logs, and the gateway's daily cost figure tracks the Azure resource's own billing.

▶ One deployment works and another returns an error

The deployment entries carry an API version each, so one wrong value affects one deployment. A feature such as structured output or tool calling that works on one deployment and fails on another is the same cause.

  1. Compare the api-version on the failing entry against the version a working application sends to that deployment.
  2. Check the deployment name for a typo. A near-miss name returns a 404 from Azure rather than a validation error from the gateway.
  3. Check the deployment still exists on the resource with az cognitiveservices account deployment list. A deployment deleted in Azure leaves a working entry in the integration.
Verification

Each deployment in the allowlist returns a model response to the call in Step F1 with its own name substituted.
