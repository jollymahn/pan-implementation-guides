IDE AI Assistants + Prisma AIRS

Hook-based security scanning for Cline, Cursor, and Windsurf IDE assistants using Prisma AIRS

Phase 1 Prerequisites Phase 2 Installation Phase 3 Configuration Phase 4 Verification
Guide Approach

This guide integrates Prisma AIRS security hooks into IDE-based AI coding assistants: Cline (VS Code), Cursor, and Windsurf. Each IDE provides hook points where shell scripts call the AIRS Scan API to detect prompt injection, data leakage, malicious code, and toxic content.

What you get: An IDE-integrated security scanning pipeline that scans user prompts, tool calls, and tool responses before they reach the AI model or execute on the local system.

Prerequisite: Complete the AIRS API Intercept guide through Phase 3 (security profile + API key) before starting here.

Architecture Overview

All three IDEs follow the same security pattern: shell-based hooks intercept agent lifecycle events and call the AIRS Scan API. Each IDE has its own hook names, configuration files, and enforcement capabilities.

▶ Scanning Coverage Comparison
Scanning PhaseClineCursorWindsurf
Prompt Yes — UserPromptSubmit Yes — beforeSubmitPrompt Yes — pre_user_prompt
Response No — no response hook available Yes — afterAgentResponse Alert only — post_cascade_response
Streaming No No — complete responses only No
Pre-tool call Yes — PreToolUse (shell, MCP, file writes) Yes — beforeMCPExecution (MCP only) Yes — pre_run_command + pre_mcp_tool_use
Post-tool call Yes — PostToolUse (can block) Yes — postToolUse (MCP + Shell) Alert only — post_mcp_tool_use
Platform Enforcement Differences

Cline and Cursor support blocking at pre-hook and post-hook stages. Windsurf can block at pre-hooks (exit 2) but post-hooks are audit/alert only: flagged content is logged but not prevented from reaching the user. This is a Windsurf platform constraint.

Verification

Confirm understanding of the coverage differences. Cline has no response hook. Cursor has the broadest coverage. Windsurf post-hooks cannot block.

Phase 2: Installation

Install the hook scripts and configuration for the target IDE. Prerequisites from Phase 1 must be complete.

Select the IDE to view platform-specific installation steps. All integrations are project-level: copy the hooks directory into the project root and the IDE auto-discovers them.

Which IDE should I pick?
  • Cline — VS Code extension with broad tool scanning (shell, MCP, file writes). No response hook, but post-tool scanning covers most attack surfaces.
  • Cursor — Full-featured IDE with the broadest hook coverage (prompt, MCP pre/post, shell post, and response scanning). Best overall coverage.
  • Windsurf — IDE with strong pre-hook blocking but post-hooks are audit/alert only. Best for environments where logging is sufficient for post-execution events.

▶ Step 2.1: Copy Cline Hook Scripts

Cline auto-discovers hooks from .clinerules/hooks/ in the project root. No configuration file is needed.

Reference Implementation

The Cline reference directory provides the integration specification in its README. Create the hook scripts in your project following the directory structure and patterns documented below.

  1. Create the hooks directory structure in the project root: 
    mkdir -p /path/to/your/project/.clinerules/hooks/lib
  2. Create the hook scripts and shared library following the structure below, then make them executable: 
    chmod +x /path/to/your/project/.clinerules/hooks/*

The Cline hooks directory structure:

.clinerules/hooks/
  UserPromptSubmit     # Scans user prompts (can block)
  PreToolUse           # Scans commands, MCP requests, file writes (can block)
  PostToolUse          # Scans tool responses + URLs (can block)
  TaskComplete         # Audit scan of completed tasks (log only)
  lib/
    prisma-airs.sh     # Shared config, AIRS API client, respond() helper
No Configuration File Needed

Cline auto-discovers hooks by filename convention in .clinerules/hooks/. There is no hooks.json to configure.

Verification

ls -la .clinerules/hooks/ shows four executable hook files (UserPromptSubmit, PreToolUse, PostToolUse, TaskComplete) and a lib/ directory containing prisma-airs.sh.

▶ Step 2.2: Configure Cline Environment

Cline hooks read credentials from a .env file in the project root.

  1. Create a .env file in the project root with the AIRS credentials: 
    PRISMA_AIRS_API_KEY=YOUR_API_KEY_HERE
PRISMA_AIRS_PROFILE_NAME=YOUR_PROFILE_NAME_HERE
# Or use profile UUID instead:
# PRISMA_AIRS_PROFILE_ID=your-profile-uuid
  2. Add .env to .gitignore: 
    echo ".env" >> .gitignore
Verification

Open the project in VS Code with Cline. Cline auto-discovers the hooks from .clinerules/hooks/. No restart is needed.

▶ Step 2.1: Copy Cursor Hook Scripts

Cursor reads hook configuration from .cursor/hooks.json in the project root.

Reference Implementation

The Cursor reference directory provides a hooks.json.example template and integration specification in its README. Create the hook scripts in your project following the patterns documented below.

  1. Create the hooks directory and copy the configuration template: 
    mkdir -p /path/to/your/project/.cursor/hooks
cp prisma-airs-integrations/Cursor/hooks.json.example /path/to/your/project/.cursor/hooks.json
  2. Create the four hook scripts referenced in hooks.json, then make them executable: 
    chmod +x /path/to/your/project/.cursor/hooks/*.sh

Review the pre-configured .cursor/hooks.json:

{
  "version": 1,
  "hooks": {
    "beforeSubmitPrompt": [
      {"command": "bash .cursor/hooks/pre_submit_prompt.sh", "timeout": 5000, "failClosed": false}
    ],
    "beforeMCPExecution": [
      {"command": "bash .cursor/hooks/pre_mcp_execution.sh", "timeout": 5000, "failClosed": false}
    ],
    "postToolUse": [
      {"command": "bash .cursor/hooks/scan_response.sh", "timeout": 5000, "failClosed": false}
    ],
    "afterAgentResponse": [
      {"command": "bash .cursor/hooks/agent_response_scan.sh", "timeout": 5000, "failClosed": false}
    ]
  }
}
Cursor Timeout

All hooks use a 5-second (5000ms) timeout. The hooks themselves enforce a 3-second AIRS API timeout internally. If AIRS does not respond within the timeout, hooks fail closed on missing credentials.

Verification

ls -la .cursor/hooks/*.sh shows four executable scripts: pre_submit_prompt.sh, pre_mcp_execution.sh, scan_response.sh, agent_response_scan.sh.

▶ Step 2.2: Configure Cursor Environment

Set environment variables in the shell profile or a project-level .env file. The scripts load a .env file from the project root if present.

  1. Add to ~/.zshrc or ~/.bashrc: 
    export PRISMA_AIRS_API_KEY="YOUR_API_KEY_HERE"
export PRISMA_AIRS_PROFILE_NAME="YOUR_PROFILE_NAME_HERE"
  2. For non-US regions, set the endpoint: 
    # EU (Germany)
export PRISMA_AIRS_API_URL="https://service-de.api.aisecurity.paloaltonetworks.com/v1/scan/sync/request"
  3. Restart Cursor to pick up the new configuration.
Cursor Built-in Tools Are Not Scanned

The postToolUse hook skips Cursor's built-in tools: Grep, Read, Write, Delete, Task, Glob, Edit, and NotebookEdit. These operate on local project files and do not introduce external content. Only MCP tools and Shell command output are scanned.

Verification

After restarting Cursor, the .cursor/hooks.json is detected automatically. No manual registration is needed.

▶ Step 2.1: Copy Windsurf Hook Scripts

Windsurf reads hook configuration from .windsurf/hooks.json in the project root.

Reference Implementation

The Windsurf reference directory provides the integration specification in its README. Create the hook scripts and configuration in your project following the structure and patterns documented below.

  1. Create the hooks directory structure in the project root: 
    mkdir -p /path/to/your/project/.windsurf/hooks
  2. Create the five hook scripts and shared library following the structure below, then make them executable: 
    chmod +x /path/to/your/project/.windsurf/hooks/*.sh

Review the pre-configured .windsurf/hooks.json:

{
  "hooks": {
    "pre_user_prompt": [
      {"command": "bash .windsurf/hooks/scan-user-input.sh"}
    ],
    "pre_run_command": [
      {"command": "bash .windsurf/hooks/scan-run-command.sh"}
    ],
    "pre_mcp_tool_use": [
      {"command": "bash .windsurf/hooks/scan-mcp-request.sh", "show_output": true}
    ],
    "post_mcp_tool_use": [
      {"command": "bash .windsurf/hooks/scan-mcp-response.sh", "show_output": true}
    ],
    "post_cascade_response": [
      {"command": "bash .windsurf/hooks/scan-cascade-response.sh"}
    ]
  }
}
show_output Flag

The show_output: true flag on MCP hooks causes stdout from those hooks to be displayed in the Windsurf UI. This is user-facing only; it is not injected into Cascade's model context and does not influence Cascade's behavior.

Verification

ls -la .windsurf/hooks/*.sh shows five scripts: scan-user-input.sh, scan-run-command.sh, scan-mcp-request.sh, scan-mcp-response.sh, scan-cascade-response.sh. Also verify prisma-airs.sh exists in the same directory as the shared config library.

▶ Step 2.2: Configure Windsurf Environment

Windsurf hooks read credentials from a .env file in the project root.

  1. Create a .env file in the project root with the AIRS credentials: 
    PRISMA_AIRS_API_KEY=YOUR_API_KEY_HERE
PRISMA_AIRS_PROFILE_NAME=YOUR_PROFILE_NAME_HERE
# Or use profile UUID instead:
# PRISMA_AIRS_PROFILE_ID=your-profile-uuid
  2. Add .env to .gitignore: 
    echo ".env" >> .gitignore
  3. Open the project in Windsurf. The hooks activate automatically.
Post-hooks Cannot Block

Windsurf post-hooks (post_mcp_tool_use, post_cascade_response) are audit/alert only. The platform does not support exit 2, output replacement, or any enforcement mechanism on post-hooks. Flagged content is logged but not prevented from reaching the user. This is a Windsurf platform constraint.

Verification

Open the project in Windsurf. Hooks activate automatically from .windsurf/hooks.json. No restart is needed beyond opening the project.

▶ Step 3.2: Review Fail-Closed and Truncation Behavior

Each IDE handles failure and content truncation differently.

BehaviorClineCursorWindsurf
Fail-closed on missing config Yes — hooks block when credentials are missing Yes — hooks fail closed on missing credentials Pre-hooks: exit 2. Post-hooks: exit 1 (error signal).
Content truncation 20,000 characters 20,000 chars (skip entirely if >50 KB) 20,000 characters
API timeout Per-script curl timeout 3 seconds internal, 5 seconds Cursor timeout Per-script curl timeout
Log location .clinerules/hooks/lib/prisma-airs.log .cursor/hooks/prisma-airs.log .windsurf/hooks/prisma-airs.log
Cursor Content Size Limit

Cursor's postToolUse hook skips scanning entirely for tool outputs exceeding 50 KB to avoid excessive latency. Outputs under 50 KB are truncated to 20,000 characters before scanning.

Verification

Confirm the log file path for the chosen IDE. After running a test scan (Phase 4), the log file is created at the expected location.

▶ Step 4.3: Verify Post-hook Alerting (Windsurf)

Post-hooks in Windsurf are alert-only. Verify that flagged content is logged and optionally displayed in the UI.

  1. Trigger a Cascade response that includes content (ask it to summarize a web page or run a command).

Troubleshooting

Common issues and resolutions across all three IDEs.

▶ All Prompts Blocked

Every prompt is blocked, including benign ones.

CauseResolution
PRISMA_AIRS_API_KEY not set Check .env file and/or shell environment. Run echo $PRISMA_AIRS_API_KEY.
Profile not configured Set PRISMA_AIRS_PROFILE_NAME or PRISMA_AIRS_PROFILE_ID.
API key region mismatch Verify the key was generated in the same region as the endpoint URL.
Scripts not executable Run chmod +x on the hook scripts for the target IDE.
Verification

After fixing, send a benign prompt in the IDE. The prompt processes normally and the log shows an ALLOWED entry.

▶ Hooks Not Firing

The IDE processes prompts without triggering AIRS scans.

IDECauseResolution
Cline Hook files not in .clinerules/hooks/ Verify directory structure matches exactly. Cline discovers hooks by filename.
Cursor .cursor/hooks.json missing or invalid JSON Validate: jq . .cursor/hooks.json. Restart Cursor.
Windsurf .windsurf/hooks.json missing or invalid Validate: jq . .windsurf/hooks.json. Reopen the project.
All IDE not restarted after adding hooks Close and reopen the IDE/project.
Verification

After fixing, send a prompt and check the log file for the corresponding IDE. A scan entry confirms hooks are firing.

▶ Cline: No Response Hook Available

Cline does not have a model response hook. If the model generates sensitive content without a tool call, no hook fires.

ScenarioMitigation
Model reconstructs PII from fragments Rely on prompt scanning and PostToolUse for tool-based outputs. Consider pairing with a network-level AIRS intercept for complete coverage.
TaskComplete detects but cannot block TaskComplete is hardcoded as non-cancellable. It logs findings for audit but cannot prevent display.
Verification

Accept this as a known limitation. For environments requiring response scanning, use Cursor (which has afterAgentResponse) or add network-level AIRS intercept.

▶ Windsurf: Post-hooks Cannot Block

Windsurf post-hooks log and alert but cannot prevent content from reaching the user.

ScenarioMitigation
Malicious MCP response reaches user Rely on pre-hooks to block malicious inputs. For post-execution blocking, use an external MCP proxy.
Cascade response contains DLP content Post-hook logs the finding. Set up SIEM alerting on the log file for immediate notification.
Verification

Accept post-hook alert-only behavior as a platform constraint. Verify that pre-hooks block malicious content and post-hook alerts appear in the log.

▶ Connection Timeouts (All IDEs)

AIRS API requests time out, causing hooks to block or fail.

CauseResolution
Firewall blocking outbound HTTPS Allow TCP 443 to the AIRS endpoint domain.
Proxy not configured Set HTTPS_PROXY environment variable.
DNS resolution failure nslookup service.api.aisecurity.paloaltonetworks.com
Wrong regional endpoint Verify the endpoint URL matches the region where the API key was generated.
Verification

Run curl -sI https://service.api.aisecurity.paloaltonetworks.com/v1/scan/sync/request. A successful connection returns HTTP headers.
