Apigee X + Prisma AIRS + Vertex AI Integration

Dual-layer AI security scanning at the Apigee gateway with Shared Flow and OAuth2 authentication to Vertex AI

Phase 1 Prerequisites Phase 2 Shared Flow Phase 3 Proxy Config Phase 4 Authentication Phase 5 Deploy Phase 6 Verify
Guide Approach

This guide integrates Prisma AIRS with Apigee X to scan prompts and responses for Vertex AI API calls. Two reference architectures are available: a monolithic proxy (all scanning policies inline) and a Shared Flow (reusable scanning library called from multiple proxies). This guide covers the Shared Flow approach because it scales to multiple LLM proxies without duplicating AIRS-calling logic.

What you get: An Apigee X proxy that scans prompts at PreFlow Request and responses at PreFlow Response, using an encrypted KVM for credentials, OAuth2 for Vertex AI authentication, and per-detector graceful block envelopes.

Community Reference Implementation

These integrations are community examples supported as best effort by Palo Alto Networks. Review, adapt, and validate them for your environment before production use. Source: PaloAltoNetworks/prisma-airs-integrations/Google/apigee.

Architecture Overview

Apigee X sits between the client and Vertex AI. A Shared Flow (PANW-AIRS) encapsulates the AIRS-calling logic: reading credentials from an encrypted KVM, building the scan payload, sending the request, and evaluating the verdict. The API proxy (vertex-airs-sync) calls this Shared Flow via FlowCallout in both the PreFlow Request (prompt scan) and PreFlow Response (response scan) phases.

▶ Shared Flow vs. Monolithic Proxy

Two reference architectures are provided in the source repository:

Multi-proxy reuse Copy-paste per proxy One Shared Flow, many proxies
Credential storage KVM named private KVM named airs-config
Block response HTTP 400 HTTP 200 (Vertex-shaped graceful block)
Deployment script deploy.sh in apigee/ deploy.sh in apigee/sharedflow/

Understanding confirmed. This guide follows the Shared Flow approach. For the monolithic alternative, see the source repository README.

▶ Step 1.2: Enable Vertex AI API
  1. In the Google Cloud Console, navigate to APIs & Services → Library.
  2. Search for Vertex AI API.
  3. Click Enable if not already enabled.
Verification

The Vertex AI API shows as Enabled in the APIs & Services dashboard.

▶ Step 1.3: Create Vertex AI Service Account

The Apigee proxy uses a dedicated service account to authenticate to Vertex AI via OAuth2. This service account requires two IAM bindings.

  1. Create the service account: 
    gcloud iam service-accounts create apigee-vertex-sa \
  --display-name="Apigee Vertex AI Service Account" \
  --project=YOUR_PROJECT_ID
  2. Grant roles/aiplatform.user (deploy-time binding): 
    gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member="serviceAccount:apigee-vertex-sa@YOUR_PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/aiplatform.user"
  3. Grant roles/iam.serviceAccountTokenCreator to the Apigee service agent (runtime binding): 
    gcloud iam service-accounts add-iam-policy-binding \
  apigee-vertex-sa@YOUR_PROJECT_ID.iam.gserviceaccount.com \
  --member="serviceAccount:service-YOUR_PROJECT_NUMBER@gcp-sa-apigee.iam.gserviceaccount.com" \
  --role="roles/iam.serviceAccountTokenCreator"
Critical: Both IAM Bindings Required

Binding #1 (aiplatform.user) is a deploy-time grant on the project. Binding #2 (serviceAccountTokenCreator) is a runtime grant on a different principal (the Apigee service agent). Without binding #2, the proxy returns HTTP 500 GoogleTokenGenerationFailure even though deployment succeeds. See Using Google authentication.

Verification

Both IAM bindings are confirmed: gcloud projects get-iam-policy YOUR_PROJECT_ID --flatten="bindings[].members" --filter="bindings.members:apigee-vertex-sa" shows roles/aiplatform.user.

Phase 2: Shared Flow Setup

The PANW-AIRS Shared Flow is the reusable library that handles AIRS scanning. It reads credentials from an encrypted KVM, builds the scan payload, sends it to the AIRS API, and routes block verdicts to per-detector RaiseFault policies.

▶ Step 2.1: Create the Encrypted KVM

The AIRS token and profile are stored in an encrypted KVM named airs-config. The Shared Flow reads both values at request time via KVM-GetAIRSConfig with a 5-minute cache TTL.

The deploy.sh script automatically creates the encrypted KVM and populates it with the AIRS_TOKEN and AIRS_PROFILE values from your .env file. No manual KVM creation is needed.

If you need to create or update the KVM manually (e.g., rotating the AIRS token without redeploying), use the Apigee Management API:

# Create or update KVM entry via Management API
TOKEN=$(gcloud auth print-access-token)

curl -X POST \
  "https://apigee.googleapis.com/v1/organizations/YOUR_ORG/environments/YOUR_ENV/keyvaluemaps/airs-config/entries" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "airs_token", "value": "YOUR_AIRS_API_KEY"}'
Note: KVM Key Naming

The shared flow uses underscore-based KVM keys (airs_token, airs_profile). These match the <Parameter> values in KVM-GetAIRSConfig.xml. If you rename the keys, update the policy XML to match.

Verification

List KVM entries: apigeecli kvms entries list --org YOUR_ORG --env YOUR_ENV --name airs-config shows both airs_token and airs_profile.

▶ Step 2.2: Understand Shared Flow Policies

The PANW-AIRS Shared Flow contains these policies in execution order:

PolicyTypePurpose
KVM-GetAIRSConfigKeyValueMapOperationsRead airs_token and airs_profile from encrypted KVM (5-min cache)
JS-BuildAIRSScanBodyJavaScriptBuild AIRS scan payload with safe JSON.stringify
AM-SetAIRSScanRequestAssignMessageSet x-pan-token header and request body for the AIRS API call
SC-AIRSScanServiceCalloutSend scan request to AIRS API with x-pan-token header (5-second timeout)
EV-ParseAIRSVerdictExtractVariablesParse verdict into per-detector boolean flow variables
RF-PromptInjection-DetectedRaiseFaultReturn graceful block for prompt injection
RF-DLP-DetectedRaiseFaultReturn graceful block for DLP violations
RF-MaliciousURL-DetectedRaiseFaultReturn graceful block for malicious URLs
RF-MaliciousCode-DetectedRaiseFaultReturn graceful block for malicious code
RF-Toxic-DetectedRaiseFaultReturn graceful block for toxic content
RF-Generic-BlockRaiseFaultCatch-all graceful block for other detectors
Note: Graceful Block Envelopes

Each RF-* policy returns HTTP 200 with a Vertex-shaped response envelope. The airs.category field names the specific detector that fired. Clients using a Vertex SDK parse it like any other response. To fail loudly instead, change the <StatusCode> in each RF-* policy from 200 to 403.

Verification

Understanding confirmed. The Shared Flow handles credential reading, payload construction, API call, verdict parsing, and per-detector block routing.

▶ Step 2.3: Import and Deploy the Shared Flow

Import the PANW-AIRS Shared Flow bundle and deploy it to the target environment.

The deploy.sh script handles Shared Flow import and deployment automatically. If you need to import and deploy manually, use the Apigee Management API:

  1. Zip and import the Shared Flow bundle: 
    TOKEN=$(gcloud auth print-access-token)

# Zip the bundle
cd PANW-AIRS && zip -r ../PANW-AIRS.zip . && cd ..

# Import
curl -X POST \
  "https://apigee.googleapis.com/v1/organizations/YOUR_ORG/sharedflows?name=PANW-AIRS&action=import" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @PANW-AIRS.zip
  2. Deploy to the environment: 
    curl -X POST \
  "https://apigee.googleapis.com/v1/organizations/YOUR_ORG/environments/YOUR_ENV/sharedflows/PANW-AIRS/revisions/1/deployments?override=true" \
  -H "Authorization: Bearer $TOKEN"
Verification

The Shared Flow appears in the Apigee Console under Develop → Shared Flows with a deployed revision in the target environment.

Phase 3: Proxy Configuration

The API proxy (vertex-airs-sync) is a thin wrapper that extracts content, calls the Shared Flow via FlowCallout, and routes to Vertex AI.

▶ Step 3.1: Understand the Proxy Structure

The proxy bundle contains these components:

ComponentPurpose
EV-ExtractFieldsExtract projectId, region, modelProvider, and model from the URL path
JS-ExtractRequestPromptExtract the user prompt from the Vertex AI request body (contents[].parts[].text)
FC-CallAIRSInputFlowCallout to PANW-AIRS Shared Flow for prompt scanning
JS-ExtractResponsePromptExtract the model response from the Vertex AI response body
FC-CallAIRSOutputFlowCallout to PANW-AIRS Shared Flow for response scanning
llm.xmlTarget endpoint configuration with GoogleAccessToken authentication
AM-SetTargetDynamically construct the Vertex AI target URL at runtime using extracted path variables
Verification

Understanding confirmed. The proxy extracts content at each phase and delegates scanning to the Shared Flow.

▶ Step 3.2: Understand the API Contract

Once deployed, the proxy accepts the same Vertex AI :generateContent payload format. Clients change only the host.

Endpoint

POST https://YOUR-ENVGROUP-HOSTNAME/vertex-airs-sync/v1/projects/YOUR_PROJECT/locations/REGION/publishers/google/models/MODEL:generateContent

Request Body (identical to Vertex AI native)

{
  "contents": [
    {
      "role": "user",
      "parts": [{"text": "Your prompt here"}]
    }
  ]
}

Session Tracking

The shared flow uses context.getVariable('messageid') as the transaction_id in each AIRS scan request. This is Apigee's built-in unique request identifier -- no client-side headers are required for request correlation.

Graceful Block Response (HTTP 200)

{
  "candidates": [{
    "content": {
      "role": "model",
      "parts": [{"text": "Your prompt has been flagged by Palo Alto AIRS..."}]
    },
    "finishReason": "STOP"
  }],
  "modelVersion": "gemini-2.5-flash",
  "airs": {
    "action": "block",
    "category": "prompt-injection",
    "scan_id": "SCAN_UUID"
  }
}
Verification

Understanding confirmed. The proxy is a transparent pass-through for the Vertex AI API contract, adding only the airs object on blocked responses.

Phase 4: Authentication Setup

Two authentication paths are configured: OAuth2 for Vertex AI access (handled by GoogleAccessToken policy) and x-pan-token for AIRS API access (read from the encrypted KVM).

▶ Step 4.1: Confirm Vertex AI Authentication

The proxy's target endpoint uses the GoogleAccessToken policy to mint OAuth2 tokens at runtime using the service account created in Phase 1. No manual key management is required.

  1. The target endpoint (llm.xml) references the service account email in the GoogleAccessToken configuration.
  2. Confirm the service account email in the proxy bundle matches the one created in Step 1.3: 
    apigee-vertex-sa@YOUR_PROJECT_ID.iam.gserviceaccount.com
  3. The deploy script sets the service account when deploying the proxy revision. No manual configuration is needed if using deploy.sh.
Verification

The service account email in the proxy bundle matches the IAM-bound service account from Phase 1.

▶ Step 4.2: Confirm AIRS Authentication

AIRS authentication uses the x-pan-token header populated from the encrypted KVM. No additional configuration is needed beyond Phase 2, Step 2.1.

  1. Confirm the AM-SetAIRSScanRequest policy in the Shared Flow sets the header: 
    <Set>
  <Headers>
    <Header name="x-pan-token">{airs.token}</Header>
    <Header name="Content-Type">application/json</Header>
  </Headers>
</Set>
  2. The {airs.token} flow variable is populated by KVM-GetAIRSConfig from the encrypted KVM.
Note: No Hardcoded Credentials

The AIRS token never appears in proxy XML, environment variables visible to operators, or commit history. It lives exclusively in the encrypted: true KVM bound to the Apigee environment.

Verification

The SC-AIRSScan policy uses the {airs.token} flow variable, populated from the encrypted KVM.

▶ Step 5.2: Run the Deployment Script

The deploy.sh script is idempotent. It handles KVM creation, Shared Flow import/deploy, and proxy import/deploy in one command.

./deploy.sh --env-file=.env

The script performs these steps in order:

  1. Upserts the encrypted KVM airs-config with airs_token and airs_profile.
  2. Imports and deploys the PANW-AIRS Shared Flow.
  3. Imports and deploys the vertex-airs-sync proxy at basepath /vertex-airs-sync, attaching the Vertex service account.
  4. Prints ready-to-paste smoke-test curl commands.

End-to-end on a fresh environment: approximately 3 to 5 minutes.

Note: Shared Flow Only

Pass --skip-sync to deploy only the Shared Flow without the proxy. Run ./deploy.sh -h for the full flag list.

Verification

The script completes without errors and prints the smoke-test curl commands. Both the Shared Flow and proxy show as deployed in the Apigee Console.

▶ Security Behavior
FeatureBehavior
Fail-closed SC-AIRSScan runs with continueOnError="false". If AIRS is unreachable, the scan policy faults before the prompt reaches Vertex. The request fails closed with Apigee's default ServiceCallout error (5xx).
Encrypted KVM AIRS token never appears in proxy XML, operator-visible env vars, or commit history.
Per-detector routing Each detector routes to its own RF-* policy, naming the specific category in airs.category.
No prompt logging Neither the Shared Flow nor the proxy persists prompt/response content. AIRS logs are viewable in Strata Cloud Manager.
Scoped Vertex access Proxy uses a dedicated SA with roles/aiplatform.user, not a developer's identity.
Verification

Understanding confirmed. The deployment is fail-closed by default with encrypted credential storage and no prompt logging.

▶ Rollback

deploy.sh is idempotent: re-running pushes new revisions and auto-undeploys older ones via override=true. To roll back manually:

# Undeploy current proxy revision
curl -X DELETE \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://apigee.googleapis.com/v1/organizations/YOUR_ORG/environments/YOUR_ENV/apis/vertex-airs-sync/revisions/CURRENT_REV/deployments"

# Deploy a prior revision
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://apigee.googleapis.com/v1/organizations/YOUR_ORG/environments/YOUR_ENV/apis/vertex-airs-sync/revisions/PREVIOUS_REV/deployments?override=true&serviceAccount=SA_EMAIL"

Use the same pattern for the Shared Flow (/sharedflows/PANW-AIRS/...), minus the serviceAccount parameter.

Verification

The prior revision is deployed and serving traffic. Confirm by sending a test request and checking the response.
