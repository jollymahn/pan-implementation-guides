Kong Gateway + Prisma AIRS Integration

Scan AI/LLM traffic for security threats at the Kong API gateway layer using Prisma AIRS

Phase 1 Prerequisites Phase 2 Plugin Setup Phase 3 Gateway Config Phase 4 Deployment Phase 5 Verification
Guide Approach

This guide integrates Prisma AIRS with Kong Gateway to scan AI/LLM prompts and responses for security threats before they reach the model or the client. Three integration methods are available, each with different coverage and deployment models. Select the method that matches your environment and proceed through the phases linearly.

What you get: A Kong Gateway that intercepts AI traffic, scans it through the Prisma AIRS API, and blocks prompt injection, data leakage, toxic content, and other threats in real time.

Community Reference Implementation

These integrations are community examples supported as best effort by Palo Alto Networks. Review, adapt, and validate them for your environment before production use. Source: PaloAltoNetworks/prisma-airs-integrations/Kong.

Architecture Overview

Kong Gateway sits between the client and the LLM provider. The AIRS plugin intercepts requests in the access phase (before the prompt reaches the LLM) and the response phase (before the completion returns to the client). Each phase sends the content to the Prisma AIRS Scan API for a synchronous verdict. If the verdict is block, Kong returns an HTTP 403 and the request never reaches (or leaves) the LLM.

Each integration method covers a different set of scanning phases. Select the method that matches your requirements.

Phase 1: Prerequisites

Which integration should I pick?
  • Custom Plugin v1 — Full prompt + response scanning. Supports all LLM providers through Kong AI Gateway (AI Proxy plugin normalizes to OpenAI format). Best for LLM-only traffic.
  • Custom Plugin v2 (MCP-aware) — Everything in v1, plus MCP tools/call inspection (scanned as AIRS tool_event) and buffered SSE response scanning. Natively parses OpenAI + Bedrock Converse. Best when Kong also brokers MCP tool calls.
  • Request Callout — Prompt-only scanning with zero custom plugin deployment. Uses Kong's native request-callout plugin with inline Lua. Best for Kong Konnect SaaS environments that only need prompt scanning (OpenAI only).
▶ Step 1.1: Confirm Kong Gateway Version

The custom plugin requires Kong Gateway 3.4 or later. The Request Callout method requires a Kong Konnect account.

  1. Check the running Kong version: 
    curl -s http://localhost:8001/ | jq '.version'
  2. Confirm the output shows version 3.4.0 or later.
  3. For Kong Konnect (Request Callout method), confirm access to the Konnect control plane at cloud.konghq.com.
Verification

The version string returned is 3.4.x or higher, or access to Kong Konnect is confirmed.

▶ Step 1.2: Obtain Prisma AIRS API Key

The AIRS API key authenticates each scan request. Generate it from Strata Cloud Manager.

  1. Log in to Strata Cloud Manager.
  2. Navigate to AI Runtime Security → Settings → API Keys.
  3. Click Generate API Key.
  4. Copy the API key and store it securely. This value is used as the x-pan-token header in all AIRS API calls.
Important: Regional API Endpoints

AIRS API keys are region-bound. Use the endpoint matching the tenant that issued the key:

RegionEndpoint
US (default)https://service.api.aisecurity.paloaltonetworks.com
EU (Germany)https://service-de.api.aisecurity.paloaltonetworks.com
Indiahttps://service-in.api.aisecurity.paloaltonetworks.com
Singaporehttps://service-sg.api.aisecurity.paloaltonetworks.com

A US-issued key will fail with 403 against EU or other regional endpoints.

Verification

An AIRS API key is generated, copied, and stored securely. The regional endpoint matching the key's tenant is noted.

▶ Step 1.3: Configure AIRS Security Profile

The security profile defines which detectors (prompt injection, DLP, toxic content, etc.) are active and whether the action is block, alert, or allow.

  1. In Strata Cloud Manager, navigate to AI Runtime Security → AI Security Profiles.
  2. Click Add Profile.
  3. Set a Profile Name (e.g., kong-gateway-profile). This exact string is used in the plugin configuration as profile_name.
  4. Enable the desired detectors and set actions per detector.
  5. Click Save.
Verification

The security profile appears in the AI Security Profiles list with the expected detectors enabled.

▶ Step 1.4: Confirm Kong Service and Route

A Kong Service and Route must already exist for the upstream LLM provider. The AIRS plugin attaches to this service or route.

  1. List existing services: 
    curl -s http://localhost:8001/services | jq '.data[].name'
  2. Note the Service ID or name for the AI/LLM backend (e.g., openai-service).
  3. Confirm a route exists for that service: 
    curl -s http://localhost:8001/services/openai-service/routes | jq '.data[].paths'
Verification

At least one service and route targeting the LLM provider endpoint are returned.

Phase 2: Plugin Setup

Plugin setup differs by integration method. Each tab below covers the file deployment or configuration required before enabling the plugin on a Kong service.

▶ Step 2.1: Deploy Plugin Files (v1)

The v1 custom plugin consists of two Lua files: schema.lua (configuration schema) and handler.lua (scan logic). These files must be placed in Kong's plugin directory.

Traditional Kong Gateway

  1. Copy the plugin files into the Kong plugins directory: 
    sudo cp -r prisma-airs-intercept/ \
  /usr/local/share/lua/5.1/kong/plugins/prisma-airs-intercept/
  2. Confirm both files are present: 
    ls /usr/local/share/lua/5.1/kong/plugins/prisma-airs-intercept/
# Expected: handler.lua  schema.lua

Docker (Volume Mount)

Mount the plugin directory as a read-only volume in the Kong container.

services:
  kong:
    image: kong/kong-gateway:3.11
    environment:
      KONG_PLUGINS: "bundled,prisma-airs-intercept"
    volumes:
      - ./kong/plugins/prisma-airs-intercept:/usr/local/share/lua/5.1/kong/plugins/prisma-airs-intercept:ro

Kubernetes (ConfigMap)

apiVersion: v1
kind: ConfigMap
metadata:
  name: prisma-airs-plugin
data:
  handler.lua: |
    # paste handler.lua content
  schema.lua: |
    # paste schema.lua content
---
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
      - name: kong
        env:
        - name: KONG_PLUGINS
          value: "bundled,prisma-airs-intercept"
        volumeMounts:
        - name: plugin-files
          mountPath: /usr/local/share/lua/5.1/kong/plugins/prisma-airs-intercept
      volumes:
      - name: plugin-files
        configMap:
          name: prisma-airs-plugin
Verification

Both handler.lua and schema.lua are present in the prisma-airs-intercept plugin directory within the Kong runtime.

▶ Step 2.2: Register Plugin in Kong Configuration (v1)

Kong must be told to load the custom plugin by name. This differs by deployment model.

Traditional / Docker

  1. Edit kong.conf (or set the environment variable) to include the plugin: 
    plugins = bundled,prisma-airs-intercept

Kong Konnect (Hybrid Mode)

  1. Upload the schema to the Control Plane: 
    export KONNECT_TOKEN="YOUR_KONNECT_TOKEN"
export CONTROL_PLANE_ID="YOUR_CONTROL_PLANE_ID"

curl -X POST \
  "https://us.api.konghq.com/v2/control-planes/${CONTROL_PLANE_ID}/core-entities/plugin-schemas" \
  -H "Authorization: Bearer ${KONNECT_TOKEN}" \
  -H "Content-Type: application/json" \
  -d "{\"lua_schema\": $(jq -Rs '.' schema.lua)}"
  2. Set KONG_PLUGINS=bundled,prisma-airs-intercept on the Data Plane node(s) and restart.
Verification

Run kong version or check the Admin API at /. The plugins.available_on_server object includes prisma-airs-intercept.

▶ Step 2.1: Deploy Plugin Files (v2 MCP-aware)

The v2 plugin uses the same two-file structure (schema.lua + handler.lua) but with MCP detection and buffered SSE scanning logic. Deploy it the same way as v1, but use the v2 source files.

Important: Plugin Name Conflict

If both v1 and v2 are deployed concurrently, they must use distinct plugin names. Rename v2's PLUGIN_NAME to prisma-airs-intercept-mcp in schema.lua and mount under the matching directory. Kong loads one Lua module per plugin name.

Traditional Kong Gateway

  1. Copy the v2 plugin files: 
    sudo cp -r prisma-airs-intercept/ \
  /usr/local/share/lua/5.1/kong/plugins/prisma-airs-intercept/
  2. Confirm both files are present: 
    ls /usr/local/share/lua/5.1/kong/plugins/prisma-airs-intercept/
# Expected: handler.lua  schema.lua

Docker (Volume Mount)

services:
  kong-dp:
    image: kong/kong-gateway:3.14.0.2
    environment:
      KONG_PLUGINS: "bundled,prisma-airs-intercept"
    volumes:
      - ./kong/plugins/prisma-airs-intercept:/usr/local/share/lua/5.1/kong/plugins/prisma-airs-intercept:ro
Verification

Both handler.lua and schema.lua (v2 versions) are present in the plugin directory within the Kong runtime.

▶ Step 2.2: Register Plugin in Kong Configuration (v2)

Registration follows the same process as v1. Add the plugin name to KONG_PLUGINS.

  1. Set in kong.conf or environment variable: 
    plugins = bundled,prisma-airs-intercept
  2. For Kong Konnect, upload the v2 schema.lua to the Control Plane: 
    curl -X POST \
  "https://us.api.konghq.com/v2/control-planes/${CONTROL_PLANE_ID}/core-entities/plugin-schemas" \
  -H "Authorization: Bearer ${KONNECT_TOKEN}" \
  -H "Content-Type: application/json" \
  -d "{\"lua_schema\": $(jq -Rs '.' schema.lua)}"
Important: Priority Difference

v2 runs at priority 1000, above Kong's AI Proxy plugin (770). v2 sees the un-normalized request body. It parses OpenAI and Bedrock Converse natively, but other formats (Anthropic Messages, Gemini) are not parsed. Use v1 if AIRS must see AI-Proxy-normalized OpenAI JSON.

Verification

The Admin API at / includes prisma-airs-intercept in plugins.available_on_server.

▶ Step 2.1: Store AIRS API Key in Kong Vault (Request Callout)

The Request Callout method uses no custom plugin files. Instead, the AIRS API key is stored in Kong Vault and referenced at runtime. This step is Kong Konnect-specific.

  1. In Kong Konnect, navigate to the Control Plane settings.
  2. Add an environment variable for the vault: 
    KONG_VAULT_ENV_AIRS_API_KEY=YOUR_AIRS_API_KEY
  3. The plugin configuration references this value as {vault://env/airs-api-key}.
Verification

The environment variable KONG_VAULT_ENV_AIRS_API_KEY is set in the Konnect Control Plane settings.

▶ Step 2.2: Confirm Service and Route (Request Callout)

The Request Callout attaches to an existing service targeting the AI provider.

  1. Confirm a service exists pointing to the AI provider (e.g., https://api.openai.com).
  2. Confirm a route exists with the path /v1/chat/completions (or equivalent).
  3. Note the Service ID for use in the configuration JSON.
Verification

A Service ID is obtained for the AI provider backend.

▶ Step 3.2: Configure Multi-Provider Support with AI Gateway (v1)

v1 supports all LLM providers when paired with Kong's AI Proxy plugin. AI Proxy normalizes all requests/responses to OpenAI format before the AIRS plugin processes them.

v1 runs at priority 760 (below AI Proxy at 770), ensuring it sees the normalized OpenAI JSON. Supported providers include OpenAI, Azure OpenAI, Anthropic Claude, Google Gemini / Vertex AI, AWS Bedrock, Mistral, and Cohere.

  1. Enable AI Proxy on the same service: 
    curl -X POST \
  "https://us.api.konghq.com/v2/control-planes/${CONTROL_PLANE_ID}/core-entities/plugins" \
  -H "Authorization: Bearer ${KONNECT_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "ai-proxy",
    "service": {"id": "YOUR_SERVICE_ID"},
    "config": {
      "route_type": "llm/v1/chat",
      "model": {
        "provider": "anthropic",
        "name": "claude-3-5-sonnet-latest"
      },
      "auth": {
        "header_name": "x-api-key",
        "header_value": "YOUR_ANTHROPIC_KEY"
      }
    }
  }'
  2. The AIRS plugin (already enabled in Step 3.1) automatically scans the AI-Proxy-normalized payload.
Note

This step is optional. If the service targets OpenAI directly, AI Proxy is not needed.

Verification

Both ai-proxy and prisma-airs-intercept appear in the service's plugin list.

▶ Step 3.2: Understand MCP Detection Behavior (v2)

v2 automatically detects MCP JSON-RPC 2.0 requests by checking for jsonrpc and method fields. Understanding which methods are scanned versus bypassed prevents false positives and scanning gaps.

Scanned (tool_event)

  • tools/call — request arguments scanned as tool_event.input; response result scanned as tool_event.output

Bypassed (control messages)

  • initialize, initialized, ping
  • notifications/initialized
  • tools/list, resources/list, prompts/list

AIRS Payload for MCP tool_event

{
  "tr_id": "{kong-request-id}",
  "ai_profile": {"profile_name": "YOUR_PROFILE_NAME"},
  "contents": [{
    "tool_event": {
      "metadata": {
        "ecosystem": "mcp",
        "method": "tools/call",
        "server_name": "kong-YOUR_APP_NAME",
        "tool_invoked": "search_docs"
      },
      "input": "{\"query\":\"kong plugin development\"}",
      "output": "{\"content\":[{\"type\":\"text\",\"text\":\"...\"}]}"
    }
  }],
  "metadata": {
    "app_name": "kong-YOUR_APP_NAME",
    "app_user": "mcp-client",
    "ai_model": "mcp"
  }
}
Verification

Understanding confirmed. MCP tools/call requests are scanned; control messages (tools/list, initialize, etc.) pass through without scanning.

▶ Step 3.1: Apply Request-Callout Plugin Configuration

The Request Callout method uses the native request-callout plugin with inline Lua scripts that extract the prompt, send it to AIRS, check the verdict, and restore the original body for upstream.

  1. Create the configuration JSON file. Replace YOUR_SERVICE_ID and YOUR_PROFILE_NAME: 
    {
  "name": "request-callout",
  "service": {
    "id": "YOUR_SERVICE_ID"
  },
  "config": {
    "callouts": [
      {
        "name": "airs_request_scan",
        "request": {
          "url": "https://service.api.aisecurity.paloaltonetworks.com/v1/scan/sync/request",
          "method": "POST",
          "headers": {
            "Content-Type": "application/json",
            "Accept": "application/json",
            "x-pan-token": "{vault://env/airs-api-key}"
          }
        },
        "timeout": {
          "connect": 2000,
          "read": 10000,
          "write": 10000
        },
        "on_error": "exit",
        "retries": 2
      }
    ],
    "request": {
      "before": "<prompt extraction Lua script>"
    },
    "response": {
      "before": "<verdict check Lua script>"
    },
    "upstream": {
      "before": "<body restore Lua script>"
    }
  }
}
  2. The three inline Lua phases:
    • request.before — Extracts the last user message from the OpenAI messages[] array, builds the AIRS scan payload, and sets it as the callout request body.
    • response.before — Checks the AIRS verdict. If action is block, returns HTTP 403.
    • upstream.before — Restores the original request body before forwarding to the LLM provider.
  3. Apply via Konnect API: 
    curl -X POST \
  "https://us.api.konghq.com/v2/control-planes/${CONTROL_PLANE_ID}/core-entities/plugins" \
  -H "Authorization: Bearer ${KONNECT_TOKEN}" \
  -H "Content-Type: application/json" \
  -d @request-callout-prisma-airs-config.json
Important: Prompt-Only Scanning

The Request Callout method scans prompts only. LLM responses are not scanned. For dual-phase scanning (prompt + response), use the Custom Plugin v1 or v2.

SettingValue
AIRS Endpointhttps://service.api.aisecurity.paloaltonetworks.com/v1/scan/sync/request
Auth Headerx-pan-token: {vault://env/airs-api-key}

Verification

The request-callout plugin appears in the service's plugin list in Kong Konnect.

▶ Common Issues
IssueCauseFix
Plugin not visible in Konnect Schema not uploaded or Data Plane not synced Re-upload schema to Control Plane and restart Data Plane nodes
All requests return 403 Invalid API key or profile name Validate the api_key and profile_name match Strata Cloud Manager values
Response scanning not working (v1) Response buffering not enabled Confirm the response body is available to the plugin (non-streaming mode required for v1)
MCP tools/call not scanned (v2) Request missing JSON-RPC fields Confirm request includes "jsonrpc":"2.0" or a top-level method field; check logs for MCP request detected
AI Proxy normalization missing (v2) v2 priority (1000) runs before AI Proxy (770) Use v1 if post-normalization scanning is required
SSE-framed MCP response decodes empty (v2) Upstream uses non-standard SSE framing Confirm upstream emits event: message\ndata: {...} format
403 from AIRS API Regional endpoint mismatch Verify the api_endpoint region matches the tenant that issued the key
Connection timeout to AIRS Network or firewall blocking outbound HTTPS Verify the Kong node can reach service.api.aisecurity.paloaltonetworks.com on port 443
