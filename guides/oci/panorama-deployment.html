Panorama Deployment on OCI

End-to-end guide: OCI tenancy setup through a fully licensed, accessible Panorama management plane

AWS Panorama Guide Azure Panorama Guide GCP Panorama Guide OCI VM-Series Guide
Phase 1 Prerequisites Phase 2 Terraform Config Phase 3 Deploy Phase 4 Post-Deploy Phase 5 Verify
Guide Approach

This guide deploys Panorama, the centralized management platform for Palo Alto Networks firewalls, as a Compute instance on Oracle Cloud Infrastructure. Panorama should be operational before deploying VM-Series firewalls so that firewalls can bootstrap into a configured management plane on first boot.

Deployment method: All OCI infrastructure is deployed with Terraform using the OCI provider. Panorama itself runs from the Palo Alto Networks Marketplace image on an OCI Compute instance, with a Block Volume attached for log storage.

No first-party Panorama module for OCI

On AWS, Azure, and GCP, Palo Alto Networks publishes SWFW Terraform modules with a ready-made panorama_standalone example. OCI has no equivalent first-party Panorama module. The joint Oracle and Palo Alto Networks repository oracle-quickstart/oci-palo-alto-networks and the PaloAltoNetworks/OracleCloud sample template target the VM-Series firewall, not Panorama. This guide therefore builds the Panorama resources directly with the standard OCI Terraform provider. The same resources can be packaged as an Oracle Resource Manager (ORM) stack if you prefer console-driven deployment.

Architecture Overview

Before deploying anything, study the target architecture. This guide provisions a dedicated management VCN with a Panorama Compute instance reachable over a public IP or through an OCI Bastion, plus a Block Volume for log storage.

▶ Topology

The deployment creates the following OCI resources:

  • Compartment — a dedicated compartment that isolates the Panorama resources for IAM and billing (for example panorama-mgmt)
  • VCN — a management Virtual Cloud Network (10.255.0.0/16), the OCI equivalent of a VPC, with an Internet Gateway for management access
  • Subnet — a regional management subnet (10.255.0.0/24) with its own Route Table and either a Security List or a Network Security Group (NSG)
  • Panorama instance — an OCI Compute instance running the Palo Alto Networks Marketplace image, with a primary VNIC in the management subnet and a static private IP
  • Block Volume — a dedicated Block Volume attached to the instance and used by Panorama as a logging disk
  • Gateways — an Internet Gateway (IGW) for public management access, or a NAT Gateway plus Service Gateway for a private deployment
OCI networking terms at a glance
  • VCN — Virtual Cloud Network, the tenancy-level virtual network (equivalent to an AWS VPC or Azure VNet)
  • Subnet — regional or availability-domain scoped; each subnet has one Route Table
  • Security List / NSG — stateful ingress and egress rules; a Security List applies to a subnet, an NSG applies to a set of VNICs
  • VNIC — Virtual Network Interface Card, the interface attached to a Compute instance
  • IGW / NAT / Service GW / DRG — Internet, NAT, Service, and Dynamic Routing gateways for internet, outbound-only, Oracle-service, and inter-VCN traffic respectively
HA pair vs. single instance

This guide deploys a single Panorama instance for clarity. For an HA pair, duplicate the Compute instance and Block Volume resources into a second availability domain (or fault domain in a single-AD region) and configure Panorama HA after both instances are running. HA peering is a Panorama configuration task, not an infrastructure task; see Phase 5.

▶ Network & Security Design

Access to the Panorama management interface is controlled by a Security List or NSG on the management subnet. The baseline configuration exposes three services:

RuleDirectionPortProtocolSource/Dest
SSHIngress22TCPYour admin IP
HTTPSIngress443TCPYour admin IP
All outboundEgressallAll0.0.0.0/0
Important: Add port 3978 for managed firewalls

If VM-Series firewalls in other VCNs will connect to this Panorama over the network (via DRG, local peering, or VPN), add an ingress rule for TCP 3978 (Panorama device management). Set the source CIDR to the firewall management subnet CIDRs. Without this rule, firewalls cannot register with Panorama.

Security List or NSG?

A Security List attaches to a subnet and applies to every VNIC in it. A Network Security Group attaches to individual VNICs and lets you scope rules per instance. This guide uses an NSG on the Panorama VNIC so the management rules travel with the instance and do not affect other workloads in the subnet.

Phase 1: Prerequisites

Complete these one-time setup tasks before deploying Panorama infrastructure. If you have already completed them for a VM-Series deployment on OCI, skip to Phase 2.

▶ Step 1.1: Verify Tenancy, Compartment & IAM Permissions

Terraform needs an OCI compartment to hold the resources and an IAM policy granting the deploying user or group permission to manage networking and Compute. In OCI, policies are written against groups or dynamic-groups scoped to a compartment.

Create a compartment

  1. In the OCI Console, open the navigation menu and go to Identity & Security > Compartments.
  2. Click Create Compartment.
  3. Set the name (for example panorama-mgmt) and a description, choose the parent compartment, and click Create Compartment.
  4. Record the compartment OCID; it is needed for the Terraform variables in Phase 2.

Grant IAM permissions

Attach a policy to the group that the deploying user belongs to. The following statements allow that group to manage the resources this guide creates within the compartment.

Allow group PanoramaAdmins to manage virtual-network-family in compartment panorama-mgmt
Allow group PanoramaAdmins to manage instance-family in compartment panorama-mgmt
Allow group PanoramaAdmins to manage volume-family in compartment panorama-mgmt
Allow group PanoramaAdmins to manage app-catalog-listing in compartment panorama-mgmt
Allow group PanoramaAdmins to read marketplace-listings in tenancy
Break-glass and least privilege

The tenancy administrator account is the break-glass account for OCI. Store its credentials in a secure vault and use a named group such as PanoramaAdmins for daily deployment work. Grant the broad policy above for the initial deployment, then narrow it once the environment is stable. Repeated failed sign-ins can trigger account lockout, so protect the administrator credentials carefully.

Verification

The compartment appears under Identity & Security > Compartments in an Active state, and the policy is listed under Identity & Security > Policies for the target compartment.

▶ Step 1.3: Obtain Panorama License

Panorama requires a valid license. All cloud deployments use the BYOL (Bring Your Own License) model with an auth code.

Option A: Existing License

  1. Log in to the Customer Support Portal.
  2. Navigate to Products > Assets and locate your Panorama serial numbers or auth codes.
  3. Confirm you have one license per Panorama instance (two licenses for an HA pair).

Option B: Provision from Flex Credits

If your organization uses a Palo Alto Networks flex credit profile, you can provision a Panorama license directly from your credit pool.

  1. Log in to the Customer Support Portal.
  2. Navigate to Products > Flex Credits.
  3. Select Provision and choose Panorama as the product.
  4. Select the desired management capacity and license term.
  5. Complete the provisioning. An auth code is generated and appears under Products > Assets.
Note

License activation happens after deployment in Phase 4. At this stage, confirm the license exists in your support portal account. Activation requires the Panorama instance to be running with outbound internet connectivity.

Verification

Your Panorama auth codes or serial numbers are visible in the Customer Support Portal under Products > Assets.

▶ Step 1.4: Create or Identify an SSH Key Pair

SSH access is the only way to reach Panorama before the web UI password is set. On OCI, the instance receives your public key at launch through instance metadata; you keep the private key locally. Unlike AWS, there is no named key-pair object stored in the cloud, so any standard SSH key works.

Option A: Create a new key pair

ssh-keygen -t ed25519 -f ~/.ssh/panorama-oci -C "panorama-oci"
chmod 400 ~/.ssh/panorama-oci

This creates ~/.ssh/panorama-oci (private key) and ~/.ssh/panorama-oci.pub (public key). The public key contents are supplied to Terraform in Phase 2.

Option B: Use an existing key pair

Print an existing public key so you can paste it into the Terraform variables:

cat ~/.ssh/id_ed25519.pub
Important

Supply the public key (.pub) to Terraform, never the private key. The private key stays on your workstation and is used only when connecting with ssh -i.

Verification

Both key files exist and the private key has permissions 400. Confirm with ls -l ~/.ssh/panorama-oci*.

▶ Step 1.5: Subscribe to the Panorama Marketplace Image

Panorama is published as a BYOL image in the Oracle Cloud Marketplace. You must accept the terms and subscribe the image to your compartment before Terraform can launch an instance from it. This is a one-time action per compartment.

  1. In the OCI Console, open the navigation menu and go to Marketplace > All Applications.
  2. Search for Palo Alto Networks Panorama and open the listing.
  3. Select the target compartment, review and accept the Oracle terms of use and the partner terms, then click Subscribe.
  4. Wait for the subscription to complete.
Subscribing through Terraform instead

The subscription can also be created in code with oci_core_app_catalog_listing_resource_version_agreement and oci_core_app_catalog_subscription resources, which is how the joint oracle-quickstart templates handle the VM-Series image. If you subscribe in the console first, you can skip those resources and reference the resulting image OCID directly.

Verification

The Panorama listing shows an active subscription for your compartment. You can now retrieve the image OCID from Marketplace > All Applications or with the OCI CLI for use in the Terraform configuration.

Phase 2: Prepare Terraform Configuration

Create a small Terraform project that provisions the compartment networking and the Panorama Compute instance. The examples below use placeholder values; replace every OCID and CIDR with values from your tenancy.

Reference implementations

There is no first-party Panorama module for OCI. The Terraform shown here is representative and self-contained. For patterns you can adapt, review the joint oracle-quickstart/oci-palo-alto-networks repository and the PaloAltoNetworks/OracleCloud sample template. Both target VM-Series but demonstrate OCI provider usage, Marketplace image subscription, and VCN construction that apply equally to Panorama.

▶ Step 2.1: Gather OCI Provider Credentials

The OCI Terraform provider authenticates with an API signing key. If you ran oci setup config in Step 1.2, the key pair and profile already exist under ~/.oci.

  1. Upload the API public key to your OCI user: Identity & Security > Users > your user > API Keys > Add API Key, then paste the contents of ~/.oci/oci_api_key_public.pem.
  2. Record the five values the provider needs: the tenancy OCID, user OCID, key fingerprint, private key path, and region. The fingerprint is shown when the key is added and also appears under the user's API Keys list.
# Confirm the profile the OCI CLI is using
cat ~/.oci/config
Never commit the private key

The API private key and the SSH private key must never be committed to version control. Keep them outside the Terraform working directory and reference them by path. Add *.pem and terraform.tfvars to .gitignore.

Verification

The new API key appears under the user's API Keys with a fingerprint that matches your local key, and oci iam region list succeeds using that profile.

▶ Step 2.2: Create the Provider & Variables Files

Create a working directory and define the provider and input variables. The OCI provider takes the five credential values from Step 2.1.

mkdir panorama-oci && cd panorama-oci

provider.tf:

terraform {
  required_version = ">= 1.5.0, < 2.0.0"
  required_providers {
    oci = {
      source  = "oracle/oci"
      version = ">= 5.0.0"
    }
  }
}

provider "oci" {
  tenancy_ocid     = var.tenancy_ocid
  user_ocid        = var.user_ocid
  fingerprint      = var.fingerprint
  private_key_path = var.private_key_path
  region           = var.region
}

variables.tf:

variable "tenancy_ocid"     { type = string }
variable "user_ocid"        { type = string }
variable "fingerprint"      { type = string }
variable "private_key_path" { type = string }
variable "region"           { type = string }

variable "compartment_ocid" {
  type        = string
  description = "Compartment where Panorama resources are created"
}

variable "availability_domain" {
  type        = string
  description = "Full AD name, e.g. Uocm:PHX-AD-1"
}

variable "panorama_image_ocid" {
  type        = string
  description = "OCID of the subscribed Panorama Marketplace image"
}

variable "ssh_public_key" {
  type        = string
  description = "Contents of your SSH public key (.pub)"
}

variable "admin_cidr" {
  type        = string
  description = "Your admin public IP in CIDR form, e.g. 203.0.113.10/32"
}
Verification

Both files exist in the working directory and reference only variables, with no hard-coded OCIDs or keys.

▶ Step 2.3: Define the VCN, Subnet & Gateways

Create the management VCN, an Internet Gateway, a Route Table with a default route to the IGW, and a regional management subnet.

network.tf:

resource "oci_core_vcn" "mgmt" {
  compartment_id = var.compartment_ocid
  cidr_blocks    = ["10.255.0.0/16"]
  display_name   = "panorama-mgmt-vcn"
  dns_label      = "panoramamgmt"
}

resource "oci_core_internet_gateway" "igw" {
  compartment_id = var.compartment_ocid
  vcn_id         = oci_core_vcn.mgmt.id
  display_name   = "panorama-igw"
}

resource "oci_core_route_table" "mgmt" {
  compartment_id = var.compartment_ocid
  vcn_id         = oci_core_vcn.mgmt.id
  display_name   = "panorama-mgmt-rt"

  route_rules {
    destination       = "0.0.0.0/0"
    network_entity_id = oci_core_internet_gateway.igw.id
  }
}

resource "oci_core_subnet" "mgmt" {
  compartment_id             = var.compartment_ocid
  vcn_id                     = oci_core_vcn.mgmt.id
  cidr_block                 = "10.255.0.0/24"
  display_name               = "panorama-mgmt-subnet"
  dns_label                  = "mgmt"
  route_table_id             = oci_core_route_table.mgmt.id
  prohibit_public_ip_on_vnic = false
}
Private deployment variant

For a Panorama with no public IP, set prohibit_public_ip_on_vnic = true, replace the IGW route with a oci_core_nat_gateway for outbound licensing and content traffic, and add a oci_core_service_gateway for Oracle service access. Inbound admin access then goes through an OCI Bastion or a DRG-connected network. See Step 2.7.

Verification

The file defines exactly one VCN, one IGW, one Route Table with a 0.0.0.0/0 rule pointing at the IGW, and one subnet referencing that Route Table.

▶ Step 2.4: Define the Network Security Group

Create an NSG that allows SSH and HTTPS from your admin IP and all outbound traffic. The NSG attaches to the Panorama VNIC in the next step.

nsg.tf:

resource "oci_core_network_security_group" "panorama" {
  compartment_id = var.compartment_ocid
  vcn_id         = oci_core_vcn.mgmt.id
  display_name   = "panorama-mgmt-nsg"
}

resource "oci_core_network_security_group_security_rule" "ssh_in" {
  network_security_group_id = oci_core_network_security_group.panorama.id
  direction                 = "INGRESS"
  protocol                  = "6" # TCP
  source                    = var.admin_cidr
  source_type               = "CIDR_BLOCK"
  tcp_options { destination_port_range { min = 22, max = 22 } }
}

resource "oci_core_network_security_group_security_rule" "https_in" {
  network_security_group_id = oci_core_network_security_group.panorama.id
  direction                 = "INGRESS"
  protocol                  = "6" # TCP
  source                    = var.admin_cidr
  source_type               = "CIDR_BLOCK"
  tcp_options { destination_port_range { min = 443, max = 443 } }
}

resource "oci_core_network_security_group_security_rule" "all_out" {
  network_security_group_id = oci_core_network_security_group.panorama.id
  direction                 = "EGRESS"
  protocol                  = "all"
  destination               = "0.0.0.0/0"
  destination_type          = "CIDR_BLOCK"
}
Do not open SSH or HTTPS to the internet

Set admin_cidr to your specific public IP with a /32 mask. Using 0.0.0.0/0 exposes the Panorama management interface to the entire internet. Find your current IP with curl -s ifconfig.me.

Important: Add port 3978 for VM-Series management

If VM-Series firewalls in other VCNs will register with this Panorama, add an ingress rule for TCP 3978 with the source set to the firewall management subnet CIDRs. Duplicate the ssh_in block, change the port range to 3978, and set source to the firewall CIDR.

Verification

The NSG defines ingress rules for ports 22 and 443 scoped to var.admin_cidr and a single permissive egress rule.

▶ Step 2.5: Define the Panorama Instance & Block Volume

Create the Compute instance from the subscribed Marketplace image, attach the NSG to its VNIC, and attach a Block Volume for log storage.

compute.tf:

resource "oci_core_instance" "panorama" {
  compartment_id      = var.compartment_ocid
  availability_domain = var.availability_domain
  display_name        = "panorama-1"
  shape               = "VM.Standard.E4.Flex"

  shape_config {
    ocpus         = 8   # 8 OCPUs = 16 vCPUs on x86 shapes
    memory_in_gbs = 32
  }

  source_details {
    source_type = "image"
    source_id   = var.panorama_image_ocid
  }

  create_vnic_details {
    subnet_id        = oci_core_subnet.mgmt.id
    private_ip       = "10.255.0.4"
    assign_public_ip = true
    nsg_ids          = [oci_core_network_security_group.panorama.id]
  }

  metadata = {
    ssh_authorized_keys = var.ssh_public_key
  }
}

resource "oci_core_volume" "panorama_logs" {
  compartment_id      = var.compartment_ocid
  availability_domain = var.availability_domain
  display_name        = "panorama-logs"
  size_in_gbs         = 2048
}

resource "oci_core_volume_attachment" "panorama_logs" {
  attachment_type = "paravirtualized"
  instance_id     = oci_core_instance.panorama.id
  volume_id       = oci_core_volume.panorama_logs.id
}
OCPU to vCPU mapping

On OCI x86 flexible shapes, 1 OCPU equals 2 vCPUs. Panorama in Panorama mode requires a minimum of 16 vCPUs and 32 GB RAM, so set ocpus = 8. Confirm the current sizing requirements in the Panorama setup prerequisites before production use, and increase the shape for larger managed-device counts.

ParameterValueDescription
shapeVM.Standard.E4.FlexFlexible AMD shape. Any supported flexible shape meeting the vCPU and RAM minimum works.
ocpus88 OCPUs equal 16 vCPUs on x86 shapes.
memory_in_gbs32Minimum for Panorama mode.
size_in_gbs2048Block Volume size for the logging disk (2 TB).
assign_public_iptrueSet to false for a private deployment reached via Bastion or DRG.
Panorama modes and the logging disk

A fresh Panorama boots in Panorama mode. The attached Block Volume is not used for logs until it is added as a virtual logging disk on Panorama itself; that is done post-deployment in Step 4.5. For a management-only deployment that forwards logs elsewhere, switch Panorama to Management Only mode and the logging disk is optional.

Verification

The file defines one instance referencing var.panorama_image_ocid, the NSG attached via nsg_ids, and a Block Volume plus attachment.

▶ Step 2.7: Optional — Private Panorama via NAT & Bastion

If Panorama should not have a public IP, keep the management interface private and provide outbound and inbound paths separately.

  1. In compute.tf, set assign_public_ip = false and, in network.tf, set prohibit_public_ip_on_vnic = true.
  2. Add a NAT Gateway for outbound licensing and content-update traffic, and point the subnet's default route at it instead of the IGW: 
    resource "oci_core_nat_gateway" "nat" {
  compartment_id = var.compartment_ocid
  vcn_id         = oci_core_vcn.mgmt.id
  display_name   = "panorama-nat"
}
  3. Add a Service Gateway if Panorama should reach Oracle services (such as Object Storage) without traversing the internet.
  4. Provide inbound admin access through an OCI Bastion session or a DRG-connected on-premises network. Create the Bastion under Identity & Security > Bastion, targeting the management subnet, then open a port-forwarding session to the Panorama private IP.
Important

With no public IP, the only access to Panorama is through the OCI Bastion or a private network path (DRG, VPN, or FastConnect). Confirm that path is in place before deploying, or you will not be able to complete the first-boot setup.

Verification

For a private deployment: assign_public_ip is false, the default route points at the NAT Gateway, and a Bastion or DRG path to the management subnet exists. For the default public deployment: the IGW route remains and assign_public_ip is true.

Phase 3: Deploy & Verify Infrastructure

With the configuration validated, deploy the Panorama infrastructure and capture the output values needed for post-deployment access.

▶ Step 3.1: Plan the Deployment

Generate an execution plan to review what Terraform will create before committing.

terraform plan -var-file=terraform.tfvars

Review the output. For a single-instance deployment, expect approximately:

  • 1 VCN with an Internet Gateway
  • 1 subnet with a Route Table
  • 1 NSG with ingress and egress rules
  • 1 Compute instance (VM.Standard.E4.Flex)
  • 1 Block Volume with an attachment
Verification

The plan completes without errors and shows the expected resources to create. No resources should show destroy on the initial deployment.

▶ Step 3.2: Apply the Configuration

Deploy the infrastructure. Terraform prompts for confirmation before making changes.

terraform apply -var-file=terraform.tfvars

Type yes when prompted. Provisioning the OCI resources takes a few minutes.

Note

The Terraform apply completing does not mean Panorama is ready. The Compute instance is created, but Panorama's internal boot process takes an additional 5 to 10 minutes after the instance reaches the Running state.

Verification

Terraform completes with Apply complete! and displays the output values (public IP and private IP).

▶ Step 3.3: Record Output Values

Capture the Panorama access details from the Terraform outputs. These values are needed for SSH, the web UI, and firewall bootstrap configuration.

terraform output panorama_public_ip
terraform output panorama_private_ip
Important

Record the private IP. This is the address VM-Series firewalls use for the panorama-server bootstrap parameter. The private IP is static and persists across reboots. The public IP is used for admin access only.

Verification

Both output commands return values, and the private IP matches the private_ip set in compute.tf (10.255.0.4).

▶ Step 3.4: Verify OCI Console Resources

Confirm the deployed resources in the OCI Console.

  1. Open Compute > Instances. Verify the Panorama instance shows the Running state and the expected shape (VM.Standard.E4.Flex).
  2. Open Storage > Block Volumes. Verify the panorama-logs volume shows Available and is attached to the instance.
  3. Open Networking > Virtual Cloud Networks. Verify the management VCN exists with the correct CIDR and that the subnet references the Route Table with a default route to the IGW.
  4. Open the instance's VNIC and confirm the panorama-mgmt-nsg is attached with ingress rules for ports 22 and 443 from your admin IP.
Verification

The instance is Running, the Block Volume is Available and attached, and the VCN, subnet, and NSG match the Terraform configuration.

Phase 4: Post-Deployment Setup

Panorama's internal boot takes several minutes after the instance reaches the Running state. Complete the initial access setup once boot finishes.

▶ Step 4.1: Wait for Panorama Boot

Panorama takes 5 to 10 minutes to complete its internal boot after the Compute instance shows Running in the OCI Console. During this time, SSH and HTTPS connections are refused.

Check boot progress by polling SSH availability:

# Replace with your Panorama public IP
PANORAMA_IP="203.0.113.50"

# Poll until SSH responds (Ctrl+C to stop)
until ssh -o ConnectTimeout=5 -o StrictHostKeyChecking=no \
  -i ~/.ssh/panorama-oci admin@${PANORAMA_IP} \
  echo "SSH ready" 2>/dev/null; do
  echo "Waiting for Panorama boot..."
  sleep 30
done
Alternative: OCI serial console

Check boot progress through the instance console connection. In the OCI Console, open Compute > Instances > your instance > Console connection, create a connection, and launch the Cloud Shell serial console. Look for the PAN-OS login: prompt in the output.

Verification

SSH connects successfully and presents the PAN-OS CLI prompt (admin@Panorama>).

▶ Step 4.2: Set the Admin Password

Panorama ships with no admin password on first boot. The web UI is inaccessible until a password is set via SSH. This is a security gate; no one can reach the web UI until credentials are set explicitly.

  1. SSH into the Panorama instance: 
    ssh -i ~/.ssh/panorama-oci admin@203.0.113.50
  2. Enter configuration mode: 
    configure
  3. Set the admin password: 
    set mgt-config users admin password

    Enter the new password twice when prompted. Use a strong password that meets your organization's policy.

  4. Commit the change: 
    commit
  5. Exit the SSH session: 
    exit
exit
Important: Break-glass account

The admin account is the break-glass account for Panorama. Store the password in a secure vault. After initial setup, create named admin accounts for daily operations and reserve admin for emergency access only. Multiple failed login attempts will lock the account.

Verification

The commit command completes without errors: Commit job completed.

▶ Step 4.3: Access the Web UI

Open the Panorama web interface in a browser using the public IP from the Terraform output.

  1. Navigate to https://<PANORAMA_PUBLIC_IP> (for example https://203.0.113.50).
  2. Accept the self-signed certificate warning.
  3. Log in with username admin and the password set in the previous step.
Note

The browser shows a certificate warning because Panorama uses a self-signed certificate by default. This is expected and safe for initial access. Replace the certificate with a CA-signed certificate after completing the initial setup.

Verification

The Panorama dashboard loads and shows the system status panel with hostname, serial number, and PAN-OS version.

▶ Step 4.4: Activate the License

Panorama must be licensed before it can manage firewalls or receive content updates.

  1. In the Panorama web UI, navigate to Panorama > Licenses.
  2. Click Activate feature using auth code.
  3. Enter the Panorama auth code obtained from the Customer Support Portal in Step 1.3.
  4. Click OK. Panorama contacts the licensing server and activates the license.
Internet connectivity required

License activation requires outbound HTTPS connectivity to updates.paloaltonetworks.com. If Panorama is behind a NAT Gateway, confirm outbound port 443 is permitted. See Troubleshooting if activation fails.

Verification

The Panorama > Licenses page shows active licenses with valid expiration dates. The Device Management license indicates the maximum number of managed devices.

▶ Step 4.5: Add the Logging Disk

The attached Block Volume is not used for logs until it is added as a virtual logging disk on Panorama. In Panorama mode, add the disk so local log collection has storage.

  1. In the web UI, navigate to Panorama > Setup > Operations.
  2. Under the Storage Partition or disk section, add the newly attached virtual disk and follow the prompt to format it.

Alternatively, from the CLI:

request system disk add

Panorama detects the unformatted Block Volume, formats it, and adds it to the logging storage pool. Adding a disk requires a reboot, which Panorama schedules as part of the operation.

Management Only mode

If Panorama is switched to Management Only mode and forwards logs to a separate Log Collector or to Strata Logging Service, the local logging disk is not required and this step can be skipped.

Verification

After the reboot completes, show system disk-space lists the new log partition with the Block Volume's capacity. This is confirmed in Step 5.5.

Troubleshooting

▶ Instance Launch Failures
SymptomCauseResolution
Terraform error referencing the image or app catalog Marketplace image not subscribed in the target compartment, or a wrong image OCID Subscribe to the Panorama listing under Marketplace > All Applications (Step 1.5) and re-copy the image OCID into terraform.tfvars.
Error: out of host capacity or shape unavailable The chosen flexible shape is not available in the selected availability domain Try a different availability domain, or switch to another supported flexible shape (for example VM.Standard3.Flex) that meets the vCPU and RAM minimum.
Error: authorization failed or 404 NotAuthorizedOrNotFound The deploying group lacks an IAM policy for the resource, or the compartment OCID is wrong Confirm the policy statements from Step 1.1 are attached to your group and that compartment_ocid is correct.
▶ SSH Connection Failures
SymptomCauseResolution
Connection timed out The NSG or Security List does not allow SSH from your IP, or Panorama is still booting Verify the NSG ingress rule for port 22 references your current IP. Wait 5 to 10 minutes for boot to complete. Check the instance serial console.
Permission denied (publickey) Wrong private key or wrong username Confirm the SSH private key matches the public key supplied in ssh_public_key. The username must be admin, not opc or root.
Permissions are too open SSH private key file permissions too permissive Run chmod 400 ~/.ssh/panorama-oci
▶ Web UI Not Accessible
SymptomCauseResolution
Browser shows ERR_CONNECTION_REFUSED Panorama is still booting, or the admin password has not been set SSH in and set the admin password first (Step 4.2). The web UI does not start until a password is configured.
Browser shows ERR_CONNECTION_TIMED_OUT The NSG does not allow HTTPS from your IP Verify the NSG includes an ingress rule for port 443 from your current public IP.
Login fails with valid credentials Account lockout after multiple failed attempts Wait for the lockout period to expire (default 30 minutes) or unlock via CLI: set mgt-config users admin lockout disabled then commit
▶ License Activation Failures
SymptomCauseResolution
Failed to connect to server No outbound internet connectivity Verify the management subnet Route Table has a default route to the IGW (or NAT Gateway). Verify the NSG allows all outbound traffic. Test connectivity from the CLI.
Invalid auth code Auth code does not match the Panorama product type Confirm the auth code is for Panorama, not VM-Series. Check the Customer Support Portal under Products > Assets.
Auth code already used The auth code was previously applied to another Panorama instance Each Panorama instance requires its own auth code. Obtain a second auth code for the HA secondary.
▶ Block Volume & Logging Disk Issues
SymptomCauseResolution
Log storage shows less than expected The Block Volume was attached but not added as a Panorama logging disk Run the add-disk operation in Panorama (Step 4.5): request system disk add, then reboot. Confirm with show system disk-space.
Volume shows attached in OCI but not seen by Panorama Attachment type or device enumeration mismatch after boot Confirm the attachment is paravirtualized in the OCI Console under Storage > Block Volumes, then reboot the instance so PAN-OS re-enumerates the disk.

Cleanup

▶ Destroy All Resources (Terraform)

To remove all resources created by this deployment, run the destroy command from the same directory where the deployment was executed.

Data loss warning

Running terraform destroy will permanently delete the Panorama instance, the Block Volume (including all stored logs and configuration), the VCN, subnet, Route Table, gateways, and NSG. This action cannot be undone.

If you need to preserve Panorama's configuration, export it first: Panorama > Setup > Operations > Export Panorama and devices config bundle.

terraform destroy -var-file=terraform.tfvars

Type yes when prompted. The destroy operation takes a few minutes.

Verification

Terraform completes with Destroy complete! and reports the number of resources destroyed. Verify in the OCI Console that the instance, Block Volume, and VCN are no longer present.

▶ Manual Teardown (Console)

If the deployment was created outside Terraform or the state file is lost, remove resources in dependency order so that no resource blocks the deletion of the one before it.

  1. Terminate the Panorama Compute instance (Compute > Instances). Choose whether to preserve or delete the boot volume.
  2. Detach and delete the Block Volume (Storage > Block Volumes).
  3. Delete the subnet, then its Route Table and NSG (Networking > Virtual Cloud Networks).
  4. Delete the gateways (Internet Gateway, and NAT or Service Gateway if used).
  5. Delete the VCN.
  6. Remove the IAM policies created in Step 1.1, and delete the compartment once it is empty.
Order matters

A VCN cannot be deleted while it still contains subnets, gateways, Route Tables, or Security Lists. A compartment cannot be deleted while it still contains active resources or policies. Work from the innermost resource outward.

Verification

The compartment shows no remaining Compute, networking, or storage resources, and the VCN no longer appears under Networking > Virtual Cloud Networks.
