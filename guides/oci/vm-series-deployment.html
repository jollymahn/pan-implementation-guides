VM-Series Deployment on OCI

End-to-end guide: Panorama or SCM configuration through Oracle Cloud Infrastructure to verified traffic inspection, covering both HA models

Guide Approach

This guide follows a management-first approach. All licensing, device groups, templates or folders, and security policy are configured on your management platform (Panorama or Strata Cloud Manager) before any OCI infrastructure is built. This ensures firewalls bootstrap into a fully configured management plane on first boot.

Design model: Central hub VCN holding the VM-Series firewalls, with spoke VCNs attached to a Dynamic Routing Gateway (DRG) for hub-and-spoke inspection. Phase 2 lets you pick the management platform; Phase 6 lets you pick the HA model.

Deployment method: All OCI infrastructure (Phases 5 through 7) is deployed with Terraform or an Oracle Resource Manager (ORM) stack. See the callout below on how OCI tooling differs from the other clouds.

OCI has no first-party SWFW Terraform module

On AWS, Azure, and GCP, Palo Alto Networks publishes the official SWFW Terraform modules. There is no equivalent first-party terraform-oci-vmseries-modules. If you are arriving from the AWS guide expecting a drop-in module, adjust your expectations here. On OCI you deploy with one of the following instead:

  • oracle-quickstart/oci-palo-alto-networks — a joint Oracle and Palo Alto Networks reference stack: github.com/oracle-quickstart/oci-palo-alto-networks
  • Oracle Resource Manager (ORM) stack — deploy the same reference architecture from the OCI Console with a guided variable form, no local Terraform install required.
  • PaloAltoNetworks/OracleCloud — a Palo Alto Networks sample template: github.com/PaloAltoNetworks/OracleCloud

Because module input names differ between these projects and change over time, this guide describes variables generically (region, compartment OCID, VCN CIDR, firewall shape, image OCID, SSH key). Always confirm the exact variable names against the variables.tf or schema.yaml of the project you choose.

No Cloud NGFW on OCI

Palo Alto Networks Cloud NGFW is a managed service on AWS, Azure, and GCP only. On Oracle Cloud Infrastructure the VM-Series firewall is the inline inspection option; there is no managed alternative for this cloud.

Architecture Overview

Before deploying anything, study the target architecture. OCI has no dedicated firewall-insertion load balancer (there is no Gateway Load Balancer as on AWS and Azure). The reference pattern places VM-Series firewalls in a central hub VCN and attaches spoke VCNs to a Dynamic Routing Gateway (DRG), which acts as the hub-and-spoke router. Traffic is steered to the firewalls through per-subnet route tables and, in the Active/Active model, a pair of OCI Flexible Network Load Balancers.

New to OCI networking?

OCI names its objects differently from AWS and Azure. The table below maps the concepts, and the How Routing Works and Traffic Flows Explained appendices give a plain-language walkthrough of every leg.

Deployment models

This guide covers two production HA models. Read both collapsibles before choosing; Phase 6 splits into a tabbed path where you build the model you pick here.

▶ Model A — Active/Active hub-and-spoke (Flexible NLB)

The hub VCN holds two or more VM-Series firewalls, each with four VNICs: management, untrust, trust, and inbound (the DMZ-facing dataplane). Spoke VCNs attach to the DRG; backend application servers live in spoke private subnets.

Two OCI Flexible Network Load Balancers front the firewalls:

  • Inbound NLB — handles north-south inbound traffic from the Internet Gateway.
  • Trust NLB — handles east-west and outbound traffic arriving from the DRG.

Both NLBs use symmetric hashing, which sends the forward and return legs of a flow to the same firewall. Because the same firewall sees both directions, its session state stays valid with no failover API calls and no floating IP movement. Firewalls can be added to or removed from an NLB backend set without disrupting existing flows, so the model scales horizontally. This model does not require an IAM policy that lets the firewall move IPs.

Why symmetric hashing matters

A stateful firewall must see both directions of a flow. On most clouds, keeping both firewalls active would require state synchronization or a floating IP that moves on failover. OCI symmetric hashing computes the same backend for (src, dst) and (dst, src), so the return leg deterministically lands on the same firewall. That is what makes a true Active/Active model possible here without any API-driven failover.

▶ Model B — Active/Passive built-in PAN-OS HA

A pair of firewalls runs native PAN-OS HA. Each firewall needs a minimum of four interfaces: management, untrust, trust, and a dedicated HA link. The data interfaces (untrust and trust) on the active peer each carry two IP addresses: a primary IP and a secondary floating IP.

On failover, the floating IPs move from the active peer to the passive peer through OCI API calls. To authorize those calls, the deployment uses three OCI constructs working together:

  • Dynamic group — both HA peer instances are members.
  • IAM policy — grants the dynamic group permission to reassign and manage private IPs on those instances.
  • Instance principals — PAN-OS authenticates to the OCI API as the instance itself (no stored API keys) to move the floating IP.

This model is the closest match to a traditional on-prem PAN-OS HA pair and gives stateful failover. It carries more moving parts than Model A: an IAM policy is mandatory, and failover time depends on how quickly the OCI API reassigns the floating IPs.

Phase 1: Prerequisites

Complete every item below before touching Terraform. Missing a compartment, an image subscription, or a licensing auth code is the most common cause of a failed first deploy.

▶ 1.1 Create a compartment and IAM identity

A compartment isolates the firewall resources for IAM and billing. Terraform authenticates as a user with an API signing key.

  1. In the OCI Console, go to Identity & Security > Compartments and click Create Compartment. Name it (for example cmp-netsec-hub) and record its OCID.
  2. Create or select a user for Terraform under Identity & Security > Domains > (your domain) > Users.
  3. Generate an API signing key for that user (User > API Keys > Add API Key). Download the private key and note the fingerprint.
  4. Record the tenancy OCID, user OCID, fingerprint, private key path, and region. These five values become your OCI Terraform provider inputs.
Break-glass account hygiene

Keep the tenancy administrator credentials as a break-glass identity: use them only to create the scoped compartment and the Terraform user, then store them offline. Grant the Terraform user permissions on the target compartment only, not the tenancy root. A lockout on an over-privileged automation user can strand the whole tenancy.

Verification

Run oci iam compartment get --compartment-id <compartment-ocid> with the Terraform user's config. A JSON object with "lifecycle-state": "ACTIVE" confirms the identity and compartment are usable.

▶ 1.2 Subscribe to the VM-Series Marketplace image

The firewall boots from an Oracle Cloud Marketplace image. Subscribe once per compartment before Terraform can reference the image.

  1. In the OCI Console, open Marketplace > All Applications and search for Palo Alto Networks VM-Series.
  2. Select the listing, choose the PAN-OS version, and accept the terms for your compartment.
  3. Record the resulting image OCID (or the app catalog listing OCID) for the Terraform image input.
Licensing: BYOL vs PAYG

The Marketplace listing offers two licensing paths:

  • BYOL (Bring Your Own License) — you supply an auth code from your Palo Alto Networks Customer Support Portal deployment profile.
  • PAYG (Pay As You Go) — billed hourly through OCI, choosing Bundle 1 (capacity plus threat prevention) or Bundle 2 (the full suite: WildFire, URL Filtering, DNS Security, and GlobalProtect).
Verification

In Marketplace > Accepted Agreements, the VM-Series listing appears with your compartment listed. The image OCID is now valid as a Terraform input.

▶ 1.3 Prepare licensing (BYOL auth code and registration PIN)

For BYOL, and for auto-registration in any licensing model, gather the Palo Alto Networks side first.

  1. In the Customer Support Portal, create a deployment profile under your software NGFW credits and copy its auth code.
  2. Generate a VM-Series registration PIN (Products > Registration PIN). Record the PIN ID and PIN Value; both are bootstrap parameters.
  3. If you will manage with Panorama, note that the auth code is also entered into the Panorama licensing plugin in Phase 2A.
Verification

The deployment profile shows an Active credit pool, and the registration PIN shows a future expiry date. Save the auth code, PIN ID, and PIN Value in your deployment checklist.

▶ 1.4 Install local tooling

You need the OCI CLI (for verification and the API config), Terraform, and Git. Skip Terraform if you plan to deploy through an Oracle Resource Manager stack in the Console.

  1. Install the OCI CLI and run oci setup config to write ~/.oci/config using the tenancy OCID, user OCID, fingerprint, private key, and region from step 1.1.
  2. Install Terraform (1.5 or later) and Git.
  3. Clone the deployment project you selected in the architecture callout (for example git clone https://github.com/oracle-quickstart/oci-palo-alto-networks).
Verification

oci iam region list returns the region table, terraform version prints 1.5+, and git --version succeeds. Your API config is valid end to end.

Phase 2: Management Platform Configuration

VM-Series can be managed by either Panorama (the on-prem or Compute-hosted management appliance) or Strata Cloud Manager (SCM) (the SaaS management plane). Pick the path that matches your environment; your selection persists across the page, so subsequent references follow your chosen platform.

Which path should I pick?
  • Panorama — choose if you already operate Panorama, need on-prem control, or use the SW Firewall License plugin for licensing. A baseline set-command script is available at Reference: Panorama Set Commands so you can paste config into a fresh Panorama instead of clicking through the UI.
  • SCM — choose for greenfield deployments, cloud-native operations, or consolidating onto Strata's SaaS management plane.

2A Panorama configuration

Configure Panorama with the SW Firewall License plugin, device groups, templates, and policy before building any OCI infrastructure. Build from the bottom of the template stack up, then bind everything with a License Manager.

▶ 2A.1 Install the SW Firewall License plugin

Palo Alto Docs: Panorama-Based License Management

  1. Log in to Panorama and go to Panorama > Plugins.
  2. Click Check Now, locate sw_fw_license, then Download and Install.
  3. Set the licensing API key over SSH: request license api-key set key <key> (the key comes from the CSP under Products > API Key Management).
Verification

request license api-key show confirms the key is set, and the plugin appears under Panorama > SW Firewall License.

▶ 2A.2 Create device groups and template stacks

Palo Alto Docs: Manage Device Groups | Manage Templates and Template Stacks

  1. Under Panorama > Device Groups, create a parent DG-OCI and a child DG-OCI-HUB (set Parent Device Group to DG-OCI).
  2. Under Panorama > Templates, create a baseline template TPL-OCI-BASELINE (DNS, NTP, log forwarding) and a network template TPL-OCI-NETWORK (interfaces, zones, logical router).
  3. Create a template stack STK-OCI-HUB and add both templates in order.
  4. Open DG-OCI-HUB and add STK-OCI-HUB as a Reference Template so zone names appear in the rule editor.
Without a reference template, zone dropdowns are empty

Security rules in DG-OCI-HUB pull zone names from the templates associated with the device group. Skip the reference template and the zone dropdown is empty, so you cannot commit policy that references untrust, trust, or inbound.

Verification

DG-OCI-HUB lists STK-OCI-HUB under Reference Templates, and the parent shows as DG-OCI.

▶ 2A.3 Configure interfaces, zones, and the logical router

Define the dataplane so the bootstrapped firewall matches its OCI VNIC layout. Column order below follows the interface configuration tabs in the PAN-OS UI.

InterfaceZoneTypeIP assignmentOCI VNIC
ethernet1/1untrustLayer 3DHCP (from untrust subnet)untrust VNIC
ethernet1/2trustLayer 3DHCP (from trust subnet)trust VNIC
ethernet1/3inboundLayer 3DHCP (from inbound subnet)inbound VNIC (Model A)

Create a logical router and add the OCI subnet gateway as the default route next hop. Use template variables for the per-firewall gateway IPs so one stack serves the whole hub; see Configure Template Variables.

OCI uses DHCP for dataplane interfaces

OCI assigns VNIC IPs through DHCP. Set the firewall dataplane interfaces to DHCP client (unchecked "automatically create default route") rather than static IPs so the firewall receives the address OCI allocated to the VNIC.

Verification

Commit to Panorama with no validation errors. Zones untrust, trust, and inbound are selectable in the security rule editor.

▶ 2A.4 Build security policy, NAT, and a security profile group

Create policy in DG-OCI-HUB. At minimum: an outbound rule (trust to untrust), an inbound rule (inbound zone to trust), an east-west rule, and a final deny.

Source NAT is model-specific

In Model A (Active/Active), the firewall performs source NAT to its untrust IP on outbound and Oracle Services flows so the return leg is symmetric before the NAT Gateway does its own SNAT. In Model B (Active/Passive), source NAT is applied on the untrust interface as well; the difference is that the untrust address is a floating IP. Configure the outbound SNAT rule in both models.

Attach a hardened profile group

Attach a Security Profile Group (Antivirus, Anti-Spyware, Vulnerability Protection, URL Filtering, WildFire, File Blocking) to every allow rule. Start from the validated Iron-Skillet baseline rather than building profiles from scratch.

Verification

Policies > Security shows the ordered rule set, each allow rule shows a profile-group icon, and the NAT rule appears under Policies > NAT.

▶ 2A.5 Configure log forwarding to the default log destination

Create a Log Forwarding profile so session and threat logs reach your log collectors.

  1. In DG-OCI-HUB, go to Objects > Log Forwarding and add a profile.
  2. Name the profile exactly default (lowercase).
  3. Add match-list entries for traffic and threat log types pointing to Panorama or your log collector group.
The magic default keyword

A Log Forwarding profile named exactly default (lowercase) is auto-attached to every new security rule that does not specify a profile. Naming it anything else means each rule must reference the profile explicitly. Use the lowercase default name to guarantee logging coverage.

Verification

New rules created afterward show default in the Log Forwarding column automatically.

▶ 2A.6 Create a License Manager and collect bootstrap parameters
  1. Go to Panorama > SW Firewall License > License Managers and click Add.
  2. Bind the device group DG-OCI-HUB, the template stack STK-OCI-HUB, and the bootstrap definition holding your auth code. Enable auto-deactivate on delete.
  3. Click Show Bootstrap Parameters and record auth-key, plugin-op-commands, panorama-server, dgname, and tplname.
  4. Commit to Panorama.
Verification

The License Manager shows a green status, and Show Bootstrap Parameters returns a complete auth-key and plugin-op-commands string. Save these for Phase 5.

2B SCM configuration

SCM manages VM-Series through a folder hierarchy and configuration snippets. Build the folders, variables, zones, interfaces, and policy before deploying, then collect the simpler SCM bootstrap parameters.

▶ 2B.1 Create the deployment profile and registration PIN
  1. In the CSP, create a deployment profile with Strata Cloud Manager selected (not Panorama). Copy its auth code.
  2. Generate a registration PIN and record the PIN ID and PIN Value.
Verification

The profile shows Strata Cloud Manager as the management type and an active credit pool.

▶ 2B.2 Build the folder hierarchy

Folders in SCM are the configuration scope. Create a hierarchy that mirrors the deployment.

  1. In SCM, go to Workflows > NGFW Setup > Folder Management.
  2. Create All Firewalls > OCI > Hub-OCI.
  3. The folder name is the value you pass as dgname at bootstrap, so keep it stable and case-consistent.
Verification

The Hub-OCI folder appears under OCI in the folder tree.

▶ 2B.3 Configure zones, interfaces, and routing

At the Hub-OCI folder, create zones and interface config that match the OCI VNIC layout.

  1. Create zones untrust, trust, and inbound.
  2. Configure interfaces ethernet1/1 (untrust), ethernet1/2 (trust), and ethernet1/3 (inbound) as Layer 3 DHCP client.
  3. Create a logical router with a default route toward the untrust subnet gateway.
SCM firewalls need outbound internet from the mgmt interface

Unlike Panorama (which can sit on a private network), an SCM-managed firewall must reach *.paloaltonetworks.com from its management interface to register. Ensure the hub management subnet has a route to the NAT Gateway or Internet Gateway.

Verification

The three zones and three interfaces appear in the Hub-OCI configuration, and a push validates green.

▶ 2B.4 Create security policy snippets and log settings
  1. Create security rules at the Hub-OCI folder: outbound, inbound, east-west, and a final deny.
  2. Attach a Security Profile Group based on Iron-Skillet to each allow rule.
  3. Enable log forwarding to Strata Logging Service on each rule.
Source NAT reminder

As in the Panorama path, configure outbound source NAT to the untrust interface so return traffic is symmetric before the OCI NAT Gateway applies its own translation. This applies to both HA models.

Verification

The rule set is ordered correctly and the configuration pushes with a green OK.

Phase 5: Prepare Terraform Configuration

Configure the OCI Terraform provider and the deployment variables. This phase is common to both HA models; the model-specific resources are handled by the project you selected and toggled by a variable.

▶ 5.1 Configure the OCI provider

The OCI provider authenticates with the five values recorded in Phase 1.1. Reference them as variables so no secrets are committed.

terraform {
  required_providers {
    oci = {
      source  = "oracle/oci"
      version = "~> 5.0"
    }
  }
}

provider "oci" {
  tenancy_ocid     = var.tenancy_ocid
  user_ocid        = var.user_ocid
  fingerprint      = var.fingerprint
  private_key_path = var.private_key_path
  region           = var.region
}
Verification

terraform init downloads the oracle/oci provider and reports Terraform has been successfully initialized.

▶ 5.2 Populate the deployment variables

Fill in a terraform.tfvars file. The names below are representative; confirm them against your project's variables.tf.

# --- Identity (Phase 1.1) ---

user_ocid        = "ocid1.user.oc1..xxxx"

Firewall shape sizing

OCI shapes map to VM-Series models by resource floor. Confirm current minimums in the VM-Series on OCI docs.

  • VM-100 / VM-300 — minimum VM.Standard2.4 (4 OCPU, 60 GB).
  • VM-500 — minimum VM.Standard2.8 (8 OCPU, 120 GB).
  • VM-700 — minimum VM.Standard2.16 (16 OCPU, 240 GB).
  • Flex shapes (VM.Standard3.Flex, VM.Optimized3.Flex, AMD E-series Flex) are also supported.
Verification

terraform validate returns Success! The configuration is valid.

▶ 5.3 Inject bootstrap parameters

The firewall reads bootstrap parameters as key=value pairs from user data (the OCI instance metadata user_data field, base64-encoded). Feed in the values collected in Phase 2.

# Panorama-managed example
bootstrap_options = "type=dhcp-client,panorama-server=10.251.2.51,tplname=STK-OCI-HUB,dgname=DG-OCI-HUB,vm-series-auto-registration-pin-id=,vm-series-auto-registration-pin-value=,auth-key=,plugin-op-commands="

# SCM-managed example
bootstrap_options = "type=dhcp-client,panorama-server=cloud,dgname=Hub-OCI,authcodes=,vm-series-auto-registration-pin-id=,vm-series-auto-registration-pin-value="
No spaces around the equals sign

Bootstrap parsing is strict. Write dgname=DG-OCI-HUB, never dgname = DG-OCI-HUB. A single stray space breaks the parser and the firewall reverts to factory defaults on first boot. User data is read exactly once, so a mistake means recreating the instance.

Verification

terraform plan shows the user_data attribute populated on the firewall instances with no interpolation errors.

Phase 6: Deploy & Verify Infrastructure

This is where the two HA models diverge. Everything up to here (management config, image subscription, licensing, provider, and variables) is shared. Pick the model you designed for in the Architecture Overview; your choice persists across the page. The steps common to both models (running terraform apply, confirming instances boot, and confirming registration) are described inside each tab because the resources they create differ.

Which model should I pick?
  • 6A Active/Active — pick for production and high throughput. Two Flexible NLBs with symmetric hashing keep both firewalls active with no failover API calls and no IAM policy. Scales horizontally by adding firewalls to the NLB backend sets.
  • 6B Active/Passive HA — pick when you want a familiar PAN-OS HA pair with stateful failover. A floating secondary IP moves between peers via OCI API calls, which requires a dynamic group, an IAM policy, and instance principals.

6A Active/Active with Flexible NLBs

▶ 6A.1 Apply the Active/Active stack

With ha_model = "active-active", apply the stack. This creates the hub VCN, the DRG, both NLBs, the NAT Gateway, the Service Gateway, and the firewall instances with four VNICs each.

terraform plan -out oci-aa.plan
terraform apply oci-aa.plan
Verification

Apply completes with Apply complete! and the outputs list two firewall instance OCIDs, the Inbound NLB IP, and the Trust NLB IP.

▶ 6A.2 Confirm symmetric hashing on both NLBs

Symmetric hashing is the single most important setting in this model. Without it, the return leg of a flow can land on the other firewall and break session state.

  1. In the OCI Console, open Networking > Load Balancers > Network Load Balancer.
  2. Open the Inbound NLB, then its backend set. Confirm the backend set is configured for symmetric flow (source and destination hashing that is order-independent) and lists both firewalls as backends.
  3. Repeat for the Trust NLB.
Both NLBs must be symmetric

If only one NLB uses symmetric hashing, asymmetric flows appear intermittently under load and show as sessions that open but never complete. Confirm the setting on both the Inbound and Trust NLBs.

Verification

Both backend sets show two healthy firewall backends and symmetric hashing enabled.

Verification

Each route table shows the expected next hop, and a spoke test VM's default route resolves to the DRG then the Trust NLB.

▶ 6A.4 Add a firewall to the backend sets (scale-out)

Horizontal scale is a defining benefit of this model. Adding a firewall does not disrupt existing flows because symmetric hashing only rebalances new flows.

  1. Increase the firewall instance count in your tfvars and apply.
  2. Add the new instance's trust and inbound VNIC IPs to the respective NLB backend sets (the project usually does this automatically).
  3. Watch the backend health checks turn healthy.
Verification

The new firewall shows healthy in both backend sets, and existing sessions on the original firewalls remain established throughout.

6B Active/Passive built-in PAN-OS HA

▶ 6B.1 Apply the Active/Passive stack

With ha_model = "active-passive", apply the stack. This creates the hub VCN with a dedicated HA-link subnet, the DRG, the NAT Gateway, and two firewall instances each with four interfaces (management, untrust, trust, HA link).

terraform plan -out oci-ap.plan
terraform apply oci-ap.plan
Verification

Apply completes and the outputs list two firewall OCIDs and the HA-link subnet OCID.

▶ 6B.2 Create the dynamic group and IAM policy

Failover moves the floating IPs through OCI API calls. Those calls are authorized by a dynamic group (which both firewalls belong to) plus an IAM policy that permits managing private IPs. PAN-OS authenticates as an instance principal, so no API keys are stored on the firewall.

  1. In Identity & Security > Domains > Dynamic Groups, create a group (for example dg-fw-ha) whose matching rule includes both firewall instance OCIDs, or all instances in the compartment: 
    ALL {instance.compartment.id = 'ocid1.compartment.oc1..xxxx'}
  2. Create an IAM policy granting that dynamic group permission to manage private IPs on those instances: 
    Allow dynamic-group dg-fw-ha to use virtual-network-family in compartment cmp-netsec-hub
Allow dynamic-group dg-fw-ha to manage private-ips in compartment cmp-netsec-hub
Allow dynamic-group dg-fw-ha to manage vnic-attachments in compartment cmp-netsec-hub
Confirm the exact policy verbs against the PAN-OS OCI HA doc

The statements above are representative. The precise resource types and verbs PAN-OS requires to reassign a floating IP can change by release. Confirm them in Set Up the VM-Series Firewall on OCI before relying on them in production. Grant the minimum needed to reassign private IPs.

Verification

Both firewall instances appear as matched members of the dynamic group, and the policy is listed in the compartment.

▶ 6B.3 Assign the secondary (floating) IPs on the active peer

Each dataplane interface on the active peer needs a secondary private IP that will float to the passive peer on failover.

  1. In the OCI Console, go to Compute > Instances and open the active firewall.
  2. Open Attached VNICs, select the untrust VNIC, then IP Addresses.
  3. Click Assign Private IP Address and add the floating untrust IP.
  4. Repeat for the trust VNIC, assigning the floating trust IP.
The floating IPs are the ones PAN-OS moves

The primary IP on each VNIC stays with the instance for management and HA housekeeping. Only the secondary (floating) IPs move on failover, which is why they, not the primary IPs, are referenced as the interface addresses in the PAN-OS HA floating-IP configuration.

Verification

The untrust and trust VNICs on the active peer each list two private IPs (primary plus the assigned floating IP).

▶ 6B.4 Configure HA1, HA2, and floating IP failover in PAN-OS

Configure native PAN-OS HA on both peers so they form an Active/Passive pair and know which floating IPs to move.

  1. On each firewall, enable HA under Device > High Availability > General (Active/Passive mode; matching Group ID).
  2. Configure the HA1 control link and HA2 data link on the dedicated HA interface.
  3. Under the interface configuration, set the untrust and trust interface IPs to the floating IP addresses assigned in 6B.3 and enable OCI IP reassignment on failover.
Verification

Dashboard > High Availability widget shows one peer Active and the other Passive, with HA1 and HA2 links green.

▶ 6B.5 Trigger a failover and watch the floating IPs move

Validate that the floating IPs actually migrate through the OCI API and that sessions survive.

  1. Start a continuous ping or session from a spoke VM through the firewall.
  2. On the active peer, run request high-availability state suspend to force a failover.
  3. In the OCI Console, watch the floating trust and untrust IPs move from the active instance's VNICs to the passive peer's VNICs.
If the IPs do not move, check the IAM policy

The most common failure is a missing or too-narrow IAM policy: the instance principal cannot reassign the private IP, so the floating IP stays on the old peer and the new active firewall is unreachable. Re-check the dynamic group membership and the manage private-ips statement from 6B.2.

Verification

The floating trust and untrust IPs now appear on the former passive peer, the ping recovers within a few seconds, and existing sessions remain established.

Troubleshooting

▶ Firewall boots but does not register with Panorama or SCM

The firewall parsed its bootstrap parameters but cannot reach the management plane. This is almost always networking or a bad parameter.

  • Panorama: the management subnet must reach the panorama-server IP on TCP 3978. Check the management subnet route table, the NSG or Security List on the management VNIC, and the DRG or peering path to Panorama.
  • SCM: the management interface needs outbound internet to *.paloaltonetworks.com. Confirm the management subnet routes to the NAT Gateway or Internet Gateway.
  • Re-check the bootstrap string for spaces around any = and confirm dgname matches the device group or folder name exactly.
User data is read once

Bootstrap parameters are consumed at first boot. Editing user data on a running instance does nothing. Fix the tfvars and recreate the instance with terraform apply.

▶ Asymmetric traffic or sessions that never complete (Model A)

Under load, flows open but never finish, or the firewall logs show half-open sessions. This is the classic symptom of a missing symmetric-hashing setting.

  • Confirm symmetric hashing is enabled on both the Inbound NLB and the Trust NLB backend sets.
  • Confirm outbound source NAT is applied on the firewall so the return leg is destined to the firewall's untrust IP, keeping the flow inside the hub.
  • Confirm the Service Gateway route whitelists the hub VCN ranges, not individual spokes.
▶ Floating IPs do not move on failover (Model B)

After a failover, the new active peer is unreachable because the floating trust and untrust IPs stayed on the old peer.

  • Confirm both firewalls are members of the dynamic group (check the matched-instances view).
  • Confirm the IAM policy grants manage private-ips (and the related virtual-network verbs) in the correct compartment.
  • Confirm the PAN-OS interface config references the floating IPs and that OCI IP reassignment is enabled on failover.
▶ Spoke traffic bypasses the firewall

Spoke traffic reaches the internet but never appears in the firewall log.

  • Confirm the spoke application subnet's route table sends 0.0.0.0/0 to the DRG, not to a local Internet Gateway.
  • Confirm the spoke VCN has no Internet Gateway or NAT Gateway of its own that would short-circuit inspection.
  • Confirm the DRG route table forwards spoke traffic into the hub toward the Trust NLB (Model A) or the trust interface (Model B).

Appendix: How Routing Works

OCI routing is per-subnet: every subnet is associated with exactly one route table, and that table decides where the subnet's egress goes. There is no single VCN-wide routing table. Getting inspection right is a matter of pointing the correct subnet and DRG route tables at the firewalls.

▶ The four route tables that matter
  1. IGW ingress route table — attached to the Internet Gateway. For inbound (Model A), it sends the inbound public service range to the Inbound NLB IP, so internet traffic lands on a firewall before reaching the app.
  2. DRG route table — the hub router's table. It forwards spoke traffic into the hub toward the Trust NLB (Model A) or the trust interface (Model B). This is what makes east-west and outbound traffic transit the firewall.
  3. Firewall trust subnet route table — sends inspected outbound traffic back toward the DRG (for spoke destinations) or onward.
  4. Firewall untrust subnet route table — sends 0.0.0.0/0 to the NAT Gateway for internet egress, and the Oracle Services range to the Service Gateway.
Spokes stay simple

A spoke needs only a default route to the DRG. All the hub steering lives in the DRG and hub subnet route tables, so onboarding a new spoke is a two-step operation: attach to the DRG, point the default route at it.

▶ Why source NAT keeps flows symmetric

In Model A, the firewall source-NATs outbound and Oracle Services flows to its untrust IP. This guarantees the return leg is addressed to the firewall (inside the hub) rather than back to the spoke directly, so symmetric hashing on the Trust NLB can send the return leg to the same firewall that saw the forward leg. Without this SNAT, the return path could bypass the firewall and break session state.

Appendix: Traffic Flows Explained

Each flow below traces a packet through the design. Model A flows reference the two NLBs; Model B flows reference the active peer's floating IPs instead.

▶ North-south inbound (Internet to app)

Model A: Internet client to Internet Gateway, to Inbound NLB (symmetric hashing selects a firewall), to the firewall (policy check), to the application load balancer or DMZ server, to the DRG, to the spoke, to the web server. The application public IP associates with the DMZ resource, not the firewall.

Model B: Internet client to the active peer's untrust floating IP, to the firewall (policy check), then forwarded to the app. On failover, the untrust floating IP moves to the new active peer.

▶ North-south outbound (OCI to Internet)

Model A: Spoke VM to DRG (default route), to Trust NLB, to the firewall (source NAT to untrust IP), to NAT Gateway (second SNAT to a public IP), to the internet. The return leg reverses through the same firewall because of symmetric hashing.

Model B: Spoke VM to DRG, to the active peer's trust floating IP, to the firewall (SNAT), to NAT Gateway, to the internet.

▶ East-west (spoke to spoke or on-prem to spoke)

Model A: Source (spoke or on-prem via IPSec/FastConnect) to DRG, to Trust NLB (symmetric hashing), to the firewall in single-arm mode on the trust interface, back to the DRG, to the destination spoke. Traffic enters and leaves the same trust interface.

Model B: Source to DRG, to the active peer's trust floating IP, inspected, back to the DRG, to the destination spoke.

▶ OCI to Oracle Services Network

Spoke VM to DRG, to Trust NLB (Model A) or trust floating IP (Model B), to the firewall (source NAT to untrust IP), to the Service Gateway, to the Oracle Services Network over the Oracle backbone (not the internet). Whitelist the hub VCN ranges on the OSN route so the SNAT-ed return path resolves inside the hub.
