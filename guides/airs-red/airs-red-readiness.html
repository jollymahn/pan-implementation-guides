This document is for the teams who own the AI Red Teaming target: the application developers, the platform engineers, and whoever holds the credentials. Work through it before the first working session. Everything here is something only you can supply, and every item left open on the day is a session that stops early.

What this covers, and what it does not

This is the customer side only. Licensing, tenant provisioning, deployment profiles and entitlement are handled separately by Palo Alto Networks and your account team, and none of it is on this list. If you are looking for that side, it is Phase 1 of the AI Red Teaming guide.

There is also a Technical Requirements Document for AI Red Teaming. That is the structured intake form filled in together during the session. This document is what gets you to that session able to answer it.

Three sections follow. Start these now is the one to action first: every item in it has a lead time measured in days rather than minutes, and it is the usual reason a kickoff slips.

1. Who needs to be in the room

Red Teaming is unusual in that almost nothing can be configured from the Palo Alto Networks side alone. Every target needs its endpoint, its credential and its request shape, and those live with three different people in most organizations. Getting all three into the same session is the single biggest predictor of whether the day produces a scan.

2. What to have ready for each target

Repeat this section once per AI system you intend to scan. Two targets means two sets of answers, and a half-answered second target usually means it does not get scanned on the day.

2.1 — What the target is

Have readyWhy it is needed
A name for the targetSomething recognizable later, such as customer-support-chatbot rather than test1.
Whether it is an application, an agent, or a raw modelThis is the first choice in the wizard and it cannot be corrected by editing a field afterwards. An agent is anything that chooses its own tools and sequences its own actions.
Industry, use case, and named competitorsMandatory for applications and agents. They are what make generated attacks specific to your business rather than generic.
The base model behind it, and the architectureFor example GPT-4o behind a retrieval-augmented application. Shapes which attack techniques are worth running.
Languages the system supportsA system that answers in five languages has five times the surface, and attacks can be generated in each.
Any tools or functions the agent can callFor an agent, the tool surface is the attack surface. Automated profiling discovers some of this, but anything you supply by hand takes precedence.
The system prompt is worth handing over

Supplying the system prompt turns the engagement into white-box testing, which is the most effective mode available. The attack agent reads the instructions and guardrails it has to get past and writes prompts aimed at those specific sentences.

Teams hesitate, and the answer is usually this: an attacker who succeeds at a System Prompt Leak gets it anyway, and finding out what happens next is the entire point of the exercise. If it genuinely cannot be shared, say so early so the engagement is scoped as grey-box instead.

2.2 — How the target is reached

Have readyWhy it is needed
The endpoint URLMust be HTTPS. Plain HTTP endpoints are not accepted.
Whether it answers from the internet, or only from inside your networkThis decides whether a Network Channel or a firewall change is needed, and both have a lead time. See section 3.
How it authenticatesAn API key in a header, basic authentication, or OAuth 2.0. Have the actual credential, or someone who can mint one during the session.
Its protocolPlain HTTPS with JSON covers most cases. Server-sent events, WebSocket, gRPC and SDK-only agents each change the plan, and the last two need code written. Flag these now.
The rate limit, in requests per minuteA scan is throttled to roughly 80 percent of this. Guessing it wrong is the most common cause of a failed run.
Whether the conversation is statefulDoes the endpoint return a session identifier you send back, or must the whole conversation history be replayed in every request? Multi-turn attacks need this answered correctly.

2.3 — A captured request and response

This is the item teams most often arrive without, and the one that takes longest to produce on the day. Capture it in advance, from a real interaction.

  1. Open the application in Chrome or Edge and press F12 to open DevTools.
  2. Go to the Network tab, filter by Fetch/XHR, and clear the log.
  3. Send one ordinary message through the application's own interface.
  4. Click the POST request that appears. From the Payload tab, copy the entire request body JSON.
  5. From the Response tab, copy the entire response body JSON. Capture one complete response, not a streaming fragment.
  6. Save both, and note which field in the response holds the assistant's reply text.
Capture a complete response, not a streamed chunk

If the application streams its answer, the Network tab shows many small fragments. A single fragment cannot be used to describe the response shape. Capture the full assembled body, or tell us the endpoint streams so it is configured as a streaming target from the start.

2.4 — How the target behaves when it refuses

Two behaviors need capturing by hand, and both change what the final report says.

Have readyWhy it is needed
The HTTP status code and body returned when a built-in guardrail blocks a prompt Send one obviously harmful prompt by hand and record what comes back. Without this, every refusal your guardrails correctly produce is filed as a scan error rather than as a defense that held, and the report understates how well the system performed.
The HTTP status code and body returned when the endpoint throttles Usually 429, but not always. Supplied, throttling is recognized and the scan backs off. Not supplied, the scan fails.

Everything in this section has a lead time. None of it can be resolved during the session.

TaskTypical lead timeDetail

Provide a Kubernetes cluster
tunnel route only		 Varies Any distribution works, including a small one on a single VM. It needs network access to the target and capacity for one very small pod. Confirm kubectl and Helm 3 are installed and pointed at the right cluster.
Create or identify a test credential for the target Varies A dedicated credential is better than a shared production one, because it can be revoked the day scanning ends. Whoever creates it must be available in the session if it needs replacing.
Check whether the credential outlives the scan 1 to 5 business days A full attack library run takes about five hours. A token that expires in one hour will expire four times inside it, and nothing renews it automatically. If your identity provider issues short-lived tokens, ask now for a service account with a long-lived one.
Flag any non-HTTP target One development sprint A WebSocket agent needing multi-turn, an SDK-only agent, a gRPC or SOAP agent, an AWS Bedrock Agent or an Azure AI Foundry agent all need code written by your team before they can be scanned. Raising this at the session rather than before it moves the engagement by weeks.
Agree a scanning window Varies Adversarial prompts will arrive at the endpoint steadily for several hours. Tell whoever watches your alerting, and decide whether to scan production or a production-shaped copy.
Some targets need software your team has to write

Most AI systems are reachable with configuration alone. A few are not, and for those the work is a piece of software with an owner and a delivery date, not a form to fill in. Palo Alto Networks does not write it, and neither does Professional Services.

Work out which category each of your targets falls into before the session. The coverage map lists every case that needs code and why.

4. What happens in the session

So you can see why each item above matters:

  1. Your targets are created, one at a time, using the endpoint and credential from section 2.2.
  2. The captured request and response from section 2.3 are used to tell the platform where to put an attack prompt and where to find the reply.
  3. Each target is validated with a single live probe. This is the first moment anything is actually sent to your system.
  4. Agent targets are profiled automatically, which discovers their tools and capabilities.
  5. A first scan is started. An attack library run is roughly five hours, so it will finish after the session.
  6. Results are reviewed together in a follow-up, with remediation and policy recommendations.
