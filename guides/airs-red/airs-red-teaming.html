Guide Approach

This guide follows a target-first approach. All licensing, deployment profiles, and target configurations are established in Strata Cloud Manager (SCM) before launching any adversarial scans. This ensures AI systems are tested against a fully validated connection from the first attack.

Product scope: AIRS AI Red Teaming is an automated adversarial testing service for AI systems: models, applications, and agents. It simulates real-world attacks using 50+ techniques and 500+ scenarios to identify safety, security, compliance, and brand vulnerabilities before they reach production.

Management platform: Strata Cloud Manager (SCM). Steps are shown for both the SCM UI and the API where paths diverge.

Architecture Overview

▶ What AI Red Teaming Does

AI Red Teaming is a SaaS adversarial testing platform that probes AI systems (models, applications, and agents) for vulnerabilities before deployment. It sends crafted attack prompts to the target system, analyzes responses for unsafe behavior, and produces a risk score with actionable remediation guidance.

The attack library is maintained by a team backed by 18,000+ threat researchers who continuously discover novel attack vectors. The library is updated every two weeks with new techniques drawn from frameworks including OWASP LLM Top 10, MITRE ATLAS, NIST AI RMF, and DASF V2.0.

▶ Key Concepts

Targets

A target is the AI system under test. It can be an Application (chatbot, copilot), an Agent (autonomous tool user), or a Model (raw LLM endpoint). Each target has a connection type, authentication method, and optional metadata that provides context for more effective attacks.

Network Channels

For AI systems on private networks, a Network Channel provides secure connectivity using an outbound WebSocket tunnel. A lightweight client deployed in the customer's Kubernetes cluster initiates the connection, so no inbound firewall rules are needed.

Agentic Profiling

Automated profiling that interrogates the target to discover its capabilities, system prompt, and available tools. Runs asynchronously after target creation for Agent-type targets. Results populate the target background and additional context fields.

Risk Score

A composite score from 0 to 100 (higher = more vulnerable) based on the Attack Success Rate (ASR), the percentage of attacks that successfully elicited unsafe behavior from the target.

Reports & Remediation

Each completed scan produces a report with findings grouped by category, severity-level distribution, an AI-generated summary, and runtime security policy recommendations that can be applied directly in AIRS.

Quota & Credits

Scans consume quota tracked per scan type (static, dynamic, custom). Each quota has allocated, unlimited, and consumed fields. Monitor usage via the /v1/metering/quota endpoint.

Okta OAuth Token Expiry: Confirming and Addressing the 1-Hour Window

If the target AI endpoint authenticates using Okta OAuth, the access token AIRS uses to send attack prompts will expire during a scan. Okta access tokens default to a 1-hour lifetime. Attack Library scans run approximately 5 hours. Without a strategy in place, scans fail mid-run when the token expires.

Step 1: Confirm the Okta token lifetime

Ask the customer's Okta administrator to check the token lifetime for the OAuth application used to access the AI target:

  1. Log in to the Okta Admin Console.
  2. Navigate to Security → API → Authorization Servers.
  3. Select the authorization server used by the AI target application.
  4. Click Access Policies and expand the relevant policy rule.
  5. Check the Access Token Lifetime field. The default is 1 hour (3600 seconds).

If the lifetime is under 6 hours, one of the three strategies below must be applied before scanning begins.

Strategy A (Preferred): Provision a long-lived service account API key

Ask the customer's Okta admin to create a dedicated service account in Okta for red teaming with an extended access token lifetime (minimum 6 hours, ideally 24 hours or no expiry if supported by the authorization server policy). Use this service account's credentials in the AIRS target configuration instead of a user-scoped token. This eliminates the expiry problem entirely and is the lowest-effort fix.

Strategy B: Run scans in category-focused batches under 1 hour

Divide the Attack Library scan into shorter runs, each covering a subset of categories that completes within the token lifetime. Refresh the Okta token between batches and update the AIRS target configuration with the new token before starting the next batch. Example batching for a 1-hour token:

  • Batch 1: SECURITY subcategories (Prompt Injection, System Prompt Leak, Evasion)
  • Batch 2: SECURITY remaining (Jailbreak, Multi-Turn, Adversarial Suffix, RCE, Tool Leak)
  • Batch 3: SAFETY and COMPLIANCE subcategories

This extends the engagement timeline but works within the token constraint. Coordinate batch timing with the customer's team.

Strategy C: Token-refresh proxy (advanced)

Deploy a lightweight proxy sidecar alongside the target that intercepts AIRS requests, refreshes the Okta token using a refresh token or client credentials flow before the access token expires, and forwards the request to the actual target with a fresh token. This requires engineering effort from the customer's platform team but is transparent to AIRS. Budget 2-4 hours for implementation. This strategy is best suited for engagements with many targets all using Okta OAuth.

Agree on a Strategy Before the Deployment Call

Token expiry is the most common cause of mid-scan failures for Okta-authenticated targets. Do not leave this as a day-of decision. Confirm the token lifetime and the chosen strategy during pre-engagement discovery so the customer's team has time to implement it before the call.

▶ Target Endpoint Requirements

What is a target? A target is the AI system being tested. Three types are supported:

  • Model — a direct API connection to a foundation model with no application layer: GPT-4o at api.openai.com, Claude at api.anthropic.com, a Bedrock-hosted model, a self-hosted Llama or Mistral instance. Simplest to configure.
  • Application — a model wrapped with a system prompt, business logic, and safety guardrails. Most enterprise targets are Applications: a customer service chatbot, an HR policy assistant, a legal document summarizer, a financial advisor application, a retail shopping assistant. Industry and use case are required fields.
  • Agent — an autonomous system with tool access that can take multi-step actions: a code review agent with repository access, a data analysis agent that writes and executes SQL, a research assistant that browses the web, an IT support agent that manages tickets. Carries the highest risk due to tool misuse potential.

Understanding rate limits: RPM (Requests Per Minute) controls how many API calls AIRS can send to the target each minute. TPM (Tokens Per Minute) controls total token throughput (input plus output combined) per minute. AIRS sends attack prompts sequentially; rate limits determine how fast. An Attack Library scan runs hundreds of prompts over approximately 5 hours. At 20 RPM that is roughly 6,000 total requests, sufficient for a full scan. Below 10 RPM the scan cannot complete in a reasonable window. TPM is a separate constraint: attack payloads are verbose when a full system prompt is included in every request, and a TPM limit below 10,000 causes throttling even when RPM is adequate.

Verify each AI target meets these requirements before the deployment call. A target that fails validation during the call adds 30–60 minutes of unplanned troubleshooting.

Validating Target Endpoint Accessibility Before the Call

Run these checks before the deployment call to confirm each target is reachable. A target that cannot be reached from AIRS cannot be configured, and discovering this during the call adds significant unplanned troubleshooting time.

Public endpoints (internet-accessible)

Send a test request directly to the endpoint using curl. The goal is to confirm the URL resolves, TLS completes, and the API returns a valid response with your credentials. Use the same request format you will enter into the AIRS target configuration.

# Test a public endpoint — substitute your actual URL, token, and model
curl -v -X POST "https://api.openai.com/v1/chat/completions" \
  -H "Authorization: Bearer sk-..." \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o","messages":[{"role":"user","content":"Hello"}]}'

# Expected: HTTP 200 with a response in choices[0].message.content
# If you receive 401: credentials are wrong
# If you receive 000 (no response): URL is unreachable or TLS failed

If the endpoint uses IP allowlisting, confirm AIRS egress IPs are added before running this test from your machine; the test only confirms the endpoint itself is accessible; AIRS may still be blocked if source IP restrictions are in place.

Private endpoints (behind firewall, VPN, or private VPC)

Private endpoints are not reachable from the public internet. You must test reachability from inside the same network, specifically from inside the Kubernetes cluster that will host the Network Channel. Run a test pod inside the cluster and curl the private endpoint from there.

# Test a private endpoint from inside the K8s cluster
kubectl run curl-test --image=curlimages/curl --rm -it --restart=Never -- \
  curl -v -X POST "https://internal.company.com/api/ai/chat" \
  -H "Authorization: Bearer ..." \
  -H "Content-Type: application/json" \
  -d '{"message":"Hello"}'

# If the request succeeds: the Network Channel will be able to reach this target
# If you get a connection refused or DNS failure: the cluster cannot see the endpoint
# check network policy, DNS resolution, and VPN/peering configuration

Also verify the three AIRS FQDNs are reachable outbound from the cluster before the deployment call; the Network Channel cannot establish its tunnel if these are blocked:

kubectl run curl-test --image=curlimages/curl --rm -it --restart=Never -- \
  sh -c "curl -sv https://api.sase.paloaltonetworks.com 2>&1 | grep -E 'Connected|SSL|TLS|failed'; \
         curl -sv https://auth.apps.paloaltonetworks.com 2>&1 | grep -E 'Connected|SSL|TLS|failed'; \
         curl -sv https://registry.ai-red-teaming.paloaltonetworks.com 2>&1 | grep -E 'Connected|SSL|TLS|failed'"

# Any "Connected" response (even if HTTP 403/404) confirms the FQDN is reachable
# A timeout or "Connection refused" means egress to that domain is blocked

Formal validation during the deployment call

After the target is created in AIRS during the deployment call, AIRS performs its own connectivity validation. See Configure Targets — Step 4.4: Validate Target Connection for the formal validation step, which sends an authenticated probe and confirms the response body path extracts model text correctly. For private endpoints, also see Network Channels — Step 5.4: Verify Channel Connectivity to confirm the Network Channel tunnel is online before attempting target validation.

Agent Target — Autonomous Decision-Making Systems Only

Agent targets support five connection methods. Select the method that matches how your agent exposes its API.

Which connection method should I use?
  • REST API — the agent exposes a standard HTTPS POST endpoint with JSON request and response bodies. Most common and most fully featured. Start here unless a specific reason requires another method.
  • Streaming — the agent streams its response token-by-token via Server-Sent Events (SSE). Configuration is nearly identical to REST API. Select this when the agent uses SSE and you need to test incremental response behavior.
  • WebSocket (Beta) — the agent uses a persistent WebSocket connection. AIRS opens a fresh WebSocket per prompt. Does not support multi-turn or sessions. Contact your PAN account team before using this method.
  • Microsoft Copilot Studio — the agent is deployed in Microsoft Copilot Studio. Uses Power Platform APIs and Entra ID delegated authentication. Available for Agent targets only.
  • Custom Adapter — the agent uses a non-standard protocol or proprietary SDK that cannot be expressed as a REST or WebSocket call. The customer writes and uploads a Python adapter. Requires Network Channel client v1.4.0+ and an active Network Channel.
Do I need a wrapper or proxy?

A wrapper is an intermediate service you deploy between AIRS and your agent. It accepts REST calls from AIRS, translates them into whatever protocol your agent uses natively, and returns JSON AIRS can parse. Consider building one in these situations:

  • SDK-only agent — the agent has no HTTP API (only a Python or Java SDK). A thin REST shim exposes the SDK over HTTPS so AIRS can reach it.
  • WebSocket with multi-turn requirements — AIRS's native WebSocket support does not maintain sessions between prompts. If you need stateful multi-turn attacks against a WebSocket-only agent, build a REST-to-WebSocket adapter that manages the connection internally and exposes a REST interface to AIRS.
  • Non-standard authentication — the agent requires request signing (AWS SigV4, HMAC, mTLS) that AIRS does not natively support. A proxy handles signing before forwarding.
  • Legacy or custom protocol — the agent speaks gRPC, SOAP, or another protocol. Try the Custom Adapter method first; a standalone REST wrapper is the alternative when Custom Adapter is not feasible.

Who builds the wrapper: The customer's development team. A wrapper is not a PAN or Professional Services deliverable. Identify during pre-engagement discovery whether a wrapper is needed and factor the build time into the engagement timeline (typically 2–4 hours for a simple REST shim, longer for stateful session management).

▶ Wizard Step 3 — Choose Method: cURL Import or Manual Entry

Step 3 determines how you supply your agent's connection details to AIRS. Two methods are available: cURL Import (recommended) and Manual Entry.

cURL Import (Recommended)

A cURL string is a complete HTTP request expressed as a shell command. When you paste it into the cURL String field and click Next, AIRS automatically extracts the endpoint URL, all HTTP headers, and the request body structure, pre-filling the parameters for the next step. This eliminates manual transcription errors and confirms the request is syntactically valid before proceeding.

What the cURL string must contain

Content-Type header-H "Content-Type: application/json"Yes
Authorization header-H "Authorization: Bearer sk-..."Required if auth is header-based

A complete, correctly formatted cURL string for a typical agent target:

curl -X POST "https://agent.company.com/api/chat" \
  -H "Authorization: Bearer YOUR_API_TOKEN_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [
      {
        "role": "system",
        "content": "You are a helpful HR assistant for Acme Corp."
      },
      {
        "role": "user",
        "content": "{INPUT}"
      }
    ],
    "temperature": 0.7,
    "max_tokens": 500
  }'
The {INPUT} Placeholder Is Mandatory

Replace the actual user message text with the literal string {INPUT} (curly braces, uppercase, no spaces). AIRS substitutes this placeholder with each attack prompt at scan time. The wizard reminds you: "Replace the input prompt's text with '{INPUT}'". Without it, every attack prompt is sent as the same fixed message and the scan produces meaningless results.

How to collect the cURL string from your agent

The cURL string must represent a real, working API call to your agent. Use one of these methods to capture it:

▶ Method A — Browser Developer Tools (recommended for agents with a web UI)

If your agent has a chat interface in a browser, DevTools can capture the exact API call it makes, including the real URL, real auth headers, and the request body format with all fields the agent expects.

  1. Open the agent's web interface in Google Chrome or Microsoft Edge.
  2. Open Developer Tools: press F12 on Windows/Linux or Cmd + Option + I on Mac. Alternatively, right-click anywhere on the page and select Inspect.
  3. Click the Network tab in the DevTools panel.
  4. Click the Fetch/XHR filter button to show only API requests (not images, CSS, or scripts).
  5. Click the clear button (the circle with a line) to remove any existing entries from the log so you start with a clean capture.
  6. Type a short, neutral test message in the chat input (e.g., "Hello") and press Enter or Send.
  7. A new entry appears in the Network log. Look for a POST request to an API URL (e.g., /api/chat, /v1/messages, /completions).
  8. Click that request to open its details panel.
  9. Go to the Payload tab (Chrome/Edge) or Request tab (Firefox) to view the full request body JSON.
  10. Right-click the request in the list and select Copy → Copy as cURL.
  11. Paste the cURL string into a text editor. This is your base cURL string.
  12. Find the field containing your test message text ("Hello") in the request body and replace just that text with {INPUT}.
  13. Remove any headers or body fields that contain per-request ephemeral values (session cookies, CSRF tokens, request nonces). Keep only static authentication credentials.
Capture the Response JSON at the Same Time

While you have the Network panel open, also capture the response JSON for Wizard Step 5. With the same request selected, click the Response tab and copy the full JSON body. Save it alongside the cURL string in your text editor. You will need it in the next step.

▶ Method B — API Documentation or Postman Collection

Many agent platforms publish API reference docs with example cURL commands. Use the example from the documentation and substitute real values for any placeholders.

  1. Find the API reference for your agent (developer portal, Swagger/OpenAPI spec URL, or Postman collection).
  2. Locate the endpoint for sending a chat or inference request. Copy the example cURL command.
  3. Replace all placeholder values with real credentials: API key, endpoint URL, model name.
  4. Run the cURL command from your terminal to confirm it returns a valid response.
  5. Replace the example prompt text in the request body with {INPUT}.

If a Postman collection is available: open the relevant request, click the three-dot menu (…), and select Copy as cURL.

▶ Method C — Platform Console Code Snippet

Some agent platforms generate cURL examples directly in their console (e.g., Azure AI Foundry "View Code" button, AWS Bedrock "API" tab, OpenAI Playground "View Code" panel). Use this as a starting point. Add authentication headers if the console-generated example omits them, then run the cURL from your terminal to confirm it works before pasting into AIRS.

Who provides the cURL string

The customer's development team is the authoritative source. They built or manage the agent and know its API contract, authentication scheme, and any request body requirements that are not documented externally.

  • During pre-engagement discovery, request a working cURL example from the customer's platform team. Confirm it returns a valid response from an external machine before the deployment call.
  • The SE can assist with the {INPUT} replacement and review the request body format, but should not be the primary source of the cURL string.
  • If the customer cannot provide a cURL string before the call, budget 30–60 additional minutes on the day to capture it via DevTools together.
Credentials in the cURL String

The cURL string contains authentication tokens or API keys. Do not share it in email, Slack, or any unencrypted channel. The customer should enter it directly into the AIRS wizard. If you need to review it during a call, use screen share rather than copying credentials into a chat window.

Manual Entry

Use Manual Entry when a cURL string is not available or when the cURL parser does not handle the endpoint's structure correctly. With Manual Entry, you configure each field individually in the steps that follow. The resulting target configuration is identical to a cURL import; Manual Entry is simply a different input path to the same fields. The same {INPUT} and {RESPONSE} placeholders apply.

▶ Wizard Step 4 — Add / Verify Parameters

After cURL import, AIRS pre-fills the fields in this step from the parsed cURL string. Review each field carefully; incorrect values here are the most common cause of target validation failures.

Endpoint URL

Verify the URL extracted from the cURL string:

  • Must use https:// for production endpoints (plain HTTP is rejected)
  • Must include the full path to the chat or inference endpoint (e.g., /api/v1/chat/completions)
  • Must include a port number if the agent listens on a non-standard port (e.g., :8080)
  • Should not contain session-specific query parameters that change per request

HTTP Headers

All -H flags from the cURL string appear as editable header rows:

  • Content-Type — should be application/json. Present automatically if it was in the cURL string.
  • Authorization — contains your API key or bearer token. Confirm it matches the correct environment (test vs production).
  • Ephemeral headers — remove any headers with per-request values (CSRF tokens, request nonces, rotating session cookies). These change each request and cannot be static.
  • x-airs-red-teaming-trace-id — do not add manually. AIRS inserts this header automatically in every outbound request so your agent's logs can distinguish scan traffic from real user traffic.

Response JSON

The hint reads: "Replace the generated response's text with '{RESPONSE}'"

AIRS needs a structural template of the response with {RESPONSE} in place of the agent's actual text output. It uses this template at scan time to locate and extract the model's reply from every response it receives.

How to capture the Response JSON using DevTools

  1. In the DevTools Network panel, click the POST request from your test message.
  2. Click the Response tab to see the raw JSON response body.
  3. Copy the entire JSON. Capture a single complete response, not a streaming chunk.
  4. Paste the full JSON into the Response JSON editor in the AIRS wizard.
  5. Find the field that contains the agent's text reply. It is usually named content, text, answer, response, or similar.
  6. Replace only the value of that field (the actual reply text) with {RESPONSE}. Leave all surrounding fields and their values exactly as captured.

Nested Responses and Dot Notation

AIRS uses dot notation to locate {RESPONSE} in nested JSON. In the example above, the extraction path is choices[0].message.content. Placing {RESPONSE} at the correct field in the template tells AIRS exactly where to look, regardless of how deeply nested the reply is. Ensure you replace only the field containing the actual text output, not a wrapper object or a metadata field.

▶ Step 2 — Write the Python Adapter Script

The adapter is a Python script implementing one or more interface functions. The AIRS runtime injects all result types and error signals; do not import them. All five functions are optional except the core pattern pair.

Typed Return Objects and Error Signals — No Import Needed

Use PreProcessResult, PostProcessResult, CallTargetResult, AuthResult, and SessionPreProcessResult directly. Error signals raise_rate_limited(retry_after=<seconds>) and raise_auth_error(<message>) are also injected. Access the prompt via inference_input.prompt; access the response body via raw_response.json_body (a property, not a method call).

Pattern A — HTTP Targets (Platform Makes the Call)

Implement pre_process and post_process together. The platform executes the HTTP request using the descriptor you return from pre_process. Use this for HTTP targets that need custom request construction, response parsing, or signing. If the target requires multiple HTTP calls per turn, make the additional calls using context.http inside pre_process().

FunctionWhen it runsReturns
pre_process(context, inference_input)Every turn, before the HTTP callPreProcessResult(url, headers, json_body) — platform fires this request
post_process(context, raw_response)Every turn, after the HTTP response arrivesPostProcessResult(output=<reply text>)

Minimal Pattern A Example

def pre_process(context, inference_input):
    return PreProcessResult(
        url=context.vars["endpoint"],
        headers={"Authorization": f"Bearer {context.secrets['api_key']}"},
        json_body={"message": inference_input.prompt},
    )

def post_process(context, raw_response):
    if raw_response.status_code == 429:
        raise_rate_limited(retry_after=30)
    if raw_response.status_code == 401:
        raise_auth_error(f"Token rejected: {raw_response.status_code}")
    return PostProcessResult(output=raw_response.json_body["reply"])

Pattern B — Non-HTTP Transports (You Make the Call)

Implement call_target alone. Use this for WebSocket, GraphQL, SDK-based clients, and custom framing or streaming protocols. If call_target is defined, the platform does not call pre_process or post_process — they are silently ignored even if present in the same script. For standard HTTP targets that need multiple calls, use context.http inside pre_process() instead of switching to Pattern B.

FunctionWhen it runsReturns
call_target(context, inference_input)Every turn; you control the full request/response cycleCallTargetResult(output=<reply text>)

Pattern B Example (WebSocket)

import json
import websockets.sync.client as ws

def call_target(context, inference_input):
    conn = ws.connect(
        context.vars["ws_url"],
        additional_headers={"Authorization": f"Bearer {context.auth['token']}"},
    )
    try:
        conn.send(json.dumps({"message": inference_input.prompt}))
        reply = ""
        for frame in conn:
            event = json.loads(frame)
            if event.get("type") == "chunk":
                reply += event["text"]
            elif event.get("type") == "done":
                break
        return CallTargetResult(output=reply)
    finally:
        conn.close()

Optional: authenticate()

Works with both patterns. Called by the platform on demand; the result is cached for the TTL you specify and re-fetched automatically on expiry or auth error. Use for OAuth2, API token exchange, or any credential that must be obtained before the first request. Per-request signing (HMAC, SigV4) goes in pre_process() or call_target() instead — the request body is not available in authenticate().

def authenticate(context):
    resp = context.http.post(
        context.vars["token_url"],
        data={
            "grant_type":    "client_credentials",
            "client_id":     context.secrets["client_id"],
            "client_secret": context.secrets["client_secret"],
        },
    )
    if resp.status_code != 200:
        raise_auth_error(f"Token endpoint returned {resp.status_code}")
    body = resp.json()
    return AuthResult(ttl=body["expires_in"], data={"token": body["access_token"]})

# In pre_process(), access the token via context.auth["token"]
def pre_process(context, inference_input):
    return PreProcessResult(
        url=context.vars["endpoint"],
        headers={"Authorization": f"Bearer {context.auth['token']}"},
        json_body={"message": inference_input.prompt},
    )

def post_process(context, raw_response):
    return PostProcessResult(output=raw_response.json_body["reply"])

Optional: session_pre_process()

Works with both patterns. Runs once on the first turn of every conversation, including single-turn Attack Library scans, independent of the multi-turn toggle. Use for one-time setup like creating a server-side session. The return value is available as context.session on every subsequent turn.

def session_pre_process(context):
    resp = context.http.post(
        context.vars["base_url"] + "/sessions",
        headers={"Authorization": f"Bearer {context.auth['token']}"},
    )
    return SessionPreProcessResult(session_state={"session_id": resp.json()["id"]})

def pre_process(context, inference_input):
    return PreProcessResult(
        url=context.vars["base_url"] + "/chat",
        headers={"Authorization": f"Bearer {context.auth['token']}"},
        json_body={
            "session_id": context.session["session_id"],
            "message":    inference_input.prompt,
        },
    )

def post_process(context, raw_response):
    return PostProcessResult(output=raw_response.json_body["reply"])

Enable Custom SSL (Self-Signed / Internal CA Certificates)

For endpoints secured with self-signed or internal CA-issued certificates, enable custom SSL by setting config.disableSSLVerification=true. This disables certificate chain validation on the Network Channel client so it can reach endpoints that do not present publicly trusted certificates.

# Deploy or upgrade with custom SSL enabled
helm upgrade panw-network-client \
  oci://registry.ai-red-teaming.paloaltonetworks.com/pairs-redteam-prd-fckx/red-teaming-onprem/charts/panw-network-client:1.0.4 \
  --set config.clientId=<CLIENT_ID> \
  --set config.clientSecret=<CLIENT_SECRET> \
  --set config.channelId=<CHANNEL_ID> \
  --set config.disableSSLVerification=true \
  -n airs-red-teaming
Security Warning

disableSSLVerification=true disables all SSL certificate verification for the Network Channel client. This means the client will not validate the certificate chain, expiry, or hostname of the target endpoint. Only use this setting when you trust the endpoint and the network path between the client and target.

  • Development / staging environments with self-signed certs — acceptable
  • Production environments with valid public certificates — this setting is not required and should not be used
  • Production environments with internal CA — required, since there is currently no option to import a custom CA trust bundle into the client
Limitation: No Custom CA Bundle Import

The Network Channel client does not currently support mounting or importing specific CA certificates or trust bundles. The only mechanism for handling non-public certificates is the binary disableSSLVerification toggle. If your organization requires certificate validation against an internal CA, this is a known gap; monitor the Network Channels documentation for future updates.

#!/bin/bash
# Example: Automated scan script for CI/CD
# Requires: ACCESS_TOKEN, TSG_ID, TARGET_UUID

# Start an Attack Library scan
JOB_ID=$(curl -s -X POST \
  "https://api.sase.paloaltonetworks.com/ai-red-teaming/data-plane/v1/scan" \
  -H "Authorization: Bearer ${ACCESS_TOKEN}" \
  -H "Prisma-Tenant: ${TSG_ID}" \
  -H "Content-Type: application/json" \
  -d '{
    "target_uuid": "'"${TARGET_UUID}"'",
    "job_type": "STATIC",
    "static_job_metadata": {
      "categories": [
        {"category": "SECURITY", "subcategories": ["JAILBREAK", "PROMPT_INJECTION"]},
        {"category": "SAFETY", "subcategories": ["BIAS", "CYBERCRIME"]}
      ]
    }
  }' | python3 -c "import sys,json; print(json.load(sys.stdin)['job_id'])")

echo "Scan started: ${JOB_ID}"

# Poll for completion
while true; do
  STATUS=$(curl -s -X GET \
    "https://api.sase.paloaltonetworks.com/ai-red-teaming/data-plane/v1/scan/${JOB_ID}" \
    -H "Authorization: Bearer ${ACCESS_TOKEN}" \
    -H "Prisma-Tenant: ${TSG_ID}" \

  if [ "${STATUS}" = "COMPLETED" ] || [ "${STATUS}" = "FAILED" ]; then
    echo "Scan finished with status: ${STATUS}"
    break
  fi
  echo "Status: ${STATUS} — waiting..."
  sleep 300  # Check every 5 minutes
done

Appendix: Wrappers and Proxy Services

A wrapper is an intermediate HTTP service you deploy between AIRS and your target AI system. It accepts REST POST requests from AIRS, translates them into whatever protocol, authentication scheme, or SDK call your agent requires, and returns standard JSON that AIRS can parse. From AIRS's perspective, the wrapper looks identical to any other REST endpoint. The wrapper handles everything the AIRS native connection methods cannot.

Palo Alto Networks' own documentation acknowledges the pattern: native WebSocket support "eliminates the need to create custom wrapper APIs or proxy services to translate between REST API and WebSocket communications." That sentence confirms wrappers are a real, recognized solution class; they remain necessary in scenarios where native AIRS connection methods have documented limitations.

▶Concept — What a Wrapper Is and When It Exists

Three analogies help frame the pattern for different audiences:

AnalogyWrapper roleBest for explaining
Hotel concierge AIRS speaks only to the concierge (the wrapper), never directly to the service (the agent). The concierge accepts requests in one format, knows how to reach the agent via its native protocol, and brings back a response in the format AIRS expects. The concierge also handles credential renewal and retries transparently. Non-technical stakeholders; explaining why a separate service is needed
Travel plug adapter AIRS speaks one socket standard (REST + JSON). Your agent may speak a different standard (gRPC, WebSocket, proprietary SDK). The wrapper is the plug adapter that converts the connection interface at the point of contact. AIRS provides the power; the adapter changes the shape. Protocol differences (gRPC, SOAP, WebSocket)
Mailroom franking machine The signing proxy sits at the mailroom between AIRS and the agent. AIRS drops unsigned requests in the outbox. The proxy stamps each one with the required authentication material (SigV4 signature, HMAC, fresh OAuth token) before forwarding. The agent only ever receives properly authenticated requests. Auth signing and token refresh scenarios

Wrappers are always built and maintained by the customer's development team. This is not a Palo Alto Networks or Professional Services deliverable. PS's role is to identify during pre-engagement discovery whether a wrapper is needed, explain the interface contract, and test the final result; building the wrapper is the customer team's responsibility.

▶The Four Scenarios Where a Wrapper Is Absolutely Required

These are not "nice to have" scenarios. In each case, the AIRS native connection methods have a documented, hard limitation that cannot be worked around without a wrapper or adapter.

Scenario 1 — SDK-Only Agent (No HTTP API)

AIRS can only communicate with agents via HTTP. If the agent is only callable through a Python or Java SDK, there is no HTTP endpoint for AIRS to reach. A REST shim exposes the SDK as an HTTPS POST endpoint. The shim runs in the same environment as the SDK (same container, same VPC, same host) so it has access to the agent's runtime.

Wrapper type: Type 1 — REST shim. Estimated build time: 2 to 4 hours for a simple single-method SDK.

Scenario 2 — WebSocket Agent with Multi-Turn or OAuth 2.0 Requirements

AIRS's native WebSocket connection method has two hard limitations: it closes the WebSocket connection after each individual prompt (so session state does not accumulate across turns in a conversation), and it does not support OAuth 2.0 authentication. If either of these is required, the native WebSocket method cannot be used.

A REST-to-WebSocket wrapper accepts a REST POST from AIRS, manages a persistent WebSocket connection internally (handling multi-turn session state), and performs OAuth 2.0 token exchange and refresh before sending each request to the agent. From AIRS's perspective, this is an ordinary REST endpoint.

Wrapper type: Type 2 — REST-to-WebSocket adapter. Estimated build time: 4 to 8 hours; longer if stateful session history must be maintained across prompts.

Scenario 3 — gRPC or SOAP Agent, No Kubernetes Available

Agents using gRPC, SOAP, or AMQP cannot be expressed as a standard HTTP cURL. The preferred solution is the Custom Target Adapter (Pattern B using call_target), which runs inside the Network Channel pod and has direct network access to the agent. However, Custom Adapter requires Kubernetes (for the Network Channel client) at version 1.4.0 or higher with the adapter sidecar explicitly enabled.

If Kubernetes is not available in the environment, a standalone REST shim is the alternative. The shim accepts AIRS REST requests and translates them to gRPC calls, SOAP envelopes, or AMQP messages before forwarding to the agent.

Wrapper type: Type 1 — REST shim (to gRPC/SOAP). Estimated build time: 4 to 8 hours; gRPC stub generation adds complexity.

Scenario 4 — Request Signing Required, No Kubernetes Available

Agents that require AWS SigV4, HMAC-SHA256, or mutual TLS (mTLS) for every request use authentication schemes that AIRS native connection methods cannot generate. The preferred solution is Custom Adapter's pre_process() function, which can compute per-request signatures using context.secrets credentials before AIRS sends the request. This requires Kubernetes.

Without Kubernetes, a signing proxy sits between AIRS and the agent. It accepts unsigned requests from AIRS, computes the required signature or presents the client certificate, and forwards the signed request to the agent. Note that per-request signing cannot use authenticate() in a Custom Adapter because the request body is not available at authentication time; signing must happen in pre_process().

Wrapper type: Type 3 — signing proxy. Estimated build time: 2 to 4 hours for SigV4; longer for mTLS certificate management.

▶Type 1 — REST Shim: Exposing an SDK or Protocol Over HTTPS

A REST shim is a thin FastAPI or Flask application with a single POST route. It accepts AIRS's JSON request, calls the agent using the SDK or protocol the agent natively supports, and returns a JSON response in a shape AIRS can map with the {RESPONSE} template.

Interface Contract

AIRS sends a POST request with the body structure you defined in the Verify & Edit JSON wizard step. The shim must return HTTP 200 with a JSON body containing the response text at the path you mapped. Any non-200 response causes AIRS to log the attack as an error.

▶Type 2 — REST-to-WebSocket Adapter: Multi-Turn and OAuth 2.0 for WebSocket Agents

A REST-to-WebSocket adapter accepts a stateless REST POST from AIRS and manages a WebSocket connection (including session state and token refresh) entirely inside the adapter. This is the only way to achieve multi-turn stateful testing or OAuth 2.0 authentication for WebSocket-only agents, because AIRS's native WebSocket connection method supports neither.

Stateless Single-Turn Example

Each AIRS request opens a new WebSocket connection, sends the prompt, collects the response, and closes. No session state is maintained. Use this when the agent is WebSocket-only but multi-turn context is not required.

"""
REST-to-WebSocket adapter (stateless, single-turn).
Install: pip install fastapi uvicorn websockets
"""
from fastapi import FastAPI, Depends, HTTPException
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
from pydantic import BaseModel
import asyncio, json, websockets

API_TOKEN = "your-secret-token"
WS_ENDPOINT = "wss://agent.company.com/ws/chat"

app = FastAPI()
security = HTTPBearer()

class Message(BaseModel):
    role: str
    content: str

class ChatRequest(BaseModel):
    messages: list[Message]

def verify_token(credentials: HTTPAuthorizationCredentials = Depends(security)):
    if credentials.credentials != API_TOKEN:
        raise HTTPException(status_code=401, detail="Invalid token")

@app.post("/chat")
async def chat(request: ChatRequest, _=Depends(verify_token)):
    user_message = next(
        (m.content for m in reversed(request.messages) if m.role == "user"), ""
    )
    async with websockets.connect(WS_ENDPOINT) as ws:
        await ws.send(json.dumps({"message": user_message}))
        raw = await asyncio.wait_for(ws.recv(), timeout=90)
        data = json.loads(raw)
    return {
        "choices": [{"message": {"role": "assistant", "content": data["reply"]}}]
    }

Stateful Multi-Turn Example

A persistent WebSocket connection is held open in a session store keyed by a conversation ID. AIRS passes the conversation ID (or a stable identifier derived from the session) so the adapter can route follow-up prompts to the correct open connection. This allows context to accumulate across turns so the agent retains earlier prompts in the conversation.

"""
REST-to-WebSocket adapter (stateful multi-turn).
Sessions are stored in memory — use Redis for multi-process deployments.
"""
from fastapi import FastAPI, Depends, HTTPException
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
from pydantic import BaseModel
import asyncio, json, websockets

API_TOKEN = "your-secret-token"
WS_ENDPOINT = "wss://agent.company.com/ws/chat"

app = FastAPI()
security = HTTPBearer()
sessions: dict = {}  # session_id -> open websockets connection

class Message(BaseModel):
    role: str
    content: str

class ChatRequest(BaseModel):
    messages: list[Message]
    session_id: str = "default"

def verify_token(credentials: HTTPAuthorizationCredentials = Depends(security)):
    if credentials.credentials != API_TOKEN:
        raise HTTPException(status_code=401, detail="Invalid token")

@app.post("/chat")
async def chat(request: ChatRequest, _=Depends(verify_token)):
    user_message = next(
        (m.content for m in reversed(request.messages) if m.role == "user"), ""
    )
    sid = request.session_id
    if sid not in sessions:
        sessions[sid] = await websockets.connect(WS_ENDPOINT)
    ws = sessions[sid]
    try:
        await ws.send(json.dumps({"message": user_message}))
        raw = await asyncio.wait_for(ws.recv(), timeout=90)
        data = json.loads(raw)
        return {"choices": [{"message": {"role": "assistant", "content": data["reply"]}}]}
    except Exception:
        # Connection dropped — clean up and let caller retry
        del sessions[sid]
        raise HTTPException(status_code=503, detail="WebSocket connection lost; retry request")

@app.delete("/session/{session_id}")
async def end_session(session_id: str, _=Depends(verify_token)):
    if session_id in sessions:
        await sessions[session_id].close()
        del sessions[session_id]
    return {"status": "closed"}
In-Memory Session Store Is Single-Process Only

The sessions dict in the example above lives in the process's memory. If you run multiple adapter replicas (for redundancy or load balancing), each process has its own session map and requests from the same conversation may land on different replicas. Use Redis or another shared store to key sessions when running more than one adapter process.

▶Type 3 — Signing and Auth Proxy: SigV4, HMAC, and Okta Token Refresh

SigV4 Signing Proxy

AWS SigV4 requires a canonical request string that includes the exact request body, timestamp, and computed HMAC-SHA256 digest. AIRS cannot compute this because it does not have access to AWS credentials and does not sign requests. A signing proxy receives the unsigned request from AIRS, computes the SigV4 signature, adds the required headers (Authorization, x-amz-date, x-amz-content-sha256), and forwards the signed request to the agent.

"""
SigV4 signing proxy using the aws-requests-auth library.
Install: pip install fastapi uvicorn httpx aws-requests-auth
"""
from fastapi import FastAPI, Request, Response
from aws_requests_auth.aws_auth import AWSRequestsAuth
import httpx, os

AWS_ACCESS_KEY = os.environ["AWS_ACCESS_KEY_ID"]
AWS_SECRET_KEY = os.environ["AWS_SECRET_ACCESS_KEY"]
AWS_REGION     = os.environ.get("AWS_REGION", "us-east-1")
AWS_SERVICE    = "execute-api"  # or "bedrock" etc.
AGENT_HOST     = "api.agent.us-east-1.amazonaws.com"
AGENT_URL      = f"https://{AGENT_HOST}/prod/chat"

app = FastAPI()

auth = AWSRequestsAuth(
    aws_access_key=AWS_ACCESS_KEY,
    aws_secret_access_key=AWS_SECRET_KEY,
    aws_host=AGENT_HOST,
    aws_region=AWS_REGION,
    aws_service=AWS_SERVICE,
)

@app.post("/chat")
async def proxy(request: Request):
    body = await request.body()
    resp = httpx.post(
        AGENT_URL,
        content=body,
        headers={"Content-Type": "application/json"},
        auth=auth,
        timeout=90,
    )
    return Response(content=resp.content, status_code=resp.status_code,
                    media_type="application/json")

Okta Token-Refresh Proxy (Strategy C)

Use this when the agent requires Okta access tokens and the token lifetime is shorter than the scan duration (Attack Library scans run approximately 5 hours). The proxy holds a refresh token, exchanges it for a fresh access token before expiry, injects the token into each forwarded request, and forwards the rest of the request body unchanged.

Try Strategy A and B First

Before building this proxy, exhaust the lower-effort Okta strategies documented in the IAM & Permissions prerequisites section: Strategy A (provision a long-lived service account with a non-expiring token) and Strategy B (schedule scans under the token lifetime and accept manual restarts). Strategy C adds operational complexity and requires the proxy to handle Okta's rate limits on token exchange requests.

"""
Okta token-refresh proxy.
Install: pip install fastapi uvicorn httpx
"""
from fastapi import FastAPI, Request, Response
import httpx, os, time

OKTA_TOKEN_URL   = os.environ["OKTA_TOKEN_URL"]   # https://your-org.okta.com/oauth2/v1/token
CLIENT_ID        = os.environ["OKTA_CLIENT_ID"]
CLIENT_SECRET    = os.environ["OKTA_CLIENT_SECRET"]
REFRESH_TOKEN    = os.environ["OKTA_REFRESH_TOKEN"]  # long-lived refresh token
AGENT_URL        = os.environ["AGENT_URL"]           # target agent HTTPS endpoint

app = FastAPI()
_token_cache = {"access_token": None, "expires_at": 0}

def get_access_token() -> str:
    if _token_cache["access_token"] and time.time() < _token_cache["expires_at"] - 120:
        return _token_cache["access_token"]
    resp = httpx.post(OKTA_TOKEN_URL, data={
        "grant_type":    "refresh_token",
        "refresh_token": REFRESH_TOKEN,
        "client_id":     CLIENT_ID,
        "client_secret": CLIENT_SECRET,
    })
    body = resp.json()
    _token_cache["access_token"] = body["access_token"]
    _token_cache["expires_at"]   = time.time() + body.get("expires_in", 3600)
    return _token_cache["access_token"]

@app.post("/chat")
async def proxy(request: Request):
    body = await request.body()
    token = get_access_token()
    resp = httpx.post(
        AGENT_URL,
        content=body,
        headers={"Content-Type": "application/json",
                 "Authorization": f"Bearer {token}"},
        timeout=90,
    )
    return Response(content=resp.content, status_code=resp.status_code,
                    media_type="application/json")

401 errors mid-scan (auth was working at validation) An OAuth 2.0 or API token expired during the scan. Attack Library scans run approximately 5 hours. For static API tokens: check if the token has an expiry policy on the agent side. Request a non-expiring token or rotate the token in the wrapper's environment and restart the wrapper.
WebSocket adapter returns 503 "connection lost" intermittently The agent closes idle WebSocket connections after a timeout. The adapter's stored connection is stale. Add a reconnect loop in the adapter: if a send or recv raises an exception, remove the session from the store, reconnect, and retry the request once before returning 503. Alternatively, add a WebSocket ping/keepalive on a background interval to prevent the agent from closing idle connections.
RATE_LIMIT errors in scan results AIRS is sending requests faster than the agent (or the wrapper) can handle. Configure the Endpoint Rate Limit in the target's Advanced Configurations (requests per minute). This causes AIRS to pace requests. Also confirm the wrapper is not the bottleneck: if the wrapper serially calls the agent (one request at a time), add async concurrency or increase worker count.
SigV4 signing fails: "Signature does not match" The signature is computed over a different request body than what is forwarded to the agent. Any middleware that modifies the body after signing (e.g., re-encoding JSON) will invalidate the signature. Sign the raw bytes of the request body, not a re-serialized version. Read the body once, sign it, and forward the exact same bytes. Do not parse and re-serialize the JSON between signing and forwarding.
gRPC shim: "StatusCode.UNAVAILABLE" or "Connection reset" The gRPC channel is created at import time but the agent service is not available when the shim starts, or the channel enters a bad state after the agent restarts. Create the gRPC channel and stub inside the request handler (not at module level), or implement channel reconnection logic. Use grpc.channel_ready_future(channel).result(timeout=5) to verify connectivity before sending the RPC.
Wrapper works locally but fails in Docker or Lambda DNS resolution for the agent hostname fails in the container/Lambda execution environment. The agent is on a private network not reachable from the container's network. For Docker: run the container with --network host (Linux only) or add the container to a custom Docker network with access to the agent. For Lambda: deploy the function inside the same VPC as the agent and configure the Lambda's subnet and security group to allow outbound traffic to the agent's port.
