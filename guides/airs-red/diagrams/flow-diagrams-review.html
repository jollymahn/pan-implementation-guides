AI Red Teaming flow diagrams

Fourteen diagrams covering how the platform reaches a target and what happens once it can. All of them are already embedded in the guide at the step they belong to; this page gathers them in one place with the commentary that would not fit beside a step.
How to read this set

Every diagram is layered on purpose. The boxes and arrows carry the story an architect can follow in one pass. The monospace insets carry the real field names, status values and version floors, so the same page works as a build reference on a deployment call. Nothing is repeated between the two layers.

Sources are .drawio, exports are .svg (26 to 68 KB each, light mode pinned, no raster fallback). Both sit in docs/guides/airs-red/diagrams/ beside this page. Open a source in diagrams.net, edit, re-export, then run clean-svg.py from the same folder.

What has been verified, and what has not

Everything on these diagrams is drawn from the guide, which in turn is drawn from the Palo Alto Networks documentation. None of it has been confirmed against a live SCM tenant. The claims most worth checking first are listed at the bottom of this page.

1AI Red Teaming end to end

The orientation diagram. One console, three API planes, five routes, one target.

Source airs-red-architecture.drawio · Export airs-red-architecture.svg

This replaces the earlier three-plane diagram. The planes are the same; what is new is the band beneath them, which makes the point the old version left implicit: the platform does not reach the target in one way, it reaches it in one of five, and the choice is made per target.

  • The three planes — split by what you do with them rather than by API path, since the paths are the detail and the purposes are the orientation.
  • The order panel — profile, IAM, channel, target, scan. The two hard gates are that a private target cannot validate until the channel is ONLINE, and a scan cannot start until the target is VALIDATED.
  • The blue panel — the thing to say out loud. Nothing is installed in front of the application, but attack prompts do arrive at a production-shaped endpoint for hours at a time, so the window and the rate limit are a conversation.

2Getting in front of the application

The one the request was really about. How the platform gets to a target, and what each route costs.

Source airs-red-reaching-the-target.drawio · Export airs-red-reaching-the-target.svg

The framing matters more than the picture. "Getting in front of the application" is how the question usually gets asked, and the honest answer is that nothing gets in front of anything: the platform opens a second door and knocks on it. Routes 4 and 5 add a component, but that component only ever carries scan traffic.

  • The lead time column — the reason this is a pre-engagement artifact rather than a deployment one. A firewall change is one to five days, an adapter is a development sprint, and neither is discoverable on the day.
  • Private splits two ways — an IP allowlist and a Network Channel are both "Private" in the wizard, and they are a very different ask of the customer. The guide covers both; this is the first place they appear side by side.
  • The blue callout — keeps Red Teaming apart from AI Gateway and Network Intercept, which do sit in the live path. Worth having in front of you when a customer who has met one of those assumes a maintenance window.

3Three target types, and what each one can connect with

The first choice in the wizard, and the one that shapes everything after it.

Source airs-red-target-types.drawio · Export airs-red-target-types.svg
  • Agent is the only type that profiles — and profiling is what hands an agent-led scan a map of the tool surface. Register an agent as an Application and the scan tests it as a chatbot.
  • The WebSocket row — carries the two limits in the same cell as the capability, because the method is genuinely native and genuinely incomplete, and reading only the first half of that sentence is the mistake this is trying to prevent.
  • The Bedrock row — says what it reaches rather than what it is named after, which is the fastest way to stop someone selecting it for a Bedrock Agent.

4One attack prompt against a REST target

The round trip a scan repeats hundreds of times, and the two fields that decide whether it works.

Source airs-red-rest-target-call.drawio · Export airs-red-rest-target-call.svg

The status code table is the part worth lingering on. Three of its four rows describe a target behaving correctly, and two of those only land in the report as findings if someone configured a field in Wizard Step 6 first.

The guardrail row is the one that changes a report

A target with good guardrails refuses a lot of prompts. With no Guardrail Error Code configured, every one of those refusals is filed as a scan error rather than as a defense that held, so the report shows noise where it should show the control working. One known-harmful test prompt before the call gets both the status code and the body needed to fix it.

5Multi-turn, and who is remembering the conversation

Stateless and stateful side by side, and the connection method where neither is possible.

Source airs-red-multi-turn.drawio · Export airs-red-multi-turn.svg
  • Three field names — assistant_role for stateless, response_id_field and request_id_field for stateful. Getting these wrong produces a scan that runs to completion and tests nothing beyond the first turn.
  • The WebSocket row — the consequence is not just a missing feature. Multi-Turn is one of the nine Security subcategories, so a WebSocket target scanned on the native method returns an incomplete assessment that still looks like a clean one.
  • The system prompt callout — the argument for white-box testing, in the form that tends to work: an attacker who finds a System Prompt Leak gets the prompt anyway, and the point of the exercise is to find out what happens next.

6The Network Channel tunnel

The route for a private target where no inbound rule is permitted.

Source airs-red-network-channel.drawio · Export airs-red-network-channel.svg

This replaces the earlier network channel diagram, which showed the tunnel but none of the things that stop it working. The two tables below the picture are the ones that get used.

  • The three FQDNs — each with the failure it causes if blocked, because "the channel is OFFLINE" is three different problems depending on which one is shut.
  • The version floors — v1.0.4 for custom SSL, v1.0.5 for a proxy, v1.3.0 for a WebSocket target through the channel, v1.4.0 for the adapter sidecar. Easy to promise a capability the installed chart cannot deliver.
  • The upgrade warning — a Helm upgrade restarts the pod and cuts every scan running through the channel. An Attack Library run is about five hours, so this is most of a working day. If an adapter might be needed later, install v1.4.0 with the sidecar enabled from the start.

7Custom Target Adapter, Pattern A and Pattern B

The native answer for a non-standard transport, and the difference between the two patterns.

Source airs-red-custom-adapter.drawio · Export airs-red-custom-adapter.svg
  • The highlighted middle step in Pattern A — pre_process returns a description of a request rather than a request, which is the part people get wrong when they first read the contract.
  • The red note in Pattern B — if call_target exists, pre_process and post_process are ignored silently, with no warning, even in the same file.
  • The runtime limits — 110 seconds a turn, a stateless script, and only stdlib, httpx and websockets importable. That last one has a support-request lead time attached, so it belongs in the plan rather than in the retrospective.

8What has a connector, and what needs code

The coverage map. Eight target shapes the platform reaches on its own, six it does not.

Source airs-red-coverage-map.drawio · Export airs-red-coverage-map.svg

This is the pre-engagement diagram. Everything in the red column turns a configuration task into a piece of software with an owner, and the question it answers is one a discovery call can ask in a sentence.

  • The Bedrock Agent row carries three blockers — no agent identifier on the connection method, no SigV4 from a REST target, and an event stream that {RESPONSE} cannot map. Fixing only the first two still fails, which is why a signing proxy is not enough here.
  • Discovery does not feed Red Teaming — an agent in SCM cloud discovery does not become a scannable target, and there is no action on a discovered asset that creates one. Worth saying before someone plans an inventory-driven rollout.
  • The credential argument — a native Bedrock model target asks for long-lived IAM keys in a SaaS console. A bridge wears an execution role instead. For a security team that balks at the keys, that is often the deciding factor even where the native connector works.

9Type 1, a REST shim

For an agent with no HTTP face at all.

Source airs-red-wrapper-rest-shim.drawio · Export airs-red-wrapper-rest-shim.svg

The route returns an OpenAI-shaped body on purpose, so the response template is a path most customers already recognize. The one rule worth repeating is that anything other than HTTP 200 is logged as a scan error and the attack is lost, so exceptions belong inside the route.

10Type 2, a REST front on a WebSocket agent

What to build when the native WebSocket method runs out of road.

Source airs-red-wrapper-websocket.drawio · Export airs-red-wrapper-websocket.svg

Pairing the two lanes is the point: the native method is not broken, it is incomplete in two specific ways, and the wrapper exists only to close those two. Where Kubernetes is available, Pattern B of the Custom Target Adapter does the same job with nothing extra to host.

11Type 3, signing and token-refresh proxies

Two problems the platform cannot solve on its own: it does not sign, and it does not refresh.

Source airs-red-wrapper-signing-proxy.drawio · Export airs-red-wrapper-signing-proxy.svg
  • The red line in the upper lane — this pattern does not reach a Bedrock Agent. It streams the upstream body straight back, which suits execute-api and fails against InvokeAgent.
  • Strategy A and B come first — a non-expiring service account token, or scanning inside the token lifetime. Strategy C is the last resort, and it ends up holding a long-lived refresh token.
  • Where the signature goes — in pre_process, never in authenticate, because the digest covers a body that does not exist yet at authentication time.

12Bridge A, an AWS Bedrock Agent

A small Lambda that speaks plain JSON on one side and InvokeAgent on the other.

Source airs-red-bridge-bedrock.drawio · Export airs-red-bridge-bedrock.svg
  • The four pieces table — the program, a permissions badge, a public address, and a bearer token, each with where it lives. Written for someone who has not deployed a Lambda before.
  • Use a real alias — TSTALIASID points at whatever is currently in the console editor, so a scan against it is not reproducible.
  • 120-second read timeout — an agent that starts calling tools takes far longer than a model completion, and the default would cut it off.

13Bridge B, an Azure AI Foundry agent

Same contract, same bearer token, different runtime and one structural trap.

Source airs-red-bridge-foundry.drawio · Export airs-red-bridge-foundry.svg
  • An Azure Function is a folder, not a file — the deployment tool expects a project, and creating function_app.py on its own and publishing it fails with nothing useful to go on.
  • Azure Functions Core Tools v4 — a separate install from the Azure CLI, and the piece most often missing on the day.
  • The thread map is process-local — a cold start mid-scan drops the history of every in-flight conversation. Tolerable for a short run, worth backing with Table Storage or Redis for a long agent-led one.

14From a validated target to a report

What happens once the target is reachable.

Source airs-red-scan-lifecycle.drawio · Export airs-red-scan-lifecycle.svg
  • Watch RUNNING, not the end — error logs are readable in real time, so a configuration mistake surfaces in the first few minutes rather than five hours later.
  • All four categories on the first run — a baseline taken across everything is what makes the second scan meaningful. Narrowing later costs nothing; narrowing first leaves nothing to compare against.
  • Quota is per scan type — static, dynamic and custom have separate allocations, and running out shows up as a scan that refuses to start.

Claims worth checking against a tenant

These are the statements a live tenant would settle quickly, ordered by how much they would change if wrong.

ClaimAppears onWhy it matters
An unconfigured Guardrail Error Code turns guardrail refusals into scan errors rather than findings Diagram 4 It changes how a report is read. If refusals are counted correctly without the field, the warning is noise.
The native WebSocket method supports neither stateful multi-turn nor OAuth 2.0 Diagrams 3, 5, 10 Three diagrams and a whole wrapper type rest on it. A change here would remove most of the case for Type 2.
No connection method reaches a Bedrock Agent or an Azure AI Foundry agent Diagrams 8, 12, 13 A new connector in either place would retire a bridge and change a discovery question.
Private splits into IP allowlist and Network Channel, with a static egress IP shown in the wizard tooltip Diagram 2 The lead time on the allowlist route is the single most common schedule risk in this product.
The adapter sidecar is off by default and needs client v1.4.0 or higher Diagrams 2, 6, 7 It decides whether the channel has to be upgraded, and an upgrade interrupts running scans.
Agentic Profiling runs only for Agent targets, after validation Diagrams 3, 12, 13 It is the reason both bridges are registered as Agent targets rather than Applications.
Adapter runtime limits: 110 seconds a turn, 64 KB of carried state, stdlib plus httpx and websockets Diagram 7 Any of these being more generous would widen what an adapter can reasonably do.
