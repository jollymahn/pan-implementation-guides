Branch NGFW ZTP to Active/Passive HA and SD-WAN AutoVPN

End-to-end guide: factory-fresh PA-410 hardware through Zero Touch Provisioning into Strata Cloud Manager, optionally formed into an Active/Passive HA pair, and joined to an existing SD-WAN AutoVPN cluster with an Azure hub. Zero local console configuration required.

Guide Approach

This guide follows a management-first approach. All SCM folder structure, ZTP snippets, labels, and onboarding rules are configured in Strata Cloud Manager (SCM) before any firewall hardware is powered on. When the PA-410s boot and reach the internet, they claim themselves automatically and receive a fully staged configuration.

Design model: One or two PA-410 hardware NGFWs at a remote branch site onboard via ZTP directly to SCM, optionally form an Active/Passive HA pair, then join an existing SD-WAN AutoVPN cluster with an Azure hub. The branch internet is behind SNAT/CG-NAT , no static public IP is assumed.

Scope: This guide covers the branch side only. The Azure hub deployment is covered in Phase 1B using the vmseries_standalone-HA Terraform example.

Architecture Overview

This deployment connects one or two PA-410 branch firewalls to an existing SD-WAN AutoVPN hub-spoke cluster. The single-firewall path provides perimeter security and SD-WAN connectivity with no local redundancy. The HA pair path matches the Small-Site HA Perimeter Firewall Design Model from Palo Alto Networks reference architecture, adding Active/Passive failover at the branch. Both paths sit the firewall(s) between the provider switch (DHCP internet) and the branch LAN switch.

SD-WAN hub-spoke topology , Azure hub A/P HA pair connected to single-firewall and HA-pair branch paths over SD-WAN AutoVPN:

SD-WAN Topology

  • Cluster type: Single hub-spoke VPN cluster. The hub is central; all branches connect to the hub. Branch-to-branch traffic routes through the hub.
  • Hub: 1 existing HA Active/Passive pair (pre-existing, not provisioned by this guide)
  • Branch (new): 1 new HA Active/Passive PA-410 pair behind SNAT/CG-NAT
  • Overlay: IKEv2/IPsec tunnels auto-built by AutoVPN from eth1/1 on each branch firewall to each hub firewall WAN interface
  • Routing: eBGP over the overlay; each site has a unique BGP AS number. AutoVPN auto-configures BGP on the branch when it joins the cluster.

Management interface placement: provider switch for ZTP, LAN switch for production

The management interface is connected to the provider switch for initial ZTP. This is required because the firewall has zero configuration at factory default and needs direct internet access to reach SCM on first boot. There is no security policy, NAT, or routing configured yet, so it cannot route through the dataplane to get out.

In production, this is not ideal. Once ZTP completes and the firewall has a working configuration, move the management cable to the LAN switch and configure a static default route on the management interface pointing to your internal next-hop. PAN-OS uses a dedicated management routing table, so management traffic exits independently of the dataplane. See Phase 4 for the recommended post-ZTP management port migration.

CG-NAT mitigates the initial risk: because this deployment is behind carrier-grade NAT, the management interface gets a private RFC1918 DHCP address. The carrier blocks all unsolicited inbound connections, so the management port is not directly reachable from the internet during ZTP. This makes the provider-switch placement acceptable for initial setup even though it is not the long-term production posture.

Active/Passive HA Behavior

In HA Active/Passive mode, only one firewall is active at a time. The passive firewall has all interfaces inactive except management. When the active firewall fails, the passive assumes the active IP/MAC addresses and sends a gratuitous ARP to update LAN switches. Failover takes under 2 seconds with Passive Link State set to Auto.

SCM management independence

SCM communicates with both HA members independently over their dedicated management interfaces. The passive unit maintains its own SCM connection regardless of which unit is active on the dataplane. This is why Phase 4 moves service routes from the ZTP dataplane path (eth1/1 via loopback.900) to the management interface before HA is formed.

Management interface placement: provider switch for ZTP, LAN switch for production

Both HA management interfaces are connected to the provider switch for initial ZTP. This is required: at factory default the firewall has no configuration and needs direct internet access to reach SCM on first boot. There is no dataplane security policy or NAT available yet to route management traffic through the LAN side.

In production, the management interfaces should be on the LAN switch on a dedicated management VLAN. Move the cables post-ZTP and configure a static default route on the management interface pointing to your internal next-hop. Because PAN-OS uses a separate management routing table, traffic exits the management interface independently of the firewall dataplane, so it can reach the internet through the LAN infrastructure without going through a security policy. See Phase 4 for the post-ZTP management migration steps.

CG-NAT mitigates the initial risk: the carrier-grade NAT blocks all unsolicited inbound connections, so management interfaces on the provider switch are not directly internet-reachable during ZTP. This makes the provider-switch placement acceptable for initial setup.

Hub HA: Azure API-Based Failover

Azure's software-defined networking does not support gratuitous ARP between VMs. Hub HA failover works differently from the branch:

  1. fw-2 detects fw-1 failure (heartbeat loss on HA1, link monitor, or path monitor).
  2. fw-2 calls the Azure REST API using its SystemAssigned Managed Identity (granted Network Contributor on the resource group by Terraform).
  3. The API call moves the floating private IPs (10.0.1.6 and 10.0.1.22) from fw-1's NICs to fw-2's NICs. The Public IP sdwan-hub-pip follows the floating private IP automatically.
  4. Branch SD-WAN tunnels re-establish to the same public IP address on fw-2.
Hub failover is slower than branch failover

Azure API calls take 15 to 60 seconds to complete, compared to sub-second failover for on-premises hardware HA using gratuitous ARP. Plan SD-WAN path-quality profile thresholds accordingly , branch firewalls will briefly lose the hub tunnel during failover and will re-establish on the same Public IP once the API call completes.

▶Step 1B.5: Add hub VMs to SD-WAN plugin as Hub devices

Add both hub VMs to the SD-WAN plugin before adding the branch. Both VMs in an A/P HA pair are added individually with the same site settings , crucially, both use the same site name. The SD-WAN plugin treats them as a single logical hub site.

Azure hub requires Upstream NAT even with a Public IP

In Azure, PAN-OS on the VM sees only the private IP on eth1/1 , Azure NATs the associated Public IP at the hypervisor level. The SD-WAN plugin needs to know the actual public IP (sdwan-hub-pip) so it can tell branch firewalls where to build tunnels. Enable Upstream NAT on the hub gateway settings, set NAT Type to IP Address, and set the IP Address field to the floating Public IP (sdwan-hub-pip) from the Terraform output.

  1. In SCM, navigate to VPN Clusters (under SD-WAN / Prisma SD-WAN).
  2. Create a new VPN cluster (e.g., name VPNC1) with SD-WAN enabled.
  3. On the Hub devices tab, click Add Hub devices.
  4. Select vmseries-fw-1 and configure Gateway Settings:
    • Site Name: hub1
    • Priority: 1
    • Router: default
    • BGP Redistribution Profile: All-Connected-Routes
    • DIA VPN: Disabled (hub has direct internet access — DIA VPN failover not needed)
    • Interface 1 — Ethernet Interface: $eth-internet
    • Interface 1 — Next Hop Gateway: $internet-dgw (Azure subnet gateway, e.g., 10.0.1.1)
    • Interface 1 — SD-WAN Interface Profile: select or create an Ethernet public profile

Troubleshooting

The five most common failure modes, in order of likelihood. Check these before opening a support case.

▶T-1: ZTP never completes — firewalls do not appear in SCM

If both firewalls are powered on and connected to the provider switch but do not appear in SCM after 30–45 minutes, work through this checklist in order:

  1. Outbound port 3978 blocked. From a device on the provider switch network, confirm port 3978 outbound is reachable. Many ISPs and CG-NAT providers block non-standard ports. If blocked, configure PAN-OS to use port 443 instead (available in PAN-OS 11.2 and later).
  2. DHCP not provided on management port. The management interface must receive a DHCP address. Check the provider switch port assignments and DHCP scope.
  3. Onboarding rule mismatch. In SCM, navigate to Configuration > NGFW and Prisma Access > Setup > Device Onboarding and confirm the rule is enabled and matches the HA-Group label assigned in the ZTP portal.
  4. Devices not claimed in ZTP portal before boot. The ZTP portal registration must exist before the firewalls first reach the internet. If the devices booted without being registered, power them off, register them, then power back on.

On the firewall CLI (console access), check ZTP status:

show system ztp status
show cloud-management-status
show jobs all
Expected healthy state

show cloud-management-status shows Connected: Yes. show jobs all shows the Advanced Routing Engine job completed. Both devices appear in SCM Settings > Device Management > Cloud Managed Devices.

▶T-2: Passive unit loses SCM connectivity after HA is formed

Symptom: SCM shows the passive firewall as Disconnected intermittently. Config sync fails. This means service routes were not moved to the management interface before HA was formed (Step 4.4 was skipped or the push failed).

Diagnosis , run on the passive firewall:

show netstat all yes numeric-ports yes numeric-hosts yes | match :3978

If the source IP in the output is eth1/1's address (not the management IP), service routes are still using the dataplane path. Break HA, return to Phase 4, complete Steps 4.4–4.5, then re-run Phase 5.

▶T-3: HA does not form — HA1 link stays down

Symptom: After the Phase 5 push, show ha all shows HA1 link state as down and peer state as unknown.

Check the physical link first:

show interface ethernet1/2
  • If link state is down: wrong cable or wrong port. Confirm the crosslink is eth1/2 ↔ eth1/2 (not eth1/2 ↔ eth1/3).
  • If link state is up but no IP address: the wizard mapped the wrong interface. Return to Phase 5 and re-run the SCM HA wizard, selecting ethernet1/2 explicitly for HA1.
  • If link state is up and IP is correct: check that both HA peers are running the same PAN-OS version. Mismatched versions block HA formation.
▶T-4: IPSec tunnels form but BGP does not establish

Symptom: show vpn ipsec-sa shows tunnels active, but show routing protocol bgp peer shows state Idle or Active (not Established).

Most common causes:

  1. Missing BGP security policy. In SCM, confirm a security policy exists that permits bgp from zone-internal to zone-to-hub and the reverse. Insert it near the top of the rulebase and push.
  2. BGP AS number conflict. Each SD-WAN site must have a unique BGP AS number. If two sites share an AS, BGP will not form. Check the VPN cluster configuration in SCM for duplicate AS numbers.
  3. Hub not pushed after branch was added to VPN cluster. The hub firewall must receive updated peer configuration when a new branch is added. Re-push to both hub and branch and confirm both pushes succeed.
▶T-5: Hub HA failover — floating IP does not move to fw-2

Symptom: After request high-availability state suspend on fw-1, fw-2 becomes active but the SD-WAN hub tunnels do not recover. Branch firewalls cannot re-establish tunnels.

Check the Azure role assignment , this is the most common cause:

az role assignment list \
  --resource-group CUSTOMER_RG_NAME \
  --query "[?roleDefinitionName=='Network Contributor'].{principal:principalName}" \
  --output table

If fw-2's Managed Identity does not appear in the output, the role assignment failed during Terraform apply. Re-run terraform apply , it is idempotent and will add the missing assignment. Then test failover again.

If the role assignment is present but the IP still doesn't move, check the system log on fw-2 for Azure API error messages:

show log system | match "azure\|HA\|floating"
