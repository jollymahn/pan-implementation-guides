Panorama Deployment on GCP

End-to-end guide: GCP project setup through a fully accessible Panorama management platform

AWS Panorama Guide Azure Panorama Guide

Guide Approach

This guide deploys a standalone Panorama instance on Google Cloud Platform in management-only mode (no additional logging disks). Panorama serves as the centralized management platform for VM-Series firewalls deployed across your cloud environment.

Deployment method: All GCP infrastructure is deployed with Terraform using the official Palo Alto Networks SWFW Modules for GCP. The panorama_standalone example creates a VPC network, subnetwork, firewall rules, and a Panorama instance with approximately 8 Terraform resources.

Access methods: Two options are documented — direct SSH/HTTPS with a public IP, or GCP Identity-Aware Proxy (IAP) tunneling for deployments without a public IP.

Architecture Overview

The deployment creates a minimal, purpose-built network for Panorama management traffic. Understanding this architecture before configuring Terraform prevents common firewall-rule and connectivity issues.

▶ Topology

The Panorama standalone deployment creates:

  • 1 VPC network (firewall-vpc) with a single subnetwork (panorama-subnet, default 172.21.21.0/24)
  • 1 Panorama instance with a static private IP (172.21.21.2) and an optional public IP
  • GCP firewall rules controlling management access (SSH, HTTPS, device registration on port 3978)

Panorama runs in management-only mode — no additional logging disks are attached. For dedicated logging, refer to the Panorama module documentation for log_disks configuration.

Network Connectivity

Managed VM-Series firewalls must reach Panorama on specific ports. Plan network connectivity (VPC Peering, Cloud VPN, or Cloud Interconnect) before deployment.

PortDirectionPurpose
TCP/22Admin → PanoramaSSH management access
TCP/443Admin → PanoramaWeb UI management access
TCP/3978Firewall → PanoramaDevice registration and management
TCP/28443Firewall → PanoramaLog forwarding (Cortex Data Lake)
IAP as an alternative to public IP

GCP Identity-Aware Proxy (IAP) enables SSH and HTTPS access to Panorama without attaching a public IP. Set attach_public_ip = false in terraform.tfvars and use the IAP tunnel commands documented in Phase 4. The example tfvars includes a dedicated firewall rule for the IAP source range 35.235.240.0/20.

▶ SSH Key Format

Panorama on GCP accepts SSH keys in a specific format: admin:ssh-rsa AAAA... admin. The admin: prefix maps the key to the PAN-OS admin user. A malformed key results in a deployed instance with no SSH access — the only recovery is to delete and redeploy.

No recovery from a bad SSH key

If the SSH key is malformed (missing admin: prefix, extra whitespace, wrong algorithm), the Panorama instance deploys but SSH access fails. The VPC network and firewall rules survive deletion — only the Panorama instance must be destroyed and recreated with the corrected key.

Phase 1: Prerequisites

Complete these one-time setup tasks before configuring Terraform. If already completed for a previous GCP deployment, skip to Phase 2.

▶ Step 1.1: Verify GCP Project & Permissions

All GCP resources are created within a single project. The account running terraform apply needs sufficient privileges to create VPC networks, firewall rules, and Compute Engine instances.

  1. Log in to the Google Cloud Console.
  2. Select or create the target project.
  3. Ensure billing is linked under Billing > Account Management.
  4. Enable the Compute Engine API:

  --project=YOUR_PROJECT_ID

Verification

Run gcloud projects describe YOUR_PROJECT_ID — confirm lifecycleState: ACTIVE. Run gcloud services list --enabled --project=YOUR_PROJECT_ID and confirm compute.googleapis.com appears.

▶ Step 1.3: Obtain Panorama License

A valid Panorama license is required before deploying. The Terraform module deploys Panorama using the panorama-byol-1000 image, which requires a BYOL license.

  1. Log in to the Customer Support Portal.
  2. Navigate to Products > Panorama.
  3. Locate or request a Panorama license auth code for the target PAN-OS version.
  4. Record the auth code — it is used for license activation in Phase 4 after Panorama is accessible.
Verification

▶ Step 1.4: Generate SSH Key Pair

An SSH key pair provides initial access to the Panorama CLI. The public key must be formatted with the admin: prefix for GCP to map it to the PAN-OS admin user.

Generate the key pair

ssh-keygen -t rsa -b 4096 -f ~/.ssh/gcp-panorama-key -C "admin" -N ""

Format for Terraform

The ssh_keys field in terraform.tfvars expects the format admin:<public-key-contents>. Generate the correctly formatted string:

echo "admin:$(cat ~/.ssh/gcp-panorama-key.pub)"

The output should look like: admin:ssh-rsa AAAA...long-base64-string... admin

Corrupted key = delete and redeploy

If the SSH key is malformed (extra spaces, missing admin: prefix, wrong algorithm), Panorama deploys but SSH access fails. The only recovery is to delete the instance and redeploy. The VPC network and firewall rules survive deletion.

Verification

The output of echo "admin:$(cat ~/.ssh/gcp-panorama-key.pub)" starts with admin:ssh-rsa AAAA and ends with admin. No line breaks or extra whitespace.

▶ Step 1.6: Windows Users
Windows Users

All shell commands in this guide use Bash syntax (Linux/macOS). If deploying from a Windows workstation, use one of the following approaches:

▶ Step 2.4: Configure VPC & Firewall Rules

The networks variable defines the VPC network, subnetwork, and GCP firewall rules that control management access to Panorama.

# VPC
networks = {
  "panorama-vpc" = {
    vpc_name                        = "firewall-vpc"
    create_network                  = true
    delete_default_routes_on_create = "false"
    mtu                             = "1460"
    routing_mode                    = "REGIONAL"
    subnetworks = {
      "panorama-sub" = {
        name              = "panorama-subnet"
        create_subnetwork = true
        ip_cidr_range     = "172.21.21.0/24"
        region            = "us-central1"
      }
    }
    firewall_rules = {
      "allow-panorama-ingress" = {
        name             = "allow-panorama-ingress"
        source_ranges    = ["YOUR.ADMIN.IP/32"]
        priority         = "1000"
        allowed_protocol = "all"
        allowed_ports    = []
      }
      "allow-cloudiap-ingress" = {
        name             = "allow-cloudiap-ingress"
        source_ranges    = ["35.235.240.0/20"]
        priority         = "1000"
        allowed_protocol = "tcp"
        allowed_ports    = [22, 443]
      }
    }
  }
}

Key fields to customize

FieldWhat to change
source_ranges in allow-panorama-ingressReplace YOUR.ADMIN.IP/32 with the public IP or CIDR of your management workstation. Include the management VPC subnet (172.21.21.0/24) if managed firewalls will connect from within GCP. For firewall-to-Panorama traffic, include the CIDR of the VM-Series management subnet.
ip_cidr_rangeChange the subnetwork CIDR if 172.21.21.0/24 conflicts with your existing IP address plan.
region in the subnetworkMust match the top-level region variable.
Important: Restrict source_ranges

The allow-panorama-ingress rule with allowed_protocol = "all" permits all traffic from the specified sources. Restrict source_ranges to known management IPs only. Never use 0.0.0.0/0 in production — this exposes Panorama SSH and HTTPS to the entire internet.

IAP firewall rule

The allow-cloudiap-ingress rule allows GCP Identity-Aware Proxy to reach Panorama on ports 22 and 443. The source range 35.235.240.0/20 is the fixed GCP IAP IP range. Keep this rule even if attaching a public IP — IAP provides a fallback access method.

Verification

The source_ranges in allow-panorama-ingress contains only known management IPs — not 0.0.0.0/0. The IAP rule source range is exactly 35.235.240.0/20. The subnetwork region matches the top-level region variable.

The panoramas variable defines the Panorama instance settings: name, zone, image version, SSH key, IP addressing, and public IP attachment.

Phase 4: Post-Deployment

Panorama takes several minutes to boot after the Terraform apply completes. This phase covers initial SSH access, password setup, and web UI access.

▶ Step 4.1: Wait for Bootstrap

Panorama boots and initializes after the Terraform apply completes. This process takes approximately 5–10 minutes. Do not attempt SSH or web UI access until the instance is fully booted.

Monitor boot progress via the GCP Console serial port output:

  1. Navigate to Compute Engine > VM instances.
  2. Click the Panorama instance name (panorama-01).
  3. Click Serial port 1 (console) under the Logs section.
  4. Watch for the PAN-OS login prompt, indicating boot is complete.
Verification

The serial console shows a PAN-OS login prompt. The instance status in the GCP Console shows a green check mark under VM instances.

▶ Step 4.2: Connect via SSH (Public IP)

Connect to Panorama using the public IP from Step 3.4 and the SSH key generated in Step 1.4.

ssh admin@PUBLIC_IP -i ~/.ssh/gcp-panorama-key

Replace PUBLIC_IP with the value from terraform output panorama_public_ips.

No public IP?

If attach_public_ip = false, skip this step and use Step 4.3 (IAP tunnel) instead.

Verification

The SSH session connects and displays Welcome admin. followed by the admin@Panorama> prompt.

▶ Step 4.3: Connect via IAP Tunnel (No Public IP)

GCP Identity-Aware Proxy (IAP) provides SSH access to instances without a public IP. This is the required access method when attach_public_ip = false, and a recommended fallback even when a public IP is attached.

gcloud compute ssh \
  --zone "ZONE" \
  "admin@INSTANCE_NAME" \
  --tunnel-through-iap \
  --project "PROJECT_ID" \
  -- -i ~/.ssh/gcp-panorama-key

Replace the placeholders:

PlaceholderValue
ZONEThe zone from terraform.tfvars (e.g., us-central1-a)
INSTANCE_NAMEThe panorama_name value (e.g., panorama-01). Include the name_prefix if one was set.
PROJECT_IDThe GCP project ID
Important: First-time IAP provisioning delay

The first IAP tunnel connection to a new instance may hang or time out while GCP provisions the IAP backend. If the connection stalls, cancel with Ctrl+C and retry after 30–60 seconds. Subsequent connections proceed without delay.

Verification

The SSH session connects through the IAP tunnel and displays Welcome admin. followed by the admin@Panorama> prompt.

▶ Step 4.4: Set Admin Password

Panorama deploys with SSH key authentication only — no password is set. Set an admin password to enable web UI login.

configure
set mgt-config users admin password
commit

Enter and confirm the new password when prompted. The commit saves the password to the running configuration.

Important: Break-glass account hygiene

The admin account is the default superuser. In production, create a separate named admin account for daily use and reserve admin as a break-glass account with a strong, stored password. Set an account lockout policy under Panorama > Setup > Management > Authentication Settings to prevent brute-force attacks.

Verification

The commit command returns Configuration committed successfully. Exit configuration mode with exit.

▶ Step 4.5: Access Web UI

Access the Panorama web interface using a browser. The method depends on whether a public IP is attached.

Direct access (public IP)

Open a browser and navigate to:

https://PUBLIC_IP

Log in with username admin and the password set in Step 4.4. Accept the self-signed certificate warning.

IAP tunnel access (no public IP)

Start an IAP TCP forwarding tunnel to port 443:

gcloud compute start-iap-tunnel INSTANCE_NAME 443 \
  --local-host-port=localhost:4443 \
  --zone=ZONE \
  --project PROJECT_ID

Leave this terminal session running. Open a browser and navigate to:

https://localhost:4443
Important: IAP multi-source-IP connection resets

IAP TCP forwarding uses multiple source IP addresses. After a successful Panorama login, the session may immediately reset because the Panorama web server sees a different source IP on the subsequent request and drops the session. If this occurs, re-establish the IAP tunnel and log in again. The second attempt succeeds because the IAP backend stabilizes on a consistent source IP after the initial negotiation.

Verification

The Panorama web UI loads and displays the Dashboard tab after login. The top-right corner shows the Panorama serial number and PAN-OS version.

▶ Step 4.6: Activate License

Activate the Panorama license using the auth code obtained in Step 1.3.

  1. Navigate to Panorama > Device > Licenses.
  2. Click Activate feature using authorization code.
  3. Enter the Panorama auth code and click OK.
  4. Wait for the license activation to complete. Panorama contacts the Palo Alto Networks licensing server over the internet.
Outbound internet required

License activation requires outbound HTTPS connectivity from Panorama to updates.paloaltonetworks.com. If Panorama does not have a direct internet path (e.g., no public IP and no NAT gateway), configure a route to the internet before activating. The default VPC route (0.0.0.0/0 via the default internet gateway) provides this connectivity.

Verification

The Licenses page shows active license entries with valid expiration dates. The Panorama serial number appears under Device > Setup > General Settings.

▶ SSH Key Rejected

SSH key issues are the most common deployment failure. The key must be in exact format: admin:ssh-rsa AAAA...base64... admin

IssueCheck
Missing admin: prefixThe ssh_keys value in terraform.tfvars must start with admin:
Missing trailing adminThe SSH key comment (generated by -C "admin") must be admin, not your email or hostname
Line breaks in keyThe entire key must be on one line in terraform.tfvars — no wrapping
Wrong algorithmUse RSA (ssh-rsa). Ed25519 and ECDSA may not be supported by all PAN-OS versions.

Verify the correct format by running:

echo "admin:$(cat ~/.ssh/gcp-panorama-key.pub)"

The output must be a single line starting with admin:ssh-rsa AAAA and ending with admin.

Recovery requires redeployment

GCP instance metadata (including SSH keys) cannot be changed for Panorama in a way that PAN-OS will read at runtime. The only recovery is: terraform destroy followed by terraform apply with the corrected key. The VPC and firewall rules are recreated automatically.

Verification

SSH connection succeeds with the corrected key.

Cleanup

▶ Destroy All Resources

Remove all Terraform-managed resources when Panorama is no longer needed or when redeploying from scratch.

terraform destroy

Type yes when prompted. If using example.tfvars: terraform destroy -var-file=example.tfvars

Warning: Data loss

Destroying the Panorama instance permanently deletes all configuration, device groups, templates, logs, and any data stored on the instance boot disk. Export the running configuration (Panorama > Setup > Operations > Export named configuration snapshot) before destroying. If log disks were attached, those are also destroyed.

Verification

The output ends with Destroy complete! Resources: 8 destroyed. (count may vary). Navigate to Compute Engine > VM instances in the GCP Console and confirm the Panorama instance no longer appears.
