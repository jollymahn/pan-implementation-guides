Customer Readiness — AI Model Scanning

What your ML and platform teams need ready before the first model scanning working session

AI Red Teaming AI Gateway API Intercept Model Scanning

This document is for the teams who own the AI Model Scanning target: the application developers, the platform engineers, and whoever holds the credentials. Work through it before the first working session. Everything here is something only you can supply, and every item left open on the day is a session that stops early.

What this covers, and what it does not

This is the customer side only. Licensing, tenant provisioning, deployment profiles and entitlement are handled separately by Palo Alto Networks and your account team, and none of it is on this list. If you are looking for that side, it is Phase 1 of the AI Model Security guide.

There is also a Technical Requirements Document for AI Model Scanning. That is the structured intake form filled in together during the session. This document is what gets you to that session able to answer it.

Three sections follow. Start these now is the one to action first: every item in it has a lead time measured in days rather than minutes, and it is the usual reason a kickoff slips.

1. Who needs to be in the room

RoleWhat they must be able to doWhat stalls without them
ML engineer or data scientist Name the models in use, say where each comes from, and run a scan from their own machine during the session. There is no inventory to scan, and nobody can confirm whether a verdict is a real problem or an expected property of a model the team already trusts.
MLOps or platform engineer Install a Python package on a build runner, hold a service credential, and add a step to a pipeline. Scanning stays a manual activity somebody remembers to do, which is not a control.
Owner of the model storage Grant read access to the buckets, containers or registries the models live in. The agent can authenticate to the scanning service and still not read a single model file.
Network or egress owner Permit outbound access from wherever the agent runs, including to the private package registry it installs from. The install itself fails, before any scanning is attempted. This is the most common first-day blocker.
Security or governance owner Decide which findings block a model from being used, and which are recorded and accepted. Rules are left at defaults and the first scan produces findings nobody has authority to act on.

2. What to have ready

2.1 — The model inventory

Every model your organization pulls in, trains, or ships. Third-party models are the point of the exercise, but models you built yourself are scanned the same way.

For every model, recordWhy it is needed
Name and versionModels are tracked by a fingerprint of their contents rather than by where they are stored, so the same model pulled from two places is recognized as one model.
Where it comes fromPublic Hugging Face, Amazon S3, Google Cloud Storage, Azure Blob Storage, a local path, Artifactory, or GitLab. This matters more than it sounds: see the note below.
File formatSafetensors, ONNX, pickle-based checkpoints, and so on. The format itself is one of the things a rule can accept or reject.
Approximate sizeModels from object storage are downloaded locally before scanning, so a large model needs disk and time. Hugging Face models are not downloaded by the agent.
Which application uses itSo a finding can be traced to something that is actually running.
Who approved itOften nobody, which is usually the finding that lands hardest.
A security group is bound to one source type, permanently

Rules are grouped, and each group is tied at creation to a single source type. That binding cannot be changed afterwards. Scanning the same model from two different registries means two groups.

So the source list in your inventory is not administrative detail; it determines how many groups you configure and how much tuning you repeat. Get it accurate before the session.

Private Hugging Face repositories are not scanned directly

Only public repositories can be scanned at source. A private model has to be downloaded first and scanned as a local path instead. If a meaningful share of your inventory is private, plan for the local route and the disk it needs.

2.2 — Where the agent will run

The client is a Python package that runs on whatever machine starts a scan: a workstation, a build runner, or a dedicated host.

RequirementDetail
Python3.11 minimum, with 3.12 preferred. Confirm what your build images actually carry rather than what the standard says.
CPU and memoryTwo cores and 2 GB will run; four cores and 4 GB is comfortable. Local scans of large models are the memory-hungry case.
DiskEnough for the largest model you will scan, with 10 GB or more a sensible floor. Hugging Face scanning needs none, because nothing is downloaded locally.
Operating systemUbuntu 20.04 or later, RHEL 8 or later, macOS 11 or later, or Windows 10 and 11 under WSL2.
Ability to install a packageFrom a private registry, using an extra index URL. In a locked-down build environment this is frequently the blocker.

2.3 — Storage credentials

The agent reads model files directly, so it needs its own read access. One per storage platform in your inventory.

  • Amazon S3 — read access to the buckets and prefixes holding models.
  • Google Cloud Storage — a service account with object read access.
  • Azure Blob Storage — a credential with read access to the containers.
  • Artifactory or GitLab — a token that can read the model repositories.
  • Local paths — the files already present on the machine running the agent.

2.4 — Where scanning fits the lifecycle

A scan that runs when someone remembers is not a control. Decide in advance where the gate sits.

Candidate gateWhat to weigh
On acquisitionScan every model as it is pulled from an external source. Catches the problem earliest, and needs a hook wherever models enter.
On registry promotionScan when a model is promoted to an approved registry. A natural gate if you already have one.
In the build pipelineScan as part of CI. Fits existing habits and existing failure handling.
Before deploymentThe last gate before serving. Latest and most disruptive place to find a problem.

Alongside that, decide what a finding does. The recommendation for a first deployment is to set the three threat-detection rules to blocking and leave the governance rules, such as approved file formats and license validity, recording only until those lists have been tuned to your own portfolio. Starting with everything blocking produces a wall of failures on day one and the control gets switched off.

3. Start these now

TaskTypical lead timeDetail
Confirm the agent can install from a private package registry 1 to 2 weeks The client is not on public PyPI. It installs from an authenticated private index, and many organizations route all package installs through an internal mirror that will not pass an extra index URL through. Test this early, because it is the blocker that most reliably stops a session before it starts.
Open outbound HTTPS from wherever the agent runs 1 to 5 business days The management and data endpoints, the authentication endpoint, the private package registry, Hugging Face if you scan it, and whichever cloud storage endpoints your models live behind.
Request a service account with a client identifier and secret 1 to 5 business days The agent authenticates as a service account rather than as a person, so scans can run unattended in a pipeline.
Grant storage read access 1 to 5 business days Usually a separate team from the one attending, and usually the item that arrives last.
Provision disk on the scanning host Varies Only matters for object storage and local scans, and only becomes obvious when a multi-gigabyte model fills a build runner.
Write the approved format and license lists 1 to 2 weeks Which model formats are acceptable, and which licenses your legal team permits. Both come from outside the ML team and neither can be invented on the day.
Pick a known-bad model to test with Minutes A model with a published deserialization vulnerability proves the pipeline actually catches something. Scan it only. Never load or execute it.

4. What happens in the session

  1. A service account is created and the agent is installed on your chosen host.
  2. Security groups are reviewed, one per source type you use, and rules are set to blocking or recording per section 2.4.
  3. A first model is scanned from each source type in your inventory.
  4. The known-bad model is scanned so you see a real finding rather than a clean run.
  5. Results are reviewed rule by rule, and the governance lists are tuned against what your own models actually look like.
  6. The pipeline integration is drafted at the gate chosen in section 2.4.

  • CPU, memory and disk confirmed against the largest model in scope
  • Install from the private package index proven to work
  • Outbound endpoints opened and tested from the scanning host
  • Service account with client identifier and secret in hand
  • Storage read credentials in hand, one per platform
Policy
  • Lifecycle gate chosen
  • Blocking and recording decided per rule
  • Approved file format list written
  • Acceptable license list written
  • A known-bad test model identified
Check your connectivity before the session

The connectivity validator generates the commands to prove the endpoints are reachable, your service account authenticates, and the private package index answers. Run it from the host that will actually do the scanning, since that is where the egress rules apply.
