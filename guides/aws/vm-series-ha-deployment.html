VM-Series Active/Passive HA on AWS

End-to-end guide: two VM-Series firewalls configured as an Active/Passive HA pair across two Availability Zones, with IAM-based EIP and route table failover.

VM-Series GWLB Guide Panorama on AWS Cloud NGFW
Phase 1 Prerequisites Phase 2 Mgmt Platform Phase 3 Review Phase 4 Terraform Prep Phase 5 Deploy Phase 6 HA Config Phase 7 Verify
Guide Approach

This guide follows a management-first approach. All licensing, device groups, templates or folders, and security policy are configured on your management platform (Panorama or Strata Cloud Manager) before any AWS infrastructure is built. Firewalls bootstrap into a fully configured management plane on first boot, then form the HA pair.

Design model: Active/Passive HA pair across two Availability Zones in a dedicated Security VPC. Five interfaces per firewall: management, untrust (public), trust (private), HA1 (heartbeat), and HA2 (session sync). On failover, PAN-OS uses the firewall's IAM instance profile to move the floating EIP and update the trust-side route table.

Deployment method: All AWS infrastructure is deployed with Terraform using the PaloAltoNetworks SWFW Modules (v2.2, sourced from the Terraform Registry). The Terraform configuration for this guide is included below in Phase 4.

Alternative: VM-Series with GWLB (no HA pair required)

If you need horizontal scale rather than a paired standby, see the VM-Series Combined Deployment guide. That guide deploys VM-Series behind a Gateway Load Balancer, which provides inherent redundancy across AZs without requiring Active/Passive HA configuration on the firewalls. Choose Active/Passive HA when you need stateful session failover, a deterministic active node, or a BYOL per-pair license. Choose GWLB when you need elastic scale, automatic instance replacement, or pay-as-you-go licensing.

Interface and HA Model

▶ Security VPC Subnet Layout

The Security VPC spans two Availability Zones. Each AZ contains four dedicated subnets, one per interface type. The management interface doubles as HA1, so no dedicated HA1 subnet is needed. The default CIDR values are set in variables.tf and can be overridden in terraform.tfvars.

Subnet AZ1 CIDR AZ2 CIDR Route Table Purpose
mgmt 10.0.0.0/24 10.0.1.0/24 Default route via IGW Out-of-band management (SSH, HTTPS). Admin access to firewall web UI and CLI.
untrust 10.0.10.0/24 10.0.11.0/24 Default route via IGW Internet-facing traffic. The floating EIP attaches to the active firewall's untrust ENI.
trust 10.0.20.0/24 10.0.21.0/24 No default route (updated by HA failover) Private-side traffic toward spoke VPCs or Transit Gateway. On failover, PAN-OS updates this route table to point to the newly-active firewall's trust ENI.
ha 10.0.40.0/24 10.0.41.0/24 VPC local only HA2 session sync (ethernet1/3). TCP 28778. Carries full session state so in-flight connections survive failover. HA1 heartbeat runs over the management interface — no dedicated HA1 subnet needed.
Why management as HA1?

Using the management interface for HA1 keeps the design within the 4-ENI limit of m5.xlarge (and most common instance types). A dedicated HA1 ENI would require a 5th interface slot, forcing an upgrade to m5.4xlarge or larger. The management plane is an ideal HA1 link: it is always up, always reachable between peers, and already has a dedicated security group and IGW route. The sg-ha security group allows all traffic within the VPC CIDR for the HA2 ENI.

▶ Per-Firewall Interface Assignments

Each firewall has four ENIs, exactly matching the 4-ENI limit of m5.xlarge. HA1 heartbeat runs over the management interface; no dedicated HA1 ENI is required. Values below are for FW1 (AZ1); FW2 uses AZ2 subnets and fw2_private_ips.

Linux eth PAN-OS Name device_index Subnet Static IP (FW1) source_dest_check Security Group Purpose
eth0 Management + HA1 0 mgmt-az1 DHCP true sg-mgmt Management plane and HA1 heartbeat/hello. EIP attached by Terraform. SSH (22), HTTPS (443). HA1 peer IP = other FW's management private IP.
eth1 ethernet1/1 1 untrust-az1 10.0.10.10 false sg-untrust Internet-facing. Floating EIP associated here on the active firewall.
eth2 ethernet1/2 2 trust-az1 10.0.20.10 false sg-trust Private-side. Trust route table next-hop is updated to this ENI on failover.
eth3 ethernet1/3 3 ha-az1 10.0.40.10 false sg-ha HA2 session sync. TCP 28778. Bulk session state sync so in-flight connections survive failover.
Important: source_dest_check on data-plane interfaces

AWS enables source_dest_check by default on all ENIs. This causes AWS to drop any packet whose source or destination IP does not match the ENI's assigned IP. For a firewall forwarding traffic on behalf of other hosts, this drops everything. The Terraform sets source_dest_check = false on ethernet1/1 through ethernet1/3. The management ENI (eth0) keeps it true because management traffic originates from the firewall itself.

▶ HA Failover Sequence

When the active firewall fails or is suspended, the following sequence executes automatically. Total elapsed time from detection to traffic restoration is typically 30 to 60 seconds.

  1. HA1 heartbeat loss detected. The passive firewall misses the configured number of hello packets on the HA1 link (TCP 28769). Default heartbeat interval is 2000 ms; default hello interval is 8000 ms.
  2. Election. The passive firewall declares itself active after the promotion hold timer expires (default 2000 ms). No external coordinator is involved.
  3. EIP failover via EC2 API. The newly-active firewall calls the EC2 API using credentials from its IAM instance profile:
    1. ec2:DisassociateAddress removes the floating EIP from the failed firewall's untrust ENI (eni-fw1-untrust).
    2. ec2:AssociateAddress attaches the floating EIP to its own untrust ENI (eni-fw2-untrust). Internet-bound traffic now arrives at FW2.
  4. Route table failover via EC2 API. The newly-active firewall calls ec2:ReplaceRoute on the trust route table, changing the next-hop for the configured CIDR to its own trust ENI (eni-fw2-trust). Spoke VPC traffic now reaches FW2.
  5. Session restoration. The HA2 link (TCP 28778) continuously synchronized session state from the active to the passive firewall. After promotion, FW2 already holds the session table. Established TCP sessions survive the failover with minimal packet loss.
IAM permissions are the prerequisite for steps 3 and 4

The Terraform creates an IAM instance profile with ec2:AssociateAddress, ec2:DisassociateAddress, and ec2:ReplaceRoute permissions. Without these, the EIP and route table will not update on failover and traffic will black-hole until corrected manually. Verify the profile is attached before completing Phase 6.

Phase 1: Prerequisites

▶ Step 1.1: AWS Account and IAM Permissions

The Terraform run requires an IAM principal with permissions to create all the resources in the deployment. The full permission set covers EC2, S3, IAM, KMS, and CloudWatch.

ServiceRequired Actions
EC2 ec2:* (VPC, subnet, route table, IGW, security group, ENI, instance, EIP, KMS alias describe)
S3 s3:CreateBucket, s3:PutObject, s3:GetObject, s3:ListBucket, s3:PutBucketVersioning, s3:PutBucketEncryption, s3:PutPublicAccessBlock, s3:PutBucketOwnershipControls, s3:DeleteBucket, s3:DeleteObject
IAM iam:CreateRole, iam:PutRolePolicy, iam:CreateInstanceProfile, iam:AddRoleToInstanceProfile, iam:PassRole, iam:GetRole, iam:GetRolePolicy, iam:DeleteRole, iam:DeleteRolePolicy, iam:DeleteInstanceProfile, iam:RemoveRoleFromInstanceProfile, iam:TagRole

In a lab environment, attaching the AdministratorAccess managed policy to the deploying IAM user or role is the fastest path. In production, scope the policy to the actions above.

Also verify that the target region supports m5.xlarge (the default instance type) and that the account has not hit the EC2 instance limit or EIP limit (default 5 EIPs per region; this deployment allocates 3).

Confirm an EC2 key pair exists in the target region:

aws ec2 describe-key-pairs --region us-east-1 --query 'KeyPairs[].KeyName'
Verification

The key pair name appears in the output. The AWS CLI returns successfully with your current credentials:

aws sts get-caller-identity

Output includes Account, UserId, and Arn with no error.

Phase 2: Management Platform Configuration

Choose your management path below. Complete all steps in your chosen path before proceeding to Phase 3. Both paths result in the same end state: firewalls that bootstrap into a configured management plane and accept security policy on first boot.

Which path should I pick?
  • Panorama: you have an existing Panorama deployment. Firewalls connect to Panorama via the panorama-server init-cfg parameter and receive a config push on first boot.
  • SCM: you use Strata Cloud Manager. Firewalls register via the VM-Series auto-registration PIN and connect to SCM on first boot.
▶ Step 2A.1: Create Device Group for HA Firewalls

A dedicated device group keeps the HA firewalls' security policy isolated from other deployments.

  1. In Panorama, navigate to Panorama > Device Groups.
  2. Click Add.
  3. Set Name to aws-ha-firewalls.
  4. Set Parent Device Group to Shared (or your existing hierarchy root).
  5. Click OK.
  6. Click Commit > Commit to Panorama.
Verification

The device group aws-ha-firewalls appears in the Panorama device group tree under Panorama > Device Groups.

▶ Step 2A.2: Create Template Stack for HA Firewalls

The template stack delivers interface, zone, and logging configuration to both firewalls. HA-specific settings (HA1/HA2 peer IPs, group ID) are configured per-firewall in Phase 6 because each peer has a unique HA1 IP that cannot be templated.

  1. Navigate to Panorama > Templates.
  2. Click Add to create a base template. Name it aws-ha-base. Click OK.
  3. Click Add Stack. Name the stack aws-ha-stack.
  4. In the stack, add aws-ha-base as a member template.
  5. Click OK.
  6. Click Commit > Commit to Panorama.
Verification

The stack aws-ha-stack appears under Panorama > Templates with aws-ha-base listed as a member.

▶ Step 2A.3: Generate VM Auth Key

The VM auth key allows firewalls to authenticate to Panorama during bootstrap. The key is placed in terraform.tfvars as the vm-auth-key bootstrap option.

  1. Navigate to Panorama > Device Deployment > VM-Series Auth Key.
  2. Click Generate.
  3. Copy the key string immediately. It is displayed only once.
  4. Note the expiration time. The default lifetime is 24 hours. If the firewall bootstraps after the key expires, it cannot authenticate to Panorama and requires a rebuild. Either time your deployment to finish within 24 hours of key generation, or set a longer expiry before generating.
Important: expiry timing

Generate the auth key immediately before running terraform apply, not at the start of Phase 2. A key generated now but used hours later in Phase 5 may expire in a busy environment.

Verification

The key string is saved. It starts with the characters LUFRPT or similar and is several hundred characters long.

Troubleshooting

▶ HA Pair Not Forming (HA1 Down)

The most common cause is the sg-ha security group not allowing traffic on TCP 28769 between the HA1 subnets. The Terraform creates sg-ha with an ingress rule allowing all traffic within the VPC CIDR, which covers TCP 28769. If the HA1 link shows Down, check in order:

  1. Security group rule present:
aws ec2 describe-security-groups \
  --filters "Name=group-name,Values=pan-ha-sg-ha" \
  --query 'SecurityGroups[0].IpPermissions'

The output must include a rule with IpProtocol: -1 (all traffic) or a rule specifically for TCP 28769.

  1. Group ID mismatch: confirm Group ID is 1 on both firewalls via Device > High Availability > General.
  2. Wrong peer HA1 IP: confirm that the Peer HA1 IP on FW1 matches the actual static private IP on FW2's HA1 ENI. Verify the ENI's private IP in the EC2 console or via:
aws ec2 describe-network-interfaces \
  --filters "Name=description,Values=HA2 session sync*" \
  --query 'NetworkInterfaces[*].{ID:NetworkInterfaceId,IP:PrivateIpAddress}'
  1. Ping test from the firewall CLI:
ping source <fw1-mgmt-private-ip> host <fw2-mgmt-private-ip>

Run this on FW1. If ping fails, the security group or routing is the issue. If ping succeeds but HA1 is still Down, the issue is in the HA configuration (port or IP mismatch).

▶ Floating EIP Not Moving on Failover

The EIP move requires ec2:AssociateAddress and ec2:DisassociateAddress in the instance profile. Check in order:

  1. Verify the IAM policy on the instance role:
aws iam get-role-policy \
  --role-name pan-ha-vmseries-role \
  --policy-name pan-ha-ha-failover

The output must include ec2:AssociateAddress and ec2:DisassociateAddress in the EIPFailover statement.

  1. EIP Allocation ID format: the field in PAN-OS AWS HA settings must be the allocation ID in the format eipalloc-..., not the public IP address. Verify via:
aws ec2 describe-addresses --query 'Addresses[*].{IP:PublicIp,ID:AllocationId}'
  1. ENI IDs not swapped: on FW1, the Active ENI ID must be FW1's untrust ENI and the Passive ENI ID must be FW2's. If these are reversed, the failover will try to disassociate from the wrong interface and fail silently.
  2. Check HA state on the firewall:
show high-availability all

Look for an AWS HA section in the output. If it shows errors related to the EC2 API call, the IAM permissions or ENI IDs are the issue.

▶ Route Table Not Updating on Failover

The route table update requires ec2:ReplaceRoute scoped to route tables in the account and region. Check in order:

  1. Verify ec2:ReplaceRoute is in the IAM policy:
aws iam get-role-policy \
  --role-name pan-ha-vmseries-role \
  --policy-name pan-ha-ha-failover

The RouteTableFailover statement must include ec2:ReplaceRoute.

  1. Verify the route table ID: confirm the Route Table ID in PAN-OS AWS HA settings matches the trust route table created by Terraform:
aws ec2 describe-route-tables \
  --filters "Name=tag:Name,Values=pan-ha-rt-trust" \
  --query 'RouteTables[0].RouteTableId'
  1. Check what routes are currently in the table:
aws ec2 describe-route-tables \
  --route-table-ids rtb-0abc1234def56789 \
  --query 'RouteTables[0].Routes'

After a failover, the NetworkInterfaceId next-hop should match the newly-active firewall's trust ENI ID.

▶ Bootstrap Failed: Firewall Not Connecting to Management Platform

Check in order:

  1. Verify S3 permissions: the firewall reads its bootstrap bucket at first boot. If the IAM instance profile is missing s3:GetObject on the bucket, or the bucket name in user_data does not match the actual bucket name, bootstrap will fail silently.
aws s3 ls s3://pan-ha-fw1-bootstrap-<suffix>/config/

Confirm init-cfg.txt appears in the output.

  1. Check the EC2 system log: in the EC2 console, select the instance, click Actions > Monitor and troubleshoot > Get system log. Search for bootstrap or Error strings.
  2. If Panorama-managed, check the auth key: if the auth key expired before the instance finished bootstrapping, the firewall connects to Panorama but cannot authenticate. Generate a new auth key and update the S3 init-cfg.txt object, then reboot the instance.
  3. Check Panorama reachability from the management subnet: the management subnet route table has a default route via the IGW. Confirm Panorama's IP or FQDN is reachable from the management subnet's IP space. If Panorama is on-premises, a VPN or Direct Connect attachment is required.
  4. Check bootstrap status from the firewall CLI (if the firewall is SSH-accessible):
show system bootstrap status

The output lists each bootstrap phase with a pass or fail status. The failing phase identifies where to focus the investigation.
