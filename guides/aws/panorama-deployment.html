Panorama Deployment on AWS

End-to-end guide: AWS account setup through a fully licensed, accessible Panorama management plane

Guide Approach

This guide deploys Panorama — the centralized management platform for Palo Alto Networks firewalls — as a standalone HA pair on AWS. Panorama must be operational before deploying VM-Series firewalls so that firewalls can bootstrap into a fully configured management plane on first boot.

Deployment method: All AWS infrastructure is deployed with Terraform using the official Palo Alto Networks SWFW Modules — Panorama Standalone example. These modules encode Palo Alto's reference architecture and handle VPC, subnets, security groups, IAM, EBS, and Panorama EC2 provisioning with tested, production-ready code.

Architecture Overview

Before deploying anything, study the target architecture. The Panorama standalone example deploys a dedicated management VPC with two Panorama instances across two availability zones for high availability.

▶ Topology

The deployment creates the following infrastructure:

  • VPC — a dedicated management VPC (10.255.0.0/16) with an Internet Gateway for Panorama management access
  • Subnets — two management subnets across two availability zones (10.255.0.0/24 in AZ-A, 10.255.1.0/24 in AZ-B)
  • Panorama instances — two c5.4xlarge EC2 instances with static private IPs (10.255.0.4 and 10.255.1.4) and Elastic IPs for public access
  • EBS volumes — two 2 TB encrypted gp3 volumes per instance for log storage (/dev/sdb and /dev/sdc)
  • IAM role — EC2 instance profile with read-only access to CloudWatch metrics and EC2 instance status
  • Security group — allows inbound SSH (22), HTTPS (443), and all outbound traffic
HA pair vs. single instance

The example deploys two instances by default — a primary and secondary — for an HA pair. To deploy a single Panorama, remove the secondary block from the panoramas variable in terraform.tfvars.

Optional: NAT Gateway for private Panorama

If Panorama should not have a public IP, the example includes commented-out NAT Gateway configuration. Uncomment the NAT GW sections in terraform.tfvars and set create_public_ip = false. This routes Panorama's outbound traffic (licensing, content updates) through a NAT Gateway while keeping the management interface private. Inbound access then requires a VPN or Direct Connect connection to the management VPC.

▶ Network & Security Design

The security group controls access to the Panorama management interface. The default configuration exposes three services:

RuleDirectionPortProtocolSource/Dest
SSHIngress22TCPYour admin IP
HTTPSIngress443TCPYour admin IP
All outboundEgress0-65535All0.0.0.0/0
Important: Add port 3978 for managed firewalls

If VM-Series firewalls in other VPCs will connect to this Panorama over the network (via TGW, VPC peering, or VPN), add an ingress rule for TCP 3978 (Panorama device management). The source CIDR should be the firewall management subnet CIDRs. Without this rule, firewalls cannot register with Panorama.

IAM role capabilities

The IAM role grants Panorama read-only access to ec2:DescribeInstances, ec2:DescribeInstanceStatus, and CloudWatch metrics. This enables the AWS plugin on Panorama to discover and monitor VM-Series instances. No write permissions are granted.

Phase 1: Prerequisites

Complete these one-time setup tasks before deploying Panorama infrastructure. If you have already completed them for a VM-Series deployment, skip to Phase 2.

▶ Step 1.1: Verify AWS Account & Permissions

Terraform requires IAM permissions to create VPCs, subnets, security groups, EC2 instances, EBS volumes, IAM roles, and Elastic IPs. Two options:

Option A: IAM Role (Preferred)

Attach an IAM role with Administrator permissions to the EC2 instance or CloudShell session running Terraform. No access keys to manage.

Option B: IAM Programmatic User

  1. Create an IAM user with programmatic access.
  2. Attach the AdministratorAccess policy (scope can be reduced after a successful deployment).
  3. Copy the Access Key ID and Secret Access Key and store them securely.
  4. Configure credentials:
# Environment variables
export AWS_ACCESS_KEY_ID="AKIA..."
export AWS_SECRET_ACCESS_KEY="..."
export AWS_DEFAULT_REGION="us-east-2"

# Or configure via AWS CLI
aws configure
Important

The initial deployment requires Administrator or equivalent privileges due to the range of resources created (VPCs, EC2, IAM roles/policies, EBS, EIPs). Scope can be reduced post-deployment.

Verification

Confirm your AWS identity is correct:

aws sts get-caller-identity

The output should show your expected account ID and IAM principal.

▶ Step 1.4: Create or Identify SSH Key Pair

SSH access is the only way to reach Panorama before the web UI password is set. The key pair must exist in the target AWS region before Terraform runs.

Option A: Create a new key pair

aws ec2 create-key-pair \
  --key-name panorama-key \
  --key-type ed25519 \
  --query 'KeyMaterial' \
  --output text \
  --region us-east-2 > ~/.ssh/panorama-key.pem

chmod 400 ~/.ssh/panorama-key.pem

Option B: Use an existing key pair

List existing key pairs in the target region:

aws ec2 describe-key-pairs \
  --query 'KeyPairs[*].KeyName' \
  --output table \
  --region us-east-2
Important

Record the exact key pair name — it must match the ssh_key_name value in terraform.tfvars. Key pair names are case-sensitive and region-specific.

Verification

Confirm the key pair exists in the target region:

aws ec2 describe-key-pairs \
  --key-names panorama-key \
  --region us-east-2

The command should return the key pair details without error.

▶ Step 2.3: Configure Region & Tags

Set the AWS region and global tags applied to every provisioned resource.

  1. Open terraform.tfvars in your editor.
  2. Set region to your target AWS region (e.g., us-east-2).
  3. Set name_prefix to a short identifier for your environment (e.g., prod- or lab-). This prefix is prepended to all resource names.
  4. Update global_tags with your organization's tagging standard:
region      = "us-east-2"

global_tags = {
  ManagedBy   = "terraform"
  Application = "Palo Alto Networks Panorama"
  Owner       = "Network Security Team"
}
Verification

The region value matches the region where your SSH key pair exists and the Marketplace subscription is accepted.

▶ Step 2.4: Configure VPC & Security Groups

The vpcs variable defines the management VPC, subnets, security groups, and routing. The critical edit is restricting the security group ingress rules to your admin IP address.

  1. Locate the vpcs block in terraform.tfvars.
  2. Update the VPC name if desired (default: management-vpc).
  3. Update the CIDR if 10.255.0.0/16 conflicts with your network.
  4. Replace 1.1.1.1/32 in the https and ssh security group rules with your actual admin IP or CIDR range.
  5. Update the subnet availability zones to match your target region (e.g., us-east-2a and us-east-2b).
vpcs = {
  management_vpc = {
    name = "management-vpc"
    cidr = "10.255.0.0/16"
    security_groups = {
      panorama_mgmt = {
        name = "panorama_mgmt"
        rules = {
          all_outbound = {
            description = "Permit All traffic outbound"
            type        = "egress", from_port = "0", to_port = "0", protocol = "-1"
            cidr_blocks = ["0.0.0.0/0"]
          }
          https = {
            description = "Permit HTTPS"
            type        = "ingress", from_port = "443", to_port = "443", protocol = "tcp"
            cidr_blocks = ["203.0.113.10/32"] # Replace with your admin IP
          }
          ssh = {
            description = "Permit SSH"
            type        = "ingress", from_port = "22", to_port = "22", protocol = "tcp"
            cidr_blocks = ["203.0.113.10/32"] # Replace with your admin IP
          }
        }
      }
    }
    subnets = {
      "10.255.0.0/24" = { az = "us-east-2a", subnet_group = "mgmt" }
      "10.255.1.0/24" = { az = "us-east-2b", subnet_group = "mgmt" }
    }
    routes = {
      mgmt_default = {
        vpc           = "management_vpc"
        subnet_group  = "mgmt"
        to_cidr       = "0.0.0.0/0"
        next_hop_key  = "management_vpc"
        next_hop_type = "internet_gateway"
      }
    }
  }
}
Replace placeholder IPs

The example file uses 1.1.1.1/32 as a placeholder. Deploying with this value will lock you out of SSH and HTTPS access. Replace it with your actual public IP. Find your current IP with curl -s ifconfig.me.

Important: Add port 3978 for VM-Series management

If VM-Series firewalls will connect to this Panorama from other VPCs, add a security group rule for TCP port 3978 with the source set to the firewall management subnet CIDRs. Add this rule inside the panorama_mgmt security group rules block:

          device_mgmt = {
            description = "Permit Panorama device management"
            type        = "ingress", from_port = "3978", to_port = "3978", protocol = "tcp"
            cidr_blocks = ["10.51.0.0/22"] # Replace with your firewall mgmt CIDR
          }
Verification

The security group rules reference your actual admin IP (not 1.1.1.1/32), and the subnet AZs match your target region.

▶ Step 2.5: Configure Panorama Instances

The panoramas variable defines instance placement, PAN-OS version, EBS storage, and IAM configuration.

  1. Update the az values to match your region (e.g., us-east-2a and us-east-2b).
  2. Update panos_version to the desired Panorama version. Recommended: 11.1.4-h7 or 11.2.x.
  3. Adjust private_ip_address values if the VPC CIDR was changed.
  4. Adjust EBS volume sizes if needed (default: 2000 GB / 2 TB per volume, two volumes per instance).
panoramas = {
  panorama_ha_pair = {
    instances = {
      "primary" = {
        az                 = "us-east-2a"
        private_ip_address = "10.255.0.4"
      }
      "secondary" = {
        az                 = "us-east-2b"
        private_ip_address = "10.255.1.4"
      }
    }

    panos_version = "11.1.4-h7"

    network = {
      vpc              = "management_vpc"
      subnet_group     = "mgmt"
      security_group   = "panorama_mgmt"
      create_public_ip = true
    }

    ebs = {
      volumes = [
        {
          name            = "ebs-1"
          ebs_device_name = "/dev/sdb"
          ebs_size        = "2000"
        },
        {
          name            = "ebs-2"
          ebs_device_name = "/dev/sdc"
          ebs_size        = "2000"
        }
      ]
      encrypted = true
    }

    iam = {
      create_role = true
      role_name   = "panorama"
    }
  }
}
ParameterDefaultDescription
instance_typec5.4xlarge16 vCPU, 32 GB RAM. Required minimum for production Panorama.
panos_version11.1.4-h7PAN-OS version for the Panorama AMI. Must match an available AMI in the region.
ebs_size2000Size in GB per EBS volume. Two volumes = 4 TB total log storage per instance.
ebs_volume_typegp3GP3 provides baseline 3,000 IOPS and 125 MB/s throughput.
encryptedtrueEBS encryption using the default aws/ebs KMS key.
create_public_iptrueAllocates an Elastic IP. Set to false with NAT Gateway for private Panorama.
enable_imdsv2falseInstance Metadata Service v2. Set to true for stricter metadata access control.
Single Panorama (no HA)

To deploy a single instance, remove the entire "secondary" block from the instances map. Only the "primary" block is required.

Verification

The AZ values match your region, the private IPs fall within the VPC CIDR, and the PAN-OS version is current.

▶ Step 2.7: Optional — Enable NAT Gateway

If Panorama should not have a public IP (e.g., accessed via VPN or Direct Connect only), enable the NAT Gateway for outbound internet access (licensing, content updates, support telemetry).

  1. In the vpcs block, uncomment the two NAT Gateway subnets: 
          "10.255.2.0/24" = { az = "us-east-2a", subnet_group = "natgw" }
      "10.255.3.0/24" = { az = "us-east-2b", subnet_group = "natgw" }
  2. Replace the existing routes block with the NAT Gateway routes (commented section in the file). The NAT GW routes send management subnet traffic through the NAT Gateway instead of directly to the IGW.
  3. Uncomment the natgws variable block at the bottom of the file: 
    natgws = {
  mgmt_natgw = {
    vpc          = "management_vpc"
    subnet_group = "natgw"
  }
}
  4. In the panoramas block, set create_public_ip = false.
Important

With create_public_ip = false, the only access to Panorama is through a private network path (VPN, Direct Connect, peered VPC). Confirm your private connectivity is in place before deploying.

Verification

If using NAT Gateway: the natgws block is uncommented, NAT GW subnets are uncommented, and create_public_ip is false. If using public IP (default): all NAT GW sections remain commented and create_public_ip is true.

Review the output. For a standard HA pair deployment, expect approximately:

  • 1 VPC with Internet Gateway
  • 2 subnets (one per AZ)
  • 1 security group with ingress/egress rules
  • 2 EC2 instances (c5.4xlarge)
  • 4 EBS volumes (2 per instance)
  • 2 Elastic IPs
  • 2 IAM instance profiles with roles and policies
  • 2 route tables with routes
Verification

The plan completes without errors and shows the expected number of resources to create. No resources should show destroy on the initial deployment.

▶ Step 3.2: Apply the Configuration

Deploy the infrastructure. Terraform will prompt for confirmation before making changes.

terraform apply -var-file=terraform.tfvars

Type yes when prompted. The deployment takes approximately 5 minutes.

Note

The Terraform apply completing does not mean Panorama is ready. The EC2 instances are launched, but Panorama's internal bootstrap process takes an additional 5–10 minutes after the instance reaches running state.

Verification

Terraform completes with Apply complete! and displays the output values (public IPs, private IPs, URLs).

▶ Step 3.4: Verify AWS Console Resources

Confirm the deployed resources in the AWS Console.

  1. Open EC2 > Instances. Verify both Panorama instances show running state and have the expected instance type (c5.4xlarge).
  2. Open EC2 > Volumes. Verify four EBS volumes (two per instance) show in-use state, type gp3, and size 2000 GiB.
  3. Open VPC > Your VPCs. Verify the management VPC exists with the correct CIDR.
  4. Open VPC > Security Groups. Verify the panorama_mgmt security group has the correct inbound rules (SSH 22, HTTPS 443 from your admin IP).
Verification

Both EC2 instances are in running state, all four EBS volumes are in-use, and the VPC/security group configuration matches the terraform.tfvars values.

Phase 4: Post-Deployment Setup

Panorama's internal bootstrap takes several minutes after the EC2 instance reaches running state. Complete the initial access setup once bootstrap finishes.

▶ Step 4.1: Wait for Panorama Bootstrap

Panorama takes 5–10 minutes to complete its internal boot process after the EC2 instance shows running in the AWS Console. During this time, SSH and HTTPS connections will be refused.

Check bootstrap progress by polling SSH availability:

# Replace with your primary Panorama public IP
PANORAMA_IP="3.14.xxx.xxx"

# Poll until SSH responds (Ctrl+C to stop)
until ssh -o ConnectTimeout=5 -o StrictHostKeyChecking=no \
  -i ~/.ssh/panorama-key.pem admin@${PANORAMA_IP} \
  echo "SSH ready" 2>/dev/null; do
  echo "Waiting for Panorama bootstrap..."
  sleep 30
done
Alternative: AWS Console serial log

Check bootstrap progress via EC2 > Instances > select instance > Actions > Monitor and troubleshoot > Get system log. Look for PAN-OS is ready or login: prompt in the output.

Verification

SSH connects successfully and presents the PAN-OS CLI prompt (admin@Panorama>).

▶ Step 4.2: Set the Admin Password

Panorama ships with no admin password on first boot. The web UI is inaccessible until a password is set via SSH. This is a security gate — no one can access the web UI until you explicitly set credentials.

  1. SSH into the primary Panorama instance: 
    ssh -i ~/.ssh/panorama-key.pem admin@3.14.xxx.xxx
  2. Enter configuration mode: 
    configure
  3. Set the admin password: 
    set mgt-config users admin password

    Enter the new password twice when prompted. Use a strong password that meets your organization's policy.

  4. Commit the change: 
    commit
  5. Exit the SSH session: 
    exit
exit
Important: Break-glass account

The admin account is the break-glass account for Panorama. Store the password in a secure vault. After initial setup, create named admin accounts for daily operations and reserve admin for emergency access only. Be aware that multiple failed login attempts will lock the account.

Repeat for secondary

If deploying an HA pair, repeat this step on the secondary Panorama instance using its public IP.

Verification

The commit command completes without errors: Commit job completed.

▶ Step 4.3: Access the Web UI

Open the Panorama web interface in a browser using the URL from the Terraform output.

  1. Navigate to https://<PRIMARY_PUBLIC_IP> (e.g., https://3.14.xxx.xxx).
  2. Accept the self-signed certificate warning.
  3. Log in with username admin and the password set in the previous step.
Note

The browser will show a certificate warning because Panorama uses a self-signed certificate by default. This is expected and safe for initial access. Replace the certificate with a CA-signed certificate after completing the initial setup.

Verification

The Panorama dashboard loads and shows the system status panel with hostname, serial number, and PAN-OS version.

▶ Step 4.4: Activate the License

Panorama must be licensed before it can manage firewalls or receive content updates.

  1. In the Panorama web UI, navigate to Panorama > Licenses.
  2. Click Activate feature using auth code.
  3. Enter the Panorama auth code obtained from the Customer Support Portal in Step 1.3.
  4. Click OK. Panorama will contact the licensing server and activate the license.
Internet connectivity required

License activation requires outbound HTTPS connectivity to updates.paloaltonetworks.com. If Panorama is behind a NAT Gateway or firewall, confirm outbound port 443 is permitted. See Troubleshooting if activation fails.

Repeat for secondary

If deploying an HA pair, repeat the license activation on the secondary Panorama using its own auth code.

Verification

The Panorama > Licenses page shows active licenses with valid expiration dates. The Device Management license indicates the maximum number of managed devices.

Cleanup

▶ Destroy All Resources

To remove all resources created by this deployment, run the destroy command from the same directory where the deployment was executed.

Data loss warning

Running terraform destroy will permanently delete both Panorama instances, all EBS volumes (including all stored logs and configuration), the VPC, subnets, security groups, IAM roles, and Elastic IPs. This action cannot be undone.

If you need to preserve Panorama's configuration, export it first: Panorama > Setup > Operations > Export Panorama and devices running config bundle.

terraform destroy -var-file=terraform.tfvars

Type yes when prompted. The destroy operation takes approximately 3–5 minutes.

Verification

Terraform completes with Destroy complete! and reports the number of resources destroyed. Verify in the AWS Console that the VPC, EC2 instances, and EBS volumes are no longer present.
