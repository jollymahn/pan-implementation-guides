Portkey AI Gateway Deployment

Deploy the Portkey AI Gateway (self-hosted on AWS, Azure, GCP, or locally, or as a fully managed Portkey instance), route to cloud-native and public LLM providers, and enforce a Prisma AIRS guardrail on every prompt and response

Guide Approach

This guide deploys the Portkey AI Gateway and secures it with Prisma AIRS. You pick how the gateway runs once (self-hosted on AWS, Azure, GCP, or your local machine, or a fully managed Portkey instance), and the guide tailors every deploy and request command to that choice. The selector is sticky: choose it in any section and the whole page follows.

Design model: Prisma AIRS runs as an inline guardrail inside the gateway's request/response pipeline. Every prompt and model response routed through the gateway is scanned by AIRS before it reaches the model provider or returns to the application.

Deployment method: Configuration-driven. AIRS is managed through Strata Cloud Manager (SCM). On a self-hosted gateway the guardrail is passed inline via the x-portkey-config header on each request; on a fully managed instance it is attached to a dashboard Config and referenced by ID. Either way, no infrastructure-as-code is required for the integration itself.

Architecture Overview

The Portkey AI Gateway sits between an application and its LLM providers, adding observability, routing, caching, and guardrails. Prisma AIRS plugs in as a guardrail that scans traffic at two points: before a prompt reaches the model (input) and before a response reaches the caller (output).

▶ The guardrail-in-pipeline design

Prisma AIRS runs as an inline guardrail inside the gateway request pipeline. Two scan points enforce policy:

  • Input scan evaluates the prompt before it reaches the model provider. A violation blocks the request before any tokens are spent.
  • Output scan evaluates the model response before it returns to the application, catching unsafe content the model may produce.

▶ Request flow, end to end

A single request travels through the pipeline in this order:

  1. The application sends a chat completion request to the gateway with the AIRS guardrail config attached via the x-portkey-config header.
  2. The gateway runs the input_guardrails. The AIRS guardrail calls the AIRS Scan API to evaluate the prompt.
  3. If AIRS returns a block verdict and deny is true, the gateway returns a 400 error and the request never reaches the model provider.
  4. If the prompt is allowed, the gateway forwards the request to the configured LLM provider and receives a completion.
  5. The gateway runs the output_guardrails. The AIRS guardrail scans the model response.
  6. If the response is allowed, the gateway returns it to the application. If blocked, the caller receives an error instead.

Happy Path: Both Scans Allow

When the prompt and response are both clean, the request flows through all five stages:

Input Block: Malicious Prompt Stopped

When AIRS detects a prompt injection or malicious content, the request is stopped before the LLM is ever contacted, so zero tokens are consumed and there is zero risk of data exfiltration:

▶ One gateway, five ways to run it, many providers

How you run the gateway and which LLM it routes to are independent choices:

  • How it runs — self-hosted as a container on AWS (EC2 or EKS), Azure (Container Instances or AKS), GCP (Cloud Run or GKE), or your local machine; or fully managed by Portkey. The platform selector covers all five.
  • What it routes to — a cloud-native model service (AWS Bedrock, Azure OpenAI, Google Vertex AI) or a public API (OpenAI, Anthropic, and others). Routing is controlled entirely by request headers, so one gateway can front many providers at once.

The AIRS guardrail does the same job in every case. On a self-hosted gateway it is passed inline as JSON in the x-portkey-config header; on a fully managed instance it is attached to a dashboard Config and referenced by ID. Either way, no gateway-side plugin rebuild is needed to turn scanning on.

Choose Your Platform

Pick where the gateway will run. Your choice is remembered and applied to every command on this page: the deploy steps, the provider credentials, and the test requests all switch to match. You can change it at any tab bar below; the rest of the page follows.

Which platform should I pick?
  • AWS — host on EC2 or ECS, route to Amazon Bedrock (or a public API).
  • Azure — host on Container Instances or AKS, route to Azure OpenAI (or a public API).
  • GCP — host on Cloud Run or GKE, route to Google Vertex AI (or a public API).
  • Local Hosted — run on your own machine for development, route to any public API (OpenAI, Anthropic) or a local model server.
  • Fully Managed (SaaS) — no self-hosting; use Portkey's managed gateway at api.portkey.ai with the account, providers, and AIRS guardrail configured in the dashboard.

AWS path selected. You will run the gateway container on AWS (EC2 for a quick start, ECS for production) and route requests to Amazon Bedrock using AWS access-key headers. A public-API option is included as well.

Azure path selected. You will run the gateway container on Azure (Container Instances for a quick start, AKS for production) and route requests to Azure OpenAI using the Azure resource and deployment headers. A public-API option is included as well.

GCP path selected. You will run the gateway on GCP (Cloud Run for a quick start, GKE for production) and route requests to Google Vertex AI using the Vertex project, region, and an OAuth access token. A public-API option is included as well.

Local path selected. You will run the gateway on your own machine with npx or Docker and route requests to a public API such as OpenAI, or to a local model server. Ideal for development and trying the AIRS guardrail end to end.

Fully Managed (SaaS) selected. No infrastructure to run. You call Portkey's managed gateway at https://api.portkey.ai. You stand the instance up in the dashboard (account, API key, provider, and AIRS guardrail Config); each request carries your Portkey API key and the Config ID.

Phase 1: Prerequisites

Gather these before starting. Missing any one will block a later phase. The first two steps are the same for every platform; the third switches to match your selected platform.

▶ Step 1.1: Confirm Prisma AIRS license and security profile

The AIRS guardrail in this guide works by sending every prompt and response to the Prisma AIRS Scan API, a Palo Alto Networks cloud service (the AIRS "API intercept" pillar) that inspects the text and returns an allow or block verdict. Before the gateway can call that API you need three things:

  • An active Prisma AIRS AI Runtime: API license, funded by Software NGFW credits (Parts A–B below).
  • An AI security profile name — the named set of detections (prompt-injection, data-leak, etc.) the Scan API applies (Parts C–D below).
  • An AIRS API key — created in Step 1.2.

This step walks the entire setup from a brand-new account. If your organization has already activated AIRS API intercept and stood up its Strata Cloud Manager tenant, skip straight to Part D (record the profile name).

Two different consoles: do not mix them up
  • Customer Support Portal (CSP) — support.paloaltonetworks.com. This is where you provision and license: credit pools and deployment profiles live here.
  • Strata Cloud Manager (SCM) — the application where you manage AIRS components (AI security profiles, API keys, scan logs). You do not browse to it directly; you open it from the Hub by selecting the tenant that your deployment profile provisioned.

Part A: Activate the license and fund Software NGFW credits

Prisma AIRS is bring-your-own-license (BYOL), paid for with Software NGFW credits (a prepaid pool of credits attached to your support account). For the API pillar, usage is metered in monthly tokens (billions), where one token is roughly four characters.

  1. Open the activation link in your purchase confirmation email.
  2. Log in to the Customer Support Portal with your Palo Alto Networks credentials (create an account first if you do not have one).
  3. Follow the prompts to associate the Prisma AIRS AI Runtime: API subscription and its Software NGFW credits with your Customer Support account.

Part B: Create the API deployment profile

A deployment profile is your AIRS license allocation. Creating it is also what stands up your management tenant: activating an API deployment profile tells the Hub to provision a Strata Cloud Manager instance with the Prisma AIRS API feature enabled.

  1. In the Customer Support Portal, go to Products → Software/Cloud NGFW Credits.
  2. Locate the appropriate credit pool and click Create Deployment Profile.
  3. Select product AI Runtime Security (API). (The AI Security package and "Use Credits to Enable" are selected by default.)
  4. Give the profile a name (for example, AIRS-API-Production) and set the estimated Monthly Tokens (Billions) (minimum 1), then click Create Deployment Profile.
  5. When the details load, click Finish Setup next to the profile you just created and complete the activation.
AIRS needs its own tenant

As a current limitation, Prisma AIRS API must live on a dedicated Strata Cloud Manager tenant. When you finish setup, let it provision a new tenant for AIRS rather than attaching it to an existing SCM tenant. The initial provisioning can take a little time to complete.

Part C: Open Strata Cloud Manager for your AIRS tenant

  1. Log in to the Hub.
  2. Select the tenant that the deployment profile in Part B provisioned (the dedicated AIRS tenant), then open its Strata Cloud Manager instance.
Supporting services are automatic

Activating the API deployment enables Strata Cloud Manager Pro, Enterprise DLP, Strata Logging Service (where scan results are stored), and ADEM for you. There is nothing extra to activate; they are registered automatically.

Part D: Create and record the AI security profile name

The AI security profile is the named bundle of detections the Scan API enforces. Its name is passed in every scan request as profile_name, so you must record it exactly, including capitalization.

  1. Use the Strata Cloud Manager instance for your AIRS tenant (the one you opened in Part C).
  2. First-time only — onboard the API application: navigate to AI Security → AI Runtime → API Applications and follow the onboarding wizard to connect the deployment profile you created in Part B.
  3. Open the security-profile manager: from AI Security → API Applications, click Manage in the top-right corner and select Security Profiles.
  4. Click Create Security Profile, enter a Security Profile Name (for example, production-api-scan), and set each protection to Allow or Block (Prompt Injection, Sensitive Data / DLP, Malicious URLs, and so on). Click to save.
  5. Copy the exact, case-sensitive Security Profile Name. You will paste it into the guardrail config in Phase 3.
Want the long-form walkthrough?

The companion AIRS API Intercept guide covers this same activation (license, deployment profile, security profile, API key) in even greater depth, including cloud-account discovery. This page inlines everything you need for the gateway, so you do not have to leave it.

Verification

The Customer Support Portal shows an active AIRS credit pool and an Active deployment profile, and you have copied the exact case-sensitive AI security profile name. With the API key from Step 1.2, you will have everything the guardrail needs.

▶ Step 1.2: Generate the AIRS deployment profile API key

The gateway authenticates to the AIRS Scan API with an API key. You generate that key in Strata Cloud Manager by onboarding an API application against the deployment profile you created in Step 1.1 (Part B). Follow every click below.

  1. Open Strata Cloud Manager for your AIRS tenant (via the Hub, as in Step 1.1 Part C).
  2. Navigate to AI Security → AI Runtime → API Applications.
  3. Click Manage Applications, select the deployment profile whose type is Prisma AIRS AI Runtime API (the one from Step 1.1), then click Next.
  4. Onboard API Account — fill in the form (an "application" is just a named entry that owns the key):
    • Application Name (required) — e.g. portkey-gateway.
    • Cloud Provider (required) — where your gateway runs.
    • Environment (required) — e.g. Production.
    • AI Agent Framework (optional) — leave as Not Applicable for the gateway.
    • Deployment Profile (required) — select the same profile.
    • Toggle Linked on to auto-associate the security profile you created in Step 1.1 (Part D).
    Then click Next.
  5. Input API Details — enter an API Key Name, choose a Rotation period (how often the key auto-refreshes), then click Generate API Key.
  6. Implement API — click to copy the API key token and paste it somewhere safe immediately, then click Done.
  7. Export the key in the shell you will run the test requests from (and store a copy in a secret manager such as AWS Secrets Manager, Azure Key Vault, or GCP Secret Manager). Phase 3 reuses this exact variable name: 
    export MY_AIRS_API_KEY="YOUR_AIRS_API_KEY"
The key is shown only once

Strata Cloud Manager displays the API key token a single time. If you lose it before copying, return to AI Security → API Applications → Manage → API Keys and Regenerate the key (the old token stops working). Never hardcode the key or commit it to version control.

Scan API endpoint

This key authenticates to the Scan API at https://service.api.aisecurity.paloaltonetworks.com. That is the US production base URL; if your deployment profile is in another region, you match the key to that region's endpoint in the table in Phase 3.

Important: API keys are region-locked

An AIRS API key generated in one region works only with that region's Scan API endpoint. Note the region the key was issued in; you will match it to an endpoint in Phase 3.

Verification

The AIRS API Key is generated and stored. Both the API key and the security profile name from Step 1.1 are now in hand.

▶ Step 1.3: Confirm LLM provider credentials

The gateway needs credentials for the upstream LLM provider it routes requests to. The credentials below match your selected platform. You pass them as request headers in Phase 4; gather and export them now.

Amazon Bedrock is AWS's hosted-LLM service. The gateway calls it using an IAM access key, a pair of strings (an access key ID and a secret) that identify an AWS identity and grant it permissions. Here is how to create one and turn on the model:

  1. Sign in to the AWS IAM console. Create (or pick) an IAM user and attach a policy that allows Bedrock. The quickest is the AWS-managed policy AmazonBedrockFullAccess; for first-time model enablement also allow aws-marketplace:Subscribe, aws-marketplace:Unsubscribe, and aws-marketplace:ViewSubscriptions.
  2. Create the access key: IAM → Users → your user → Security credentials → Create access key. Choose "Application running outside AWS", create it, and copy both the Access key ID and the Secret access key (the secret is shown only once).
  3. Enable the model: open the Amazon Bedrock console, switch to your target Region (top-right), then Bedrock configurations → Model access → Modify model access, select the models you want (e.g. an Anthropic Claude model), click Next, submit any use-case details if prompted, and Submit. The model's status changes to Access granted.
  4. Confirm the model is available in the same Region you set as AWS_REGION below.
Model access is often already on

In commercial AWS Regions, foundation-model access is enabled by default once the IAM identity has the AWS Marketplace permissions above, and the first request auto-subscribes (this can take a few minutes). If Model access already shows Access granted, you are done and do not need to request it again.

export AWS_ACCESS_KEY_ID="YOUR_AWS_ACCESS_KEY_ID"
export AWS_SECRET_ACCESS_KEY="YOUR_AWS_SECRET_ACCESS_KEY"
export AWS_REGION="us-east-1"
# Optional, only for temporary STS credentials:
export AWS_SESSION_TOKEN="YOUR_AWS_SESSION_TOKEN"

The gateway maps these to the x-portkey-aws-access-key-id, x-portkey-aws-secret-access-key, x-portkey-aws-region, and x-portkey-aws-session-token headers.

Azure OpenAI serves OpenAI models from your own Azure subscription. You need a resource (the Azure object that hosts the service), a deployment (a named instance of a specific model inside that resource), and a key. Here is how to create all three:

  1. In the Azure Portal, click Create a resource, search Azure OpenAI, and click Create. On the Basics tab choose your Subscription, Resource group, Region, and a Name (this name becomes AZURE_RESOURCE), pick pricing tier Standard S0, then step through to Review + submit → Create, then Go to resource.
  2. Deploy a model: open Microsoft Foundry (ai.azure.com) for that resource, go to Deployments → + Deploy model → Deploy base model, choose a model, confirm, and set a Deployment name (this becomes AZURE_DEPLOYMENT). Click Deploy.
  3. Copy the credentials: back in the Azure Portal resource, open the Keys and Endpoint blade and copy KEY 1 (this becomes AZURE_OPENAI_API_KEY).
  4. AZURE_API_VERSION is the REST API version string (the example below, 2025-01-01-preview, is a valid value).
Resource name vs deployment name

These are different. The resource name identifies the Azure service; the deployment name identifies the specific model you deployed inside it. Requests always target the deployment name, not the underlying model name.

export AZURE_OPENAI_API_KEY="YOUR_AZURE_OPENAI_API_KEY"
export AZURE_RESOURCE="YOUR_AZURE_RESOURCE_NAME"
export AZURE_DEPLOYMENT="YOUR_AZURE_DEPLOYMENT_ID"
export AZURE_API_VERSION="2025-01-01-preview"

The gateway maps these to the Authorization, x-portkey-azure-resource-name, x-portkey-azure-deployment-id, and x-portkey-azure-api-version headers.

Vertex AI is Google Cloud's hosted-LLM service. Unlike a static key, Vertex authenticates with a short-lived OAuth access token that you mint from the gcloud CLI. You need a Google Cloud project with the Vertex API turned on and an identity holding the Vertex AI User role. Set it up like this:

  1. Install the Google Cloud CLI, then sign in and select your project: 
    gcloud auth login
gcloud config set project <YOUR_GCP_PROJECT_ID>
  2. Enable the Vertex AI API on the project: 
    gcloud services enable aiplatform.googleapis.com
  3. Grant your account (or a service account) the Vertex AI User role, roles/aiplatform.user. In the Console this is IAM & Admin → IAM → Grant access; the role lets the identity call Vertex models.
  4. The token in the export below is produced by gcloud auth print-access-token. For a service account instead of your user login, run gcloud auth activate-service-account --key-file=KEY.json first, then print the token.
export VERTEX_PROJECT_ID="YOUR_GCP_PROJECT_ID"
export VERTEX_REGION="us-central1"
# Short-lived OAuth token (refreshes roughly hourly):
export VERTEX_ACCESS_TOKEN="$(gcloud auth print-access-token)"

The gateway maps these to the Authorization (the access token), x-portkey-vertex-project-id, and x-portkey-vertex-region headers.

Token lifetime

A token from gcloud auth print-access-token is short-lived. Re-run the export before testing if requests start returning 401. For production, attach a service account to the gateway host or use Workload Identity instead of a manual token.

This path routes to any public LLM API. OpenAI is shown here; the same pattern works for other providers by changing x-portkey-provider and the key. To get an OpenAI key:

  1. Sign in at platform.openai.com.
  2. Open the API keys page (left nav → API keys).
  3. Click Create new secret key, give it a name, pick the project, and click Create.
  4. Copy the key now — it is shown only once — and paste it into the export below.
export OPENAI_API_KEY="YOUR_OPENAI_API_KEY"

The gateway maps this to the Authorization: Bearer header with x-portkey-provider: openai. To route to a self-hosted or local model server instead, see Phase 4's public-API panel, which uses x-portkey-custom-host.

A fully managed instance handles provider credentials differently: instead of exporting provider keys for request headers, you create the account, API key, and provider connection inside Portkey. Those steps live in Phase 2 (Fully Managed). From this prerequisites phase you only need the AIRS license, security profile, and API key from Steps 1.1 and 1.2.

What you will create in Phase 2
  • A Portkey account and workspace.
  • A Portkey API key (PORTKEY_API_KEY).
  • A Model Catalog provider slug (PORTKEY_PROVIDER, e.g. @openai-prod) that holds your LLM provider credentials.
Verification

Credentials for the selected platform's provider are exported in the shell. A later test request will confirm they work end to end.

Phase 2: Deploy the Gateway

Stand up the gateway for your selected platform. The four self-hosted options listen on port 8787 and expose /v1/chat/completions; the Fully Managed option runs no infrastructure but still stands up an instance in the dashboard. After deploying (or completing the Fully Managed setup), set GATEWAY_URL so the request commands in later phases point at it.

How to read the commands below

Anything in <ANGLE_BRACKETS> is a placeholder; replace it (including the brackets) with your own value. When the same placeholder appears more than once (for example <AWS_REGION> or <CLUSTER_NAME>), use the identical value everywhere so the cluster, storage bucket, and gateway all line up. Commands are run from your own machine with the matching cloud CLI installed and signed in.

Two ways to run on AWS. Pick one, you don't run both:

▶ Option A — Run on EC2 with Docker

The quickest path is the container image on an EC2 instance with Docker installed. On the instance:

sudo docker run -d --restart unless-stopped -p 8787:8787 portkeyai/gateway:latest

Open inbound TCP 8787 in the instance security group from the clients that will call the gateway. Portkey publishes an AWS EC2 CloudFormation template that provisions the instance, security group, and Docker run in one step. For production, use the ECS Terraform module with an Application Load Balancer.

Point the rest of the guide at the deployed gateway:

export GATEWAY_URL="http://YOUR_EC2_PUBLIC_DNS:8787"
Verification

curl -s "$GATEWAY_URL/v1/health" returns a healthy response, confirming the gateway is reachable on port 8787.

▶ Option B — Run on EKS with Helm

For a load-balanced production deployment on Kubernetes, deploy the enterprise gateway to EKS with Portkey's Helm chart, the same chart used for AKS and GKE. This tier connects to the Portkey control plane. The steps below build everything from zero: the cluster, the identity that lets it write logs, the log bucket, and finally the gateway.

Before you start you need an AWS account with billing enabled and permission to create EKS clusters, IAM roles, and S3 buckets; and your Portkey Organisation ID, Docker credentials, and Client Auth Key (request these from Portkey; they authenticate the enterprise image to the control plane).

1. Install the command-line tools and sign in. You need the AWS CLI v2, kubectl, Helm v3+, and eksctl. Then authenticate:

aws configure   # enter your access key, secret, and default region

2. Create the EKS cluster (this provisions the control plane and 2 worker nodes; it takes roughly 15–20 minutes), then enable its OIDC provider so Kubernetes service accounts can assume IAM roles:

eksctl create cluster --name <CLUSTER_NAME> --region <AWS_REGION> --nodes 2

eksctl utils associate-iam-oidc-provider --cluster=<CLUSTER_NAME> --approve

Verify: kubectl get nodes lists 2 nodes in Ready state (eksctl writes your kubeconfig automatically).

3. Create the S3 bucket that will hold request/response logs. For us-east-1, omit the --create-bucket-configuration line; every other region requires it:

aws s3api create-bucket --bucket <BUCKET_NAME> --region <AWS_REGION> \
  --create-bucket-configuration LocationConstraint=<AWS_REGION>

Verify: aws s3 ls | grep <BUCKET_NAME> shows the bucket.

4. Create an IAM-backed Kubernetes service account (IRSA) so the gateway pod can write to that bucket without static keys. Attach a policy that grants S3 access to the bucket (for a quick start you can attach arn:aws:iam::aws:policy/AmazonS3FullAccess and scope it down later). eksctl creates the IAM role and annotates the service account for you:

eksctl create iamserviceaccount --cluster=<CLUSTER_NAME> \
  --name=<SERVICE_ACCOUNT_NAME> --namespace=portkey \
  --attach-policy-arn=<S3_POLICY_ARN> --approve

Verify: kubectl get serviceaccount <SERVICE_ACCOUNT_NAME> -n portkey -o yaml shows an eks.amazonaws.com/role-arn annotation. Copy that role ARN; it goes into values.yaml below.

5. Add the Portkey Helm repository:

helm repo add portkey-ai https://portkey-ai.github.io/helm
helm repo update

6. Create values.yaml with the enterprise image, registry credentials, control-plane settings, built-in Redis, an S3 log store via IRSA, and a public Network Load Balancer service that maps port 80 to the gateway's 8787. Set serviceAccount.name to your <SERVICE_ACCOUNT_NAME>, the eks.amazonaws.com/role-arn annotation to the role ARN from step 4, and LOG_STORE_GENERATIONS_BUCKET to your <BUCKET_NAME>:

imageCredentials:
  - name: portkey-enterprise-registry-credentials
    create: true
    registry: https://index.docker.io/v1/
    username: <PROVIDED_BY_PORTKEY>
    password: <PROVIDED_BY_PORTKEY>

images:
  gatewayImage:
    repository: "docker.io/portkeyai/gateway_enterprise"
    tag: "latest"
  redisImage:
    repository: "docker.io/redis"
    tag: "7.2-alpine"

serviceAccount:
  create: true
  automount: true
  name: <SERVICE_ACCOUNT_NAME>
  annotations:
    eks.amazonaws.com/role-arn: <ROLE_ARN>

environment:
  create: true
  secret: true
  data:
    ANALYTICS_STORE: control_plane
    SERVICE_NAME: gateway
    PORTKEY_CLIENT_AUTH: <PROVIDED_BY_PORTKEY>
    ORGANISATIONS_TO_SYNC: <ORGANISATION_ID>
    PORT: "8787"
    CACHE_STORE: redis
    REDIS_URL: "redis://redis:6379"
    REDIS_TLS_ENABLED: "false"
    LOG_STORE: s3_assume
    LOG_STORE_REGION: <AWS_REGION>
    LOG_STORE_GENERATIONS_BUCKET: <BUCKET_NAME>

service:
  type: LoadBalancer
  port: 80
  containerPort: 8787
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
    service.beta.kubernetes.io/aws-load-balancer-internal: "false"
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: "ip"
    service.beta.kubernetes.io/aws-load-balancer-healthcheck-path: "/v1/health"

7. Install or upgrade the release:

helm upgrade --install portkey-ai portkey-ai/gateway -f ./values.yaml \
  -n portkey --create-namespace

8. Confirm the pods are running, then read the load balancer hostname and point the guide at it:

kubectl get pods -n portkey
kubectl get svc -n portkey
export GATEWAY_URL="http://<LOAD_BALANCER_HOSTNAME>"
Not on Kubernetes? Use ECS instead

If you would rather not run Kubernetes, Portkey also ships an ECS Terraform module (portkey-gateway-infrastructure//terraform/ecs) that provisions ECS, Redis, an S3 log store, and a load balancer from AWS Secrets Manager inputs, the non-Kubernetes equivalent of this Helm deployment.

This incurs ongoing charges, so tear it down when finished

The EKS cluster, its worker nodes, the Network Load Balancer, and the S3 bucket all bill continuously. When you are done testing, remove the cluster (this also deletes the node group and the IRSA role) and the bucket:

eksctl delete cluster --name <CLUSTER_NAME> --region <AWS_REGION>
aws s3 rb s3://<BUCKET_NAME> --force
Verification

All pods show Running, and curl -s "$GATEWAY_URL/v1/health" returns healthy from the load balancer. The deployment appears in the Portkey dashboard once it syncs with the control plane.

Two ways to run on Azure. Pick one, you don't run both:

▶ Option A — Run on Container Instances (ACI)

Azure Container Instances (ACI) runs the public image without managing a VM. Create the container and expose port 8787 with a public DNS label:

az container create \
  --resource-group YOUR_RESOURCE_GROUP \
  --name portkey-gateway \
  --image portkeyai/gateway:latest \
  --dns-name-label YOUR_UNIQUE_LABEL \
  --ports 8787

ACI assigns the FQDN YOUR_UNIQUE_LABEL.<region>.azurecontainer.io. For production, deploy the enterprise gateway on AKS with the Portkey Helm chart behind an ingress.

Point the rest of the guide at the deployed gateway:

export GATEWAY_URL="http://YOUR_UNIQUE_LABEL.YOUR_REGION.azurecontainer.io:8787"
Verification

curl -s "$GATEWAY_URL/v1/health" returns a healthy response from the ACI FQDN.

▶ Option B — Run on AKS with Helm

For production, deploy the enterprise gateway to AKS with Portkey's Helm chart behind a load balancer. The steps below build everything from zero: the resource group, the cluster, the log storage, and the identity the gateway uses to write logs.

Before you start you need an Azure subscription with permission to create AKS clusters, storage accounts, and Entra (Azure AD) app registrations; and your Portkey Organisation ID, Docker credentials, and Client Auth Key (request these from Portkey).

1. Install the Azure CLI, kubectl, and Helm v3+, then sign in:

az login

2. Create a resource group (a logical container for the cluster and storage):

az group create --name <RESOURCE_GROUP> --location <LOCATION>

3. Create the AKS cluster with 2 nodes (this takes several minutes), then download its credentials so kubectl targets it:

az aks create --resource-group <RESOURCE_GROUP> --name <CLUSTER_NAME> \
  --node-count 2 --generate-ssh-keys

az aks get-credentials --resource-group <RESOURCE_GROUP> --name <CLUSTER_NAME>

Verify: kubectl get nodes lists 2 nodes in Ready state.

  --account-name <STORAGE_ACCOUNT_NAME> --auth-mode login

  --role "Storage Blob Data Contributor" \
  --scope "/subscriptions/<SUBSCRIPTION_ID>/resourceGroups/<RESOURCE_GROUP>/providers/Microsoft.Storage/storageAccounts/<STORAGE_ACCOUNT_NAME>"

Verify: in the Azure Portal, the storage account's Access Control (IAM) blade lists your app with the Storage Blob Data Contributor role.

For production, deploy the enterprise gateway to GKE with Portkey's Helm chart, using Workload Identity for GCS log storage. Workload Identity lets a Kubernetes service account (KSA) act as a Google service account (GSA) without any static key files. The steps below build everything from zero.

Before you start you need a Google Cloud project with billing enabled and permission to create GKE clusters, service accounts, and buckets; and your Portkey Organisation ID, Docker credentials, and Client Auth Key (request these from Portkey).

1. Install the Google Cloud CLI, kubectl, and Helm v3+. Sign in and pin the names you will reuse to shell variables so the later commands line up:

gcloud auth login

export PROJECT_ID=<YOUR_GCP_PROJECT_ID>
export NAMESPACE=portkey
export GSA=portkey-logs        # Google service account name
export KSA=portkey-gateway     # Kubernetes service account name
gcloud config set project ${PROJECT_ID}

2. Enable the GKE API on the project:

gcloud services enable container.googleapis.com

3. Create the GKE cluster with Workload Identity turned on (the --workload-pool flag is what enables it), then fetch its credentials for kubectl:

gcloud container clusters create <CLUSTER_NAME> \
  --location <LOCATION> \
  --workload-pool=${PROJECT_ID}.svc.id.goog

gcloud container clusters get-credentials <CLUSTER_NAME> --location <LOCATION>

Verify: kubectl get nodes lists the cluster's nodes in Ready state.

4. Create the Google service account (GSA) the gateway will use to write logs:

gcloud iam service-accounts create ${GSA}

5. Create the GCS bucket for logs and grant the GSA read/write on it:

gcloud storage buckets create gs://<GCS_BUCKET_NAME> --location <GCS_BUCKET_REGION>

gcloud storage buckets add-iam-policy-binding gs://<GCS_BUCKET_NAME> \
  --member "serviceAccount:${GSA}@${PROJECT_ID}.iam.gserviceaccount.com" \
  --role roles/storage.objectAdmin

6. Create the Kubernetes namespace and service account that the gateway pod runs as (Helm can also create the KSA, but creating it now lets you bind it in the next step):

kubectl create namespace ${NAMESPACE}
kubectl create serviceaccount ${KSA} --namespace ${NAMESPACE}

7. Bind the Google service account (GSA) to the gateway's Kubernetes service account (KSA) for Workload Identity:

gcloud iam service-accounts \
  add-iam-policy-binding ${GSA}@${PROJECT_ID}.iam.gserviceaccount.com \
  --role roles/iam.workloadIdentityUser \
  --member "serviceAccount:${PROJECT_ID}.svc.id.goog[${NAMESPACE}/${KSA}]"

8. Add the Portkey Helm repository:

helm repo add portkey-ai https://portkey-ai.github.io/helm
helm repo update

9. Create values.yaml with the enterprise image, the Workload Identity service account, control-plane settings, and a GCS log store. Set serviceAccount.name to your KSA, the iam.gke.io/gcp-service-account annotation to <GSA>@<PROJECT_ID>.iam.gserviceaccount.com, and LOG_STORE_GENERATIONS_BUCKET to your <GCS_BUCKET_NAME>:

imageCredentials:
  - name: portkey-enterprise-registry-credentials
    create: true
    registry: https://index.docker.io/v1/
    username: <PROVIDED_BY_PORTKEY>
    password: <PROVIDED_BY_PORTKEY>

images:
  gatewayImage:
    repository: "docker.io/portkeyai/gateway_enterprise"
    pullPolicy: Always
    tag: "latest"

serviceAccount:
  create: true
  automount: true
  name: <KSA>
  annotations:
    iam.gke.io/gcp-service-account: <GSA>@<PROJECT_ID>.iam.gserviceaccount.com

environment:
  create: true
  secret: true
  data:
    ANALYTICS_STORE: control_plane
    SERVICE_NAME: gateway
    PORTKEY_CLIENT_AUTH: <PROVIDED_BY_PORTKEY>
    ORGANISATIONS_TO_SYNC: <ORGANISATION_ID>
    PORT: "8787"
    CACHE_STORE: redis
    REDIS_URL: "redis://redis:6379"
    REDIS_TLS_ENABLED: "false"
    LOG_STORE: gcs_assume
    GCP_AUTH_MODE: workload
    LOG_STORE_REGION: <GCS_BUCKET_REGION>
    LOG_STORE_GENERATIONS_BUCKET: <GCS_BUCKET_NAME>

10. Install or upgrade the release:

helm upgrade --install portkey-ai portkey-ai/gateway -f ./values.yaml \
  -n portkey --create-namespace

11. Confirm the pods are running, then expose the gateway with a GCP load balancer (Ingress for an Application Load Balancer, or a Service of type LoadBalancer for a Network Load Balancer) and point the guide at it:

kubectl get pods -n portkey
kubectl get svc -n portkey
export GATEWAY_URL="http://<LOAD_BALANCER_IP>"
This incurs ongoing charges, so tear it down when finished

The GKE cluster, its nodes, the load balancer, and the GCS bucket all bill continuously. When you are done, delete the cluster and empty/remove the bucket:

gcloud container clusters delete <CLUSTER_NAME> --location <LOCATION>
gcloud storage rm --recursive gs://<GCS_BUCKET_NAME>
Verification

All pods show Running, and curl -s "$GATEWAY_URL/v1/health" returns healthy from the load balancer. The deployment appears in the Portkey dashboard once it syncs with the control plane.

Phase 3: Configure the AIRS Guardrail

Build the AIRS guardrail configuration that the gateway passes on each request. This config is the same regardless of platform or LLM provider; it is the security layer that wraps whatever the gateway routes to.

▶ Step 3.1: Build the AIRS guardrail

Use the method that matches the image you deployed in Phase 2.

Option A (open-source image): inline config

The open-source gateway accepts a JSON config object in the x-portkey-config header. The AIRS guardrail uses the panw-prisma-airs.intercept plugin identifier.

Guardrail config structure:

{
  "input_guardrails": [
    {
      "deny": true,
      "panw-prisma-airs.intercept": {
        "profile_name": "YOUR_SECURITY_PROFILE_NAME",
        "credentials": {
          "AIRS_API_KEY": "YOUR_AIRS_API_KEY_HERE"
        }
      }
    }
  ],
  "output_guardrails": [
    {
      "deny": true,
      "panw-prisma-airs.intercept": {
        "profile_name": "YOUR_SECURITY_PROFILE_NAME",
        "credentials": {
          "AIRS_API_KEY": "YOUR_AIRS_API_KEY_HERE"
        }
      }
    }
  ]
}
FieldDescription
deny When true, blocked content returns an error to the caller. When false, the guardrail logs the violation but allows the request through.
panw-prisma-airs.intercept The AIRS guardrail plugin identifier. Must be exactly this string.
profile_name The exact security profile name from Strata Cloud Manager (case-sensitive).
credentials.AIRS_API_KEY The Prisma AIRS API key from Step 1.2.
Separate profiles for input and output

The input_guardrails and output_guardrails can reference different security profiles. For example, use a prompt-focused profile for input scanning and a response-focused profile for output scanning. In the test scripts in Phase 4, prompt-profile and response-profile are used respectively.

Export the AIRS key and compile the config into a single-line value the requests in Phase 4 will reuse:

export MY_AIRS_API_KEY="YOUR_AIRS_API_KEY_HERE"

export CONFIG=$(cat <<EOM | jq -c .
{
  "input_guardrails": [
    {
      "deny": true,
      "panw-prisma-airs.intercept": {
        "profile_name": "prompt-profile",
        "credentials": { "AIRS_API_KEY": "$MY_AIRS_API_KEY" }
      }
    }
  ],
  "output_guardrails": [
    {
      "deny": true,
      "panw-prisma-airs.intercept": {
        "profile_name": "response-profile",
        "credentials": { "AIRS_API_KEY": "$MY_AIRS_API_KEY" }
      }
    }
  ]
}
EOM
)
Environment variables

Store credentials in environment variables rather than hardcoding them in scripts. Create a .env file (excluded from version control) with the required values and source it before running requests.

Verification

echo "$CONFIG" prints valid single-line JSON containing both input_guardrails and output_guardrails arrays with the AIRS plugin configuration.

RegionEndpoint

Troubleshooting

▶ Gateway unreachable: connection refused or timeout on $GATEWAY_URL

Requests fail before reaching the LLM because the gateway is not reachable at the URL set in Phase 2.

Confirm the container is running and listening on 8787. For cloud hosts, confirm the security group (AWS), network rule (Azure), or ingress settings (GCP) allow inbound access on the gateway port from your client, and that $GATEWAY_URL uses the correct scheme and port (Cloud Run serves HTTPS with no :8787 suffix; EC2 and ACI use http://...:8787).

▶ 400 from AIRS API: profile not found

The profile_name sent by the guardrail does not match any security profile in Strata Cloud Manager.

Profile names are case-sensitive. In Strata Cloud Manager open AI Security → API Applications → Manage → Security Profiles, confirm the exact name, then update the guardrail configuration to match it character for character.

▶ 403 from AIRS API

The AIRS API key and the regional endpoint do not match. AIRS keys are region-locked.

Check the plugin's endpoint configuration against the region the key was issued for, using the table in Step 3.2.

▶ Provider auth fails: 401/403 from the LLM provider

The gateway reached the provider but the provider rejected the credentials.

  • AWS Bedrock — confirm the IAM principal has bedrock:InvokeModel, the model is enabled under Model access, and x-portkey-aws-region matches where the model is available.
  • Azure OpenAI — confirm the resource name, deployment id, and API version, and that the key belongs to that resource.
  • Vertex AI — the access token expires roughly hourly. Re-run export VERTEX_ACCESS_TOKEN="$(gcloud auth print-access-token)" and confirm the project has the Vertex AI API enabled.
  • Public API — confirm the bearer token is valid and x-portkey-provider matches the provider.
▶ Guardrail not invoked: request passes without scanning

The request reaches the LLM without going through Prisma AIRS, so no scan happens.

Confirm the x-portkey-config header is present and that $CONFIG expanded to non-empty JSON. Confirm the panw-prisma-airs.intercept key in the config is spelled exactly.

▶ Invalid JSON in x-portkey-config header

The header value is not valid compact JSON, so the gateway rejects the request.

The config must be single-line JSON. Run jq -c . to compact it. Verify there are no shell variable expansion issues: use single quotes for the heredoc delimiter to prevent premature expansion, or escape $ signs.

▶ Streaming responses not scanned

Portkey guardrails process complete requests and responses only. Streaming is not intercepted.

Use non-streaming requests for full guardrail coverage.

▶ 401 from AIRS API: invalid or missing API key

The AIRS API key is missing, expired, or mistyped in the guardrail credential.

Confirm $MY_AIRS_API_KEY is set and contains no surrounding whitespace or trailing newline, then rebuild $CONFIG from Step 3.1.

▶ AIRS endpoint unreachable: timeouts or connection refused

The gateway cannot reach the AIRS endpoint, so requests stall or fail before scanning completes.

Confirm the configured AIRS endpoint URL is correct for the region and that outbound network access from the gateway host to that endpoint is allowed. Verify egress firewall rules and DNS resolution from the gateway container.
