Prisma AIRS: API Intercept Deployment

End-to-end guide: license activation through validated AI security scanning with API-embedded threat detection

Guide Approach

This guide deploys Prisma AIRS API Intercept, a security-as-code solution that embeds AI threat detection directly into your application via the Scan API. Unlike Network Intercept (which deploys inline firewall instances), API Intercept requires no infrastructure deployment. You integrate a REST API into your application code to scan prompts and model responses for threats.

What you get: A working API Intercept integration that scans AI prompts and responses for prompt injection, data leakage, toxic content, malicious code, and more, plus cloud asset discovery for visibility into your AI workloads.

Bolt-on modules: After completing this core deployment, you can add MCP Server integration, SaaS Agent Security, or SDK integration independently.

Architecture Overview

Prisma AIRS is a comprehensive AI security platform with four components. This guide focuses on API Intercept: the code-level integration that scans AI prompts and responses before and after they reach an AI model.

▶ Prisma AIRS Platform Components

▶ API Intercept Traffic Flow

API Intercept sits between your application code and the AI model. Your application sends prompts and responses to the Scan API for threat assessment before forwarding to or returning from the AI model.

Request/response scanning flow through the Prisma AIRS Scan API:

Model-Agnostic Design

API Intercept works with any AI model: public, private, or self-hosted. The Scan API evaluates the content of prompts and responses regardless of which model generates them. Your application controls the integration flow.

▶ Synchronous vs. Asynchronous Scanning

The Scan API offers two modes. Choose based on your latency requirements and payload size.

ModeEndpointMax PayloadBest For
Synchronous POST /v1/scan/sync/request 2 MB Real-time scanning where latency matters. Single prompt/response pair. Returns verdict immediately.
Asynchronous POST /v1/scan/async/request 5 MB / 25 batch requests Batch processing, larger payloads, background scanning. Returns a scan_id — poll for results.
Synchronous Flow Asynchronous Flow App ──POST /v1/scan/sync/request──► API App ──POST /v1/scan/async/request──► API ◄──── verdict (immediate) ───── ◄──── scan_id (immediate) ────── ... processing ... App ──GET /v1/scan/results?scan_ids=──► API ◄──── verdict + details ──────
▶ Detection Services

The Scan API runs your content through multiple detection services simultaneously. Each service produces its own verdict.

Prompt Injection

Detects attempts to manipulate the AI model through crafted prompts that override system instructions.

DLP (Data Loss Prevention)

Identifies sensitive data (PII, credentials, financial data) in prompts or responses. Can mask detected patterns.

Toxic Content

Flags harmful, offensive, or inappropriate content with confidence levels and category classification.

Malicious Code

Analyzes code blocks in prompts/responses for malware, command injection, and other malicious patterns.

URL Categorization

Evaluates URLs in content for risk level and category. Max 100 URLs per request.

Topic Guardrails

Enforces allowed and blocked topic lists to keep AI interactions within defined boundaries.

Database Security

Detects SQL queries in responses (create, read, update, delete) that could indicate data exfiltration.

Agent Threats

Identifies agent-specific threats like tools misuse, memory manipulation, and framework-specific attack patterns.

Contextual Grounding

Evaluates whether AI responses are grounded in provided context, detecting hallucinations or fabricated content.

▶ Step 3.3 — Generate an API Key

The API key authenticates your application to the Scan API. It is the value you will send in the x-pan-token header on every scan request. Each application you onboarded in Step 3.1 gets its own API key.

If you are continuing the first-time onboarding wizard from Step 3.1, you are already on the Input API Details screen. If you are adding a key later, go to AI Security → API Applications, click Manage in the top right, select API Keys, then select Add new application/API key.

  1. Enter the API Key Name. This is a label for you, so use something that identifies the application and environment (e.g., "chatbot-prod").
  2. Select the Rotation period that the key refreshes on: every month, 3 months, or 6 months. Rotation takes effect only when you regenerate or create a key, so it does not retroactively change an existing key.
  3. Select Generate API Key.
  4. On the Implement API screen, copy and save the API key.
  5. Copy and save the Code Template, which is a prefilled snippet you can embed in your application.
  6. Choose Done.
Store Your API Key Securely

The API key is shown only once. Store it in a secrets manager (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, HashiCorp Vault, etc.). Never hardcode it in source code or commit it to version control.

If you lose the key, you cannot recover it. Go to Manage → API Keys and Regenerate, which revokes the old key and issues a new one. Any application still using the old key starts failing authentication immediately.

One key can serve several profiles

A single API key can be used against multiple AI security profiles, because the profile is chosen per request in the ai_profile field rather than being bound to the key. That is convenient for testing. For production, prefer one application and one key per deployed workload so that you can revoke one without affecting the others.

Authentication — OAuth 2.0 Token as an Alternative

Sending a long-lived API key from automation is sometimes unacceptable to a security team, and fetching an API key requires someone to log in to the SCM web interface. For those cases the Scan API also accepts an OAuth 2.0 bearer token. The token is derived from an API key you have already created, so this is an alternative way to present the same credential, not a second credential.

To generate one:

  1. In SCM, navigate to AI Security → API Applications.
  2. Click Manage in the top right corner, then select API Keys.
  3. Select the API key you want the token to be derived from.
  4. Select Generate Token for OAuth 2.0.
  5. Set the token lifetime: 1 hour, 3 hours, 1 day, 7 days, or 30 days.
  6. Select Generate Token and copy the token.
PropertyBehavior
Default lifetime24 hours when generated through the SCM web interface
Maximum lifetime30 days
Expiry couplingBound to the underlying API key. The token stops working as soon as that key expires, even if the token's own lifetime has not elapsed
VisibilityDisplayed only once, same as the API key
QuotaIdentical to API key authentication. Using a token does not change your daily call allowance
AttributionScans are logged against the originating API key identifier either way, so logs stay consistent
PermissionsThe super user role can generate and manage both API keys and OAuth tokens. Other roles may be limited to one or neither

The examples throughout Phase 6 use the x-pan-token API key header, since that is the form Palo Alto Networks documents for scan requests. Confirm the exact header your tenant expects for token authentication against the Code Template on the Implement API screen before switching your application over.

Creating the key programmatically — the Management API

Everything the wizard just did has a REST equivalent. Palo Alto Networks publishes a Prisma AIRS Management API that creates and rotates API keys, creates AI security profiles, manages custom topics, and lists deployment profiles. Use it when you want onboarding to be reproducible rather than a sequence of clicks.

Two different APIs, two different credentials
  • Scan API — base URL https://service.api.aisecurity.paloaltonetworks.com, authenticated with the API key in the x-pan-token header. This is the one your application calls at runtime.
  • Management API — base URL https://api.sase.paloaltonetworks.com/aisec, authenticated with an OAuth 2.0 bearer token from a Strata Cloud Manager service account. This is the one your provisioning automation calls.

The API key cannot authenticate to the Management API, and the service account token cannot authenticate a scan. Keep them separate in your secrets store so nobody wires the wrong one into the wrong call.

Where the OAuth token comes from

The <OAUTH_TOKEN> in the request below is a standard Strata Cloud Manager service account access token. You create the service account once, then your automation mints a fresh token whenever it needs one. These tokens are short lived, so request one per run rather than storing it.

  1. In SCM, navigate to Identity & Access → Service Accounts and select Add Service Account.
  2. Assign a role that covers API key management. Superuser has full CRUD access to API keys, security profiles, and custom topics. For least privilege, create a custom role instead at Identity & Access → Roles → Custom Roles → Add Custom Role, open the API tab, and grant only the airs_api.api_keys permissions your automation needs.
  3. Save the Client ID and Client Secret shown on creation. The secret is displayed once.
  4. Find your TSG ID at Common Services → Tenant Management.
  5. Exchange those three values for a token:
export SCM_CLIENT_ID="your-service-account-client-id"
export SCM_CLIENT_SECRET="your-service-account-client-secret"
export TSG_ID="your-tenant-service-group-id"

OAUTH_TOKEN=$(curl -s -X POST "https://auth.apps.paloaltonetworks.com/oauth2/access_token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -u "${SCM_CLIENT_ID}:${SCM_CLIENT_SECRET}" \
  -d "grant_type=client_credentials&scope=tsg_id:${TSG_ID}" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['access_token'])")

echo "${OAUTH_TOKEN:0:20}..."

A successful response is JSON containing access_token and expires_in. If you get a 401, the client ID or secret is wrong. If you get a 400 mentioning the scope, the TSG ID is wrong or the service account is not attached to that tenant.

This is not the same token as the one above

The Generate Token for OAuth 2.0 button in the SCM web interface produces a token derived from an existing API key, and that token authenticates scan requests. The service account token on this page authenticates management requests. They are issued by different systems and are not interchangeable.

Where the deployment profile value comes from

The Management API identifies the deployment profile by dp_name, not by a UUID, and the field is optional. It is not the AI security profile you created in Step 3.2. It is the Prisma AIRS AI Runtime API deployment profile you created in the Customer Support Portal in Phase 2, Step 2.3 and associated with your Tenant Service Group.

To list the profiles available to your tenant, call GET /v1/mgmt/deployment-profiles with the same bearer token. Adding ?unactivated=true narrows the list to profiles that have no application or API key attached yet, which is usually the one you want when onboarding something new.

Confirm the field names against the live reference

The field names above come from the Palo Alto Networks Management API Python SDK documentation, which is the most explicit published description of this request body. Before you build automation on it, check the request schema on the Create New API Key reference page, since the API is still gaining endpoints and the schema is the authoritative source.

If you would rather not hand-build the requests, the airs_api_mgmt Python SDK wraps every endpoint on this page and handles token refresh for you.

Verification: Test the API key with a minimal scan request (the connectivity test in Phase 5). A 200 response confirms the key is valid. To confirm the Management API side independently, call GET https://api.sase.paloaltonetworks.com/aisec/v1/mgmt/apikey with your bearer token and check that the new key name appears in the list.

Logs are not instant

The HTTP response is immediate, but the API Scan Log and Log Viewer entries are written asynchronously. Allow a few minutes before concluding that a scan did not register, and widen the time filter before you retry the request.

▶ Step 6.3 — Integration Pattern: Python

A minimal integration that scans prompts before sending to an AI model and scans responses before returning to the user.

import requests
import os

AIRS_API_KEY = os.environ["AIRS_API_KEY"]
AIRS_ENDPOINT = "https://service.api.aisecurity.paloaltonetworks.com"
AIRS_PROFILE = "your-profile-name"

def scan_content(prompt: str, response: str = None) -> dict:
    """Scan a prompt (and optionally a response) with AIRS API Intercept."""
    content = {"prompt": prompt}
    if response:
        content["response"] = response

    payload = {
        "ai_profile": {"profile_name": AIRS_PROFILE},
        "metadata": {
            "app_name": "my-ai-app",
            "ai_model": "gpt-4"
        },
        "contents": [content]
    }

    resp = requests.post(
        f"{AIRS_ENDPOINT}/v1/scan/sync/request",
        headers={
            "x-pan-token": AIRS_API_KEY,
            "Content-Type": "application/json"
        },
        json=payload,
        timeout=30
    )
    resp.raise_for_status()
    return resp.json()

def chat_with_ai(user_prompt: str) -> str:
    """Example: scan prompt, call AI model, scan response, return."""
    # 1. Scan the user's prompt
    prompt_scan = scan_content(prompt=user_prompt)
    if prompt_scan["action"] == "block":
        return "Your request was blocked by security policy."

    # 2. Send to your AI model (example: OpenAI)
    ai_response = call_your_ai_model(user_prompt)

    # 3. Scan the AI model's response
    response_scan = scan_content(
        prompt=user_prompt,
        response=ai_response
    )
    if response_scan["action"] == "block":
        return "The AI response was blocked by security policy."

    # 4. Return the safe response
    return ai_response

Why both calls share one tr_id

The prompt scan and the response scan are two separate API calls with two separate scan_id values. Passing the same tr_id to both lets you pull up one conversation turn as a unit in the API Scan Log instead of two unrelated rows.

Asynchronous Batch Scan

Submitting is a separate call from retrieving. You post a batch, get a scan_id back immediately, and then poll until the results are ready.

# 1. Submit the batch. Each element needs its own req_id so you can
#    tell the results apart.
SCAN_RESPONSE=$(curl -s -X POST "$AIRS_ENDPOINT/v1/scan/async/request" \
  -H "x-pan-token: $AIRS_API_KEY" \
  -H "Content-Type: application/json" \
  -d "[

      \"ai_profile\": {\"profile_name\": \"$AIRS_PROFILE\"},
      \"contents\": [{\"prompt\": \"First prompt to scan\"}]
    }},
    {\"req_id\": 2, \"scan_req\": {
      \"ai_profile\": {\"profile_name\": \"$AIRS_PROFILE\"},
      \"contents\": [{\"prompt\": \"Second prompt to scan\"}]
    }}
  ]")

echo "$SCAN_RESPONSE" | jq .

# 2. Pull the scan_id out of the submission response.
SCAN_ID=$(echo "$SCAN_RESPONSE" | jq -r '.scan_id')
echo "scan_id: $SCAN_ID"

The submission response carries identifiers rather than verdicts. The scan_id it returns is what you poll with.

Print the raw body before you code against it

This guide does not reproduce the async submission and results schemas, because they are versioned and they change as detection services are added. Run the submission once, print the whole body, and write your field access against what your own tenant actually returns. The authoritative schemas are on the Send an Asynchronous Scan Request and Retrieve Scan results by ScanIDs reference pages.

# 3. Poll for results. An empty array means the batch is still processing,
#    so retry rather than treating it as a failure.
for attempt in 1 2 3 4 5; do
  RESULTS=$(curl -s "$AIRS_ENDPOINT/v1/scan/results?scan_ids=$SCAN_ID" \
    -H "x-pan-token: $AIRS_API_KEY")

  if [ "$(echo "$RESULTS" | jq 'length')" -gt 0 ]; then
    echo "$RESULTS" | jq .
    break
  fi

  echo "attempt $attempt: not ready, waiting 5s"
  sleep 5
done

Each element of the results array corresponds to one element of the batch you submitted. Match them up by the req_id values you assigned, which is the reason you assign them. Each element carries the same verdict information a synchronous scan returns, so the fields you read in Step 6.2 apply here too.

Batch and lookup limits
  • An async submission accepts up to 25 scan requests and a 5 MB payload, against 2 MB for a synchronous call.
  • GET /v1/scan/results accepts a maximum of 5 scan IDs per call. Chunk the query string if you are reconciling more than five batches at once.

Split anything larger across submissions. See the comparison table in the Architecture Overview.

▶ Step 6.5 — Integration Pattern: MCP Tool Events

If your AI agent calls MCP (Model Context Protocol) tools, the thing you need to inspect is not the user's prompt. It is what the tool returned. A compromised or impersonated MCP server attacks the agent through tool descriptions and tool output, and that traffic never passes through the prompt scan you set up in Step 6.3.

Prisma AIRS scans MCP traffic through the same sync and async endpoints, using a tool_event content item instead of a prompt and response pair. It detects two threat classes:

  • Context poisoning — an adversary tampers with the tool definition so the agent reasons on false context and leaks data, bypasses its own rules, or runs dangerous commands.
  • Credential leakage — tokens, keys, or account data sitting in plaintext come back in the tool output and end up in the model's context.

Configure the profile first

MCP detection does nothing unless the security profile from Step 3.2 has the right protections turned on. Open that profile and confirm both:

  • Context poisoning — enable a Protection Type (AI Model Protection, AI Application Protection, or AI Agent Protection), then enable Database Security Detection under AI Data Protection. Contextual grounding is not supported for MCP, so do not rely on it here.
  • Credential leakage — enable Sensitive Data Detection under AI Data Protection, which switches on the DLP patterns.

Select Update after each change. The Manage API Security Profiles screen refreshes to show the new configuration.

Where server_name comes from

It is a label, not an address

server_name is free text that you choose. It is not an FQDN, not an IP address, and Prisma AIRS does not resolve it or connect to it. Nothing validates the value. Palo Alto Networks uses "Figma MCP server" in its own example, which shows the intent: a human-readable name for the MCP server the agent called.

Its only job is attribution. It is echoed back in the response and written to the API Scan Log, so when a detection fires you can tell which MCP server produced it. Pick names your on-call engineer will recognise at three in the morning and keep them stable, because changing a name later breaks the correlation with older logs.

Running a scan

You call this from the code that wraps your MCP client, after the tool returns and before the agent sees the result. The example below uses the same environment variables as Step 6.4.

▶ Step 6.6 — Handling DLP Data Masking
This is a response body, not a log entry

The JSON below is what the Scan API returns to your code, in the HTTP response to the POST /v1/scan/sync/request call you made in Step 6.3. Your application receives it inline, in the same request cycle, and it is the only place the masked text exists. You do not fetch it from anywhere and you cannot look it up later.

The scan is also written to the API Scan Log in SCM, but that log records the verdict and the detection metadata, not a reusable masked copy of the content. If you want the masked text, you have to take it out of this response at the moment of the call. Step 6.2 covers where the logs live and what they contain.

When DLP detects sensitive data, the response includes a masked copy of the content alongside the verdict:

{
  "category": "malicious",
  "action": "block",
  "prompt_detected": {"dlp": true},
  "prompt_masked_data": {
    "data": "My SSN is ***-**-**** and my email is ****@****.***",
    "pattern_detections": [
      {
        "pattern": "SSN",
        "locations": [[10, 21]]
      },
      {
        "pattern": "Email",
        "locations": [[39, 55]]
      }
    ]
  }
}
FieldWhat it holds
prompt_detected.dlptrue when a sensitive data pattern matched in the prompt. The matching field for model output is response_detected.dlp.
prompt_masked_data.dataThe original text with every match replaced by asterisks. This is the string you forward instead of the original.
pattern_detections[].patternThe name of the pattern that matched, for example SSN or Credit Card Number. Useful for deciding whether to mask and continue or to reject outright.
pattern_detections[].locationsCharacter offset pairs into the original string. You need these only if you are doing your own highlighting or partial redaction.

Using the masked text

Masking lets you keep a request alive that you would otherwise have to drop. Read prompt_masked_data.data and send that to the model in place of what the user typed, so the model gets a usable question without the sensitive values.

result = scan_prompt(user_prompt, tr_id)

if result.get("action") == "block":
    masked = result.get("prompt_masked_data", {}).get("data")
    if masked:
        # Sensitive data was the only problem. Continue on the masked text.
        model_input = masked
    else:
        # Blocked for some other reason, such as injection. Do not continue.
        raise SecurityError(f"Blocked: {result.get('category')}")
else:
    model_input = user_prompt

answer = call_your_ai_model(model_input)
Masked text is not a licence to ignore the verdict

A response can be blocked for prompt injection and carry masked data at the same time. Checking only for the presence of prompt_masked_data and continuing would forward an injection attempt to your model with its sensitive values conveniently removed. Branch on the reason for the block, as the example above does, rather than on whether masked text exists.

Verification: Send a prompt containing an obviously fake identifier, such as My SSN is 123-45-6789, and confirm the response sets prompt_detected.dlp to true and returns prompt_masked_data.data with the digits replaced. Then open the API Scan Log in SCM and confirm the same scan appears with a DLP detection against its Scan ID. If the detection fires in the response but no row appears in the log, give it a minute: logging is asynchronous.

▶ API Key Rotation

Rotate your API key periodically:

  1. Generate a new API key via SCM or the Management API.
  2. Update your application's secrets manager with the new key.
  3. Deploy the configuration change to your application.
  4. Verify scanning works with the new key.
  5. Revoke the old API key.
Zero-Downtime Rotation

Generate the new key before revoking the old one. Both keys are valid simultaneously until you explicitly revoke the old key.

Troubleshooting

▶ API Errors
HTTP StatusErrorCause & Fix
401 Not Authenticated Missing or invalid x-pan-token header. Verify your API key is correct and not expired.
403 Invalid API Key API key is invalid or being used against the wrong regional endpoint. Keys are region-locked — ensure the endpoint matches the region where the key was generated.
404 Resource Not Found Check the endpoint URL. Verify you are using /v1/scan/sync/request or /v1/scan/async/request.
413 Request Too Large Payload exceeds limits: 2 MB sync, 5 MB async. Split into smaller requests or use async mode.
415 Unsupported Media Type Ensure Content-Type: application/json header is set.
429 Too Many Requests Rate limit exceeded. The response includes a retry_after interval. Implement exponential backoff.
▶ Scan Result Issues
SymptomCause & Fix
Scan returns "category": "error" A detection service encountered an error. Check the errors array for which service failed and the error type. Retry the request.
Scan returns "category": "timeout" A detection service timed out. This can happen with very large payloads. Try reducing content size or using async mode.
DLP not detecting expected patterns Check your DLP profile configuration in SCM. Ensure the data patterns you expect to catch are enabled in the profile.
Profile not found Verify the profile_name in your request matches exactly (case-sensitive) what you configured in SCM.
Benign content being blocked Your security profile may be too aggressive. Review detection service settings and lower sensitivity for specific services.

Appendix: Bolt-on Modules

These capabilities extend the core API Intercept deployment. Each module is independently useful and assumes you have completed the core deployment above.

▶ Module A: MCP Server Integration

The Prisma AIRS MCP Server provides a standardized security gateway for AI agents using the Model Context Protocol (MCP) standard.

What It Does

  • Scans tool inputs and outputs (files, API calls, database queries) for threats
  • Detects credential leakage, context poisoning, and unauthorized tool usage
  • Integrates with MCP-compatible hosts (Claude Desktop, Cursor IDE, custom agents)

Prerequisites

  • Core API Intercept deployment complete (this guide)
  • AI agent using MCP-compatible framework

Integration

Use the tool_event content type in your scan requests (shown in Step 6.5 above). The Scan API evaluates tool inputs/outputs using the same detection services as prompt/response scanning, plus agent-specific threat detection.

For detailed setup: Prisma AIRS MCP Server Documentation

▶ Module B: SaaS Agent Security

SaaS Agent Security provides visibility and posture monitoring for AI agents deployed on enterprise SaaS platforms.

What It Does

  • Discovers AI agents across onboarded SaaS platforms (Microsoft Copilot Studio, ServiceNow, etc.)
  • Detects Shadow AI — unauthorized or unknown agent deployments
  • Monitors for misconfigurations (disabled auth, overly permissive access)
  • Automated remediation: pause, deactivate, or terminate risky agents

Prerequisites

  • Core API Intercept deployment complete (this guide)
  • One of: CASB-X, CASB-PA, or SaaS Security Posture Management license

For detailed setup: SaaS Agent Security Documentation

▶ Module C: Network Intercept (Firewall Deployment)

If your Cloud Asset Map reveals unprotected network traffic paths (App-to-Model, App-to-Internet, East-West), you may need Network Intercept in addition to API Intercept.

What It Does

  • Deploys Prisma AIRS Runtime Firewall instances (or VM-Series) inline in your cloud environment
  • Inspects network traffic at the packet level
  • Provides real-time AI-powered network protection
  • Supports Auto-Execute deployment from the Cloud Asset Map

When to Add It

  • Discovery shows unprotected App-to-Model traffic that bypasses your application code
  • You need to protect AI traffic from applications you don't control (third-party, legacy)
  • Compliance requires network-level inspection in addition to API-level scanning

Deployment Options

  • Auto-Execute — SCM orchestrates the entire deployment from the Cloud Asset Map (AWS and Azure)
  • Terraform — Manual infrastructure deployment using Palo Alto Networks SWFW modules

For detailed deployment: Auto-Execute Deployment Documentation

▶ Module D: Agent Discovery

Agent Discovery identifies AI agents built through cloud provider low-code/no-code platforms.

What It Discovers

  • AWS Bedrock Agents — Configuration discovery + runtime interaction monitoring (agent-to-model, agent-to-tool, agent-to-agent)
  • Azure AI Foundry / OpenAI Agents — Configuration discovery (runtime monitoring pending)

Prerequisites

  • Cloud accounts onboarded in SCM (Phase 4)
  • For AWS: S3 bucket access for invocation log analysis

What You See

The discovery dashboard shows agents as Protected or Unprotected, with Sankey-style diagrams showing agent interactions, dependencies, knowledge bases, and tool usage.

For detailed setup: Agent Discovery Documentation
