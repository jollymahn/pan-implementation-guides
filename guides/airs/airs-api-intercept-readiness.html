Customer Readiness — API Intercept

What your application teams need ready before the first API Intercept working session

AI Red Teaming AI Gateway API Intercept Model Scanning

This document is for the teams who own the API Intercept target: the application developers, the platform engineers, and whoever holds the credentials. Work through it before the first working session. Everything here is something only you can supply, and every item left open on the day is a session that stops early.

What this covers, and what it does not

This is the customer side only. Licensing, tenant provisioning, deployment profiles and entitlement are handled separately by Palo Alto Networks and your account team, and none of it is on this list. If you are looking for that side, it is Phase 1 of the API Intercept guide.

There is also a Technical Requirements Document for API Intercept. That is the structured intake form filled in together during the session. This document is what gets you to that session able to answer it.

Three sections follow. Start these now is the one to action first: every item in it has a lead time measured in days rather than minutes, and it is the usual reason a kickoff slips.

This one needs your developers to write code

API Intercept is not deployed in front of anything. Your application calls a scan endpoint with the prompt before sending it to the model, calls it again with the response before showing it to the user, and acts on the verdict it gets back. That is application code, written by your team, in your repository.

Nothing on the Palo Alto Networks side can substitute for it. Budget developer time per application, and bring a developer to the session rather than only an architect.

1. Who needs to be in the room

RoleWhat they must be able to doWhat stalls without them
Application developer Add an HTTP call to the application at two points, handle three possible verdicts, and run it in a test environment during the session. Nothing is integrated. The profile can be configured and the key issued, and no traffic is ever scanned.
Application or product owner Decide what the application does when a prompt is blocked: refuse, mask, warn, or log and continue. Decide what the user sees. The developer has no specification for the most important branch in the code, and usually implements log-and-continue by default, which detects everything and prevents nothing.
Data protection or compliance owner Say which categories of sensitive data matter, which topics are out of bounds, and what the regulatory position is on content being sent to a scanning service. The security profile is configured on guesswork and then rewritten after the first review.
Network or egress owner Confirm the application's environment can reach the regional scan endpoint on TCP 443. Every scan call times out. In a container platform with a restrictive egress policy this is the most common first-day failure.
Performance or SRE owner
worth including		 Agree the latency budget, and what the application does if the scan service is slow or unreachable. A synchronous scan is added to the critical path of every request with nobody having decided whether that is acceptable or what the timeout behavior should be.

2. What to have ready

2.1 — The application inventory

For every application, recordWhy it is needed
Application name and owning teamEach application gets its own API key, and the name appears on every scan record in the logs.
Language and frameworkDecides whether the integration uses the Python SDK or a plain HTTP call.
Which model it callsSent as metadata on every scan, so results can be filtered by model later.
Where in the code the scan calls will goTypically immediately before the model call, and immediately after the response returns. Identify the exact functions now.
Whether it streams responses to the userA streamed response reaches the user progressively, which changes when a response scan can usefully intervene.
Peak requests per minuteFeeds both the latency conversation and the transaction allowance.

2.2 — Decisions the security profile needs

A profile says which detections run and whether each one allows or blocks. Come with a position on each row rather than deciding live.

DetectionWhat to decide
Prompt injectionBlock or allow-and-log. Most teams block.
Data loss preventionWhich categories matter: personal data, credentials, financial records, your own internal identifiers. Whether detected data should be masked rather than blocked.
Toxic contentWhether this applies to prompts, responses, or both.
Malicious codeRelevant where the application handles code. A developer assistant and a banking chatbot want different answers.
URL categorizationWhether links in prompts or responses should be evaluated, and which categories are unacceptable.
Topic guardrailsThe explicit lists of permitted and forbidden subjects. This needs writing by the business, not by the developer.
Database securityRelevant where a response could contain a query. Flags possible data exfiltration.
Agent threatsRelevant for agents that call tools. Covers tool misuse and memory manipulation.
Contextual groundingWhether responses must be grounded in supplied context, which is how fabricated answers are caught.

2.3 — Integration shape

DecisionWhat to weigh
Synchronous or asynchronous Synchronous returns a verdict immediately and suits anything where a user is waiting; it caps at 2 MB per call. Asynchronous returns an identifier to poll, accepts 5 MB and up to 25 requests in a batch, and suits background or bulk processing.
What a block verdict does Refuse and show a message, substitute a safe response, mask the detected content, or log and continue. Write the user-facing message now.
What a scan failure does If the scan service is unreachable or slow, does the application fail open or fail closed? This is a security decision with an availability cost and belongs to the product owner, not the developer.
Your latency budget A synchronous scan on both the prompt and the response adds two network round trips to every interaction. Know what the application's current latency is and how much headroom exists.
Metadata to send An application name and model name travel with each scan and are what make the logs filterable later. Agree a naming convention before several teams invent their own.

2.4 — Test content

Bring real examples. Scanning a toy prompt proves the plumbing; scanning your own content proves the profile.

  • Several ordinary prompts that must pass cleanly. False positives on these are the fastest way to lose a team's confidence.
  • One prompt that should trip each detection you intend to enable, drawn from your own domain where possible.
  • A sample containing the kind of sensitive data you actually hold, so the data loss policy is tested against your formats rather than generic ones.
  • A test environment the developer can deploy to during the session.

3. Start these now

TaskTypical lead timeDetail
Choose your region, and stay in it Decision The scan service runs in several regions and API keys are locked to the region they were created in. A key made in one region will not authenticate against another region's endpoint. Decide the region first, on data residency grounds, because correcting it later means reissuing every key.
Open outbound HTTPS to the regional scan endpoint 1 to 5 business days TCP 443 from wherever your applications run, which is often several environments. Also allow the management hostname if keys and profiles will be managed through the API, and certificate validation endpoints on TCP 80.
Confirm TLS inspection will not break the call 1 to 5 business days An intercepting proxy presents its own certificate. Either exempt the scan endpoint or make sure your runtime trusts the proxy's CA.
Allocate developer time Varies Per application, not per engagement. A simple integration is small; agreeing behavior on a block verdict usually takes longer than writing it.
Write the topic guardrail lists 1 to 2 weeks Permitted and forbidden subjects have to come from the business. This reliably takes longer than anyone expects and blocks nothing else, so start it early.
Agree the fail-open or fail-closed position Discussion Needs the product owner and the security owner in the same conversation. Worth settling before the session rather than during it.
Two different APIs, two different credentials

The scan endpoint authenticates with an API key sent in a request header. The management endpoint, used to create keys and profiles programmatically, authenticates with an OAuth token from a service account. They are not interchangeable, and presenting one to the other is a common early confusion. You only need the second if you intend to automate.

4. What happens in the session

  1. A security profile is built from your answers in section 2.2.
  2. An API key is generated for the first application, in the region chosen in section 3.
  3. Connectivity is proven from the application's own environment, not from a laptop.
  4. Your developer adds the scan call at the two integration points and runs it against the test content from section 2.4.
  5. Verdicts are reviewed together, and the profile is tuned where ordinary content trips a detection.
  6. The block path is exercised deliberately, so the user-facing behavior is seen rather than assumed.

Check your connectivity before the session

The connectivity validator generates the commands to prove the scan endpoint is reachable and your key authenticates, and decodes the output to tell you what is broken. Run it from inside the environment your application runs in, not from a laptop, because that is where egress policy applies.
