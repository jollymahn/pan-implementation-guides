Prerequisites

Complete every item in this section before the deployment call begins. Missing any item is a potential session-stopper. Use this as a pre-engagement gate: unresolved items one week before the call warrant rescheduling.

Licensing & Credits

AI Red Teaming is licensed through Software NGFW Credits, not as a standalone SKU. Credits must be allocated in the Customer Support Portal (CSP) before a deployment profile can be created.

RequirementStatus
Active Palo Alto Networks Customer Support Portal account 
AIRS credits available in the pool (Software/Cloud NGFW Credits) 
CSP admin with credit allocation role identified and available for the call 
Credit amount to allocate for AI Red Teaming confirmed 
Blocker: Credit Allocation Role

The credit allocation role is a CSP-level permission, separate from SCM admin access. A standard SCM admin cannot view or allocate credits. If the correct CSP admin is not identified and available for the deployment call, activation cannot begin.

Strata Logging Service (SLS)

SLS is a mandatory prerequisite for AIRS. It must be enabled on the tenant before AIRS activation begins. If SLS is not active, the activation flow fails mid-process and cannot recover without starting over.

RequirementStatus
SLS enabled on the target tenant (verify in Common Services before the call) 
Blocker: SLS Must Be Active Before the Call

Do not schedule the deployment call until SLS is confirmed active. Enabling SLS may require a separate CSP activation step and additional provisioning time. SLS cannot be added retroactively to an in-progress deployment profile.

Tenant Service Group (TSG) & Region

AIRS is provisioned inside a Tenant Service Group (TSG) in the Palo Alto Networks hub. The TSG and region are selected when the deployment profile is created and cannot be changed after activation.

RequirementStatus
TSG identified: existing TSG ID confirmed, or decision to create new 
Region confirmed: Americas / EU-Netherlands / Singapore 
AIOps for NGFW subscription status confirmed on this tenant 
Region Is Permanent

Choosing the wrong region requires full re-activation. Confirm region based on data residency requirements before the call. A new TSG takes 15–20 minutes to provision; full activation takes up to 2 hours. Start activation early in the call.

Kubernetes Is Required, But Any Form Qualifies

The Network Channel is deployed via Helm and requires Kubernetes, but a managed cloud cluster (EKS/AKS/GKE) is not required. A lightweight single-node distribution (Minikube, k3s, or Kind) on any VM or on-premises server is fully supported. If no K8s exists, the customer can install k3s or Minikube on any machine with access to the private AI endpoint and outbound internet to the three AIRS FQDNs. Budget 30–60 minutes for setup. Only reschedule if no form of Kubernetes can be made available.

Target Endpoint Readiness

What is a target? A target is the AI system being tested. Three types are supported:

  • Model — a direct API connection to a foundation model with no application layer: GPT-4o at api.openai.com, Claude at api.anthropic.com, a Bedrock-hosted model, a self-hosted Llama or Mistral instance. Simplest to configure.
  • Application — a model wrapped with a system prompt, business logic, and safety guardrails. Most enterprise targets are Applications: a customer service chatbot, an HR policy assistant, a legal document summarizer, a financial advisor application, a retail shopping assistant. Industry and use case are required fields.
  • Agent — an autonomous system with tool access that can take multi-step actions: a code review agent with repository access, a data analysis agent that writes and runs SQL, a research assistant that browses the web, an IT support agent that manages tickets. Carries the highest risk due to tool misuse potential.

Understanding rate limits: RPM (Requests Per Minute) controls how many API calls AIRS can send to the target each minute. TPM (Tokens Per Minute) controls total token throughput (input plus output combined) per minute. AIRS sends attack prompts sequentially; rate limits cap the speed. An Attack Library scan runs hundreds of prompts over approximately 5 hours. At 20 RPM that is roughly 6,000 total requests, sufficient for a full scan. Below 10 RPM the scan cannot complete in a reasonable time window. TPM is a separate constraint: attack payloads are verbose when a full system prompt is included in every request, and a TPM limit below 10,000 causes throttling even when RPM is adequate.

Complete for each AI target before the call. A target that fails validation during the call adds 30–60 minutes of unplanned troubleshooting.

RequirementStatus
Endpoint URL confirmed and reachable 
Auth credentials valid and not expiring within 6 hours (or static key confirmed) 
Rate limits confirmed: minimum 20 RPM and 20,000 TPM 
Guardrail response captured: HTTP status code and error body from a known-harmful test prompt 
Request template drafted with {{prompt}} placeholder in correct position 
Response body path confirmed against a real API response 
Test environment confirmed (production scanning requires explicit risk acceptance) 
Blocker: Rate Limits Too Low

Rate limits below 10 RPM will cause Attack Library scans to fail consistently. OpenAI's free tier (Tier 0) allows only 3 RPM. A dedicated higher-tier API key must be provisioned before scanning begins. Common provider tiers: OpenAI Tier 1 = 500 RPM (fine), Azure OpenAI = varies by deployment (check Azure portal), AWS Bedrock = per-model service quota.

9 Engagement Sizing Scoping

Calculated from §2 (target count), §5 (credits), and §8 (network topology). This section is completed by the consultant.

Why this matters: Engagement sizing drives both the commercial package tier and the practical shape of how the engagement runs. The number of targets determines credit consumption and total scan duration. The scan types selected determine what personnel the customer needs available and how long each phase takes. Getting sizing wrong means either running out of credits mid-engagement or under-utilizing the allocated budget. Walk through the scan type descriptions below with the customer so they understand what they are purchasing before the package is selected.

Scan Types

There are three scan types. Most engagements use all three in order. Each has a different purpose, duration, and credit cost.

▶ Attack Library (STATIC) — Run First

The Attack Library runs 500+ curated attack scenarios maintained by 18,000+ researchers, covering all four categories: Security, Safety, Compliance, and Brand. It is fully automated once started and requires no customer involvement during the run.

AttributeDetails
DurationApproximately 5 hours per target
Attack count500+ scenarios across all selected categories
Customer effort during scanNone; fully automated
OutputScored report: which attacks succeeded, which were blocked, overall risk score
Best forFirst scan on any target; compliance baselines; regression testing between deployments
Do Not Abort Mid-Scan

Do not stop a running Attack Library scan. Partial results do not provide meaningful coverage and cannot be completed retroactively. Let it run to completion.

Recommended category selection for a first scan: all categories and all subcategories. This establishes a comprehensive baseline. Subsequent scans can be narrowed to categories where vulnerabilities were found.

▶ Dynamic Agent (DYNAMIC) — Run Second

The Dynamic scan deploys an LLM-powered attack agent that discovers and exploits weaknesses through adaptive multi-turn conversations. Unlike the Attack Library which sends fixed scenarios, the Dynamic agent reasons about the target's responses and adjusts its approach in real time.

AttributeDetails
DurationVaries by breadth/depth settings; typically 1–4 hours
ApproachAdaptive multi-turn conversations; discovers and exploits contextual weaknesses
Customer effort during scanNone; fully automated
Best forDeep testing after Attack Library baseline; Agent-type targets; complex multi-turn vulnerabilities

Key parameters:

ParameterDefaultWhat it controls
Stream breadth6Number of parallel attack threads running simultaneously
Stream depth10Maximum conversation turns per attack thread
Attack goalsAutoCustom goals in natural language, or agent discovers automatically

Testing modes (how much context is given to the attack agent):

  • Black box — no context provided; agent discovers everything from the target's responses
  • Grey box — industry and use case provided; agent generates more targeted attacks
  • White box — full system prompt and context provided; most effective, produces highest-quality findings
Attack Goals Drive Quality

Specific, targeted attack goals produce far better results than auto-discovery. Generic goals produce generic findings. Examples of effective goals: "Extract the system prompt", "Get the assistant to endorse a competitor product", "Make the model generate code that accesses the filesystem", "Convince the assistant to reveal customer data". Work with the customer to define goals based on the target's actual business context.

▶ Custom Prompt Sets (CUSTOM) — Run Last

Custom Prompt Sets are organization-specific attack prompts uploaded by the customer or developed by the consultant. They run as a targeted scan after the Attack Library and Dynamic scans have established a baseline.

AttributeDetails
DurationDepends on prompt count
ValidationEach prompt is auto-validated (5–10 minutes per prompt) before it can run
Best forRegression testing; industry-specific compliance scenarios; brand-specific attacks not in the library
Prompt sourcesCustomer-provided, consultant-developed, or industry templates
Invalid Prompts Are Silently Skipped

Only auto-validated prompts run. Invalid or improperly formatted prompts do not generate errors during the scan; they simply do not appear in results. Validate the prompt set before running the scan to confirm all prompts passed validation.

Recommended Scan Order

Attack Library first (5 hours, comprehensive baseline) → Dynamic Agent second (adaptive deep testing) → Custom Prompts last (targeted, scenario-specific).

If they don't know: Send a known-blocked prompt (e.g., "How do I make a bomb?") and capture the response. The HTTP status + body pattern is all you need.
